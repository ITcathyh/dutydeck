# Dutydeck 飞书体验候选：产品优先级评估

日期：2026-09-13 ｜ 方式：只读分析，未改代码。
输入：github 竞品调研（§4 12 模式/§5 反模式）、lark 平台与内部产品调研、飞书现状盘点（11 粗糙点）、工程评估 E1-E24（其代码事实结论本文直接接受为约束，不再复核代码）。

## 评估口径

- **唯一价值标尺：飞书内完成率**——从飞书发起、必要决策不跳出飞书、成果在飞书送达并被验收的任务占比；辅以七原则（Task first、先回答下一步、进展非噪音、控制在上下文旁、结果可验证、跨通道一致、最小充分）。
- 判断一个候选值不值，依次问三句：它是否消除了一个"不离开飞书就过不去"的卡点？卡住的频率高不高？没有它用户现在怎么绕？
- 受众标记：**新**=新用户/首次上手，**老**=高频老用户，**管**=团队管理员（受信小团队场景）。
- 成本 S/M/L/XL 沿用工程评估口径；工程未单列的新增项（A-N 中除映射到 E 项外）由本文给出产品侧粗估。

## P0：立即做（完成率卡点 + 低成本顺滑）

### A. 审批四按钮：本次允许 / 始终允许同工具+目录 / 拒绝但换方案 / 拒绝并中断

- **场景与阶段**：一个真实开发任务里，改 10 个文件、跑一串命令，审批卡一张接一张亮手机；用户要么反复掏手机点"允许"，要么看出方向不对，先"拒绝"再另外找"中断"按钮。阶段：**决策**。
- **价值：高。** 这是本批候选中对"无人盯守时长"影响最大的一项。"始终允许"把单次决策沉淀为规则，直接消灭长尾审批打扰；"拒绝并中断"把现在的两步操作合成一步，缩短错误方向的燃烧时间。四个内部桥接产品（code-anywhere、tlive、共识 §2.5-4）独立收敛到同一设计，不是个别偏好。
- **受众**：新 中 / 老 **高** / 管 中。
- **产品裁决**：工程评估 E2 只论证了"宽限时序"，**漏掉了按钮语义本身，产品要求补立项 P0**。v1 范围：①规则按"工具 + 工作目录"本地持久化，匹配命中即本地自动决议、不发卡；②当前 reject 语义就是"拒绝本次、agent 换路"，改文案让用户看懂；③"拒绝并中断"= reject + interrupt 一次完成；④规则管理首版放 Web，卡片上明示"已记住此类操作"。ACP only，PTY 按工程结论在终端答，卡片不承诺。

### E15. /tasks 列表行内操作（取消/中断/重试/审批）+ Web 深链

- **场景与阶段**：任务多了以后，用户在 /tasks 里看到一条失败任务，却只能"返回原会话"翻聊天流找到那条卡才能重试；待审批埋在列表里也无法就地处理。阶段：**复访、决策**。
- **价值：高。** /tasks 是多任务用户的任务首页，行内无操作等于"看得到、摸不着"，直接逼用户在聊天流里考古，是复访路径上最大的完成率漏点。
- **受众**：新 中 / 老 **高** / 管 中。
- **裁决**：与工程一致，直接做 M；行内审批必须复用 workflow-interactions 的一次性决议 CAS，不另开决议入口。

### E10. 问答卡结构化：单选/多选/输入框

- **场景与阶段**：agent 提问"A/B/C 选哪个"，用户要引用卡片打字回复；/answer 编号已从卡上删除，不引用卡片就答不了，这条回落路径普通用户发现不了。阶段：**决策**。
- **价值：高。** 消灭粗糙点 1 的一半（问答侧），让"回答 agent"在手机上变成点按钮，是最纯粹的"决策不离开飞书"。
- **受众**：新 **高** / 老 **高** / 管 中。
- **裁决**：与工程一致，M 直接做；tlive 式多问游标（Back/整批提交）成本 L、需求未证实，不进 v1。

### E14. /work 卡点击后 PATCH 原卡，不再每次发新卡

- **场景与阶段**：一个多步骤 /work 目标，每点一次"批准/重试/刷新"就多一张卡，长目标结束时聊天流里半屏是工作卡，真正的进展和结果被稀释。阶段：**跟踪**。
- **价值：高。** 这是现状实测最明显的粗糙点，且幂等键、revision CAS、并发闸门都已就绪，工程上属于"接线"而非"修路"。
- **受众**：新 低 / 老 **高** / 管 中。
- **裁决**：与工程一致，M 直接做；waiting/状态指纹变化时推新卡的现有规则保留（需要人看时仍有红点）。

### E20. 群内操作者归属 + agent 显示名

- **场景与阶段**：群里任务被人中断/重试了，其他人不知道谁动的；/work 卡直接印原始 agentId，看不懂是哪个 agent 在跑。阶段：**跟踪**（信任）。
- **价值：中。** 个人场景无感；一旦两人以上同群，"谁干的"是信任地基。
- **受众**：新 低 / 老 中 / 管 **高**。
- **裁决**：与工程一致，agent 名 S 先走、操作者注记 M（落持久字段扛心跳重绘与重启）。

## P1：近期做（高频效率与信任补强）

### E2. 审批发卡前 10 秒宽限（人在键盘前答了就不推手机）

- **场景与阶段**：人就在终端前坐着，每次工具审批依然亮一次手机。阶段：**决策（打扰治理）**。
- **价值：高（对高频用户），但是降噪项不是完成率卡点**——卡发出去用户也能批，所以排在 A 之后，与 A 同一审批主线交付。
- **受众**：新 低 / 老 **高** / 管 低。
- **裁决**：与工程一致，ACP only、可配置可关，M；工程列出的四个恢复/竞态边界（重启补卡、agent 撤回、空闲提醒抑制、世代围栏）是验收条件。PTY 手机双通道的 XL 驳回，产品**认可**：终端原生提示就该在终端答，不承诺手机能批 PTY。

### E12. /repair 一键增量补权并重新发布

- **场景与阶段**：新功能需要新事件/权限（👍 需要 reaction 事件、欢迎语需要 bot added 事件、多 bot 需要 include_bot），存量 bot 不补权就拿不到，让用户翻开放平台后台等于功能白做。阶段：**上手/运维**。
- **价值：中，但它是 E7b、E24a、E9 的前置依赖，时序上必须提前。**
- **受众**：新 中 / 老 **高** / 管 中。
- **裁决**：S-M，与工程一致；发布后的审核态要如实回显，不能声称"已生效"。

### BC. 新建任务表单卡：目标 + 目录下拉 + agent（合并候选 B+C）

- **场景与阶段**：想让 agent 在另一个目录干活，得记住 `/new --cwd … --model … --effort … -- 目标` 这串参数；手机上几乎不可输入。阶段：**发起**。
- **价值：中-高。** 自然语言直发已经是零摩擦主路径，所以不是 P0；但表单是"非默认目录/指定 agent"这一高频次路径的唯一可达解，也顺手消灭 /new 的参数手册。code-anywhere、DevCockpit 都有目录选择 UI。
- **受众**：新 **高** / 老 中 / 管 中。
- **裁决**：工程 E10 把 JSON 2.0 form 只用于问答，产品主张**同一表单能力同时承接 /new**：/new 无参数发空白表单卡（替代现在的用法引导卡），目录用 select 拉已有工作区/目录，agent 用 select 拉 listAgents，模型/推理强度折叠为可选项，整批一次回调。M。

### E24b. bot 单聊菜单（"发消息"型，挂 5 个高频入口）

- **场景与阶段**：12 条斜杠命令没有任何可见入口，全靠记忆和 /help。阶段：**上手、发起**。
- **价值：中。** 菜单是常驻的"下一步"提示，直接落地原则 2（先回答下一步）。
- **受众**：新 **高** / 老 中 / 管 低。
- **裁决**：与工程一致，先用零事件门槛的"发送消息"型（/tasks、/new、/help、/status、/work），M；事件型菜单 SDK 未就绪，失败就回退纯命令，不阻塞交付。

### K1. 卡死探活自动终态（lark-channel-bridge / Agent Workflow）

- **场景与阶段**：agent 挂死或长时间无输出，卡永远停在"正在执行"，任务不到终态、结果永远不来，用户从"等一下"变成"忘了它"。阶段：**跟踪（终态诚实性）**。
- **价值：中。** 完成率的暗伤不是失败，是**没有终态**。Bridge 的"⏱ N 分钟无响应，已自动终止"是值得照抄的诚实文案。
- **受众**：新 中 / 老 **高** / 管 中。
- **裁决**：工程 E 列表漏项，产品补 P1，粗估 M。判活条件必须是"无任何事件**且**无在途工具调用"持续 N 分钟（构建、测试等长命令不算卡死），默认宽松阈值、可关；终止走正常终态通道——冻结卡 + 说明卡，不允许静默杀。

### Ectx. 上下文余量脚注 + /compact 提示（Vonvon，用量三件套之一）

- **场景与阶段**：长任务跑到后段上下文见底，agent 开始丢前面的约束而用户毫无察觉，结果跑偏才发现。阶段：**跟踪（信任/防跑偏）**。
- **价值：中。** 把"agent 的脑子还剩多少"从黑盒变成脚注一行，用户可以主动 /compact 或 /new 开新任务。
- **受众**：新 低 / 老 **高** / 管 低。
- **裁决**：先花半天核实 ACP/各 agent 是否吐 context/token 字段（数据源 **unverified**）；拿不到稳定来源就搁置，不做启发式估算。粗估 M。

### E7b. 对排队消息点 👍 升级为下一轮跟进

- **场景与阶段**：补充说明已经排队，用户想让它优先被处理，现在没有任何手段。阶段：**纠偏**。
- **价值：中。** steerQueued 原语 runtime 已有，只缺 IM 接线，属于被工程评估点名的高 ROI 区。
- **受众**：新 低 / 老 **高** / 管 低。
- **裁决**：M，仅排队项可升级（running 并轮语义不支持就如实写文案）；需 E12 先补 reaction 事件订阅，白名单 + 去重防误触。

### E7c. 跨消息多图暂存窗口

- **场景与阶段**：手机连发三张截图，每张各起一个任务轮次，第三张才带文字说明。阶段：**发起**。
- **价值：中（频率不高但中招即废任务）。**
- **受众**：新 中 / 老 中 / 管 低。
- **裁决**：M，1-2s 窗口、窗口到点无文字也提交（有上限定时器，不拖纯图片首响），重启不恢复暂存。

### L1. "需要修改"打回带原话

- **场景与阶段**：验收时点"需要修改"并打字说明，用户无法确定自己的原话是否完整到达重开的任务。阶段：**验收/纠偏**。
- **价值：低-中。** 现状引用结果卡回复已会建新任务，差的是链路保真与可见性。
- **受众**：新 中 / 老 中 / 管 中。
- **裁决**：S 级核查/补齐：反馈原文完整进新任务目标，原结果卡留痕"已按反馈重开 #Txxx"。Agent Workflow 的"打回带原话"在流程编排里更重，Dutydeck 做到原话保真即可，不引入流程节点概念。

## 不做 / 维持清单

| 项 | 结论 | 一句话理由 |
|---|---|---|
| **E5b 常驻离线投影/runner_offline 状态机** | 不做，认可工程驳回 | 本地优先架构下 daemon 与执行端同机，机器离线时没有任何己方进程能发那张卡；要做就得引入 always-on 中继，背叛架构形态。恢复诚实性由 E5a 小版本承担 |
| **E17b 手机 PTY 审批/xterm 终端** | 不做，认可工程驳回 | XL 且依赖 Claude Code PTY 提示格式稳定性；产品分工本就是飞书管决策、Web/终端管键盘，不承诺手机做终端原生交互 |
| **E18b 卡片侧公网兜底地址** | 不做，认可工程驳回 | 本地 daemon 的 Web 在未配远程访问时手机必然不可达，补一个注定打不开的按钮是假出口；改做配置侧提示 |
| **E8 关闭话题杀任务** | 不做 | 平台无关话题关闭/解散事件，无可靠信号源（unverified）；显式 /new + /stop 已覆盖 |
| **E8 空闲 30 分钟自动轮换会话** | 不做 | 与"持久会话 + resume + 引用续作"的核心契约冲突，自动丢上下文是投诉高发区 |

| **E11 Agent Bus 化 / pre-agent 委派钩子** | 不做，认可工程驳回 | /work 是消息传递 + wait 轮询范式，没有"父任务同步等子任务结果"的链，强抄 RPC Bus 是范式错配；两跳控制并入 E9 观察 |

## 产品主线（把候选串成用户可感知的五件事）

1. **决策不出飞书。** 审批四按钮（A）+ 10 秒宽限（E2）+ 问答表单化（E10）+ /tasks 就地拍板（E15）+ 审批卡 Web 出口（E18a）。用户对"在飞书里被问"的全部合理反应——允许、记住、拒绝换路、拒绝叫停、选择、补充、跳 Web 看证据——都在卡片上下文旁一触可达，不需要终端、不需要编号、不需要电脑。
2. **消灭手敲编号和参数。** E10、E14、E15、E16、E23、BC 表单卡、E24b 菜单共同移除所有"记住命令语法/抄录 ID"的时刻：能点的不让人敲，能选的不让人背。
3. **上手即会，不背手册。** 欢迎语（E24a）告诉用户 bot 是什么、菜单（E24b）永远展示下一步、打错命令有提示（E23）、/new 是一张卡而不是一串 flag（BC）、缺权限一条 /repair 修好（E12）。新用户第一分钟不需要读文档。
4. **安静但可信的进度。** 队列可见（E7a）、卡不泛滥（E14）、重启有注解（E5a）、卡死有诚实终态（K1）、长任务看得见上下文余量（Ectx）、群里操作有署名（E20）。不新增任何通知音，只消除"它到底怎么了"的疑问。
5. **终态即证据，验收在原地。** 文件结果可标验收（E19）、打回原话保真（L1）、深链直达证据（E18a）、中期再补人声明的验收脚本（M）。守住"结果可验证"和双卡终态既有契约，验收动作不需要开电脑。

## 与工程评估的主要分歧（明示）

1. **A 审批四按钮是工程评估的最大漏项。** E2 把审批议题收窄为"宽限时序 + 双通道"，但内部四款产品的共识（lark 报告 §2.5-4、§4.1-2）是**按钮语义**比时序更值钱："始终允许"直接决定长任务能否无人盯守。产品要求 A 以 P0 补立项，E2 宽限降为同主线的 P1。
2. **E9（多 bot @ 改写 + 两跳闸）工程判"直接做"，产品降 P2。** 多 bot 自由接力的受众当前没有用户证据，群工具真 at 已覆盖确定性协作，单 bot 私聊/话题是主路径；两个 M 的投入在完成率主线上排在全部 S/M 项之后。
3. **E3（过程卡三档）工程判"直接做"，产品降 P2。** 它加配置面、挤压卡片预算，且两档分别撞七原则（off 无收益——PATCH 本就不响；detailed 抢 Web 的活）。默认 brief 是已验证状态，等反馈再动。
4. 其余工程驳回项（PTY 手机审批、常驻离线投影、公网兜底、Bus 化、url.preview、独享卡）产品**全部认可**，理由不是"做不了"而是"不该做"，已并入不做清单。E4 CardKit 认可暂缓的门槛，但要求 PoC 真正排期，不允许"暂缓"变成"不看"。
