**平台红线对上述判定的约束**（[LK §3.1.1/§4.3][ENG 附注]）：

- 现网卡栈已经是 JSON 2.0 + `update_multi:true`（`L/service.ts:575`，[ENG 报告不符清单 6]）——**7.20 版本下限已经是现网依赖**，表单 form、折叠面板 collapsible_panel、overflow 不再引入新的版本门槛；低版本兜底文案仍要保留。
- 卡片 ≤200 组件 / JSON ≤30KB（PB 100KB）：现网自限 24KB/180 组件 [AUDIT §2]，/tasks 改造后 60–75 元素、四按钮审批均不触限；真正要防的是 /work 长目标 + detailed 档过程卡叠加（E3 已要求保留"绝不剥成空"兜底）。
- 流式卡（CardKit）自定义流式参数需 7.23+、开启 10 分钟自动关、**流式期间不可转发、不可用回调直接更新卡**（必须先关流式）[LK §3.1.3]。不可转发与 Dutydeck"冻结卡即历史凭证、可传播"的契约冲突 [AUDIT §6]：关流式冻结后是否恢复可转发，**unverified**，列入 E4 PoC 必验项，不验不迁。
- H5 弱网体验弱于原生 [LK §3.4.1]；webBaseUrl 指向本机 daemon、手机默认不可达且不存在有意义的公网兜底 [ENG E18]——**结论：手机卡片必须自足，不能把长内容/关键操作甩给 Web/H5**，Web 深链只是配置了远程访问用户的加成。

## A3. 手机上"发起带目录/agent 选择的任务"的最短路径

现状最短路径其实已经对：私聊直接发一句话 / 群里 @ 一句话，默认目录、默认 agent，一步到位 [AUDIT §1]。要保护这条路径，**任何表单化都不许加在它前面**。

需要非默认目录/agent 时，按成本从低到高：

1. **话题内继承（零操作）**：会话已按 thread 路由 [AUDIT §1]，在已有话题里追任务沿用该话题 cwd；支持"引用一条任务消息发 /new"继承目录。
2. **菜单 → 表单卡（3 次点按 + 打目标）**：单聊菜单「新建任务」→ 表单：目标（multiline input）+ 目录（select：默认/最近/workspace，不给自由路径）+ agent（select，默认预选）→ 提交一次回调。
3. `/new --cwd ... --model ...` 保留给桌面，手机文档里不出现。

## A4. 手机上的 PTY 终端确认：驳回意味着什么，轻量替代是什么

工程驳回"飞书内做终端"是对的（双向驱动 stdin + 解析终端提示格式，XL，[ENG E2/E17]）。但要如实承认驳回对手机用户的实际后果：

- ACP agent：审批/问答有结构化卡，手机可拍板，闭环完整。
- **PTY agent（pty-cli ask 模式）：终端提示不进 runtime 权限 map，observe 根本不发审批卡**（`getPendingPermissions` 对无 resolvePermission 的 driver 返回空，[ENG E2]）。任务在终端挂起等输入时，手机上只看到进度卡停止前进——**没有卡、没有通知、没有任何可操作物**，通勤用户无法区分"在跑"和"死了"。这是信任缺口，不是功能缺失可以忽略。

建议的轻量替代（不做终端、只做固定两个键）：

1. **v1（建议做，S-M）**：停滞检测——PTY 运行 N 秒无新输出且进程未退出，发**一张**"任务似乎在终端等待输入"卡：只给两个按钮：「中断任务」（Ctrl-C，pty-driver 已支持该键，`L/workbench.ts:188-194`）和「知道了」。**不给自由输入、不给"回车"**：向未知提示发回车可能等于授权，安全边界不能靠猜提示格式。
2. **v2（可选，需白名单）**：runtime 能确定提示类别（如纯 informational 的 Press enter）时才出「继续（回车）」；识别不到一律只给中断。识别逻辑失效必须 fail-closed 到 v1。
3. **产品姿态明示**：PTY 运行的任务在卡片上标注"终端模式，交互审批需在电脑前"，让用户派活前就知道，而不是挂起后才发现；手机盯梢场景引导使用 ACP agent。

`/work` 步骤的 PTY 确认同此问题，A1 的步骤级按钮同样适用。

## A5. 长结果 / 文件 / diff 在手机上的验收

现状：结论在结果卡、长正文转 `执行结果.md`、验收按钮在结果卡（文件型结果靠回复）[AUDIT §2/§5.7]、页脚 Web 链接在本机部署下手机打不开 [ENG E18]。问题排序与改法：

1. **决策摘要必须留在卡内**：结果卡内联一段证据摘要——改动文件数、每文件 +/- 行数、测试/检查结论（[P1.0] 原则 5 的手机版落地）。没有这段，用户只能在"盲签"和"放弃手机验收"之间二选一。
2. **短 diff 进卡、长 diff 进文件**：短 diff 用带语言标注的代码块 + JSON 2.0 collapsible_panel 按文件折叠（7.20 已是现网依赖）；超 30KB 仍走文件，发送层保留拆分。不做把整份 diff 塞一张卡的尝试。
3. **文件验收一键化**：E19 reaction 标注（✅/📝），先 list 后写防重复（reaction 对文件消息可用性 **unverified**，需实测 [ENG E19]）。
4. **Web 链接是加成不是依赖**：配置了远程访问才渲染深链（E18 已判定），手机验收链路在没有 Web 时必须完整。
5. 视觉类结果优先截图/图片回传，手机原生渲染，零成本。

# B. 通知策略

## B1. 典型长任务的通知时间线（排队 2 分钟 → 跑 15 分钟 → 中途 1 次审批 → 完成）

事实基础：新消息产生会话红点并按用户免打扰设置推送；PATCH/延时更新**无红点**；reaction/pin 不产生新消息红点；@ 是强提醒；加急更强但受 200 未读上限/群设置/外部群限制 [LK §3.5/§3.2.4]。

| 时刻 | 系统行为（现状代码） | 手机锁屏 | 必要性判定 |
|---|---|---|---|
| t=0 发起 | OK reaction（无红点）+ 进度首卡"已接收"**新消息** [AUDIT §2] | **亮 1 次** | 基本必要：reaction 触达语义 unverified，首卡是"入队/排队中前还有 N 个"的唯一可信凭证 [P1.0 §消息承诺 1-2]；用户发完就揣兜时这条承担"收到了"的确认。保留。 |
| 0–2min 排队 | 同一卡 PATCH（排队位置/取消） | 不亮 | 正确 |
| t=2min 开跑 | PATCH 变蓝，1s 心跳 | 不亮 | 正确，竞品最吵的事故（每个 chunk 亮屏）现网天然免疫 [ENG E21] |
| t≈8min 审批 | 审批卡**立即新发**，无宽限（[ENG E2]）；群里**不带 @**（已核 `workflow-interactions.ts`） | 私聊**亮 1 次**；群里只有群红点，**免打扰群不亮** | 本次审批本身是必要亮屏；但两个缺陷：①人在电脑前也照推（E2 grace 解决）；②群聊场景漏强触达，与"收到审批后拍板"的主打场景直接冲突（B3 解决） |
| 审批后继续 | 审批卡 PATCH 决议态，任务继续跑 | 不亮 | 正确 |
| t≈17min 完成 | 进度卡 PATCH 冻结（静默）+ 结果卡**新消息** [AUDIT §2][P1.0 §5] | 私聊**亮 1 次**；群里无 @ 同审批问题 | 必要。结论：**锁屏共亮 3 次，必要的是审批和完成 2 次，首卡 1 次保留**；E2 grace 上线后人在终端前时只亮 2 次。 |

另一个现状缺口：**审批无人答时没有升级、没有自动拒绝**（永不自动拒绝是对的 [ENG E2]），但手机用户错过审批后，任务会无限期静默挂起，除主动打开飞书外没有任何再触达。需要 B3 的升级规则。

## B2. 各候选通知机制对质量的影响

- **审批 10s grace（E2，建议做）**：人在键盘前当场答掉就不发卡——直接消灭一类"陪跑推送"；纯手机用户代价只是审批卡晚到 10 秒（任务本就阻塞，无感）。必须带两个配套：①daemon 在 grace 窗口重启后要补发未发过的审批卡 [ENG E2 风险①]；②**审批卡挂起期间抑制闲置提醒**（tlive 同款），一件事不亮两次 [GH §2.8]。
- **reaction 三态（E1，出站已暂缓——同意）**：reaction 变更是否产生推送/红点证据库零文档、仅 cc-connect README 断言，**unverified** [ENG E1]；且 Dutydeck 已有独立结果新消息承担完成通知，done 表情是重复通知 + 每任务 2–4 次额外 API 调用。**通知职责永不迁给 reaction**。入站 👍 做 steer（E7）是控制面，与通知无关，可独立做。
- **加急（不立项——同意且强化）**：竞品 0 家用 [GH §3]、受 200 未读上限和信噪比申报约束、外部群不支持 [LK §3.2.4]；加急是消耗信任的动作，v1 不做。未来若做，唯一合法场景是"审批阻塞超时 + 发起人本人 + 预先 opt-in"。
- **pin（暂缓——同意）**：无红点、群里可能仅管理员可 pin、是群级共享资源 [LK §3.2.3]；只适合长生命周期项目群 pin **一张**总览卡，不适合每任务 pin，不解决任何触达问题。
- **闲置提醒（K）**：区分两类——①"任务 N 分钟无输出"的**卡死探测**值得做，每任务最多一条新消息，带「中断/重试」，这是活性信号（Bridge 探活 kill 同类 [LK §2.2.1]）；②"审批/问答等你很久了"的**催办**值得做但要克制：每个待决事项最多升级 1 次、只 @ 发起人、与 grace 抑制联动；③"还在跑"式汇报一律不发——打开飞书看 PATCH 即可。
- **审批连发合并**：一个任务短时间内多个权限请求时，grace + "始终允许"已能消掉大部分；残余情况建议同一任务 60s 内的新增审批 PATCH 进同一张待决卡（多组按钮），不每审一条新消息。

## B3. 什么事件才允许新消息 / @ / 加急（建议策略表）

| 事件 | 允许的触达通道 | 群聊定向 |
|---|---|---|
| 接收/入队 | 首卡新消息（现状）+ OK reaction | 不 @ |
| 排队、心跳、阶段、工具流、daemon 恢复注记（E5） | 仅 PATCH，永不新消息 | — |
| 需要人决策（审批/问答） | 新消息卡 | **@ 发起人**（现状缺，已核代码无 at）；白名单内其他人可见可点但不被 @ |
| 完成（成功） | 结果新消息（现状） | **@ 发起人**（现状缺），不 @ 全员 |
| 失败/中断/重试终态 | 新消息 | @ 发起人；被他人中断时另在卡面注明操作者（E20） |
| 审批/问答超时未答 | 每事项最多 1 条升级消息，只 @ 发起人；再无响应保持静默 | 不 @ 其他人、不加急 |
| 卡死/无输出超时 | 每任务最多 1 条 | @ 发起人 |
| 加急 urgent_app | v1 全部禁止；远期 opt-in 后仅限审批升级，外部群不可用 | — |
| reaction / pin | 永不承担通知 | — |

一句话原则：**新消息只花在"需要人知道或需要人行动"的时刻；需要人行动就 @ 具体的那个人；其余一切原位刷新。**

补充两条总量规则：同一任务 60s 窗口内同类触达合并；任何异常路径（对账补发、重启恢复）遵守同一表，恢复事实用 PATCH，只有终态/待决允许补发新消息（dsh-im"发送失败最多 3 次、结果不确定不重发、不重放审批/问题/文件"纪律 [GH §5 反模式 2]）。

## B4. /work 多步骤目标（3 分支并行 + 汇总）怎么通知

现状代码有具体缺陷：notify 在"目标 running 且无 waiting 且无权限请求"时静默返回，但**一旦任一步骤进入 waiting，fingerprint 含全部步骤状态，之后其他分支每完成一个步骤都推一张新卡**（`L/workbench.ts:150,156-161`，已核）。私聊下这就是锁屏连亮；配合 E14 之前"点一下也发新卡"，长目标的线程会被卡片淹没。

建议模型：

1. **一块目标看板，只 PATCH**：一张卡三行分支状态（执行中/完成/失败/待输入）+ 汇总步骤行，所有正常进展只刷这张卡，零亮屏。
2. **亮屏只允许三种时刻**：①进入 waiting/权限请求——一条消息 @ 发起人，写明哪个分支等什么；②分支终态失败且目标无法继续——**合并播报**：首个失败后开 30–60s 收集窗，同批失败聚合成一条，不连亮；③全部分支完成 + 汇总交付——一条结果消息，摘要 + 每分支一行结论 + 证据入口。
3. 单分支成功不发消息；汇总步骤失败按目标失败算一条。
4. 修复 fingerprint 触发条件：步骤 running↔completed 的正常流转即使在 waiting 期间也只 PATCH，只有 waiting/blocked/failed/completed 这些**焦点态**变化才允许新消息。
5. 总量承诺：每个目标亮屏次数 ≤ 2 + 待决次数 + 1 次升级。

# C. 群协作

## C1. 任何人可中断他人任务 vs 仅发起人可点（Oncall 模型）

现状是受信白名单内任何人可取消/重试任何人的任务，卡面无操作者归属 [AUDIT 粗糙点 8][ENG E20]；Oncall Agent 的"中断"按钮仅发起人可点 [LK §2.3]。

**判定：不做"仅发起人"硬锁，做"开放操作 + 责任可见 + 危险操作二次确认"的中间态。**

- Dutydeck 群是白名单受信团队，不是公开群。真实的协作场景是"发起人进地铁/开会，同事帮忙叫停一个正在烧钱或写错方向的任务"，硬锁会把这个场景锁死，且与刻意保留的"人能干预 AI 协作链"设计注释相悖（`L/coordinator.ts:1215-1224`，[ENG E20]）。
- 但匿名可中断必然产生"谁杀了我的任务"。必须配套（E20）：①卡面状态行写"由 X 操作"，进 task 持久字段，扛得住心跳重绘和重启；②他人对非本人任务执行中断/取消/重试时多一次确认（本人操作不拦）——/tasks 列表场景尤其需要，列表里没有上下文；③任务被他人中断/失败时结果消息 @ 发起人（B3 表）。
- 权限边界保持现状分层：普通控制操作（中断/重试）白名单皆可；审批走白名单 + high_risk 门；不新增"仅发起人"分支。
- "仅发起人"留作未来群策略配置项（群主可选），没有用户诉求前不建。

## C2. 多 bot 同群

**真 at 改写（E9，做）**。include_bot scope 配置器已申请 [ENG E9]，但只有真 at 标签能唤醒对端 bot：agent 自由输出里的"@名字"现在是纯文本，跨 bot 接力静默失败。改造边界按工程评估：出站文本统一过改写器、bot open_id 映射优先、真人重名歧义拒绝改写并提示 openId、邮箱/路径里的 @ 不动。

**TTMate 无中心协议（I）：不整体采用，只取防环纪律。** TTMate 的消息读面对所有 bot 开放（任何 bot 的发言都被读入，Dutydeck 可作为普通参与者 [LK §2.3]），但让位/错峰只对实现了该协议的成员有约束力；对异构 bot，我方发的任何协议头都不被遵守，"全群两跳"在分布式事实上无法承诺 [ENG E9]。具体选择：

- 做：自家 bot 的服务端两跳计数（不只是提示词）、不响应自己刚发出的消息（服务端去重，不能只靠 prompt）、精确 @ 才唤醒（现状已有一半 `L/coordinator.ts:557`）、bot 间消息 per-scope 令牌桶（连续 N 轮自动静默并留审计）。
- 不做：共享台账、随机错峰、主持人协议——对异构群无效，对自家多 bot 是过度设计（自家多 bot 由同一 runtime 调度，不需要群里喊话协商）。
- 远期低成本兼容：若群里有 TTMate bot，Dutydeck 把其台账消息当 ambient 输入读即可（TTMate 本就读所有 bot 发言），不需要实现它的协议。

**@ 唤醒噪音**：群默认 @ 才回是全行业共识 [LK §2.5]，保持；topic 策略下 bot 拥有话题内免 @ 是有界豁免，可保留 [AUDIT §1]；include_bot 开通后他 bot 消息量上升，mentionPolicy 白名单要复测 [ENG E9]，ambient 模式不得对 bot 消息生效。**循环消息风险真实存在但可被上面四道（精确@、自环去重、两跳闸、令牌桶）封死**，不是拒绝多 bot 协作的理由。

## C3. 私聊管理台 vs 群里干活（D）

Vonvon 的"私聊只管理、项目群跑活"在它"一群=一项目"模型里成立 [LK §2.2.2]，但 Dutydeck 现状是私聊即主工作台、一句话直接建任务，这是手机最短路径和单人用户的全部体验。**判定：不迁移职责，只补齐私聊的管理能力。**

- 改造成本：强制"先建项目群才能干活"会同时打穿首用引导、手机 1 步发起和单用户场景，收益（上下文整洁）已由 thread 路由实现大部分。
- 取其精华：私聊补 bot 菜单（E24）、/tasks、配置类回执卡，让私聊"既是控制台也能干活"；群侧靠话题=会话边界和可选的群菜单看板增强，而不是把私聊的活赶出去。配置/接入类操作本来就主要在私聊和 Web，不需动。

## C4. 话题=任务的心智：怎么显式化（没有关闭事件的前提下）

现状是"话题 → 会话"路由成熟，但一个话题里可以 /new 多个任务、会话持久 resume，任务与话题不是 1:1 [AUDIT §1][ENG E8]。"关闭话题联动杀任务"依赖的话题关闭/解散事件平台不存在，**unverified**，工程驳回成立 [ENG E8][LK §3.3.1]。ccbot 的"关 topic 杀 window"无法照搬 [GH §2.7]。在没有平台事件的世界里，用 UX 把边界做显式：

1. **任务身份可见**：结果卡/进度卡标题或页脚带任务号（[P1.0] 卡片层级已定），冻结卡即该任务的永久凭证；/tasks"返回原会话"跳回原话题（已有）。
2. **给"另起一个任务"一个一键出口**：bot 可以用 reply API 对自己的消息 `reply_in_thread:true` 开新话题（平台有此能力 [LK §3.3.1]，无独立建话题接口但回复即可形成话题）。在话题闲置后下一条任务入口处给一张轻提示：「沿用本话题上下文 / 开新话题处理」，两个按钮，不自动丢上下文——用用户的一次显式选择替代平台缺失的关闭事件，也避开空闲自动轮换与持久 resume 契约的冲突 [ENG E8]。
3. **话题可辨认**：bot 话题首条消息带任务标题，飞书话题列表里一眼能认出是哪个任务。
4. 不做：空闲 30 分钟自动轮换（默认关都嫌危险，投诉高发区 [ENG E8]）、thread 级 workspace 绑定（需求未被证明）。
