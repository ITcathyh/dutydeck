## 二、最危险的 3 个"照做会出事"

1. **持久化"始终允许"规则（L §4.1-2 / §4.4）**。一次手机误触或群成员误点就沉淀为长期授权，而"同工具+同目录"在 Bash 这类工具上约等于任意命令放行；规则存储、跨 agent 语义、撤销、审计全部空白，且直接撕掉审批卡上"只处理这一条请求"的现行契约（`L/workflow-interactions.ts:139-145`）。最成熟的 tlive 恰恰只敢做内存态重启清空。来源仅一篇内部 wiki，工程评估还漏裁。**1.0 必须剔除。**
2. **把 👍 reaction 接成控制面且复用 `steerQueued`（E7-2）**。社交表情在群里天然被用来"点赞/收到"，而现有原语的真实行为是 `discardSession: true` 硬中断当前轮（`packages/agent-runtime/src/index.ts:922-933,1034-1044`）：同一话题共享队列里，任何人对自己排队消息的一个误触，会把队友正在跑的轮次无声杀掉且不自动重排。这把"中断"从一个带文字标签的故意点击降级成了手势误触。**必须限制为发起人本人+只重排不杀轮，否则不做。**
3. **按 L TL;DR 的姿态立刻上 cardkit 流式卡**。10 分钟自动关流是官方硬限制（`raw/f_cardstream.txt:249`），长编码任务必然永久双轨；叠加流式中回调不能更新（中断按钮失效窗口）、不可转发、11311 创建竞态、7.20 门和限流放大，在移动端 PoC 证明收益前投入 L 成本，属于用平台新能力制造新故障域。**以 E4 的 spike-first 为准，L 的推荐等级必须下调。**

## 三、高信心结论：红队认为稳、不应动摇的部分

1. **双卡终态 + 独立结果新消息 + PATCH 不打扰**：官方发送语义、Bridge"纯文本有小红点"自述（L §3.5）、Oncall"终态帧必发"与 Dutydeck 自有产品契约（product-1.0:55-64）四方一致。reaction 通知语义在真机验证前不得替换它。
2. **永不自动拒绝 + 先答先赢**：现状已实现（E2 引 runtime :1147-1184），tlive README 独立印证同一设计，是保持项。
3. **群默认 @ 才回、话题=会话=隔离边界**：全部专职竞品和内部产品趋同，Dutydeck thread 路由已成熟。
4. **E6 云文档评论先 spike**：Bridge 自认多轮 bug 未修完，平台风险证据具体，差异化价值真实，值得做但不值得赌。
5. **架构性驳回**：always-on 中继（E5 完整版）、Agent Bus 化（E11）、url_preview、独享/临时卡、群话题关闭联动、加急、PTY 手机终端化——每条都有架构或官方文档硬约束，驳回有理。
6. **S 批小修方向**（E16/E17/E18/E20/E23/E5 恢复注解/E12 /repair）：均有当前代码 file:line 支撑，复用现有 CAS 与能力门，是这批候选里 ROI 最实的部分。
7. **平台红线清单**（30KB/100KB、200 组件、回调 3 秒、延时 token 30 分钟 2 次、11311 退避、JSON2.0 仅共享卡、5 QPS/会话）官方文档核证，可直接贴墙。
8. **E 对上游报告的 10 条代码纠偏**（流式开关已发、include_bot 已申请、先答先赢已实现、表单不依赖 cardkit 等）经抽查全部属实（`L/service.ts:577`、`L/open-platform-configurator.ts:12-15` 均已复核），这种"先证伪再立项"的处置应成为后续候选的默认流程。
9. **现有资产清单**（A §6）：一次性审批、单一鉴权事实源、诚实能力门、冻结契约、入站持久化+5s 对账——所有候选都应在这些设施上增量，B1/B2 是仅有的两个会反向侵蚀它们的候选。

## 四、遗漏问题清单（四份材料合起来没人讨论）

1. **daemon/执行端离线时的入站消息保证**（高）：长连接断连期间用户从手机发的任务是否被飞书补投、补投窗口多长——无文档、无代码、无实测（unverified）。E5 只回答了出站投影。这正对豆包文档"依赖本机开机"的叙事打击，必须实测断线/重连投递语义，并给用户一个"没收到 OK=没入队"的明确预期（现状唯一信号就是没有回执）。
2. **误发/过曝敏感信息到群**（高，见 D8）：agent 主动 `group send` 无内容脱敏；审批卡/结果卡是共享卡，cwd、命令、结果文件对群内及未来成员默认可见；跨群误投的防线只有提示词。需要：出站脱敏复用卡面同一套清洗、敏感结果默认私聊/仅发起人可见的策略评估。
3. **bot 自身故障时用户怎么办**（中）：daemon 挂=完全沉默，无 OK 无失败卡；Web 健康页在手机上不可达。至少需要文档化超时预期与重发约定；有远程 devhost 模式的用户可考虑健康检查走独立通道。
4. **飞书侧 API 故障/宕机降级**（中）：本地任务应继续执行（runtime 与发卡解耦需验证），但完成通知、审批、问答全部失联时：卡片是否堆积重试、恢复后对账顺序、用户会不会重复下单——5s 对账与幂等键有雏形，缺故障演练。
5. **历史任务搜索**（中）：/tasks 仅分页无搜索（`L/task-dashboard.ts` 无 search），长生命周期私聊/大群找历史任务只能翻页；E18 的 Web 深链部分缓解，但 IM 内仍无检索入口。
6. **完成通知找不到发起人**（中）：结果新消息只产生会话红点，不 @ 发起人；在 ambient 免@策略的高频群里发起人可能漏看。可验证的替代是结果卡按发起人 open_id 定向 @（入站事件已有该 id）——这恰是 cc-connect done reaction 想解决的真问题，但没人评估 @ 方案。
7. **PTY ask 静默挂死**（中，见 D4）：无审批卡、无 watchdog，是当前版本就存在的状态，不是假设风险。
8. **多语言**（低）：卡面文案全硬编码中文（`L/card-renderer.ts` 无 locale 分支），cc-connect 连 cron 提示词都 i18n。个人/受信小团队可判 1.0 后，但应记录为已知边界；UI 语言与 agent 输出语言要分离。
9. **重启时在飞审批集体过期**（低-中）：pending 卡重启即 expired 并 PATCH"已失效"（`L/workflow-interactions.ts:54-67`），daemon 频繁发版时用户会看到一堆同时失效的审批；可考虑恢复后对仍 live 的请求自动补卡而非宣告失效。
10. **结果在手机上的可引用/转发完整性**（低）：转发结果卡时交互默认关闭是对的，但证据区/文件型结果（飞书云空间权限）随不随转发、转发后"验收"态如何呈现，未讨论；E19 用 reaction 标注文件验收部分弥补。
11. **限流容量核算**（低-中）：默认全局并发 10，同群多任务的 1s 心跳+5s 对账+终态 3 重试+新增 reaction 调用，相对单会话 5 QPS 红线的峰值没有测算；230020 退避是否覆盖新调用面需在 M 批一并验证。
12. **群成员变动与历史可见性**（低）：平台文档已提新成员对历史话题可见性受限（L §3.3.1），但 Dutydeck 会话按 thread 持久，成员退入群后卡片/文件可见性与 agent 继续响应的授权变化无人讨论。
