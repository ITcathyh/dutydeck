# 消息交付记录与恢复

状态：controller 草案，待独立复核。接续 [飞书执行接线](lark-execution-ledger-design.md)；统一过程卡、结果、自动化通知和 Agent 主动交付的持久事实，不新增任务执行器。当前实现仍使用 card mapping 和各来源 KV，本稿尚未实施。

## 对象和唯一性

一个 Delivery 表示一个固定来源在一个明确目的地的交付意图。来源保存严格的种类及引用：任务接收/具体 Attempt、WorkItem 运行、自动化 occurrence 或已接受任务内的主动发送操作。结果来源必须包含固定 AttemptResult 的 Task/Attempt/settlement/throughSequence/outputDigest；不能只给 Session ID 后在发送时取“最新结果”。

Delivery ID 由来源的稳定业务键、用途和原目的地生成。过程展示与最终结果是两个用途，不能用同一行覆盖；明确重试产生的新 Attempt 有自己的记录。首次过程卡可能先于 Attempt 产生，引用已接受 Task 及固定 number=1；一旦绑定具体 Attempt，后续写入不能换绑。来源未被接受前的接收回执引用 Inbox 原事件及业务轮次，不能伪装为执行结果。

每条 Delivery 保存 revision、原始操作者、所属 App/brand、目的地、来源、当前展示操作引用、交付状态、创建/更新时间。目的地为严格的群/用户发送或原消息回复联合，回复固定 messageId/replyInThread。归属 Task 的新配置不能改变已准备消息的目的地；跨群主动发送在准备时经过明确授权并固定目标。

每个实际平台操作另存不可变 DeliveryOperation：operationId、Delivery ID、单调操作序号、方法与目标、实际请求体/摘要、素材引用、provider UUID、首次提交时间、去重期限、状态与回执。创建一条消息、更新原消息、已证实拒绝后的修订是不同操作。新内容不能重用旧 UUID；同操作重投按实际冻结请求体发送，不能重新渲染动态时间、Agent 名称或配置。

平台字段按方法区分：发送/回复保存其 UUID；当前消息卡 PATCH 不虚构 UUID 或服务端 CAS。已读完整 [更新卡片契约](https://open.feishu.cn/document/server-docs/im-v1/message-card/patch)：请求体只有 content，成功 data 为空，接口说明是无条件更新。若使用平台模板，固定 template_version_name；省略版本会随模板发布变动，不能作为冻结请求。官方原文快照为 `/tmp/dutydeck-full-product-20260914/lark-card-patch-official.json`，SHA-256 `4c7f08a30447655a6a768bac2897dc862eb48e8286e9f6ac37fb463a2467ec5b`。

数据库使用 deliveries 和 delivery_operations 两张表，唯一约束分别固定来源/用途/目的地以及 Delivery/操作序号。操作回执属于操作行，原成功回执不可覆盖成另一个 messageId。来源当前卡片的 channel_mappings 只作可重建索引，包含 Delivery ID；所有恢复和回调按实际 Delivery 读原 Task/Attempt。历史每次卡片不再因索引指向新卡而消失。

## 素材与冻结请求

发送前将完整结果和媒体准备成稳定内容。文本、富文本、卡片、图片、文件、视频及封面、语音使用同一交付记录；实际上传文件类型和消息类型必须匹配。网络上传在 SQL 事务外，保存实际 App 范围、文件摘要、字节数、媒体类型和平台 key，不能把平台 key 当跨 App 通用引用。

本地素材使用服务管理的不可变副本或已有内容寻址产物；重开后读取同一摘要验证，不能直接重读用户原路径而悄悄换内容。记录不含凭据明文。上传失败不进入“消息已提交”；上传成功但回执丢失的素材可重新准备，尚未发给接收者的孤立上传与重复消息区别记录，不虚构已删除平台孤立文件。

超长结果转文件在准备阶段决定，完整结果摘要保持不变。平台明确内容拒绝后，过程卡可沿用当前原地降级规则创建新的更新操作，保留上次已接受的内容；最终结果不能降级成缺正文的“已完成”。旧成功结果更新反馈状态时，保存新的展示操作，原结果与送达收据保持。

## 事务与外部步骤

仓储提供 enqueue、prepareOperation、beginSubmission、recordReceipt、recordFailure、reconcileReceipt 和 requestResend 命令；不暴露任意 JSON 改状态接口。所有命令验证严格输入、稳定 operationId、原 revision、来源和目标集合，在一个短 SQLite 事务内提交。涉及 TaskResult 的准备重查原结算及摘要，不接受客户端自报的完整结果 JSON。

Delivery worker 使用当前 Runtime 的数据库控制权领取操作；监听器不各建一个恢复发送器。领取只是本地调度资格，不能证明旧网络请求没有发生。服务在令牌等待与退避结束后，再核对领取、App 当前授权、原操作者和目的地，持久记录提交意图，才调用平台。事务不包网络等待；权限在实际请求进入后撤销，保留这个请求可能已发生的事实。

成功回执按方法判别。发送/回复保存原 operationId、请求摘要、实际返回 messageId、返回 chat/thread/parent、接收时间和可用的平台请求关联；目标不符或响应缺 messageId 保持未知。更新操作使用已有已验证消息收据的目标 messageId，保存原请求摘要、平台 code=0 ACK 与可用关联，不要求 PATCH 返回不存在的 messageId 字段。迟到回执可以结算其原操作，不能修改后续操作或新卡；取消意图不抹掉已经发生的成功。当前消费者收到的 delivered 只来自对应方法的收据，不再各自凭函数返回另写一套权威状态。

服务关闭先停止领取和新入站，撤销等待中的操作，然后等待实际进入的网络调用及回执持久化尾声，最后释放数据库控制权。原进程已退出的 pending 操作恢复为待核对；新进程不能仅凭租约过期重发。进程内 active Promise 与原代际核验只解决当前实例，跨进程事实依赖持久操作。

## 失败、重放和用户修复

状态区分 prepared、submitting、delivered、retryable、unknown、blocked、cancelled。cancelled 只用于已证明未进入平台的操作；网络开始后的取消先保留 submitting/unknown，不能向用户保证消息未发出。明确拒绝保存业务码与脱敏原因，网络错误不冒充拒绝。

平台去重范围及期限依照已核对的 [发送](https://open.feishu.cn/document/server-docs/im-v1/message/create) 与 [回复](https://open.feishu.cn/document/server-docs/im-v1/message/reply) 契约。未知请求仅在仍有平台保证时自动重投完全相同操作；重投不延长首次去重期限。时钟变化、长时间挂起或旧记录缺首次提交依据使期限不可确认时，保持 unknown。不得把网关重试次数归零当新的一小时。

reply 失败后的群内发送只能来自已证实原请求未送达、原意图允许且当前仍获授权的回退操作；不能由任意 catch 触发。权限拒绝、内容审查、未知回执不能通过换端点、换 App、换目的地或转附件绕过。明确被撤回的原消息是否允许换为同群落点由固定交付意图决定，执行时不猜用户意图。

同一 App/messageId 的内容更新持久串行，跨来源的反馈/过程更新也不得各自抢写。PATCH 不适用发送 UUID 的一小时重投规则；网关关闭其网络结果未知后的自动重发。原更新未知时阻止该消息的后续更新，避免旧请求迟到把新内容覆盖。只读正文看似匹配但没有确切操作关联，不足以宣称全部在途旧更新已经结束。修复可以核对原操作，或由已授权的明确决定冻结原卡更新并创建替代卡；原操作与旧卡保留，所有迟到结果只记原行。独立最终结果仍可正常交付，不能让过程卡未知重新执行任务。

期限外有确切 messageId 时，读取原消息并核验 App/目的地/关联后补记收据；没有精确关联不按相似正文或时间猜匹配。用户可在交付详情中核对并确认已有消息，或明确选择再次发送并接受可能重复；命令保存实际操作者、原操作、说明与稳定决定 ID，新操作不会再次执行任务。旧不确定操作及新发送均保留，不能把旧记录改成明确失败来隐藏不确定性。

公开详情只展示来源、目的地、送达状态、实际消息链接、可解释原因和受权限保护的修复动作；不展示 provider 请求体、秘密引用、原生控制身份或内部操作者令牌。任务结果与交付状态分别展示，交付失败不改 Task outcome。

## 旧数据与来源接线

迁移只把确切已送达历史映射成 delivered，不追发旧单卡结果。旧 pending 有明确 Task/Attempt/结果边界和消息身份才可转成对应操作；其余保留 legacy 待核对，缺字段不补造 platform UUID、首次提交时间或操作者。迁移保存原行与稳定来源映射，重复启动不建第二份 Delivery。

WorkItem/Automation 的现有接收和固定结果契约保持；其 deliver 函数改为 enqueue/读取对应 Delivery 的稳定结果，最终各来源的“已交付”展示从统一收据导出。运行授权与交付授权分别检查，原来源取消不撤回已经送达消息。工具发送、通知、反馈也通过同一执行器，不保留网关背后的无身份自动重试写口。

## 验收

真实 SQLite 与本地 HTTP 平台 fixture 固定故障点：来源入库后关闭、上传返回前断线、平台已收消息但回执丢失、收据写失败、相同操作并发、去重期限内外重开、领取期间撤权、关闭中迟到 ACK。每个场景核对实际收到的端点/目标/正文摘要与本地全部操作记录，不能只断言一个 mock 函数被调用。

覆盖 Attempt 1 未知和 Attempt 2 完成的独立过程/结果卡、旧回调不修改新卡、同操作异载荷冲突、来源 CAS 失败、超过历史分页上限的恢复、媒体 App 不一致、结果转文件、限流与内容拒绝。增加 PATCH 成功空 data 的真实 HTTP fixture，以及旧 PATCH 回执丢失/迟到时新更新被阻止、替代卡不被旧请求改写的用例。兼容测试语义变更逐项说明，保留完整结果及原地降级的有效断言。
