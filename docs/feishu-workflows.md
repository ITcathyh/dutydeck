# 在飞书完成一轮 Agent 工作

在私聊发送目标，或在群里 `@机器人` 开始任务。收到消息后先持久保存，再显示 `OK` 接收回执；进度和最终结果更新在同一张任务卡上。原卡确定不可更新时才补发替代卡。

## 查任务与继续工作

- `/tasks`：按待处理、运行中和最近结果查看任务，包含目标、工作区、执行状态与验收状态。群里展示本群任务；私聊跨群只展示本人发起且当前仍有权查看的任务。按钮返回原群或话题。
- `/tasks 2`：翻页；`/help`：查看可用命令。
- 完成后点击“验收通过”或“需要修改”。验收记录与执行结果分开保存。
- 直接回复待验收结果卡片并说明修改要求，会记录“需要修改”，新一轮沿用原任务上下文。已验收通过的结果再收到补充要求时，保留原验收记录并另开新任务。群里按当前机器人的唤醒策略使用 `@机器人`。
- `/new <目标>`：结束旧上下文，开始新的工作；`/cancel`、`/retry` 沿用现有取消和重试行为。

## 回答问题与批准操作

Agent 发起 `dockmux session ask "问题"` 后，问题卡会出现在原讨论中。回复问题卡即可回答，也可以发送 `/answer <卡片上的编号> <回答>`。回答送回等待中的原任务。

问题卡临时发送失败时，只要原任务仍在等待，入口会随任务心跳重试投递，失败后的重投间隔至少 5 秒。

在机器人设置的“Agent 与风险控制”中选择“飞书逐项确认”后，ACP 的操作确认会显示“批准一次”和“拒绝”按钮；也可使用 `/approve <编号>`、`/reject <编号>`。群内文字命令遵循机器人当前的唤醒策略。

批准要求当前操作人的高危操作权限。受管理群还会校验当前成员身份、操作范围和本轮发起人；仅能查看任务的成员不能批准。每次请求只接受一个决策，旧卡、重复点击和已结束的任务会被拒绝。回执表示执行端已接受决策，最终是否成功仍以任务结果为准。

逐项确认只支持 ACP Agent。旧配置继续使用已确认的完全信任模式；切换模式时如有运行或排队任务，先结束这些任务再应用配置。

## 自动补充任务材料

明确引用的同群消息、当前话题近期消息、附件，以及 `https://…feishu.cn/docx/…`、`/wiki/…` 和对应 Lark 链接，会作为带来源的参考材料加入 Agent 输入。原始任务目标保持独立。

每轮话题扫描最多 20 条消息，文档最多 3 份、单份最多 8,000 字符，参考正文合计最多 16,000 字符。后续轮次使用增量水位，水位在执行端接收后保存。未授权、读取失败和被截断的材料会有说明。文档通过机器人的开放平台权限读取；当前不使用用户身份授权。

## Agent 回传文件

启用当前机器人的群协作工具及发送权限后，Agent 可在已有会话中执行：

```bash
dockmux group send-file ./report.pdf --idempotency-key report-v1
dockmux group send-file ./preview.png --image --reply-to om_xxx --in-thread
```

文件必须位于该 Session 的工作目录内。普通文件上限 30 MiB，图片上限 10 MiB；目录、非普通文件、空文件和路径逃逸会被拒绝。目标由当前会话绑定，不能传任意群 ID。目前文件回传要求 Linux 且可读取 `/proc/self/fd`，以校验打开后的真实文件位置；其他平台会明确拒绝发送。

发送失败后可重复同一命令，复用相同交付键。上传成功而消息发送失败时，重试复用已上传的文件；成功后返回原消息。同一个键不能换内容或发送位置。飞书端的最终去重仍依赖其消息 UUID 机制，不承诺超出平台有效期的无限期 exactly-once。

## 重启后的行为

尚未提交执行的入站任务会重新验证当前配置和权限，再尝试接收；稳定任务键覆盖“执行端已接收、入口尚未来得及记成功”的窗口。已有队列沿用 Runtime 恢复机制。运行中的任务在守护进程重启后明确标为中断。

若重启时聊天命令正执行且无法确认结果，入口会提示检查结果并手动重试，不自动重复执行 `/new` 等命令。卡片重试使用当前操作人的身份和当前配置，保留原任务材料。

失去原等待器的问答和审批会失效。监听器重新连接时，只为执行端仍然存在的请求建立新的问题卡；历史卡不能重新授予权限。文件交付状态和验收结果持久保存。

当前版本把原请求、展开的参考材料、问答及交付记录保存在本地数据库，用于恢复、重试和历史查询，尚无自动过期清理。备份中也会包含这些内容；长期使用时数据库和历史扫描开销会增长。按终态和保留期归档列为后续优化。

本轮验证使用自动化测试、真实本地 ACPX/mock ACP 进程及模拟飞书服务，未改动真实飞书应用配置，也未执行真实账号联调。
