# Dutydeck 完整产品与 Botmux 能力追平方案

分析基线：2026-09-14，Dutydeck 5e2743e，Botmux e8c9bbdf。只使用当前源码、现存项目文档和本会话的验证结果，没有读取 memory、个人知识库或历史 session。本文固定完整终态与验收范围；开发进展另见 [实施记录](full-product-execution.md)，不能将方案中的要求视为已实现。

**建议继续以 Dutydeck 为产品主体，保留现有任务、群协作、工作目录与验证能力，统一运行和管理模型，复用 Botmux 已有明确边界的组件。完整交付覆盖执行器、会话流转、工作流、自动化、插件、远端设备、飞书扩展、桌面与运维、迁移回滚。各批次用于安排依赖，全部验收完成才称为能力追平。**

## 1. 追平的范围要固定到用户能力

目标用户是个人开发者和共享飞书群的工程团队。保留本地优先：没有云控制服务也能完成本机任务；需要远端机器和多设备时再部署相应服务。没有依据把企业计费、任意 IM、原生 Windows daemon 或跨供应商无损上下文转换加入范围。

以指定 Botmux 提交的已接线用户能力为基线，包括需要显式开启的能力。实验功能单独记录限制；仓库以外的中心服务标记为外部未验证。实现期间新增的 Botmux 功能进入后续差距清单，不能让本轮目标无限移动。

本轮按用户指定排除 **Mira、Riff、Mojo** 的补齐与验收；`mir` 是另一执行器，仍在范围内。Botmux 原始执行器基线保留供核对，必交付范围为其余 28 个 ID。远端机器、设备控制与 Codex App 不受这项排除影响。现有占位适配器不因登记而算可用，迁移报告必须保留这些排除项及原因。

一项范围内能力只有同时满足以下条件才交付：

1. 用户有可发现的入口，可完成配置、使用、失败处理和关闭。
2. 服务端、执行器、权限、持久化和交付已接通；创建了对象或暴露按钮不算完成。
3. 在承诺支持的真实环境中通过正常路径、失败、重启和撤销测试。
4. 安装、升级、迁移和诊断能够保留其状态，支持限制写进同一份能力清单。

追平允许不同实现。例如用户要能继续操作已有 CLI，会话后端不必复制 Botmux 的进程组织；用户要能在空白机器安装，不要求产物一定是单文件二进制。不能用“未来可以通过插件实现”代替当前应交付的插件与完整入口。

### 现状中的四个重要修正

- Dutydeck 已有多 Agent DAG、人工等待、条件分支、单步重试、模板和原话题交付。现有代码需要升级与整合，不能再建一套并行编排器。
- live 群管理也在使用 ChannelBot、GroupBinding 和身份事实。它通过 live_lark 激活路径运行；generic 新建或导入对象没有完整激活链。准确的问题是同一模型有不同的生命周期约定，不能说所有 staged 群配置都无效。
- 自有 Session Automation 已真正执行 Cron、定时计划和 GitHub CI 续作；独立 Schedule Foundation 仍只有定义、预览和账本。应合并执行语义，保留已有可用能力。
- 适配器登记不等于执行器完整。Dutydeck 的 Mira 文件明确依赖尚未随产品提供的 runner，Riff、Mojo 文件明确没有对应后端；Codex App 也需要补齐 runner/协议执行链。

上述事实分别可从 [WorkPlan](../packages/shared/src/work-items.ts)、[WorkItemService](../apps/server/src/work-items.ts)、[live 群管理](../apps/server/src/lark/group-management.ts)、[自动化服务](../apps/server/src/session-automation.ts)、[Schedule 管理](../apps/server/src/schedule-routes.ts)和[适配器工厂](../packages/cli-adapters/src/factory.ts)核验。

## 2. 能力差距逐项落实到交付

“已有”指当前入口和实现已接线，不代表真实外部链路均已验收；“部分”指存在明确边界或只有基础组件；“待补”指当前入口、执行契约及集成代码未接通相应用户操作。外部依赖不能因为拿不到测试环境就计为通过。工作包编号对应第 5 节。

| E08 项目与成果验证 | worktree、产物 manifest 与实际文件校验 | 已有 worktree 及独立命令/代码指纹验证；工作流成功仍主要依赖文本输出 | P4 补实体成果清单、版本/摘要、下游输入和代码成果归并；保留 Dutydeck 已有验证证据优势 |

## 3. 产品只保留一套任务和管理语义

用户主要看到“项目、任务、Agent/Bot、自动化、设备”。任务可由一句目标开始，也可展开为多个步骤；用户无需先理解 Session、TaskRecord、WorkItem 三套内部名词。

| 产品对象 | 承担的职责 | 对当前实现的处理 |
|---|---|---|
| 项目与工作目录 | 源仓库、执行位置、共享目录或 worktree、验证规则 | 保留 WorkspaceManager，补成果归并、清理和完整平台支持 |
| 任务 | 用户目标、参与者、步骤、审批、成果、验证及最终交付 | 以现有 WorkItem 能力统一投影；普通对话任务是单 Agent 的简单形态，兼容既有任务链接 |
| 一次运行 | 一次指令或某步骤的一次尝试，拥有独立状态和执行身份 | 将现有 TaskRecord、WorkAttempt、runId 的关系明确并持久化，不依赖 Session 当前状态推断旧尝试 |
| Agent 会话 | 某执行器的原生上下文与进程/远端资源 | 保留 Session 与原生会话 ID；任务可以包含多个会话，重试是否复用上下文必须明确 |
| Bot 与群绑定 | 消息身份、默认 Agent、项目、唤醒和操作权限 | 收拢 live/generic/import 三条配置路径，页面及监听器读取同一份生效配置 |
| 自动化 | 定义触发条件，发起或继续任务/工作流 | 一份定义、一份触发记录和执行所有权，复用当前自动化与 Foundation 的有效实现 |

先建立兼容映射和统一查询投影，再分步迁移存储；保留 /api/sessions 及既有 ID。不能一次重命名数据库，也不能同时运行两套调度器“等待以后合并”。

运行事实的权威关系保持清晰：普通多轮会话仍是一条 Session 对应多条 TaskRecord，不强制套入现有 WorkPlan 的 12 步或一小时限制；WorkAttempt 引用具体 TaskRecord 和资源运行代际；Session.runId 表示会话运行身份，不能代替指令 ID。Runtime 写入指令执行事实，工作流据此推进步骤状态，界面聚合这些事实，不生成第二份独立任务终态。

### 运行内核要解决的共同问题

保留模块化单体服务，执行器进程按需要隔离。以下职责分开，避免卡片逻辑决定运行状态：

- 入站接收负责验证来源、保存消息与附件引用、产生可追踪的接收记录。
- 任务运行负责幂等接受、持久队列顺序、尝试代际、权限复核、执行器资源所有权和恢复。
- 工作流只决定哪个步骤可运行；定时器只决定何时产生触发；二者都通过同一任务运行入口执行。
- 交付服务读取运行事实，通过持久待发送记录处理卡片、文本、文件、通知和反馈。执行成功与交付成功分别记录。
- Web、飞书、CLI、桌面与远端入口使用相同的操作接口及权限判断，不能各自实现状态迁移。

必须先修复本会话已经隔离复现的三个缺陷：冷缓存并发事件撞序号、人工队列优先级在重启后丢失、停止兜底超时后旧任务仍能影响新运行。具体位置见 [Runtime](../packages/agent-runtime/src/index.ts)。第三项以假 driver 模拟迟到完成，真实供应商触发条件仍为 unverified。

事件序号应由事务或单会话串行写入分配；队列顺序需要持久记录；每次尝试的回调、状态保存和清理都检查代际与资源身份。仅清几个内存 Map 不足以解决旧异步任务迟到写入。

对无法确认的执行保留“结果待核对”，提供查看原进程/远端状态、确认已完成、终止后重试等操作。不能自动重发可能已执行的指令。外部服务不支持幂等时，通过回执核对或人工确认处理，不宣称跨所有供应商绝对恰好执行一次。

### Bot 激活与群权限必须合并

配置状态、期望监听状态、实际监听状态分别记录。例如应用凭据已保存，不代表发布审核通过，更不代表机器人已进群。

新建、现有和导入 Bot 都使用同一套生命周期。应用级流程为：凭据绑定 → 目标应用下身份验证 → 监听所有权 → 启动与健康状态。群绑定另行完成目标群可达性、群身份和生效策略检查。仅使用私聊不要求预先加入群；一个群失效不能停掉同 App 的其他有效群和私聊。失败停在具体步骤，修复后原地继续。

明确区分聊天、操作自己的运行、操作他人运行、终端写入、执行高风险工具及管理 Bot。Dutydeck 当前 live 路径会为 canTalk 用户合成 own_runs 操作能力；迁移 Botmux 时不能无提示扩大原有授权。App 范围内的 open_id 不能跨应用复制；远端、工作流子任务、插件与定时任务都携带真实发起者及独立授权依据。

## 4. 实现路线选择复用边界

| 路线 | 结果与代价 | 结论 |
|---|---|---|
| 在 Dutydeck 内从头重写全部 Botmux 能力 | 模型可控，但重新承担大量 CLI、平台、恢复和交付兼容工作 | 不作为默认路线 |
| 让 Dutydeck 长期成为 Botmux daemon 的前端 | 快速获得部分现成能力，但两个任务状态源、权限和升级边界会一直存在 | 仅可作明确边界的过渡执行桥，不作为完整产品终态 |
| 保留 Dutydeck 产品和运行内核，提取或使用独立组件 | 保留已有优势，继承成熟协议处理；需要组件契约和跨仓兼容验证 | 推荐 |

优先验证 Botmux 的 [workflow-core 独立包](../../botmux/packages/workflow-core/README.md)。它提供图定义、调度/控制和运行接口，不能当成已经包含模板管理、飞书卡片、PTY、供应商执行器的完整工作流产品。通过 host 接口接入 Dutydeck 的身份、运行、审批、验证与交付；只使用公开导出并固定版本或提交，禁止业务层深导入 Botmux daemon 内部文件。

在验证包集成可行后，以该引擎替换现有 WorkItem 的图推进部分，保留任务 API、模板、身份和交付服务；旧计划转换到同一引擎。若独立性验证失败，则提取必要的纯调度/控制组件。最终只能有一个权威的工作流推进实现。

集成验收必须接上 Dutydeck 的持久尝试租约、资源身份、host 动作核对和 gate 恢复。该包默认的进程内租约无法在崩溃后证明旧尝试已经终止；只提供 executeAgent 回调就开始运行，会留下恢复缺口。先验证普通运行、人工等待后重启、旧 worker 仍活着时恢复、外部发送成功但回执未落库四种样本，再完成产品级集成。

CLI 输入协议、原生会话发现、输出解析、持久后端探测、插件协议适合按组件提取。Botmux 的 daemon、worker、worker-pool 不整体搬入 Dutydeck；保留测试样本和来源说明，分别验证依赖、原生模块、资源所有权、授权与升级兼容。现有 MIT 元数据只是源码复用调查的起点，发布产物仍需完成组件及来源清单。

执行器按四类实现统一契约：本地 ACP、本地交互 CLI、协议/API Agent、远端设备执行。协议特有分支留在执行器，不把供应商判断散落在任务运行、卡片和调度模块。

## 5. 完整交付拆成可验收工作包

下表各工作包均属于完整终态，按本节依赖推进；优先级只决定先后。Mira/Riff/Mojo 已依用户要求排除，所有涉及执行器、迁移与验收的条目均遵循这一范围。

| 工作包 | 完整输出 | 主要承接位置 | 依赖与验收出口 |

## 6. 迁移必须能切换，也必须能撤回

延续现有只读 discover/plan/archive，新增独立的显式执行流程。默认迁移对象为同一台机器、同一供应商的可恢复上下文；跨主机或跨供应商的上下文转换另标语义限制，不能承诺原进程无损移动。

1. 生成逐对象映射：Bot、群、身份、项目、会话、计划、工作流、插件/Skill、反馈和交付历史。保留源指纹、未知字段和不能转换的原因；Mira/Riff/Mojo 配置作为本轮排除项归档展示，不静默丢弃或激活。
2. 导入为待激活对象；绑定真实凭据并在目标应用下验证身份。不得直接复制不同 App 的 open_id，也不得把脱敏清单当完整恢复数据。
3. 影子核对有效配置与执行意图，不启动第二个消费者。存量计划以原时区、下次触发、最近执行和去重记录核对。
4. 进入切换窗口：停止源入站与调度接收，等待已接受工作落账，记录消费水位；禁止源 supervisor 自动重连，取得可验证的资源与监听所有权。
5. 目标按新代际接管，验证同 App/群只有一个有效消费者和调度写入者，再恢复接收。Dutydeck 本地一把锁不能隔离另一台机器上的 Botmux，源端必须实际支持停止/禁止重连或共同遵守租约。
6. 核对切换前后接收、执行、结果与反馈数量及对象归属。结果未知的工作不自动重发。
7. 回滚先停止目标产生新副作用，再对账目标已接受/已执行工作并回传必要状态，最后恢复源。不能仅恢复旧数据库而遗失切换期间的新工作。

切换前生成反向兼容清单，列出可回传的配置、游标、结果及源端不能表达的目标功能。默认回滚先排空目标执行；不能排空的任务需明确终止并保存结果/状态，再恢复源。保证任务可核账和用户可继续处理，不保证旧 Botmux 能原生继续执行 Dutydeck 新增的所有任务类型。

外部发版、飞书写入、真实 listener 切换和生产迁移均留到可审阅的执行阶段按授权开展。本文只定义实现与演练要求。

## 7. 完成验收必须看真实用户旅程

### 能力矩阵按支持组合记录

每个范围内执行器记录：发现/安装、首次启动、连续输入、材料、流式输出、审批、中断、排队/提升、空闲续接、活动轮次恢复、原生 fork/adopt、模型/实例切换、终端、Skill/MCP、隔离、工作流和资源回收。每格为“已通过、失败、未验证、不适用”，并关联版本、平台、测试与证据。协议本身不提供终端可以是不适用；缺 runner 或缺测试账号只能是未完成/未验证。

逐执行器跑其支持契约，再选代表组合做跨层测试：Claude Code/自定义 wrapper、Codex、Traex、一个其它终端 CLI、Codex App 协议执行链、一个远端设备执行器。Botmux 自身不支持的组合不加入硬性要求，也不能把主流三款通过泛化成全部适配器通过。

### 必须交付的真实旅程

| 旅程 | 验收必须观察到的结果 |
|---|---|
| 新用户接入 | 空白机器安装，扫码或绑定已有 App，选工作目录与 Agent，收到第一条真实结果；任一步失败可原地恢复 |
| 手机接管外部工作 | 本机已有 CLI 被发现，可观察或输入接管，手机追问/打断、Web 终端操作并退出接管；不顺带要求该 adopt 会话可跨群 relay/fork |
| 受管会话接力与分支 | Dutydeck 创建并管理的可迁移会话，保持原上下文跨群接力；支持原生 fork 的执行器创建独立分支，源会话保留；在途输入和迟到结果不串路由 |
| 团队值班 | 普通成员可提问，未授权者不能终端写入或操作他人任务；改权限后旧卡片、排队任务和插件调用即时按新权限判断 |
| 多 Agent 交付 | 并行分析→条件汇总→人工 gate→修改/验证→成果交付；分支失败只重试指定尝试，取消后旧分支不能补写终态 |
| 长任务恢复 | 活动轮次中杀 daemon、worker 或网络；按供应商能力续接/明确中断，能核对结果且不重复提交原指令 |
| 自动任务 | 定时、CI 与受控前置检查、Webhook/API 触发任务和工作流；离线补偿、DST、修改定义、撤销/限流均可观测；测试前置检查不意外派发模型 |
| 插件与材料 | 安装带 Skill/MCP/服务/卡片 action 的插件，处理文件和图片，升级或撤销后隔离与权限仍成立 |
| 扩展协作 | 语音转写/播报、文档评论、会议事件到达正确任务，多个会议消费者不串身份，输出遵循用户配置和授权 |
| 远端设备 | 配对机器、出站连接、执行/终端/文件/预览，掉线恢复；撤销设备后旧凭据、连接及新派发均失效 |
| 反馈与运营 | 对指定最终结果反馈、修改和导出；事件重试不重复计数，监控能关联 Bot、任务、Agent、设备与资源 |
| 领取外部任务 | 从平台 Issue 看板领取并选仓启动，防重复占用，结果回写后由人验收；退回、释放、断线重试与外部状态一致 |
| 更新和恢复 | 从实际发布产物安装/升级，启动失败回到可工作版本，数据迁移与备份恢复不丢任务和配置 |
| 迁移与回滚 | 从测试 Botmux 迁移完整样本，切换前后无双消费；目标产生新工作后仍能执行可核账的回滚 |

上述旅程跨飞书、Web、CLI、桌面验证同一对象；真实浏览器测试检查入口可发现、状态一致、移动端可操作及错误补救，不以源码字符串或截图存在代替可用性。

性能和资源验收覆盖长历史、并发任务、卡片限流、文件上传、机器掉线和批量恢复。保留 Dutydeck 已有有界事件窗口及 benchmark，在同一主机/数据/负载下测双方的耗时、内存和进程数，再给目标值。工作流并发/步骤/运行时长改成有解释的资源策略，不把取消所有上限当成能力增强。

### 当前已有证据与最终完成边界

同一源码基线的前一轮检查：Dutydeck 默认套件 3,248 通过、7 跳过，workspace typecheck 通过；Botmux 13 个定向测试文件共 246 条通过，源码 typecheck 通过。本轮另通过 Botmux 的 Spec、条件边、Manifest、模板 Schema、host binding 和调度前置条件 6 个定向文件共 100 条测试。这些证明了相应本地测试，不证明完整飞书、供应商、远端中心或跨平台发布链。后续新增能力必须补相应真实验收。

当前 README 引用的产品、架构、验收、迁移等 docs 文件在分析开始时并不存在于工作树或 Git 跟踪清单。本文新增 docs 目录不代表修复了那些失效链接；P8 要补齐真实文档并校验安装包内外链接。
