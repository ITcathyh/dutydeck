# Bot、群与身份的统一激活设计

属于完整产品方案 P1，授权撤销、配置切换、导入载荷及兼容规则已通过独立设计复核，不表示功能已实现。依据 `b1520be` 及本轮整合源码；P0 的持久运行所有权与恢复仍是前置条件。

## 1. 当前真正缺少的链路

现有 live 配置能运行。`lark.bots` 保存凭据、监听意图和执行默认值，listener 直接消费它；群管理另外写 ChannelBot、SecretRef 元数据和群身份事实，但仍从 legacy 配置计算策略。generic 路径可以保存管理对象、写本地凭据和做身份预检；其 schema、授权器与 listener 都明确禁止激活。Botmux import 只有 discover、plan、archive，尚未把计划写入 Dutydeck 数据库。

因此交付必须包含配置归并、实际导入、激活与撤销，不能把 `desiredListenerState` 改成布尔开关就算完成。具体证据见 [ChannelBot schema](../packages/shared/src/index.ts)、[执行授权](../apps/server/src/foundation-policy.ts)、[群管理](../apps/server/src/lark/group-management.ts)、[listener pool](../apps/server/src/lark/listener.ts) 和 [导入 CLI](../apps/server/src/legacy-import-cli.ts)。

还有一个需要先复现的 listener 竞争：pool 在 `await listener.start` 后才登记实例；其间 stop 或删除看不到尚在启动的对象。P1 需用进入启动的停点证明并修复，不能将正常启停测试当作覆盖。

## 2. 只保留一个生效配置来源

ChannelBot 表及关联策略成为 Bot 的管理权威，SecretRef 指向实际凭据，GroupBinding 保存群覆盖。App 内默认 Agent、工作目录、模型、路由、访问规则和工具上限必须有唯一归属。现有模型尚不能表达的私聊配置和身份定位器补到相应关联配置，避免把整个 legacy JSON 再藏进一个不受校验的扩展字段。

`/api/lark/config` 和现有页面保留兼容入口，通过同一配置服务读写新模型；`StoredLarkConfig` 仅作为旧 listener/coordinator 的临时执行投影。投影带 Bot、配置、凭据和激活版本，不成为第二份可独立修改的配置。新的管理页面也调用同一个配置服务。

live 配置转换保留原 Bot/群/Session 的 ID 映射与权限语义。转换后 legacy KV 保留只读迁移快照，不能与新表长期双向写入。先验证转换、读回与恢复，再让 listener 切换消费；不能在迁移事务尚未完成时提前启动。

权威切换有持久标记，迁移提交在同一数据库事务中核对来源版本或内容摘要、写入新对象并切换标记。外部凭据文件准备期间若旧配置被编辑，旧快照不能提交，重新读取并转换。API、应用创建向导、创建 CLI、群管理的事务内授权读取以及 listener 全部遵循该标记；旧写入口统一转入配置服务。迟到的应用创建结果也必须核对预期版本，不能切换后覆盖为旧配置。

现有 live SecretRef 只是 `live_lark_config` 元数据，实际 secret 仍在 KV。归并需要将值写入真正的 SecretProvider 并回读验证，再原子关联新引用；写文件成功而数据库失败产生的未引用文件应可重试清理。旧凭据何时删除由完成的切换和备份策略决定，不能先删除再尝试迁移。

## 3. 配置、监听意图与运行事实分开

| 对象 | 表达的事实 | 不能代替的事实 |
|---|---|---|
| ChannelBot 配置 | Bot 身份、凭据引用、启用/停用及执行策略 | 凭据有效、平台已允许连接 |
| 监听意图 | 用户希望接收或暂停新消息 | listener 实际已经连接 |
| 应用身份事实 | 某凭据版本在目标 App 下验证过，含有效期 | 已进入所有目标群 |
| 群事实与绑定 | Bot 在指定群的身份、群覆盖及有效期 | 同 App 其他群或私聊的可用性 |
| 激活记录 | 当前生效版本、持有者、运行代际与失败步骤 | 仅凭 lease 过期便可以接管旧连接 |

激活按应用执行：解析凭据 → 验证目标 App 身份 → 校验执行配置 → 获得监听所有权 → 启动连接 → 记录健康状态。群另行验证；没有群的私聊 Bot 可以完成应用激活，一个无效群不能停掉同 App 的其他有效入口。

已有 live 的 full-trust 确认仅在迁移时等价的执行姿态和授权范围内保留，不能通过导入补成 true。新建和已迁移 Bot 都遵守同一规则：改成更宽权限后旧确认不能继续使用。标题等无关配置改变不要求重新确认。平台身份预检成功也不能代替运行授权。

失败记录具体步骤和原因；修好凭据、权限或目录后可原地重试，不新建一组重复 Bot。配置 revision 改变时，旧启动结果不能把新版本标成健康。

## 4. Listener 的创建与撤销

P0 的持久控制所有权提供同一部署的单写者基础；P1 在 App 层登记启动意图和实际实例，启动前即捕获代际。远端连接等待不占配置提交序列。停止、删除、换凭据在开始时撤销旧代际，并覆盖尚未完成的启动。

所有消息、卡片、群事件和重连回调使用其启动时捕获的 Bot/配置/凭据/激活身份；提交接收记录前重新校验。旧 `start` 迟到返回要回收其自己的连接，不能放回当前 pool。撤销后 supervisor 重连也只能重试已失效的代际，不能取得新的运行权。

连接代际和执行授权版本分别推进。换凭据、停用等操作撤销连接代际；标题等普通编辑可保留连接，但必须更新当前执行投影。存活连接的回调先证明自己仍属当前连接，再读取最新投影并固定本次处理版本；不能把启动时的旧配置 revision 永久带入每条消息，导致普通编辑后所有新消息被拒绝。

服务停机还需跟踪已受理的入站、授权事实刷新和交付尾声，在关闭仓储前完成或封住其本地写入。P0 的 Runtime 屏障不自动覆盖这些外部服务；清空 listener map 也不能证明异步回调已结束。

UI 区分两种操作：暂停接收只停止新入站，保留已接受工作的原授权复核；停用/删除 Bot 撤销其执行授权，拒绝旧卡、排队任务和新工具调用，并安排受影响的运行停止。停止未核实的资源继续展示为待核对，不能因 listener 已断开就宣称任务已终止。

这一区别需要同时覆盖群和私聊。当前无群 RunContext 的私聊不会经过群 `beginTurn` 检查，统一接入后不能保留这个绕过 App 撤销的入口。

## 5. 身份与群权限

运行入口携带 ChannelBot、可选 GroupBinding、发起者及本次授权依据。每次执行前重新检查实际操作者，身份提交复用 P0 的 prepare/commit 接缝。安装者、群成员、工作流子任务和自动化不能互相借身份。

prepare 捕获与该决定有关的 App、凭据、群绑定和权限版本；commit 在本地重新核对这些版本与启用状态，不能仅检查 RunContext 的 app/chat/binding。接收和执行提交与 App/群撤销共用本地授权序列：撤销先提交，旧授权证据不能再提交；执行先提交，登记的已受理任务必须被随后撤销覆盖。Runtime 的 Session 短序列中可以进入这一授权序列；管理撤销先提交版本并收集受影响任务，退出授权序列后才调用 Runtime.stop，避免反向等待 Session 序列。远端验证、连接关闭和进程退出都不占授权序列。跨 daemon 提交仍须服从 P0 持久控制权，进程内锁不能替代它。

迁移保留 can_talk、can_operate、operateScope、终端写入、高风险执行与群工具发送上限的区别。`whole_group` 或允许提问不能直接换成操作所有人的任务。open_id 只在所属 App 内使用；email、mobile、union_id 与未经验证的导入定位器保留种类和状态，解析失败时明确要求补齐，不默认开放。

应用身份或凭据版本失效，相关群事实同步失效；群退群事件撤销该群绑定的运行资格，其他群不受影响。平台事件漏收时仍需在授权/刷新时核对事实有效期。实时退群事件种类、权限和平台投递行为需后续真实联调，当前为 unverified，不能承诺仅靠一小时缓存即时撤销。

角色、人设和实际权限分别处理；切换角色不得顺带扩大操作授权。Botmux 未支持或本轮明确排除的配置保留原因，不借激活过程偷偷启用。

## 6. 实际导入与兼容迁移

保留现有 discover/plan/archive 的只读契约，新增明确的导入准备和应用入口。当前公开 manifest 的 app_ref、人数等脱敏信息无法还原 App、群、身份和目录；现有 CLI 每次销毁的随机 fingerprint key 也不能用于跨进程重投。已有脱敏计划只作审阅材料，不可直接应用。

新准备入口从受控来源读取完整样本，创建受本地文件权限保护的导入作业，保存固定作业 ID、版本、来源命名空间、来源指纹及完整对象映射；公开审阅报告从这份载荷生成并绑定其摘要。应用和重试均引用已保存的同一作业，不能重新随机生成映射。凭据单独解析并存入 SecretProvider，公开报告只显示引用和状态。载荷或来源变化要求重新准备并报告差异，不能静默应用另一份数据。

应用事务逐对象保存源映射与转换结果，同源对象的后续作业复用持久映射，避免每个作业各建一套 Bot。进程重启或同一作业重投不重复建对象。导入后是可管理的待激活对象；缺少真实凭据时补绑 SecretRef，身份定位器和目录缺失也各自阻塞，应用身份在目标环境重新验证。不能把计划里的 `staged_only` 视为数据库里已经存在的对象。

同 App 已有 live/generic 对象时，展示和处理具体映射冲突，再复用统一身份；不能继续通过不同来源前缀各建一个可连接的 Bot。无法自动转换的路由或权限字段保持阻塞，并给出具体修复入口。Mira、Riff、Mojo 保留为本轮排除项。

源 listener/调度器的真实切换仍由 P9 执行。P1 的导入和激活演练只使用隔离样本，不能在源 Botmux 仍消费真实消息时自动启动第二个生产消费者。

## 7. 实施单元与验收

1. 模型与配置归并：迁移真实现有字段，兼容旧管理 API；验证重复执行、凭据文件写入失败、事务回滚、旧数据读回、迁移中并发编辑、应用创建迟到保存和切换后 CLI 编辑，确认权限不扩大。
2. 激活与 listener：应用预检、代际和所有权、启动/停止/换凭据、健康查询；用 deferred 验证 stop/delete 越过 pending start、旧重连和旧卡回调。
3. 群与私聊授权：统一 App 撤销、身份提交、群事实失效和 own/group/bot 操作范围；验证排队、运行中、自动化与工作流入口。用 deferred 暂停已通过的 prepare，撤销先提交时旧 commit 拒绝；执行先提交时撤销覆盖该任务。不能只测撤销后重新授权。
4. 导入落库和管理入口：受保护作业准备、计划应用、冲突处理、凭据绑定、继续激活及失败修复；验证同源两次 CLI 调用与进程重启后重投的稳定映射，同时完成 Web/CLI 中的可发现入口。
5. 三种来源走同一条完整旅程，加入真实应用身份验证、私聊、至少两个群、撤销与服务重开；源系统无双消费。真实平台环境尚未验证的项保持未完成。

开发依次接通这些单元，不允许只交模型或 disabled 对象就结束 P1。普通实现交 ccflash；跨进程监听所有权和权限模型由 controller 先固定设计，并在整合后独立复审。
