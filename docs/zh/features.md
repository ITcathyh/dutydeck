## 为什么选择 Dutydeck <a id="why-dutydeck"></a>

| 痛点场景 | 传统终端 CLI 使用方式 | Dutydeck 体验 |
|---|---|---|
| **移动交办与异步等待** | 必须守在电脑前；断开 SSH 任务就中断 | 飞书发一句话派活，后台持续执行，结果以卡片回传 |
| **高危操作管控** | 要么全局 YOLO 跳过确认，要么频繁弹窗卡住执行 | 卡片上点「允许本次」或「拒绝」，在手机上放行 |
| **代码冲突与脏工作区** | 直接改当前分支，容易污染未提交的改动 | 可选 **Git Worktree**：从当前提交派生独立目录，不动主工作区（Web 新建会话默认开启，飞书默认不开，见下文） |
| **交付质量验证** | Agent 说“测试通过了”，可能没跑 | **服务端实际执行验证命令**，留存退出码、耗时与代码指纹，失败自动打回返修（飞书任务，需先配验证命令） |
| **团队协同与项目记忆** | 每次新会话都要重述规范 | **跨会话记忆**自动沉淀；进群后按需参与，也可用自然语言交办定时任务 |
| **流水线无人值守** | 推送后手动盯 CI，挂了再叫 Agent | 装上 CI 插件后，构建失败可唤醒 Agent 按规则修复（见[插件](plugins.md)） |

---

## 核心能力 <a id="key-highlights"></a>

### 1. 飞书指挥台
- **流式进度卡片**：在私聊或群聊下达指令，状态、阶段、耗时实时更新。
- **手机审批**：Agent 要写文件、执行命令时，卡片弹出「允许本次 / 本会话允许此命令 / 本工作区允许此类命令 / 拒绝」，点一次即可。
- **长文本打包**：超长代码或分析文档自动打成 Markdown 附件。
- **ADHD 友好输出**（`adhdMode`）：命令、路径或代码放前面，清单按组拆分，进展和验证写清楚。飞书结果卡隐藏续问按钮；未配置验证命令且没有候选建议时省略验证占位行。结构化提问卡只保留问题和按钮：卡片没有标题栏或品牌页脚，单个选项使用主按钮，也不显示普通提问卡上的「其他」文字输入框。登记后工具返回 `deferred` 并安静结束原轮（账本记为取消、原因是等待持久确认），不发中断结果卡，也不能重试原轮；确认不随后续消息或服务重启作废；24 小时无人点击按已过期结案，卡片只留“已过期，未执行”，不回放原请求（升级前登记、没有截止时间的确认按发卡时间计算）。仅原发起人或当前高危名单成员可点击，群成员与权限在点击时按当前状态校验，等待期间不查群成员；点击后在原会话登记一轮带原问题、操作上下文快照和所选选项的新输入；该轮飞书卡片、任务导航及队列预览沿用原请求标题，缺少原文时显示“已确认”，内部回放文本不作展示名，写入前仍须按原流程检索去重（同卡只登记一轮输入，不承诺外部写入恰好一次）。多题只登记第一题；原会话归档或停止监听时终止确认，原请求授权撤回（如发起人已退群）在点击时发现并终止。回答后只保留所选选项、处理人和时间，终止后只保留简短状态；自由文本提问、计划卡和权限卡沿用原超时与授权边界。不额外要求确认或在三轮后停止修复。
- **交互卡收起**：所有机器人的静态待处理卡（提问、审批、计划等）首发采用非流式模式，生成内容的过程卡和结果卡保留既有流式规则。工作流点击决议与关闭文案先持久化，回调处理返回后延迟约 1 秒异步收卡；失败记警告并自动重试，最多 5 次。收卡前退出时由启动对账补关，重启后沿用剩余重试次数。
- **手机看改动**：结果卡带「改动 N 个文件 +A −D · 查看改动」，打开就能看这一轮的 diff，还能逐行评论。

### 2. Git Worktree 目录（可选）
- 任务在从当前提交派生的独立 Git Worktree 里改代码，不动你正在写的主工作区。
- **默认值不同**：Web 新建会话默认“独立 Git 工作目录”；飞书任务默认“直接使用所选目录”（`shared`）。飞书里要用 Worktree，在 `/new` 里加 `--workspace worktree`。
- 任务归档时检查未提交改动、未合并提交和占用进程，确认安全才释放目录。

### 3. 验证门禁（Verification Gate）
- 给机器人配好验证命令（`verificationCommand`，如 `pnpm test`）后，飞书任务改了代码就会在宿主机工作区真实执行。
- 记录命令退出码、耗时、标准输出和代码指纹。
- 验证不通过时，把失败输出发回 Agent 返修，最多 2 轮。
- 目前只对飞书任务生效；Web 会话不会自动触发。没配验证命令时不执行。

### 4. 跨会话长期记忆
- **默认关闭**：`memoryEnabled` 未设置时，只有群默认参与强度为「按需」或「积极」才开启。
- **范围**：私聊各自独立。群聊默认同一机器人的所有群共享一个记忆池；把 `groupMemoryScope` 设为 `per-group` 后，各群记忆互不可见（Web「群记忆范围」，或 `dutydeck settings bot set <appId> groupMemoryScope=per-group`）。切换不迁移也不删除：`per-group` 下原共享池保留但不读取，切回共享即恢复。
- **记录与提取**：`/remember` 手动记录；后台每 3 轮提取环境事实与偏好，每 8 轮合并去重。后台作业连续 5 次可重试失败或记忆 Agent 已被删除时放弃该作业、让出记忆池；结果未知、等待恢复核对的作业不在此列。作业记录不保存凭据原文；结束的作业每个记忆池每类只留最近 2 条，且只留任务编号和结果计数（不含对话原文），更早的删除。
- **注入**：新任务注入精简记忆索引（`MEMORY.md`，≤ 3000 字符），执行中 Agent 可检索完整细节。
- **管理**：任务详情的「管理记忆」可搜索、修订和删除实际记忆池；普通 Web 会话可显式创建和绑定项目记忆，目录相同不自动共享。见[配置来源与记忆管理](web-console.md#configuration-and-memory)。

### 5. 群聊协作与定时委托
- **参与强度**：只在 @ 时 / 话题内免 @ / 按需 / 积极（见下文）。
- **少 @ 一次**：在机器人认领的话题里继续追问不用重复 @；忘了 @ 时，10 分钟内补发一个 `@机器人`，会认领前一条消息。
- **定时委托**：在群里或私聊说“每天 18:00 总结本群今日进展”“每 15 分钟看看这个话题有没有结论”，Agent 会发一张确认卡，写明做什么、什么时候、发到哪，点「启用」才开始，不用记命令；每次的结果卡上可以停用。也可以用 `/schedule` 按分钟间隔创建。
  - 确认卡保留任务正文与原有换行，不再只显示前 200 个字符。确认卡发送失败时，计划仍保存且停用，Agent 会收到计划编号和恢复说明；本轮用相同参数重试可补发确认卡，也可由用户在当前对话发送 `/schedule enable <编号>` 启用。
  - 群协作委托（`collaborate mandate-update`）由 Agent 修改时，暂停、停止、暂停发送结果直接生效；改内容、时间、条件或恢复执行会在原话题发一张修改确认卡，列出改后的设置和新的执行内容全文，发起人或有操作权限的人点「确认」后才生效，确认前按原设置继续。委托在此期间被改过，这张卡确认时失效。Web 群设置里的修改不经确认卡。
  - 说“改一下定时任务”时，Agent 先用 `schedules` 查编号，再用 `schedule update <编号>` 修改时间或内容，保留原计划编号；更新后先暂停，点「确认启用」后按新设置执行。启停用 `schedule enable/disable <编号>`。同一事项已有生效循环计划时，创建请求默认拒绝并列出现有计划；确需另建才加 `--additional`。同一请求重试仍返回原计划；旧会话对已停用同名计划的兼容更新保留，但请求与原计划的工作项模板不一致时拒绝，提示改用 `schedule update` 或换名称。
  - Agent 或飞书 `/schedule every` 新建的循环计划默认“每次新会话”（`--mode fresh`），避免每次都带上整段对话；只有明确要求“接着上次的对话做”时才沿用本对话（`--mode session`）。一次性（`--at`）计划仍沿用本对话。更新未指定运行模式时保留原模式。需要试跑就在本轮直接执行一次，Agent 不会为此建“测试计划”。
  - 一直跟进直到办完：说“每半小时看一下这个 PR，一直跟到合并，周五 18:00 前没合就别跟了”，计划会带上完成条件和截止时间。每次运行先核对条件，达成后 Agent 自己停用；到截止仍未完成就自动停用并在原话题说明“已到截止，未确认完成”。计划也可以每次启动一个已保存的工作项模板。详见[定时任务](web-console.md#5-通用定时任务)。
  - 计划不会在上一次触发还没结束时再触发。某次触发超过一个周期（至少 10 分钟，从触发建出算起）还没开始或没结束时，会在计划的原话题提醒一次，说明卡在哪（排队受阻、等人处理“结果未知”，取不到原因就写“还没开始/还没结束”）；同一次卡住只提醒一次；发送中断且 10 分钟未确认时，在总计 3 次尝试的上限内重试。一次性计划没有周期，不提醒。
  - 每次新会话的计划，结果和提醒都发回原话题；新的一次只带上一次结果的摘要（约 500 字），在原话题回复时，接手的会话会带上最近一次的结果（约 1500 字）。旧版本建的、没保存运行模式的飞书循环计划自动改为每次新会话，不用重建；明确选了 `--mode session` 的不变。
  - 某次触发没跑起来（开会话或派发就出错）：执行会话暂时不可用（被锁、正在停止、终端没收干净）时，在新会话里按同一时间重跑一次，计划本身的运行模式不变，下一次照常在原来的会话里跑；其它错误或重跑仍失败，在原话题说一句出了什么错、下次几点再跑，服务日志记一条告警，带计划、触发编号和错误码。“CI 出现新失败”条件查不了（例如工作区换了提交，计划还盯着创建时那个提交）也记为没做成。Agent 收尾报了“受阻”或“等你决定”，这次记为没做成，任务本身仍是完成。结果卡发送失败按 1、2 分钟退避重发（服务重启后不等退避，立刻补发），最多 3 次，之后停止并在计划记录里标出失败原因。同一原因连续没做成（触发出错按错误码，收尾按“受阻”或“等你决定”，执行失败算一类）时，第 2 次起不再另发，改上一条为“已连续 N 次没做成：原因”，改不了再回一条短的；连续 3 次自动停用，并照常发停用说明。在话题里说“恢复”，Agent 会用 `schedule enable <编号>` 代办，重新启用后从头计数。
- **分层协作**：PMO 接需求、Leader 拆方案、Worker 落地，Leader 验收后回传原话题。

### 6. 开 PR 与跟进
- 飞书发 `/pr [标题]`，或在 Web 任务的「结果检视」点「开 PR」，Dutydeck 先出确认卡 / 确认框，有权限的人确认后才推送。
- 开出 PR 后自动跟进 CI 失败和评审意见，能修的交给 Agent 修好再推回同一分支。详见下文[开 PR 与跟进](lark.md#pr-loop)。
- 已有的 PR 也能交给会话跟进：飞书 `/pr follow <PR 链接或编号>`、Web「跟进已有的 PR」或 `dutydeck pr follow`。要求 PR 和会话工作区同一个仓库、工作区已检出 PR 分支、操作者有该会话的操作权限。
- 需要装支持开 PR 的 CI 插件（仓库自带的 `plugins/github`），否则 `/pr` 回“开 PR 未配置”。

### 7. CI 续作（插件提供）
- 核心不内置任何 CI 平台。GitHub Actions 和 Codebase 是两个自带插件：`plugins/github`、`plugins/codebase`，装上后才有 `/ci`。
- 构建失败时按规则交给 Agent 修复：单次故障最多 3 轮、同一报错指纹出现 2 次即停、推送前校验提交 SHA、不合入、不强制推送。
- 详见[插件](plugins.md)一节的“CI 提供方”。
