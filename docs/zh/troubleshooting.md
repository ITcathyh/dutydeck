## 已知限制 <a id="known-limits"></a>

- **本机 `~/.claude/settings.json` 的 allow 规则会绕过飞书逐项审批。** 飞书里 `ask` / `approve-reads` 的 Claude 终端模式虽然固定用 `default` 权限模式启动，但本机 `permissions.allow` 里的规则仍然生效，命中的操作不会出飞书审批卡。需要严格逐项审批时，清理本机的 allow 规则。
- **ACP 侧预先放行时，`/plan` 的计划阶段拦不住写操作。** 计划阶段靠拒绝 Agent 发来的每个权限请求来拦写。Claude ACP 如果自己预先配了允许规则（如 settings 里的 allow 列表）或默认模式是 bypass，这些操作根本不会来问 Dutydeck。用 `/plan` 时，ACP 侧不要预先放行写操作。
- **凭据保护按规则匹配，不是隔离。** 换个写法（编码、拼接路径、写脚本再执行）可能绕过；完全信任模式下，不在允许名单里的人仍能让 Agent 以本机用户身份运行任意命令。对外开放的机器人用强制拦截，或者不给它完全信任。
- **高危命令正则按原始文本匹配，不是沙箱。** 引号、反斜杠、路径前缀或子 shell 改写（如 `"rm" -rf`、`\rm`、`/bin/rm`、`$(rm …)`、`git 'push'`）都可能绕过；`git -C . push` 这类中间夹了选项的写法同样匹配不到。它只缩小暴露面，口径和凭据保护一致。
- Cursor 终端会话只有原始屏幕输出时，即使回放中可见回答，也可能因缺少规范化最终正文而记为失败。
- 验证门禁目前只对飞书任务生效，且需要先配验证命令。
- 终端模式下，Traex 没有用量数据；Codex 有按轮 token 与估算金额，但暂不计入用量上限。两者都不受美元上限约束。
- 用量金额是估算，不含加价项（见“用量与成本”），不是账单。
- 触发器的普通 token 鉴权不带时间戳和 nonce，靠 HTTPS 或内网保护传输；HMAC 签名请求带时间戳和一次性 nonce。见“插件 → 安全说明”。
- Web 的“群与权限”等草稿页默认隐藏，见“实验功能”。

## 常见问题与排障 (FAQ) <a id="faq"></a>

### 启动报 `DATABASE_SCHEMA_TOO_NEW`，或备份提示版本不匹配？

错误中的两个版本分别是数据库实际 schema 和当前程序支持的上限。复制错误里带实际路径的完整命令检查，不要把 `--database` 换成别的实例：

```bash
dutydeck database execution-status --database /path/to/runtime/dutydeck.db
```

它只读，不修复或降级数据库。优先换用支持该 schema 的 Dutydeck。只有停止所有写入方并确认备份时间后，才考虑把备份恢复到独立新目录核对；恢复会丢备份后的写入，切回旧代码本身不会回滚数据库。

### Web 能打开，status / doctor 却说服务未运行或端口被其他进程占用？

直接运行根命令的前台服务，以及某些由外部托管的入口，可能没有 daemon 状态记录。新版 `status` 和 `doctor` 会在**当前配置端口**依次短超时请求 `/health` 与 `/health/ready`：前者必须是 `ok===true` 的 JSON，后者还必须有布尔 `ready` 和字符串数组 `pending`；不跟随重定向。两者都符合时才显示未登记前台服务及地址，端口检查也不再把它当成其他进程。`ready=false` 表示服务已识别但尚未就绪，不会改写旧的 daemon `ready` 字段。

这项识别只是保守的结构检查，不是身份认证。HTML、通用 `{ "ok": true }`、结构不符、连接拒绝或超时都保持原诊断；已有登记、残留或损坏状态记录时也不做这项探测。服务确实只是临时 `--port` 启动、而当前 CLI 配置的是另一个端口时，请用启动时的同一配置运行 `status`。未登记进程的飞书连接状态无法由 daemon 记录核验，请查看它的启动终端，不要再启动第二个实例。

### 服务被 SIGKILL 后，doctor 为什么说“原因待富集”？

SIGKILL 无法执行进程内退出处理，所以下一代先根据上一代缺少 `clean-exit` 标记写基础异常。Linux/systemd 下会异步查有界 journal，只有同一 unit、boot、PID 与启动时间精确对齐才补 `SIGKILL`；journal 不存在、无权限、超时或归属不唯一时保留基础记录，不阻塞服务就绪。干净停止和计划重启在干净标记写成功时不写异常；若该标记写失败，进程会向 stderr 输出明确警告且保持原退出码，下一代仍可能按缺少干净标记保守补记异常，请检查数据库目录和 `last-abnormal-exit.json` 的类型、权限与可写性。上一代 PID 仍存活也不报崩溃。文件只留最近 10 条；launchd 富集本轮不支持。

### Q1: 在飞书给机器人发消息，没有反应，也没贴 `👌`？
1. 运行 `dutydeck doctor`，看「飞书监听」一栏是否正常。
2. 到飞书开放平台检查应用是否开启了 **「机器人能力」**，事件订阅方式为 **长连接**（已订阅 `im.message.receive_v1`）。
3. 检查机器人是否在群里；群聊里消息是否 `@` 了机器人（按“话题内免 @”以上的强度时，在已认领的话题里可以不 @）。
4. 默认 Agent 没装或登录过期也会表现为不回：`doctor` 会对默认 Agent 跑 `--version`，并点名找不到的命令。
5. 长连接断开后先由飞书 SDK 自己重连。重连卡住（例如代理接受连接却不回包）超过 10 分钟时，Dutydeck 会只重建这条长连接，进行中的会话不受影响；仍然卡住就按同样的间隔再重建。间隔用守护进程的环境变量 `DUTYDECK_LARK_RECONNECT_STALL_MS`（毫秒）调整，最小 60 秒，`0` 关闭。`doctor` 提示「Dutydeck 已在 … 重建长连接，仍未恢复」时，说明重建过但还没连上，优先检查到飞书开放平台的网络和代理。

### Q2: 提示 `Persisted key policy violation`？
- **原因**：ACPX 持久化键名必须是全小写 `snake_case`。
- **解决**：不要把大写环境变量名直接写进 ACPX session 配置；群聊工具的运行时变量用 `dutydeck_group_tools_url` 和 `dutydeck_group_tools_token`。

### Q3: 自定义 Agent 没出现在列表里，或提示找不到命令？
- **原因**：守护进程是非交互子进程，不读 `~/.bashrc`、`~/.zshrc` 里的 alias；`command` 找不到的 Agent 不会被登记。
- **解决**：`dutydeck doctor` 会点名没登记的 Agent 和它的命令。在 `DUTYDECK_AGENTS_JSON` 里把 `command` 改成可执行文件的绝对路径（如 `/usr/local/bin/claude`），再 `dutydeck restart`。

### Q4: 飞书里报“逐项确认”相关的错误，或会话启动失败？
- 所选 Agent 不支持飞书逐项审批时（只有 ACP 和 Claude Code / Seed / Relay 终端模式支持），机器人只能用 `full-trust`。修法二选一：
  - `dutydeck settings bot set <appId> permissionMode=full-trust fullTrustConfirmed=true`（Agent 会无人值守地执行命令和改文件）；
  - 换成 ACP 或 Claude 终端模式的 Agent。

### Q5: 能否在同一台机器上运行多个机器人？
- 可以。每个机器人有自己的默认工作区、Agent 和飞书应用凭据，服务不同的群组。

### 同机 peer 实例改了地址不生效，或暂时无法连接？

- 主服务的 `DUTYDECK_INSTANCES_JSON` 只在组装服务时读取一次。新增、删除 peer 或修改 `url` 后，要重启**主服务**；只重启 peer 不会让主服务重新读取这份 JSON。用主服务的 `/api/instances` 核对当前实际加载的列表。
- 每个 peer 都要用自己的数据库和端口，以 `--local-only` 启动，并使用 `http:` 地址，例如 `http://127.0.0.1:4311`。主服务会移除自己的登录与来源请求头再转发，因此不能把远程或需要另一套认证的地址当成这里的 peer。
- 这是静态列表，不做动态发现或健康摘除。peer 暂时不可用时代理请求会报错，但 `/api/instances` 中仍保留该条目；恢复 peer 或修正地址并重启主服务后再试，不要期待健康检查自动改写配置。

### Q6: Claude Code / CCFlash 已完成，飞书卡片却提示工具未返回结果？
- 旧版本可能把 CLI 日志中的历史请求快照当成本轮工具调用。升级后，这些快照不会进入执行记录或确认本轮指令已接收；真实工具缺少结果时仍会提示失败。

### Q7: Claude 终端会话报“Claude 启动尚未就绪（最后屏幕：X）”？
- Claude 启动 30 秒内既没出现空输入框，也没出现可识别的确认页。任务还没写入，按失败记录，处理后可以重发。括号里是最后一屏的类别：
  - **目录信任页未能核对**：屏幕停在目录信任页，但页上的目录和会话目录对不上、页面不完整，或者 `full-trust` 下已认出这一页、自动确认的按键却一直没生效。打开终端确认目录；如果页上的目录不是你预期的，检查会话或机器人配置的工作目录。
  - **空白**：终端里没有任何内容。检查 Claude 命令能否启动，再看守护进程日志（`journalctl --user -u <unit>`）。
  - **未识别**：屏幕上是 Dutydeck 不认识的提示。打开终端查看并处理当前提示。
- 目录很长、在信任页上从字符中间折成多行时，也能认出是当前目录：`ask` / `approve-reads` 下提示“Claude 正在确认此目录是否可信”，请在终端确认；`full-trust` 下自动选择信任该目录。目录含空格且恰好在空格处折行时可能认不出，超时后报“目录信任页未能核对”，在终端手动确认一次信任即可。

### Q8: 报 tmux socket 被删、原终端仍在运行，无法启动会话？
- **原因**：Linux 上 `/tmp` 清理了 tmux socket 文件，但原 tmux server 和 pane 仍在；Dutydeck 会拒绝再启动一个同名 server，避免同一会话同时跑两个 CLI。
- **处理**：按 tmux 手册向原 server 进程发送 `SIGUSR1` 重建 socket，或结束原 tmux server 后重新发送消息。可把 `TMUX_TMPDIR` 指到不会被清理的目录，或让 `systemd-tmpfiles` 排除 tmux 目录。非 Linux 不做这项内核检查，行为保持原样。开启 `remain-on-exit` 时，Dutydeck 下次启动会回收自己留下且所有 pane 都已退出的死会话；仍有运行中 pane 的会话会保留。

### Q9: 同一台机器的不同端口登录或登出互相影响？
- 升级到带端口 Cookie 隔离的版本。Host 带合法显式端口时登录写入 `dutydeck_access_<port>`，无端口仍写 `dutydeck_access`；旧 Cookie 按本实例验证接受；显式端口下，共享 legacy 只有验证通过才额外清除，无端口同名 Cookie 保留旧登出语义。
- 回滚旧程序后，只持有新端口 Cookie 的浏览器需要重新登录。不要手工把其他实例的令牌复制到当前实例。

### Q10: 发送响应丢失后，怎样重试才不会重复执行？
- 排队或立即中断在服务端已接受、客户端未收到响应时，从同一草稿对未修改的提交点重试即可；服务端会按幂等键取回原任务。编辑内容、收到接受回执后有意再发，或选择「重新加入队尾」都会创建新任务。
- `steer` 不自动重试。其响应未知时先查看现有任务和执行记录，确认状态后再决定下一步，不要直接重发。

### Q11: 页面上已经有回答，为什么轮次仍被判为失败？
- 先区分最终正文和工具前的开场白。只有工具已经开始、随后出现最终正文时，正文后同一非空 id 的重复非终态 `tool_call` 才会被忽略；工具前的“我先看一下”不能充当最终答复。
- 正文后的 `tool_result`、`thinking`、无 id 或不同 id 的调用、终态调用仍表示后面还有实质活动，没有新的最终正文时轮次会失败。原始事件和输出 digest 不因这项判定改变。

### Q12: 主命令已经成功，验证或计划前置命令为什么曾报超时？清理错误又是什么意思？
- 旧行为会等所有管道关闭才停止主计时，后台后代持有 stdout/stderr 时可能同时出现退出码 0 和假超时。现在主 Shell 的 `exit` 就结算主进程；这种成功命令不再误报超时，以前被阻断的前置命令可能通过并触发一次计划。
- 主进程退出后仍要确认同组资源退出并有界排空管道。同组进程未退出或管道未排空会显示清理错误并阻断，不是主进程超时；检查命令是否留下后台进程或继承管道的后代。完全 `setsid` 脱离进程组且重定向管道的后代无法由当前执行器证明已经清理。
- 前置命令一旦通过，同一次触发只推进一次；崩溃恢复沿用原幂等键继续，不重跑这次已通过的命令。

### Q13: Claude 后台 Agent 续派后，完成通知和运行计数怎样对应？
- `resumedAgentId` / `revivedAgentId` 只有在通知时间严格晚于最近结束时间时才形成新代。旧代迟到通知仍归旧代，不会把新代标成完成；同代重复通知和转写重放不重复计数。
- 同时间戳、缺少时间或来源顺序无法核对时不会猜测复活。若使用的 Claude 版本不写这些字段，续派不会凭一条旧通知自动建立新代，也不会自动重发续派指令。

### Q14: 计划遇到 Agent 环境暂不可用，会换会话补跑或连续失败后停用吗？
- `AGENT_UNAVAILABLE` 单独归类：记录本次触发和同因连续提醒，计划保持启用，等待下一次正常日程；不换会话补跑，也不按这个连续计数停用。环境恢复并成功推进后计数清零。
- 已接受或结果未知的任务先对账，不重放。模型内容失败、权限拒绝、用户主动停止以及其他环境错误仍按各自的原有策略处理；持续报错时先运行 `dutydeck doctor` 检查 Agent 命令和可用性。

### Q15: 慢工作项的调度次数和耗时日志怎样理解？
- 上一轮 tick 仍在推进时，后续每秒回调直接跳过，不再叠加 wrapper，所以日志只记录真实推进次数和真实耗时；这不是吞吐提升承诺。
- 某次推进 rejection 后，后续正常 tick 仍可继续。直接调用同一个 tick 时仍共享原 Promise，持久状态和恢复语义不变。

### Q16: 宿主没有 UTF-8 locale 会怎样？
- Dutydeck 会强制其发起的 tmux 客户端使用 UTF-8（`-u`）；即使宿主没有 UTF-8 locale，也能正确识别终端会话，中文等非 ASCII 字符不会因此被显示为下划线。

### Q17: `doctor` 的 `lark.exposure` 报警或显示监听地址未知？
- **报警**：只有非回环无认证、可运行的完全信任机器人、广范围高危用户和弱风控同时出现时，这项才升级为 warn/fail。按报告选择：用 `dutydeck setup --local-only` 收口监听；设置访问密码并重新开启认证；或用报告给出的 `dutydeck settings bot set <appId> permissionMode=ask fullTrustConfirmed=false` 降低权限。保留完全信任时，先 `dutydeck settings bot install-hook <appId>`，再启用 `riskControlMode=enforced` 并缩小高危名单。`off` 下即使配置了高危名单也不会限制执行，`guidance` 也不是强制拦截。单条无效机器人配置只跳过该条并标明数量，其他有效机器人仍参与判定，不会把已有的危险 fail/warn 变成 skip；无效条目本身按「飞书配置」检查修复。
- **地址未知**：socket 激活的 `LISTEN_*` 或 unit `TriggeredBy` 只能证明激活关系，不能证明继承 fd 的实际地址。即使 service 已停止，doctor 也会通过 `TriggeredBy` 找到关联 `.socket`，再核对 `ActiveState=active` 与 `SubState=listening`；查询失败或状态不完整同样按未知处理。此时本项降级为 skip，不会把 `.env` 里的 host 当成实际监听；请核对 `.socket` 的 `ListenStream=` 与服务 `--host` / `--port`，再重跑 `dutydeck doctor`。反向代理、防火墙和端口转发不在这项观测范围内。

### Q18: Claude 守卫超时、读取失败或恢复后提示设置不完整？
- **守卫超时**：只有官方 Claude Code 2.1.295+ 会通过 `onFailure: "block"` 让守卫超时也阻断工具调用。旧版、版本探测失败和未验证分支的受保护轮次照常提交，超时维持原行为；显式拒绝和脚本崩溃仍由 `|| exit 2` 拦截。需要超时阻断时升级官方 Claude Code 并重开会话。
- **恢复后的设置不完整**：真正拉起 Claude 时会记录本次实际设置中的 marker、精确 matcher、command type、`onFailure: "block"` 和当时的能力探测结果。服务重启后接管仍在运行的终端优先使用这份启动记录，不重新探测磁盘 CLI；磁盘 CLI 后续升降级不会改变该进程的判定。旧版或探测失败的启动记录只要求真实守卫接线，不因缺少该字段拒绝轮次。仅当启动记录不存在时，才检查接管前会话私有目录已有的 JSON 设置：至少一份且每份都可读、结构合法，并满足所请求守卫的精确 matcher、command type 和 marker，才按旧版规则继续（不要求 `onFailure: "block"`）；inline-only、空快照或任一份不符合都拒绝。记录本身损坏、字段非法或不可读时不能使用快照回退，受保护发送会拒绝；此时重开会话（飞书发 `/new`）生成完整设置和记录。
- **策略或脚本故障**：会话 ID 为空时由 shell 直接放行，不启动 Node；合法单组件 ID 和规范策略路径下，只有可证明的 `ENOENT` 缺策略才由 shell 快放。异常 ID、超长路径、权限或符号链接等不确定状态进入 Node fail closed，不再把任意 `test` 失败或任意缺策略路径都当成快放。策略未启用或没有未授权匹配时同样放行。文件存在后的读取错误、损坏 JSON、active 计划脚本缺失会拒绝操作。检查 `.dutydeck/security/sessions/` 的文件类型与 JSON、会话私有设置目录和机器负载。错误文本不会回显策略里的敏感值。

### Q19: 如何查看最近服务日志？为什么有些行没有显示？
- 普通 daemon 用 `dutydeck logs`，systemd 用户实例用 `dutydeck logs --unit <unit>`；默认请求最近 50 行，可用 `-n 200` 增加请求行数。带 `--unit` 时先取原始最近 N 行，再过滤疑似秘密，所以可能少于 N 行。命令只取一次快照，不会持续等待新日志。
- 普通行、错误行和多行堆栈都会保留。含疑似 token、密码、凭据或 Authorization 的整行会被过滤，所以原始日志里的这些行不会出现在命令输出中，原始日志不变。
- 如果普通 daemon 日志文件不存在（ENOENT），错误会给出完整路径：前台根命令启动的服务没有这份 daemon 日志，请看启动终端；systemd 托管服务请用 `journalctl --user -u <unit>` 或 `dutydeck logs --unit <unit>` 查看对应 unit 的日志。路径和其他读取错误保持不变。
- 如果提示找不到 `journalctl`，检查 systemd 是否已安装且命令在 PATH 中；提示 unit 不存在或尚无日志时先核对名称，名称正确则说明该 unit 当前没有匹配日志。普通 daemon 不依赖 `journalctl`，不带 `--unit` 即可读取当前 daemon 日志文件。

### Q20: `doctor` 的 `terminal.backend` 检查失败？
- 先看失败阶段：找不到命令时装 tmux 或修正 `PATH`；`tmux -V` 失败时检查二进制是否可执行、是否与本机架构匹配；创建或核验私有会话失败时检查临时目录权限和 tmux server 日志。检查只使用独立临时 socket，所有调用带 `-f /dev/null`，`XDG_CONFIG_HOME` 指向私有目录，测试会话只运行受控命令，不读取系统或用户 tmux 配置，也不会连接或结束你的默认 tmux server、自动安装软件。
- setup 的同类预检只读获取 `dutydeck.terminal_backend`，不会为了读取设置而建库、迁移旧库或写控制表；数据库、`configs` 表或键不存在时沿用 tmux 默认值。即使后续工作目录校验失败或用户取消，旧库 schema 也保持不变。
- 只配置 ACP 或已经选择 Herdr 时，tmux 缺失不是致命故障；需要 tmux 的 `pty-cli` 终端 Agent 才依赖这项检查。

### Q21: setup 的飞书收发验证超时或失败？
- 专用确认默认 No。选择 Yes 后先等终端显示一次性 UUID，再在飞书里私聊机器人发送这段验证码；群消息、错误验证码和机器人消息都不算有效入站。
- 有界等待内收到有效私聊后，机器人会回复该消息并携带同一 UUID。「入站通过、出站已发送」只表示飞书接受了回复，仍需在飞书确认收到；回复失败或结果未知时入站仍已通过，但出站未验证。
- 超时表示未收到有效私聊，不会发送任何消息。`--yes`、非交互和 `--json` 不进入该验证。此流程不改变机器人权限，也不持久化用户 open_id。

### Q22: 空闲压缩后，原消息为什么失败或没有发出？
- **上下文不足等明确失败**：终端已经恢复可输入时，原业务消息会继续发送，不需要重发。其他未实测 CLI 会报告不支持主动压缩，也会继续原消息。
- **你中断了任务**：只取消压缩等待，原业务消息不写入；后续消息在终端恢复后照常提交。
- **压缩超过 5 分钟**：Dutydeck 先中断压缩；确认空输入框恢复后按失败处理并继续原业务消息。
- **终端已有 raw write 尚未结束**：自动 compact 会先建立维护栅栏并有界等待，期间新 raw write 不会写入；最终 Enter 前还会再查。维护未写入时超时按未提交处理；`/compact` 已写入或 Enter 后发生冲突则保持维护未知，旧写结算前后续输入仍被挡住。停止、detach 和取消会中断等待，不会自动重发业务正文。
- **提示压缩结果或终端恢复未知**：维护命令可能已经发出，但 Dutydeck 无法证明终端能安全接收下一条输入，所以原消息按“未提交”失败，不会标成“结果未知”，也不会自动重发。后续每次输入都会重新确认终端，确认恢复后正常继续，无需先重建会话；仍无法确认时本次不写入，请稍后重发，持续如此可发 `/new` 开新会话。可打开该会话终端，确认压缩是否结束、是否停在权限或人工确认页；不要并发另开 Claude 接管同一原生会话。

### Q23: Claude 显示 `Removed … invisible character · review and press Enter to send`，任务为什么成了结果未知？
- 新版 Claude 会删掉粘贴里的不可见字符，并拦下第一次 Enter，等人检查。当前 Dutydeck 会在写入前按同一规则清理这些字符，合法 emoji 组合和文字组合序列保留；任务保存的原提示词不变。
- 如果终端仍停在这条提示，说明输入已经写入但没有确认提交。Dutydeck 不会自动再按 Enter 或重发；打开该会话终端检查内容并人工决定是否按 Enter，不要把同一条消息再发一遍。

### Q24: 为什么 Claude 任务提示“当前输入框不是空白”或写入后结果未知？
- Dutydeck 会等 Claude 屏幕静止后、首个业务字节写入前，再确认屏幕底部是完整的空输入框。普通 `❯`、原生 `Try "…"` 占位提示、底部权限栏和最多两行 statusLine 都可正常输入；人工草稿、未提交的 `/compact`、slash 菜单或只有历史提示符的画面不算空框。此时任务没有写入，可在终端处理草稿后重发。
- 首个 chunk、软换行或 Enter 一旦已经尝试，之后输入框无法复核或出现外来变化就按结果未知处理，不会自动再按 Enter、清空草稿或重发。请打开终端核对实际内容。tmux 管理端读屏与写入不是原子操作，这项检查不能排除所有其他终端同时写入的竞态。

### Q25: ACP Agent 已退出，为什么报 `ACP_LAUNCHER_CLEANUP_UNKNOWN` 或清理超时？
- 正常下游慢读不是错误，也没有 5 秒截断期限。主 Agent 已退出时，stdout/stderr 尾部会等目的地恢复并完整交付，再按原退出码或信号语义结束；不要因暂停超过 5 秒就重发原任务。
- 只有遗留源描述符或自有进程组退出无法证明时才走有界失败。诊断里的 `sourcesClosed=false` 表示还有后代持有继承的 stdout/stderr；`destinationFlushed=false` 表示异常收尾时目的地尚有未写完数据；`groupExited=false` 表示进程组退出尚未得到证明，三者不再合并成一个 `drained=false`。
- 此时不要删除会话工作区 `.dutydeck/launchers/` 下的 report。ACP adapter 用它收养并停止仍存活的进程树，证明退出后才删除。请检查该 Agent 是否留下后台后代、继承管道或无法探测的进程组；即使 stderr 背压导致 launcher 诊断没有显示，adapter 也会用 `ACP_LAUNCHER_CLEANUP_UNKNOWN` 标识该路径。普通 Agent exit 1 或没有 report 标记的同数值退出不属于这种状态。
