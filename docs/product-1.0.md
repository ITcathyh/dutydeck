# Dutydeck 1.0 产品定义

> 状态：2026-08-30 已对齐。产品名保留 Dutydeck，产品定位不再由来源项目定义。

1.0 按完整产品一次性交付。实现可以分内部并行波次，但只有本文定义的体验、运行时、迁移、安全、性能和端到端验收全部收口后才算完成；不得用“后续补齐”的占位实现通过验收。

## 一句话定位

Dutydeck 是本地优先的 Agent 工程工作台：飞书是下达目标的核心入口，Web 承担接入配置、证据深挖与排障；用户能够看懂进展、及时干预、恢复失败，并验证最终结果。

```text
绑定飞书 Bot → 在飞书下达目标 → 查看有效进展 → 审批或纠偏 → 验证结果 → 继续工作
```

## 产品原则

1. **Task first**：用户操作的是任务，Session 只是上下文连续性的实现。
2. **先回答下一步**：任何页面或卡片都应说明当前状态和用户能做什么。
3. **展示进展而非噪音**：合并重复工具活动，不倾倒原始日志或模型思维链。
4. **控制就在上下文旁**：排队、介入、中断、审批、重试和继续出现在对应内容附近。
5. **结果可验证**：最终回答同时展示改动、命令、检查和异常等证据。
6. **跨通道一致**：Web 与飞书看到同一任务状态，不制造两份互相冲突的运行。
7. **最小充分设计**：没有当前用户路径或已知故障支撑的抽象、门禁和配置不进入 1.0。

## 核心对象

```text
Workspace → Task → Run → Event / Approval
                     ↘ Agent
Task ↔ Web / Lark channel binding
```

现有 Session、TaskRecord 和 AgentEvent 是迁移输入，不再决定用户界面的信息架构。文件改动、命令结果和检查结论作为 Run 的可验证证据呈现，不引入独立 Artifact 状态机。

## Web 信息架构

Web 用于飞书 Bot 接入状态、配置、任务记录与排障。

- 首页上段：飞书 Bot 概览——每个机器人的名称、Agent、工作区与真实接入状态，主操作是绑定或管理 Bot；无 Bot 时说明绑定后如何在飞书使用。接入状态必须由真实字段驱动，逐档区分配置未完成、用户暂停监听、本次启动禁用监听、监听尚未启动与监听已启动，不把配置记录当成“已接入”，也不因监听已启动就声称消息已验证送达。
- 首页下段：正在运行、等待处理、失败和最近完成的任务。
- 工作区：侧栏按工程目录聚合任务，首页提供跨工作区总览。
- 任务详情：目标、当前状态、精简活动、对话、审批、结果、文件/命令/检查证据和终端。
- 新建任务：Web 创建入口保留为次操作，先选工作区并描述目标，仅在需要时覆盖 Agent、模型和推理强度。
- 集成与健康：飞书从首页 Bot 概览与侧栏「飞书接入」两处配置；远程访问由 CLI 启用并通过登录页认证；连接和运行健康在任务上下文中展示，不另造空壳管理页。

首次使用应自动发现已安装 Agent，用户不需要先理解 Session 或协议即可绑定 Bot 并启动任务。缺少可用 Agent 时首页给出可执行的准备入口，但不阻塞用户先完成 Bot 配置。

## 飞书指挥体验

飞书是一等交互面，不是日志输出通道。

接入体验同样属于产品：用户提供应用 ID 后，可在工作台自动增量配置 Dutydeck 所需的最小权限、机器人能力、长连接事件、卡片回调与应用版本。没有开放平台登录态时直接展示扫码入口；完成态给出账号、企业、权限/事件/回调数量与发版结果。自动配置不增加第二个保存门禁，不申请用户身份发消息权限，也不把 botmux 的文档、日历、会议等无关权限带入 Dutydeck。

### 消息承诺与双卡终态

1. 收到消息后立即用固定 `OK` reaction 确认；解析失败也必须发送可见失败回执。
2. 创建可变进度卡：先显示“已接收/准备中”，进入队列后显示“排队中”，仅在 Runtime running 事件后显示“正在执行”。状态不得倒退。
3. 以人可读节奏更新进度，重复活动合并，只保留有意义的近期信息；每张卡最多一个主动作。
4. 需要用户输入时，将问题和当前有效操作提升为视觉焦点。飞书承担通知与决策，完整上下文与证据由 Web 承接。
5. 到达终态时，原进度卡原地冻结为简洁只读收据；最终结果、失败原因或恢复建议作为一条新的回复卡发送。新消息是必要的，因为 PATCH 已有飞书卡片不会产生新的完成提醒。
6. 完成通知结论优先。默认隐藏详细 trace、保留简短证据摘要；配置为不隐藏时，详细轨迹仍折叠展示。
7. 重试创建新的进度卡，不修改已经冻结的终态收据。
8. 更新失败或 daemon 重启后，以持久化的结果消息 ID、交付状态和同一幂等键继续对账；不得生成重复或互相矛盾的结果通知。

### 卡片层级

```text
标题区    状态 · 任务标题 · Agent · 耗时
焦点区    当前步骤 / 最终结论 / 待用户决策
进展区    2～5 条合并后的有效活动
证据区    检查、改动文件、产物、风险或异常
操作区    仅展示当前状态真实支持的操作
页脚      任务号 · 工作区 · Web 详情入口
```

运行态优先可扫描性，完成态优先结论与证据，失败态说明失败位置、已完成内容和是否值得重试。卡片不展示私有思维链；thinking 只映射为阶段/时长，工具活动使用安全摘要并默认折叠输入输出。

## Agent 支持策略

- 认证支持：持续维护真实 fresh/resume/interrupt/permission E2E。
- 实验支持：可以被发现和使用，但明确展示限制与诊断信息。
- Agent 数量不是成功指标，真实任务的可靠完成才是。

## 1.0 非目标

- 公网多租户 SaaS；
- 跨机器 fleet 调度；
- Electron 外壳；
- 所有 CLI 的表面能力平权；
- 把原始思维链作为产品功能。
