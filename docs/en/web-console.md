Connection and record catch-up have separate statuses: a connected stream may still be catching up. After the first calibration failure, it retries automatically with backoff up to five times; if those fail, use “重试同步” (retry sync) beside the status. “Live sync” appears only after catch-up succeeds. When opening long history, older completed turns initially show summaries; select “expand full record” to read their events. A preparation failure that cannot be reliably matched to its prompt, and subsequent records, conservatively retain raw events. The workbench first reads summaries of only the latest 50 turns plus every turn's position (the first 40 characters of its prompt); earlier turns read their summaries 50 turns per page when scrolled to or chosen from “跳到轮次” (jump to turn), showing the prompt meanwhile. The position list still grows with the number of turns. The jump list builds its options when opened, so the first open waits briefly in sessions with many turns. An open raw log continues to update live; copy and export each read a complete snapshot at the watermark captured when clicked, and “refresh full record” captures a new watermark. The native command menu remains available in history.

ACP structured images and resources are retained and displayed; supported embedded images can be previewed, while unknown or oversized non-text content has a visible placeholder. Non-text content has size and count budgets; old long plain text remains complete without a duplicate parts copy. The Results inspector lists per-turn artifact references with their source; long sessions check the newest 50 turns first, and **检查更早的轮次** (check earlier turns) reads earlier turns a page at a time. A reference does not grant download access or automatically read the URI's file or webpage. Markdown images (`![alt](url)`) in the Workbench and on shared pages are never loaded automatically: http(s) URLs appear as an "图片：alt" link that opens in a new window, and other URLs show text only. The page's Content Security Policy also limits images to the same origin, `data:` and `blob:`.

In **Results inspector → 每轮产物引用** (per-turn artifact references), expand a turn and choose **保存当前文件快照** to save a registered local file. Saved snapshots show capture time, size and SHA-256, with text preview and download controls. They capture click-time bytes, not proof of the original turn's file contents; later source changes leave old snapshots intact. Only ordinary files inside the session's working directory are eligible, up to 20 MiB. Credentials, instance internals, symlinks, hardlinks and special files are rejected; remote URLs are not fetched. Safety checks currently require Linux. Preview is limited to 16,384 characters, with HTML/SVG displayed as escaped text. Listing, capture, preview and download require installation administrator and original-session access; share links and task capabilities do not grant these rights.

- **Navigation**: Overview highlights pending decisions, active execution and recent deliveries; Tasks provides search and project filters without hiding the current task in the sidebar; Inbox aggregates blocking decisions; Automation manages real task schedules. The primary navigation in the sidebar and on mobile retains only Overview, Tasks, Inbox, and Automation, while Bots & groups, Usage & cost, and Settings live in the lower management section. The sidebar provides an "In progress" live task list for running and attention-demanding tasks. Lark and bot status panels appear on the home screen only when an integration issue or error occurs.
- **Unified status vocabulary**: The header, sidebar, task rows and inbox cards share a unified status vocabulary: **"执行中" (Running)**, **"等你审批" (Awaiting approval)**, **"等你回答" (Awaiting answer)**, **"等你核对" (Awaiting reconciliation)**, **"已完成" (Completed)**, as well as terminal states (failed, stopped, interrupted, continuable, archived).
- **Context usage badge**: a sidebar task row shows a small amber badge (for example `82%`) once its latest context usage reaches 80%; hover text and screen readers say "上下文已用 82%" (context used 82%). Nothing is shown below 80%, when the Agent reports no usage, or when the capacity is unknown. `GET /api/sessions/summaries` returns the value in a `context` field: the server reads the latest usage event of every session with one query and caches the whole batch for 30 seconds. It reads existing events only (no native logs, no new storage). It refreshes every 15 seconds with the task list; the exact value for the current task stays in the usage panel at the top of the task.
- **Goal step duration**: in an expanded goal, each step shows the duration of its latest attempt. Finished attempts (completed, failed, interrupted, cancelled) show "用时 2 分 30 秒" (took 2 min 30 s); an attempt the executor has accepted and that is still running shows "已运行 5 分钟" (running for 5 min); under one second shows "<1 秒". The time prefers the attempt's task record, from creation to last update (read from the task list endpoint; it excludes preparation and is not affected by review evidence written later). If the task record is unavailable or not finished yet, it falls back to the attempt's own timestamps and is marked approximate, for example "用时 约 2 分钟". For finished attempts whose task is not finished yet the task list is re-read every 5 seconds until it is. "已运行" refreshes with the goal data (polled every 5 seconds; the page does not redraw when the data is unchanged, so the figure can lag slightly). Expanding a step shows each attempt's own duration; steps with no attempt, or whose attempt is preparing or needs attention, show none.

Results show the Bot name, App ID and scope; use the App ID to distinguish namesakes. Selecting a result expands its page and focuses the field. Terminal backend and model service settings are searchable too; navigation retains unsaved-change protection and browser back/forward behavior.

If browser storage is unavailable, they remain in memory for the current page only. Failed sends retain the draft; a successful acknowledgment clears only the submitted revision, preserving edits made while sending. Messages are never automatically replayed. The new-task form also survives closing, including a created session whose first message failed to send; this creation draft lasts only for the current page and is cleared by refresh.

Theme, sidebar layout, task tab and inspector preferences stay in this browser. None of these preferences or drafts sync across devices.
- **Waiting on you**: the top of the Workbench gathers everything that waits for a button press into one list, grouped by type, each item showing its task, how long it has waited and its available actions: permission approvals, Agent questions, unknown results to reconcile, reports that wait for your decision, plan cards from plan-first, work-item confirmations / answers / step requests, work-item plan revisions awaiting confirmation (the work item keeps its own status; the entry shows the revision version, the first 8 characters of its digest and how many steps are affected), PR confirmation lists and review questions, and Lark result acceptance cards. Items that can be decided on the Web (approve / reject a permission, approve / cancel a plan, confirm / cancel a work item, confirm / discard a plan revision, confirm a PR push) call the existing endpoint directly; the others open the original task. When rejecting a permission you can choose **拒绝并说明** (reject with reason) and enter a reason of up to 1000 characters, the same as the approval card in the task: the reason is recorded in the approval history, terminal-mode Agents receive it, and ACP-mode Agents only learn that the request was rejected. Plain **拒绝** sends no reason. Items that can only be decided on a Lark card (plan cards of Lark sessions, result acceptance, PR review questions) are shown read-only with a note to act in Lark. Bulk actions are limited to decisions that neither start execution nor need you to read the content first: rejecting permissions and discarding a plan revision. Approving a permission, approving a plan, confirming a PR push, and confirming a work item (including a plan revision) start work immediately, so they are handled one by one; PR items list the changed files and plans open the original task to read. Bulk rejection carries no reason; reject items one by one to explain. After ticking items of one type and a confirmation step the browser calls the existing endpoint once per item and shows success, expired or failed for each, with no new bulk semantics on the server; mixed types offer no bulk action. Items keep the checks of their own objects, so a stale decision is refused and shown as expired: a permission already handled, a plan that is no longer the latest or was already decided, a work item whose revision changed whose revision is no longer pending, or whose pending revision was replaced by the Agent (digest mismatch). The list is a read-only aggregate from `GET /api/inbox`: no new storage, each task's own view permission applies, and share links cannot read it. Tasks whose permission requests are already listed there do not repeat under "Needs you" below.

- **Shared Agent model settings drafts** require confirmation before switching settings sections, closing or navigating away; browser refresh and page exit prompt while edits remain unsaved. - **Read-only task details from Lark cards** show the source topic, group or private chat, and original initiator, with links back to known topics or chats. Unrecorded topics and missing historical origin records are marked explicitly; unavailable names fall back to known IDs. The shared page leads with the conclusion: the top shows the question, status and start–end time in the browser's time zone; the conclusion card enlarges its first paragraph as a lead, and on phones each table row becomes a small card with the title and value on its first line and the other columns labelled with their headers. - Interrupting a task cancels its pending questions, including requests still being validated, and rejects late answers. Idle sessions can still ask questions normally.
- The installation owner can cancel or stop tasks in legacy Lark sessions, subject to execution-state and permission checks.
- **Native background tasks** show their count and lifecycle separately. When the main round has ended, the status says so while background tasks continue; late notices are not new answers. Replies Claude writes after a background task finishes appear in the timeline in arrival order, labelled “后台任务结果” (background task result); they are not the conclusion of any turn and are not shown in Lark or on shared pages.
- **Session streams** recover from silent stalls. A background tab releases its connection after 60 seconds; returning to the foreground reconnects and reconciles events, tasks and sessions. Observed buffered streams are exempt from silence detection. No new setting is needed.
- `/sessions/<session ID>?panel=workspace` opens the existing workspace panel, including archived sessions, through the usual login gate. Opening it does not preview or execute cleanup.
- **Automatic verification gate**: Lark tasks only, after a command is configured. Web manual verification is available from the Results inspector. Result states: passed, failed, expired, not verified.
- **Before verification starts**, Dutydeck checks whether this session's previous execution result is unknown (reconcile it in the recovery view first), this session still has native background tasks, or another session in the same directory (same real path or one containing the other) has unfinished execution, native background tasks or verification. If so, verification does not run and the API returns 409 `SESSION_BUSY`. Only one verification runs in that directory at a time; other requests can retry after it ends. Automatic Lark verification waits about 5 seconds, then skips if still busy, shows “not verified” with the reason on the result card and sends no repair round. A long-running background development server also counts as occupied; end it before verifying manually. While verification runs, new tasks from other sessions in the same Git repository queue and can start once it ends, including failure, timeout or stop.
- **Submodules**: repositories with submodules that are not checked out (a plain clone without `--recursive`, after `git submodule deinit`, or an isolated worktree) can be verified. - **Verification refresh**: in the result inspector, verification records refresh every 5 seconds while a verification is running. Line comments: signed-in Web users send them straight to the agent; people with only the share link create a confirmation card in the Lark topic, and someone with permission must tap "Hand to agent". Comment drafts added or edited during submission are kept. `dutydeck auth share-key rotate` invalidates all issued links.
- **File order and folding in the changes page.** Files are ordered source, then tests, then docs, and when the 1 MiB patch budget runs out the later docs and tests are omitted before source. Lockfiles (a fixed list: `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `pnpm-lock.yaml`, `bun.lock`, `bun.lockb`, `deno.lock`, `Cargo.lock`, `go.sum`, `poetry.lock`, `uv.lock`, `Pipfile.lock`, `composer.lock`, `Gemfile.lock`, `Podfile.lock`, `pubspec.lock`, `flake.lock`, `packages.lock.json`, `gradle.lockfile`) and files the repository's `.gitattributes` marks `linguist-generated` are folded by default: listed last with only their added/removed line counts and a "folded" note, their bodies are not read and use none of the 1 MiB budget. "展开查看" (expand) loads one file on demand (up to 1 MiB per file, beyond that it only says the change is too large); expanded lines cannot be line-commented. Generated files are not guessed from paths: `dist/` and `.min.js` show normally unless `.gitattributes` marks them. The Lark result card only shows the summary line and is unaffected.
- **Session insight analyzer**: built into the npm package and built automatically with the server. It runs locally in an isolated child process using Dutydeck's current Node.js runtime; no Go compiler, external analyzer binary, or separate engine build is required. Source development uses the workspace's `tsx` loader. Metrics now use version `v2`: old snapshots remain readable, and different metric versions are excluded from shared deltas and group totals; reanalyze to align versions. A native user input for Codex is counted only once; inherited history from forks is excluded from independent session totals; and amounts and timestamps for priced entries are preserved in insights and exports. Refreshing generates a corrected snapshot while existing snapshots remain unchanged. Insight refresh does not change task usage or billing records. The check for whether a snapshot is out of date is reused for 15 seconds and skipped while a refresh is queued or running, so repository or task changes can take up to 15 seconds to mark it stale.
- **Usage and cost**: tabs "Cost", "Detail", "Session insight". The session usage HUD also shows cache-hit rate when the provider reports uncached input and cache-read tokens. Monthly USD caps per bot or group (`dutydeck settings usage set-cap <usd> --app <appId> [--chat <chatId>]`). The built-in price table covers OpenAI and Claude models (longest-prefix match; unmatched models are "unpriced"); override it entirely with `DUTYDECK_USAGE_PRICING_JSON`, or add prices for individual models with `DUTYDECK_USAGE_PRICING_EXTRA_JSON` (format in the [agents.md](agents.md) environment table). Once set, these models' cost counts toward monthly caps, so an instance with caps may be blocked earlier than before; an invalid value stops the service from starting, and `dutydeck doctor` names the invalid variable. The model name comes from the reading, task, session or Agent config in that order; when none is set, the model the ACP Agent itself reports (without the `[effort]` suffix, e.g. Codex) is used and its source is recorded as `runtime`. Terminal-mode Claude usage is estimated from the transcript (subagent usage from `<session>/subagents/`). Terminal-mode Codex records tokens per turn from the rollout's per-response usage (older rollouts without it: the difference of the cumulative total); resume, fork and a re-read after a daemon restart are not counted twice. The model is the one the rollout names; an unpriced model keeps only tokens. Traex terminal mode reports none. APIs: `GET /api/usage/report`, `GET /api/usage/tasks` (params `from`, `to`, `model`, `agentId`, `appId`, `origin`; tasks also `limit`, `offset`; dates in daemon local time; installation admin only).

- **Session mode (`session`)** is the default, including older records without a mode. It keeps the source task's context. Stopping or archiving the source promptly disables its session-mode plans with a retained reason; disable and delete remain available.
- **Fresh-session mode (`fresh`)** starts a new session for every occurrence. It runs only the plan instruction, without the source task's chat history, and still delivers to the source task (the original Lark chat or topic). Saving freezes the source task's Agent, directory, model, reasoning effort and permissions; it runs in the source task's directory (no separate worktree) and queues behind same-repository work under the resource coordination below. Retries, restarts and late receipts of one occurrence land in the same session derived from that occurrence, never a second one. The next occurrence archives the previous execution session (read-only, records kept); while that session still has queued, running or unsettled tasks (for example a follow-up you added there), it is left open and retried on a later occurrence. While it stays open, its queued tasks still run, and anyone who can add messages or cancel queued tasks in the plan's current session can do the same there; the plan's own later occurrences run only in the new session. Once the plan is deleted, the creator loses access to the source task, or that session is archived, tasks that have not started will not run and adding messages or cancelling is refused; a turn already started is not affected. The last one is not archived and its terminal process is released after the idle timeout. Stopping or archiving the source task disables the plan as in session mode. Editing can switch between `session` and `fresh`; the switch is rejected while an execution is unfinished.
- **Independent mode (`independent`)** must be chosen explicitly at creation. It requires a Git repository and a dedicated managed worktree; preparation failure never falls back to a shared directory. It freezes the Agent, model, permissions, directory and plan-only context (`prompt_only`) and reuses a stable execution session. Stopping the source conversation leaves the plan active; revoked permissions still block later submission and delivery. Origin, execution and delivery locations remain distinct. Existing plans are not migrated automatically, and editing cannot change the mode.
- **Resource coordination covers the current instance database.** Interactive, collaboration and scheduled tasks share atomic admission using normalized repository identity. Worktrees, subdirectories and symlinks do not bypass the same-repository limit; non-Git tasks coordinate by normalized working directory. Restarting or a timeout does not release unknown executions or resources that have not ended safely (except unknown outcomes older than 7 days whose process is proven to have exited; see unknown outcomes above). Lark group-memory jobs take no part in this coordination. Other databases, older service processes and external tools are outside this coordination. Requests transferred to a new session still wait for unknown executions and unsafe resources in the same repository; confirm the original task and resource safety in its recovery view before queued work can run.

Plans support once, daily, weekly, intervals and five-field cron in an IANA timezone. The default `coalesce` policy catches up at most once after downtime. The `skip` policy skips only when lateness exceeds the normal scan allowance: lateness is measured from the start of the scan that finds the time, and the allowance is 60 seconds plus the previous scan's duration. The `maxLatenessSeconds` validity limit applies to either policy: expired times are not caught up, a limit shorter than the scan allowance counts as the allowance, and an update with `null` clears the limit. Persisted decisions explain the covered interval without creating an unbounded backlog. An unfinished or unknown execution blocks the next occurrence; a misfire policy cannot bypass it. Completion events wake settlement and delivery, with periodic scans retained for recovery. Phase times use actual records, and absent times are not replaced by an update timestamp. Renaming increments the revision while preserving the execution generation, due time, pending occurrence and original actor; changing instructions, timing or other execution configuration creates a new generation. Names of undeleted plans are unique within a source task, disabled plans included: creating or renaming onto an existing name returns `SESSION_AUTOMATION_SCHEDULE_NAME_CONFLICT` (409) with the existing plan ID; use `update` instead. In Lark, `/schedule every` and the result card's daily button also neither create nor change anything on a name clash; they reply in Chinese with the existing plan's state, its enable/disable command and, when a Web address is configured, an edit link. Duplicates left by older versions are not merged automatically; delete the extra ones.

For unknown results, the overview identifies the blocking execution and waiting time. Fixed run details lead to the existing authorized recovery flow. Confirming completion, confirming failure or explicitly retrying is audited. A manual retry creates a new attempt of the same task; the original unknown attempt and successor result remain distinct. Unknown execution is never replayed automatically, and the latest attempt is not treated as the original result. Unknown collaboration delivery is reconciled against persisted trustworthy receipts and stays unknown when no receipt proves its outcome. Disable notices persist sending intent first: failures known to precede sending can retry, while an unknown send outcome is not resent automatically.

For the cron day-of-month and day-of-week fields, if either starts with `*` (including `*/n`), both must match; otherwise either may match. For example, `0 9 */2 * 1` runs at 09:00 only on Mondays that fall on an odd day of the month. One-time schedules reject invalid calendar dates or times, such as February 30. Historical invalid schedules remain readable and editable but are disabled until corrected and enabled again. A schedule with no upcoming run time cannot be created or enabled: a one-time time that has passed or falls in a DST gap skipped by policy, or a cron that never matches, such as `0 0 30 2 *`.

```bash
# New source session and session-mode plan; shared workspace by default
dutydeck schedule create --agent codex --cwd /path/to/project --name Daily --prompt 'Review changes and summarize' --cron '0 9 * * 1-5' --timezone UTC
# A new session for every occurrence, without chat history; results still go back to the source task
dutydeck schedule create --session ses_xxx --name Deploy --prompt 'Pull the latest code and deploy' --cron '0 2 * * *' --timezone UTC --mode fresh
# Switch an existing plan to fresh sessions (or back with --mode session)
dutydeck schedule update schedule_xxx --session ses_xxx --mode fresh
# Explicit independent mode: dedicated managed worktree and plan-only context
dutydeck schedule create --agent codex --cwd /path/to/project --name Independent --prompt 'Review changes and summarize' --cron '0 9 * * 1-5' --timezone UTC --input '{"mode":"independent","misfirePolicy":"coalesce","maxLatenessSeconds":3600}'
# Existing session: --session ses_xxx --every 30 (minutes), or --at 2026-12-01T09:00
dutydeck schedule list
dutydeck schedule show schedule_xxx --session ses_xxx
dutydeck schedule enable schedule_xxx --session ses_xxx
dutydeck schedule update schedule_xxx --session ses_xxx --prompt 'Review builds and summarize'
dutydeck schedule disable schedule_xxx --session ses_xxx
dutydeck schedule run schedule_xxx --session ses_xxx --idempotency-key daily-check-1
dutydeck schedule history schedule_xxx --session ses_xxx
dutydeck schedule delete schedule_xxx --session ses_xxx
```

Run now also works while paused. It bypasses the clock, keeps conditions and permissions, and leaves the next scheduled time unchanged. Reuse `--idempotency-key` when retrying a manual request: the same key returns the original execution. Deletion prevents future triggers and invalidates work not yet submitted; submitted tasks finish, and their history/results remain available. `history` returns the latest 1000 occurrences of that plan, newest first; specify `--session` for deleted plan history. `show --session` reads its retained definition. CLI output is JSON. Use `--input '<JSON>'` or `--file plan.json` for complete create input or an update patch (including `condition`, `dstPolicy`, `misfirePolicy`, `maxLatenessSeconds` and `mode`; `--mode` accepts `session`, `fresh` or `independent` at creation, and only switches between `session` and `fresh` on update), and `--expected-revision` to reject concurrent edits. Runtime targeting with `--instance`, `--url` and `--database` follows `dutydeck settings`. If saving fails or its response is lost after a new session is created, the CLI reports its ID. Inspect `list --session <id>` first, then retry with that `--session` only if the schedule is absent.

API: `GET /api/automation/schedules` accepts `offset/limit/name/sessionId/agentId/enabled/health/sort` and returns these plans, counts across the authorized scope and pagination. `GET /api/sessions/:sessionId/automation/schedules/:id/history?offset=0&limit=20` paginates one plan; omitting pagination retains the previous limit. `GET /api/sessions/:sessionId/automation/schedules/:id/runs/:occurrenceId` returns fixed run details. All endpoints retain source-task authorization; a share link does not grant global plan-list access. Updates use `expectedRevision` to reject stale edits.

Scheduled tasks keep the selected permission posture; `ask` can wait for human approval, so choose permissions explicitly for unattended work. Each runtime database owns its schedules and execution history and permits one runtime executor. Switch instances to reach the Web or bot runtime that owns the task.

After reaching the user's stopping condition, a recurring task can request disabling its own schedule with `dutydeck agent --turn "$TURN" schedule stop-self`. No schedule ID is accepted. Only the active host-triggered scheduled occurrence qualifies; manual runs and one-off schedules cannot use it. The host waits for successful execution and for result delivery to finish, then rechecks the original actor and that the schedule is still the same version before disabling it and retaining history. No new run starts while that result is still being delivered. If the result card still fails after its last automatic retry, the plan is disabled anyway, the disable reason says the result was not delivered, and the usual disable notice is sent. Failure, an Agent closing report of blocked or waiting for a decision, delivery still in progress, revoked permission or a user edit prevents self-disabling.

**Follow up until done.** Recurring plans can set a completion condition (`completionCondition`, natural language) and a deadline (`deadlineAt`):

- With a completion condition, every run appends the condition and the deadline to the plan instruction and tells the Agent to check it first and, once it is confirmed, disable the plan with `schedule stop-self` above. The saved instruction itself is unchanged. stop-self is currently offered only in Lark-sourced sessions; Agents elsewhere start their result with “completion condition met” and you disable the plan.
- If a plan is still enabled at its deadline, the host disables it with the reason “deadline reached …, completion not confirmed” and sends the usual disable notice to the delivery destination (the original Lark topic; Web tasks show it on the plan). A run already submitted finishes, but its later stop-self no longer changes the outcome. A plan whose deadline has passed cannot be enabled until the deadline is moved or cleared.
- One-time plans cannot have a completion condition or deadline. Changing either counts as an execution change and creates a new generation.
- Plans and the automation overview show the follow-up state: waiting for the next run, running, awaiting a human (a pending approval or question in this run, an unknown result awaiting reconciliation, or a template work item awaiting confirmation), last run failed, completed (confirmed by stop-self), deadline reached (completion not confirmed), or disabled. Re-enabling clears the previous completion or deadline outcome.

**Start a work-item template.** A plan can instead start a saved work-item template on every run (`workTemplate: {id, version}`), with the plan instruction as the work item goal and the occurrence as its idempotency key, so retries of one occurrence return the same work item. Plans that need confirmation still need it, and permissions follow the template-start rules. The work item is not attributed to the turn currently running in that task: it does not inherit that turn's risk policy or count toward its usage. While the previously started work item is unfinished, the run is skipped. If the template was deleted or is not visible to the plan actor, the run fails with an explanation at the delivery destination; three consecutive failures for the same reason disable the plan. Template plans support only session mode and the always condition, and no completion condition; a deadline is allowed.

```bash
# Check every 30 minutes until the PR is merged; disable with a notice if not done by 18:00 on Dec 1 (plan timezone)
dutydeck schedule create --session ses_xxx --name 'Follow PR' --prompt 'Check CI and review comments on the PR and move it forward' --every 30 --timezone Asia/Shanghai --until 'PR merged' --deadline 2026-12-01T18:00
# Start a saved work-item template (id@version) at 09:00 on weekdays
dutydeck schedule create --session ses_xxx --name 'Release check' --prompt "Check today's release" --cron '0 9 * * 1-5' --template template_xxx@2
# Clear the completion condition, deadline or template
dutydeck schedule update schedule_xxx --session ses_xxx --input '{"completionCondition":null,"deadlineAt":null}'
```

**Run a pre-check command first.** A plan with the always condition can set a pre-check command (`precondition: {command, timeoutSeconds}`), for polls like "don't wake the Agent unless there is a new commit":

- When the plan is due, before an execution session is opened or a work-item template is started, the host runs the command with `/bin/sh` in the plan's execution directory (the directory frozen at save time, resolved to its real path). Only exit 0 continues the run. A non-zero exit records the run as skipped: no task, no usage, no notification, and it does not count as a failed run. A timeout (15 seconds by default, at most 20), a failure to start, or a process group that does not exit counts as a failed run, is explained at the delivery destination, and three in a row disable the plan. "Run now" also runs the pre-check but does not count toward consecutive failures. The command runs in the background and does not hold up other plans; "Run now" returns the run as pending without waiting, and the result shows up in the run history afterwards. A pass is recorded before the run continues, so a service restart does not run the command again and goes straight on to open the session or start the work item.
- The command uses the same runner as pre-delivery verification: only a minimal environment (`PATH`, `HOME`, `LANG` and similar), without Agent configuration, secrets or group tool tokens. It runs in its own process group, which is killed on timeout or exit; children that start their own process group or session (for example via `setsid` or `timeout`) are not cleaned up and may keep running after a timeout. Keep the command a quick read-only check and do not start background or detached processes in it. Output (stdout and stderr together) is redacted against secret values in the service environment and kept to the first 4 KB. The plan card shows the command, its latest result and output, and how many runs were skipped in a row since it last passed; the run record keeps a one-line summary (exit code and the end of the output).
- Only the Web plan panel or the local `dutydeck schedule --condition-command` can set, change or clear it (installation owner identity required). `dutydeck agent schedule create/update`, the Lark `/schedule` command and confirm cards do not accept the field; a request carrying it gets 400. It cannot be combined with the CI new-failure condition; template plans can use it. Linux only for now.
- Commands matching the default high-risk rules (such as `rm`, `sudo`, `git push/reset`, `curl -X POST`) are rejected on save. This only guards against mistakes and is not a security boundary: anyone who can edit plans can already run commands on this machine, so keep the command a read-only check.
- The command is stored separately and written together with the plan revision; the plan's own condition stays "always". After switching back to an older version that does not know pre-check commands, the command no longer applies and the plan wakes the Agent every time; see [Upgrade Notes](upgrading.md).

```bash
# Check every 5 minutes; wake the Agent only when ready.flag exists in the workspace; 10-second timeout
dutydeck schedule create --session ses_xxx --name wait-ready --prompt 'Process the new data' --every 5 --condition-command 'test -f ready.flag' --condition-timeout 10
# Clear the pre-check command (or --input '{"precondition":null}')
dutydeck schedule update schedule_xxx --session ses_xxx --condition-command ''
```

`--deadline` accepts an ISO time with offset, or `YYYY-MM-DDTHH:mm` in the plan timezone. API create and update use the same field names (`null` clears on update); `deadlineAt` must carry an offset. `GET /api/sessions/:sessionId/automation` returns `runStates` and `preconditions` (each plan's pre-check command and latest result), and each item of `GET /api/automation/schedules` returns `runState`.

## Goal plan revisions <a id="work-plan-revision"></a>

The **目标** panel in task details can revise the plan of an unfinished goal (awaiting confirmation, running, waiting for an answer or failed). Under **修改计划**, edit the complete plan JSON (the same `plan` format used at creation), choose **预览影响** to see which steps keep their results, are invalidated and rerun, are stopped first, removed or added, then choose **提交修订**. Preview and submission are bound to the same revision; any change to the goal in between rejects the submission and requires a new preview. Revising requires the same permission as cancelling or retrying the goal; newly assigned Agents are authorized as at creation.

- **Impact**: added steps, steps whose content changed (instruction, title, Agent, dependencies, condition, workspace, Skills, review policy) and all of their downstream steps lose their results and rerun. Other completed steps keep their results and do not run again.
- **Stopping running steps**: affected or removed running steps are stopped with the cancellation stop path first. If any one cannot be proven stopped, the whole revision fails and the plan stays on its current version. The stopped execution has an unknown outcome: until it is resolved as an unknown result in its execution record (marked failed or completed), the step stays pending and no other new step starts in the same workspace; it reruns after the resolution. A revision never resends it as if it had not run.
- **Unresolved or finished goals cannot be revised**: reconcile a goal that needs attention through the existing recovery flow first; completed and cancelled goals are final.
- **Agent revisions**: an Agent may only narrow a plan (change titles or instructions of steps that have not failed, remove Agent steps without a review policy, add dependencies, remove Skills). Adding steps or Agents, changing a step's Agent, adding Skills, changing workspace, conditions or review policy, dropping dependencies, removing a human wait or a step with a review policy, changing the final output step, making a failed step run again (by changing it or anything upstream of it), or any revision of a goal that required confirmation at creation (for example in group chats) becomes a pending revision. The panel and the Lark card show the reasons, the impact and a content digest (first 12 characters); **确认修订** stops and applies it, **放弃修订** continues with the current plan. While it is pending the goal keeps its status and its current plan version: running steps still report results and later steps are still dispatched under the current plan. Completing or cancelling the goal drops the pending revision. A new submission from the Agent replaces the pending content and changes the digest, so Lark posts a new card; confirming from an old card or with an old digest is refused. The impact also lists completed results that will be discarded. Confirmation recomputes the impact from the current step states: if a step the card did not list must now be stopped or have its completed result discarded (for example a step that had not started when the revision was submitted started while it waited), the confirmation is refused; a step shown as stopped that has since finished and is now discarded does not count as new. When refused, the pending revision is updated to the new impact with a new digest and Lark posts a new card to review. A blocked goal cannot confirm a revision, only discard it. A failed step cannot be retried on its own while a revision is pending; confirm or discard the revision first. Plugin triggers count a failed goal with a pending revision as still in progress and keep its concurrency slot, and take the slot back when the revision arrives after the failure (for runs recorded within the last 24 hours). Schedules only check the most recently started work item: if it failed and has a pending revision the next start is skipped; earlier work items are not checked.
- **Attempt limits**: attempts invalidated by an Agent revision (including one a person confirmed) still count toward the three attempts per step and the review rework rounds. Only a revision a person submitted resets those counts.
- **Version history**: every applied plan is kept as a new version with an increasing number, its source (creation, human edit, Agent edit), who submitted or confirmed it (goal creator or installation administrator), time, reason and impact. Execution records of removed steps remain viewable. If the service restarts during a revision, the goal is entirely on the old plan or entirely on the new one.

## Configuration sources and memory management <a id="configuration-and-memory"></a>

Open **配置来源** in the task's Results inspector for saved Agent/Bot defaults, group resolver results and the current session. Select a historical task and attempt to inspect accepted execution options, recorded skill delivery metadata and existing plugin action evidence. New settings never fill gaps in historical records: missing fields remain `unknown`, and native CLI-owned MCP/Skills/private configuration remains `unverified`. Secret files are not scanned; environment values, secret bodies and tool bodies are excluded. Plugin settings also show readable sources under **解释已保存配置**. Tools still resolve bindings and authorization for every call.

**管理记忆** searches, replaces and deletes entries in the Lark session's actual bot-shared, per-group or private pool. A stale revision preserves the draft and asks for a reload. Source links require separate source-session access. Saved and injected entries remain distinct: up to 20 turn associations and 100 tombstones are retained, Web shows up to 10 turns, and full historical prompts cannot be reconstructed.

In ordinary Web sessions, create a project, select it and choose **绑定所选项目**. Each other session must explicitly bind the same stable project ID to share memory. Paths, visual groups, reused directories and worktrees never infer a binding; Lark and managed work-item sessions cannot join. Management requires installation administrator access; binding also requires session access. Every new turn rereads the enabled state and binding with a 3000-character entry budget. Disabling or unbinding stops next-turn injection; previously delivered context cannot be revoked. Limits are 200 live entries, 12 topics, 100 tombstones and 1000 characters per entry. Credentials and injection instructions are rejected. There is no automatic project extraction or Agent write interface.

```bash
dutydeck settings explain --session ses_xxx --task task_xxx --attempt attempt_xxx
dutydeck memory manage pool-list --session ses_lark --query 'deployment'
dutydeck memory manage pool-revise mem_xxx --session ses_lark --content 'Corrected fact' --expected-fingerprint <read-fingerprint>
dutydeck memory manage project-create --name 'Project name'
dutydeck memory manage project-show --project proj_xxx
dutydeck memory manage project-add --project proj_xxx --content 'Project fact' --expected-fingerprint <read-fingerprint>
dutydeck memory manage project-bind --session ses_web --project proj_xxx
dutydeck memory manage project-enable --project proj_xxx --enabled false
dutydeck memory manage project-unbind --session ses_web
```

These are administrator management commands. `settings explain` supports the existing `settings --instance` selector. For an explicit local runtime address, all commands above require both `--url http://127.0.0.1:<port>` and `--database /path/to/dutydeck.db`. `--attempt` requires `--task`. Memory additions and revisions use the fingerprint returned by the read to reject stale writes.
