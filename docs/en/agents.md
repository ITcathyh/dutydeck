# Agent Configuration & Permissions <a id="agent-config"></a>

> [← Back to README](../../README.en.md) · [All docs](../../README.en.md#docs) · [简体中文](../zh/agents.md)

Dutydeck prefers terminal adapters for installed CLI agents, with `tmux` as the default backend for new sessions. When both terminal and ACP entries share an ID, the terminal entry wins. Agents without an available terminal adapter or executable are still discovered through ACP (Agent Client Protocol). Existing Herdr settings, session protocols and permissions are preserved. Explicit protocols, commands and permissions in `DUTYDECK_AGENTS_JSON` take priority.

The built-in CodeM (`codem`) terminal adapter uses explicit `--session` / `--resume` identifiers and never guesses the latest session. It requires the local `codem` command and adds `--yolo` for `full-trust` sessions.

For `full-trust` sessions, both new and resumed, the built-in Kimi (`kimi`) terminal adapter reads `kimi --help` asynchronously before launch (with the same cleaned environment used to start Kimi, waiting at most 3 seconds; once per command, per process): if the help lists `--auto` (Never Ask) it passes `--auto`, otherwise (including when reading fails or times out) `--yolo`. In Kimi Code `--yolo` only auto-approves regular tool calls, and risky actions still wait for a human; the Python kimi-cli, also installed as `kimi`, has no `--auto`, and there `--yolo` approves everything.

The built-in `codex` and `codex-cli` terminal entries and “Codex (ACP)” (`codex-acp`) give an explicit `CODEX_PATH` priority for discovery, version detection and launch, including executables outside `PATH`. Without that override, each new execution process resolves Codex from the Dutydeck process `PATH`, using the user's login and configuration. New processes use user-installed upgrades automatically. If the user-installed or explicitly configured Codex is missing, startup fails instead of using the ACP adapter's cached version.

Codex terminal Agents read `[profiles.<name>]` entries from `CODEX_HOME/config.toml` and expose those profiles in the Web new-session dialog. A selected profile applies to the new session only; leaving it empty keeps the Agent's default profile. The profile name is passed as a Codex CLI option rather than persisted in the Agent environment.

Ordinary relay questions support querying and waiting again after disconnection or a server restart using a stable `requestId`. `session ask` prints the ID to stderr; `--request-id` supplies your own. `session ask-result <id> --json` reads history, while `session ask-wait <id>` waits for the original question without resending a prompt or creating a turn. The question, choices, original task/attempt and deadline are frozen, with a 24-hour maximum. Legacy requests without IDs and native permissions retain their existing finite limits. Wait returns an answer with exit code 0 only while the original attempt can continue under current permissions. Ended, replaced or unknown attempts return 3; historical answers do not authorize execution. History queries check current result access; waiting and answering recheck group membership, email allowlists and expired permission facts. A temporary permission lookup failure preserves the question for another wait with the same ID after recovery. Queries may refresh permission caches but do not change the question, answer or task execution. ADHD structured confirmations still continue in a new turn after a click. See the [CLI reference](cli.md) for commands and exit codes.

## 1. Custom agents (`DUTYDECK_AGENTS_JSON`)

```json
[
  {
    "id": "ccflash",
    "name": "CCFlash (Claude Code)",
    "protocol": "pty-cli",
    "adapterId": "claude-code",
    "command": "claude",
    "args": ["--settings", "/home/username/.claude/ccflash.settings.json"],
    "model": "claude-sonnet-5-5",
    "permissionMode": "ask"
  }
]
```

- Use an absolute path (or a `PATH` binary) for `command`, never a shell alias. **An agent whose command cannot be found is not registered**: `dutydeck doctor` fails and names it, and the daemon logs a warning. Invalid JSON errors name the `DUTYDECK_AGENTS_JSON` variable.
- With the default tmux backend, an Agent's `env.PATH` (including an empty string) becomes the Agent process `PATH` unchanged, and a bare `command` is resolved through it; registration still checks the Dutydeck service's own `PATH`. When overriding `PATH`, include the directory of `command` or use an absolute `command`; otherwise the Agent can be registered but fail to start.
- Agent processes do not inherit Dutydeck's own service configuration: uppercase `DUTYDECK_*` variables (such as `DUTYDECK_AGENTS_JSON`, `DUTYDECK_DATABASE_URL`, `DUTYDECK_INSTANCES_JSON`) and Lark/Feishu app secrets are removed, except `DUTYDECK_DAEMON_DIR` and `DUTYDECK_BOT_APP_ID`, which keep an Agent's own `dutydeck` commands on its instance. Generic provider variables in the service environment (such as `OPENAI_API_KEY`) are still inherited; give each Agent its own account through its `env`, which always applies.
- ACP sessions keep their records and launch environment under `.dutydeck/` in the session working directory. Dutydeck creates it owner-only (directories `0700`, session files `0600`, existing ones are tightened on next use) and writes `.dutydeck/.gitignore` containing `*`, so `git add -A` in that workspace does not pick up session credentials.
- The built-in ACP Claude launcher does not read the workspace `.env` or `.env.local`. `env` from the user's `~/.claude/settings.json` and the project's `.claude/settings.json` / `settings.local.json` still applies, except, for the project files, keys that change how the process loads or which program runs (`NODE_OPTIONS`, `NODE_PATH`, `PATH`, `SHELL`, `BASH_ENV`, `ENV`, `LD_*`, `DYLD_*`, `*_EXECUTABLE`, `CLAUDE_CONFIG_DIR`, `DUTYDECK_*`). Put such values in the service environment or the Agent `env` instead.
- Claude Code / Seed / Relay terminal modes support Lark approval (`ask` and `approve-reads`). Other terminal CLIs need `full-trust`. Saving a default Agent change for an existing `ask` / `approve-reads` bot rejects an Agent without approval support and preserves the previous Agent and permissions. Permissions are never raised automatically. Existing incompatible configurations still fail to start with two fixes: `dutydeck settings bot set <appId> permissionMode=full-trust fullTrustConfirmed=true`, or switch to an ACP / Claude terminal agent.
- Claude terminal sessions started from Lark always use the `default` permission mode; defaults such as `auto` in your local `~/.claude` do not apply (but see [Known limits](troubleshooting.md#known-limits)).
- Claude terminal sessions started from the Web with `ask` or `approve-reads` do not change Claude's permission mode and keep your local Claude default: if that default is `auto`, file writes and commands may run without approval. When Claude does ask, the prompt is Claude's native terminal confirmation, not a Dutydeck approval card. To confirm each action, press Shift+Tab in the terminal to switch to a mode that asks, or change your local Claude default permission mode.

`timeout` is in seconds (default `600`) and must convert to an integer from 1 to 2147483647 milliseconds (`0.001`–`2147483.647` seconds). If an ACP Agent never answers the cancellation after a timed-out turn, Dutydeck ends that session's stuck Agent process (including the actual Agent behind a wrapper such as `npx` or a shell) once the longer of `timeout` and 60 seconds has passed since the timeout; other sessions are not touched. An explicit stop while the Agent is stuck waits at most 10 seconds for the cancellation, then ends the Agent processes the same way instead of hanging. The timed-out turn stays result-unknown, is not resent, and waits for confirmation under the usual rules; until then it cannot be confirmed because the Agent has not stopped. A message that was waiting meanwhile is not sent to the Agent; the session explains why and says to simply resend it. Later messages start a new Agent process that reconnects the saved session; if that fails, the existing session recovery rules apply. Fallback CLI model discovery uses the Agent's configured direct CLI executable, cleaned child `env` and `cwd`, passing only supported global options (with separate option/value arguments). Other launch arguments, equals forms, or wrapper commands skip fallback discovery and retain the configured default model without substituting a host command.

### Terminal task status and recovery

Claude Code terminal sessions use OSC 7501 signals for busy, approval and completion detection, with automatic screen detection fallback and recovery when valid signals resume. A native terminal bound to the current input and written after the latest busy signal, including in a turn recovered after daemon restart, or a resolved approval hook can release stale busy status after a lost signal.

If an idle terminal-mode (`pty-cli`) CLI exits, the next task first verifies that the old process has exited and retires it, then rebuilds the terminal using the existing native session recovery rules. If safe recovery cannot be confirmed, the task fails before submission. Tasks with an unknown submitted result still require reconciliation and are never resent automatically.

On Unix, PTY teardown drains up to 1 MiB of remaining data before closing the reader, preserving UTF-8 decoding, pause/resume and data-before-exit ordering. Direct terminals and pane relays share this path. It has been checked on Linux / Node 22; macOS remains unverified, and Windows keeps its existing implementation.

Once Claude Code logs show support for a full-turn completion marker (`turn_duration`), split answers wait for that marker, retaining later text, Stop-hook continuation and late errors from the same turn. Older formats without the marker retain their compatibility completion path. Tool context produced by a Skill tool call is not mistaken for new user input; the final answer and task completion after a Skill call are delivered normally.

When Claude Code provides verifiable native PID state on Linux, Dutydeck follows the same verified process across `/clear`, `/resume` or `/branch`, switches collection sources and persists the new recovery identity. Existing history in the new file is not delivered again. A source switch during an active turn leaves an unknown outcome for the existing manual reconciliation flow; input is never automatically resent. Empty or metadata-only files are not cold-resume targets, and do not cause a fallback to the pre-switch context. Older CLIs missing process-birth identity fields, and macOS, retain the existing marker-based ownership path without native-switch guarantees.

On Linux, collection stays on the existing marker path when native PID state is missing or temporarily unverifiable; in that case, or when the latest conversation identity is not confirmed in the database, automatic idle cleanup and normal service shutdown preserve the original terminal. Only an idle `full-trust` tmux terminal with complete ownership evidence and no unresolved tasks, pending approvals or background tasks can be adopted automatically; other cases remain blocked for manual confirmation.

After automatic idle cleanup closes a terminal, Dutydeck waits up to 10 seconds to prove that the original processes have exited (the status relay wrapping a Claude terminal now exits together with Claude). If exit still cannot be proven, the service log records a warning and messages sent to that session fail immediately with a stop-blocked error (`DRIVER_STOP_UNVERIFIED`) instead of sitting in the queue. A background recheck runs after 45 seconds, first verifying the exit proof the earlier stop left and stopping the terminal again only when that fails, then at doubling intervals up to every 30 minutes; once exit is proven the session reopens on its own, without a restart or manual retirement. A recheck does not cancel queued messages or abort a running verification, and new messages during a recheck get the same stop-blocked error. If the first recheck still fails, the session gets one notice (Lark sessions in the original topic). When the driver reports that process exit can never be verified (for example without a readable process table), rechecks stop and a single notice asks an administrator to check the processes; new messages queue until the recovery flow lifts the block. A terminal whose native session can never be confirmed (for example one stuck at a startup prompt) is retired anyway, with a warning, once it has been idle 18 hours past the release threshold; native records stay on disk and only the process ends. At startup, a session whose saved working directory is gone (for example a deleted worktree) is skipped and the reason is recorded in the log and the session; other sessions recover normally.

Stopping, deleting or idle-retiring a terminal Agent that keeps forking short-lived children (builds, tests, git) still ends its tmux session, and children born meanwhile are included in the exit proof; if the terminal identity was not captured at launch or reattach, stop captures it. When the stop itself fails (the terminal was not ended), the stop-blocked reason names the cause and stopping again retries. If the tmux socket file is deleted (for example by periodic /tmp cleanup) while the Agent process keeps running, the Agent is no longer reported as exited. Agent children no longer inherit `TMUX` and `TMUX_PANE` from the tmux pane Dutydeck runs in (values set explicitly in the Agent `env` are kept), so tmux commands inside the Agent do not reach your own pane. Stop uses the same tmux as launch, the `tmux` found on the service `PATH`, instead of a fixed `/usr/bin/tmux`. The exit proof relies on Linux `/proc`; on other systems stopping a tmux session is blocked with `LEGACY_TMUX_PLATFORM_UNSUPPORTED`. When processes recorded in the exit proof outlive the end of the tmux session (for example a `nohup` / `setsid` background job or a process that ignores the hangup), stop sends them SIGTERM and then SIGKILL, about 2 seconds apart, once the original session is confirmed gone. Processes that are not recorded are never signalled, and a survivor that still does not exit leaves the stop unproven.

After a session's Agent is retired for idleness or the service restarts, the next message starts the Agent again; the first start of a new session works the same way. If that start fails, the message fails with the reason, and Dutydeck immediately checks that the half-started process has exited: once proven, the next message starts the Agent normally; if not, the same background recheck as above runs, and new messages fail right away with a stop-blocked error saying the session recovers on its own, instead of queuing silently. If the user explicitly stops or restarts the session while the Agent is starting, that stop handles the process and no such recheck is scheduled.

Switching model or reasoning effort in a Web session first checks the Agent's published options (the same list as Lark `/model` and `/effort`); a value not in the list is rejected and nothing changes. When the Agent explicitly rejects a value before applying anything, the session stays usable; only a switch whose outcome is uncertain (for example, the Agent received the request but never confirmed it) marks the configuration unknown and blocks new messages, with an error that points to `dutydeck recovery restore-configuration`.

When Codex switches log files within the same native session, Dutydeck verifies ownership, drains complete records from the old file and continues from the new one. Copied history is not delivered again, and files belonging to another session are rejected.

Codex and TraeX native recovery uses only records confirmed to belong to the current session. If inherited context cannot establish ownership, recovery is refused to avoid resuming another session. After an idle Codex session is released, the next turn resumes its verified native context.

Codex and TraeX terminal tasks settle from success, failure or cancellation events bound to the current native turn. A partial answer does not override a later failure; cancellation is recorded as an interruption. A recovering Codex or TraeX turn without text output still ends with the confirmed cancellation or error when the corresponding input is verified. TraeX reads session metadata containing large model catalogs so final answers arrive and tasks complete. Recovery drains the old log segment before reading the next segment for the same session. New canonical records retain progress, input receipts and final answers while deduplicating mirrored records.

TraeX uses the full terminal viewport to distinguish busy and ready states, including layouts with keyboard controls on a separate footer row; status text quoted in output or drafts is not treated as an active footer. Codex accepts `›` / `»` input prompts and the 0.164.0 footer showing only the model and remaining weekly quota, without treating trust or update menus as ready. Ordinary Cursor input sends one Enter, preserving multiline input and normal task queueing without a second empty-input control action. Empty input prompts for Claude Code, Seed, and Relay are recognized as idle so recovery operations for unconfirmed tasks can proceed. Up to two custom `statusLine` rows between the empty composer and permission mode footer are supported, including the first message after resuming a session.

When a direct child explicitly started by the current Codex parent turn reports quota exhaustion or rate limiting, Web and Lark progress records show a fixed diagnostic without the upstream error body. The parent continues; Dutydeck does not automatically retry or switch accounts because of this diagnostic. Observation is bounded and best effort; children started before recovery are not reported retroactively. This diagnostic is not enabled for TraeX.

Claude background Agent, Bash and Monitor tasks are counted by native task ID. The main turn may complete after an explicit answer when the CLI is no longer waiting for a child result; background tasks continue. Legacy pending counters and an explicit Waiting screen retain wait-and-merge behavior. Late notices keep their original input identity instead of becoming the next turn's answer. Restart rebuilds background state; non-persistent Monitors expire at the CLI deadline, and after `/clear` the old log is used only to reconcile stop notices for known background tasks. Successful Write/Edit operations in the known project memory directory preserve the same-turn answer and postscript in the final result; business files and Bash commands do not trigger this rule.

An exact Codex model-capacity failure without a business tool or permission call can retry automatically at most twice, after 30 and 90 seconds, each with a separate recorded execution attempt. Stop and new input cancel unsubmitted retries. Each submission rechecks the original requester's current permissions; restart retains deadlines and cancellation state. Unknown submission or completion is never automatically replayed. HTTP 429, quota, authentication and generic server errors are excluded. Multi-step work waits for this verified automatic retry chain and advances after success; unrelated manual reruns are not adopted as its result.

For a recognized Codex model-migration menu, Dutydeck selects only “Use existing model” and waits for the composer again. An unclear highlighted row or menu remains for manual handling. Terminal capture sockets support long and non-ASCII temporary-directory paths.

Kiro 3.x is unverified: the Kiro 3.0.0 release notes say Kiro CLI is now a single standalone `kiro-cli` binary ([CLI changelog](https://kiro.dev/changelog/cli/)) and do not say whether `kiro-cli-chat` is still shipped. The built-in Kiro ACP agent is registered only when `kiro-cli-chat` is found; terminal mode (`kiro-cli chat`) is not affected.

Do not enable Claude's `CLAUDE_CODE_RETRY_WATCHDOG` under Dutydeck: while it waits for a quota reset it produces no output and the process is not CPU-active, so the terminal-task idle timeout (the Agent `timeout`, default 600 seconds) ends the turn as stuck.

Claude Code / Seed / Relay / Genius terminals start with `CLAUDE_CODE_DISABLE_MCP_TASK_BACKGROUND=1` by default. From Claude 2.1.319, tool calls that an MCP server runs as tasks are moved to the background and their results no longer belong to the current turn; with this variable the MCP tool result stays in the turn, and a long MCP call keeps the turn busy. To restore backgrounding, set `CLAUDE_CODE_DISABLE_MCP_TASK_BACKGROUND=0` in the Agent env; the same key in the `env` of `~/.claude/settings.json` also takes precedence over this default. Older Claude versions ignore the variable; terminals that are already running pick it up only after they are relaunched.

When a bot sets `claudeAutoMemory` to `off`, Claude processes started afterwards in its group-chat sessions get `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` (Claude Code / Seed / Relay / Genius terminals and the built-in ACP Claude; scope in [features.md](features.md)). It sits at the same layer as the default above: a value the user sets explicitly in the Agent env or in the `env` of `~/.claude/settings.json` or the project's `.claude/settings.json` wins (`0` / `false` force auto memory on). `autoMemoryEnabled: true` in Claude settings does not override the variable; to keep auto memory for a bot, set the bot setting back to `inherit`. The setting is the only switch; do not toggle it by adding uppercase env to an Agent: an ACP Agent that had no uppercase env switches from direct launch to the launcher once you add one, and its existing persisted ACP sessions then fail to restore with an identity conflict. Changing the setting never recreates a session: terminals and ACP (controlled and local sessions alike) pick it up the next time the Claude process starts and resume the same conversation; processes that are already running are unaffected.

Do not enable `CLAUDE_CODE_RESUME_INTERRUPTED_TURN` for the Claude used by Dutydeck: Claude may rerun the interrupted turn itself when the session is resumed, which conflicts with Dutydeck never automatically resending work whose result is unknown.

### Git commands while planning <a id="plan-git"></a>

Plan-first Git reads must use `env GIT_ALLOW_PROTOCOL= git` to disable all transport protocols, and explicitly disable the pager, optional write locks, filesystem monitor, default signature display and custom default formatting. Diff reads must also disable external diff and text conversion. Ordinary `git status`, `git diff` and similar calls that do not follow these examples are blocked. Use:

```sh
env GIT_ALLOW_PROTOCOL= git --no-pager --no-optional-locks -c core.fsmonitor=false -c log.showSignature=false -c format.pretty=medium status --short
env GIT_ALLOW_PROTOCOL= git --no-pager --no-optional-locks -c core.fsmonitor=false -c log.showSignature=false -c format.pretty=medium diff --no-ext-diff --no-textconv -- file.txt
```

History reads use the same prefix, for example followed by `log --no-ext-diff --no-textconv --oneline`. Only locally available objects can be read. A command that needs missing objects in a partial clone fails instead of downloading them; clearly state which content could not be checked. `remote show`, which contacts the remote, explicit converters, signature verification and arbitrary configuration overrides are blocked. Put operations that need execution in the plan and run them after approval. The plan guard is not a general process sandbox.

## 2. Permission modes

Lark bots can use `ask`, `approve-reads` and `full-trust`. `deny-all` is not available for Lark bots.

| Mode | Behavior |
|---|---|
| `ask` | Writes and commands wait for approval. **Default for new bots** when the chosen Agent supports Lark approval |
| `approve-reads` | Reads and searches pass; writes and commands need approval; network access is not a read. ACP and Claude terminal mode |
| `deny-all` | Rejects every privileged action; not for Lark bots |
| `full-trust` | No confirmation. The only option when the Agent cannot do Lark approval; needs an explicit confirmation |

For Codex ACP, every non-full-trust native turn, including restored sessions, uses `untrusted` approval, user review and a read-only sandbox. Writes and privileged commands reach Dutydeck approval instead of Codex ACP auto-review. Codex can still allow reads its native policy considers safe, so every read-only action is not guaranteed to produce an approval request; `approve-reads` also allows explicitly declared reads and searches. Explicit `full-trust` uses native full access. These child-only settings do not change global Codex configuration.

Codex ACP forwards native output through separate pipes, waits for downstream readers when tool results are large, and drains remaining data before exiting. This prevents tasks from timing out after native execution has already finished, such as when reading a long document.

`lark create` defaults to `ask` and refuses unsupported Agents without `--full-trust`; the Web wizard defaults to `ask` when the Agent supports approval, else `full-trust`.

Lark email admission and identity lookups cache confirmed invalid, cross-app or invisible-user failures for up to 60 seconds per client, so a permission repair may take that long to be retried. Bot configuration refreshes or credential changes clear the cache. Successful identities, rate limits, server errors, network errors and timeouts are not cached; subsequent lookups still check for revoked access.

### Workspace approval rules <a id="workspace-approval-rules"></a>

The "本工作区允许此类命令" (allow this kind of command in this workspace) button on Lark approval cards saves the command as a workspace rule (SQLite table `workspace_approval_rules`, with bot, creator and creation time) that survives restarts. The table arrives with a database schema upgrade; afterwards older builds refuse to open the database, so rolling back means restoring the pre-deployment database backup. No model is involved; matching is deterministic on the command text:

- **Scope**: only Lark-sourced, non-`full-trust` sessions, only turns started by a Lark user in person, and only requests that would otherwise show an approval card. Web, scheduled, automation and CI/PR-triggered turns still ask; the Web approval card has no such button.
- **Bot and workspace**: a rule applies only to the bot that created it; bots do not share rules. The workspace is the real path (realpath) of the command's execution directory (the directory the Agent reports, shown on the card's 目录 line). Later commands are matched by their own execution directory, which must be the same directory as the rule's workspace; subdirectories, parent directories and other directories do not count. When the Agent reports no execution directory, a relative one, or one that does not exist, there is no button and no automatic allow. A Git worktree and its main checkout are different workspaces and do not share rules. The home directory and the filesystem root `/` cannot hold rules; when the execution directory is one of them the button does not appear.
- **Which commands can become rules**: only the unredacted, untruncated string command received from the executor; redacted, truncated or array-form commands (such as Codex command arrays) get no button. Only the commands below can become rules, and the rule is the command words on the left. Everything else (including `pnpm install`, `npm init`, `npm config`, `git stash`, `git branch`, `pnpm exec`, shells and interpreters) cannot:

  | Rule | Arguments allowed after it |
  |---|---|
  | `git status`, `git diff`, `git log`, `git show` | read-only display options (such as `--short`, `--stat`, `--name-only`, `--cached`, `--oneline`, `-<number>`) and paths/revisions; not `--output`, `--ext-diff`, `--textconv`, `--no-index` and the like |
  | `pnpm test`, `npm test`, `yarn test`, `pnpm run <script>`, `npm run <script>` | no options, only positional arguments (such as test files) |
  | `cargo test`, `cargo build`, `cargo check` | `--release`, `--workspace`, `-p`, `--features`, `--locked` and similar; not `--config`, `--manifest-path`, `--target-dir` or `--` |
  | `go test`, `go build`, `go vet` | `-v`, `-race`, `-count=<n>`, `-run=<name>` and similar; packages only as relative paths such as `.` or `./...`; not `-exec`, `-o`, `-ldflags` and the like |
  | `make <target>` | no arguments |
  | `pytest` | `-q`, `-v`, `-x`, `-s`, `-k`, `--lf`, `--ff` and test paths; not `-p`, `-c`, `--basetemp` and the like |

  Positional arguments may not start with `-`, contain `=`, be absolute paths or contain a `..` path segment. Script shorthands such as `pnpm lint` are not accepted (pnpm runs a program of that name when the script is missing); use `pnpm run lint`.
- **Coverage**: every segment of the command is checked against the table again, and it is covered only when the resulting rule is saved: `pnpm test` covers `pnpm test src/a.test.ts` but not `pnpm test --filter x` or `pnpm testx`. Saved rules that are not in the table have no effect. A leading environment assignment, `$(`, backticks, `<(`, any redirection, a pipe, a single `&`, a newline, a heredoc, quotes, parentheses or braces always ask. Compound commands are split only on `&&` and `;`, and every segment must be covered, so `pnpm test && curl x` still asks.
- **Precedence**: allow/deny from a plugin `permission.request` hook and the Agent's own deny rules come first. The high-risk pattern is re-run before every match and a matching command always asks; before an automatic allow, Dutydeck also checks that the requester still has high-risk execution permission. Rules never relax the high-risk block for unauthorized senders.
- **Who can create rules**: a rule applies to the whole bot, so the check uses bot-level identity, not group-level roles in the card's chat. A bot connected to group management accepts only bot-level admins (admin roles not scoped to a group); a bot without group management accepts only people in a non-empty access whitelist. The clicker must also be able to approve the request.
- **Records**: an automatically allowed approval record names the matching rule; the progress-card annotation states whether the source was a workspace rule or "allow this command for the session".
- **Risk**: a rule looks at the command text, not at what the command runs. After allowing `pnpm test`, an Agent that edits the scripts in package.json (or repository config such as a Makefile, conftest.py, `.cargo/config.toml` or `.git/config`) can run arbitrary code through that command. Only create rules in repositories whose scripts you trust.
- **List and revoke**: Web Settings → Agent → 按工作区允许的命令, or `dutydeck settings approval-rules list [--app <bot>] [--workspace <dir>] / remove <rule-id>` (installation owner). Revocation takes effect immediately; nothing is cached.

## 3. Environment variables

| Variable | Default | Purpose |
|---|---|---|
| `DUTYDECK_HOST` | `127.0.0.1` | Listen address |
| `DUTYDECK_PORT` | `4310` | Web/API port |
| `DUTYDECK_AUTH` | `true` | Require authentication for non-local access (`false` disables; on a non-loopback address the server refuses to start unless `--unsafe-no-auth`) |
| `DUTYDECK_DEFAULT_CWD` | start dir | Default workspace |
| `DUTYDECK_DATABASE_URL` | `<cwd>/.dutydeck/dutydeck.db` | SQLite file |
| `DUTYDECK_AGENTS_JSON` | `[]` | Custom agents |
| `DUTYDECK_CLEANUP_INTERVAL_MS` | `300000` | Cleanup interval: integer milliseconds from 1 to 2147483647 |
| `DUTYDECK_DRIVER_IDLE_CPU_ACTION` | `diagnose` | Policy for sustained CPU use by idle CLIs: `off` disables this check, `diagnose` logs candidates, `retire` releases the process early only after safety checks |
| `DUTYDECK_DRIVER_IDLE_TIMEOUT_MS` | `21600000` | Nonnegative idle-terminal release threshold in milliseconds; `0` disables it; the periodic timer's 32-bit limit does not apply; sessions whose native background tasks are still running are not released |
| `DUTYDECK_USAGE_PRICING_JSON` | built-in table | Override usage prices |
| `DUTYDECK_USAGE_PRICING_EXTRA_JSON` | unset | Add per-model prices on top of the price table: `{"version"?: "...", "models": [{"match": "...", "inputPerMTok": ..., "cachedInputPerMTok": ..., "outputPerMTok": ...}]}`, each entry may carry an optional `provider`; a base entry with the same `match` and `provider` (case-insensitive) is replaced, entries for other providers are kept, the same `match` and `provider` may not appear twice, and `default` is not allowed. Once set, these models' cost counts toward monthly caps, so an instance with caps may be blocked earlier than before; an invalid value stops the service from starting and `dutydeck doctor` reports a failed `usage.pricing` check naming the variable |
| `DUTYDECK_DEPLOY_WINDOW` | any time | Allowed `dutydeck deploy` windows, e.g. `10:00-11:00,16:00-17:00` (Asia/Shanghai) |
| `LARK_APP_ID`, `LARK_APP_SECRET` | - | Fallback for `dutydeck lark send`-style commands only. Bots configured by `dutydeck setup` keep the secret in the bot configuration |

CI tokens and webhook secrets are **no longer environment variables**; see Plugins.

### Sustained CPU use by idle CLIs

The default, `diagnose`, logs candidates without ending processes early. To enable early release, start the service with `--driver-idle-cpu-action retire` or set `DUTYDECK_DRIVER_IDLE_CPU_ACTION=retire`; use `off` to disable this check. The existing six-hour idle release remains independent: `--idle-timeout-ms 0` disables only that general timeout.

Early release supports Linux PTY CLIs only when process birth identity and native conversation recovery can be verified. Current checks cover Claude-family adapter instances without live children (such as `seed` and `relay`). Codex is currently skipped because complete idle-state and current native-conversation evidence is unavailable. The standard `claude-code` tmux relay wrapper and other instances with live children are also skipped. Conservative defaults require at least 10 minutes idle and at least three valid sample windows spanning five minutes, each using at least 50% of one CPU core. Samples follow the maintenance interval, so the actual wait may be longer; a gap over 10 minutes restarts evidence collection. New input, queued or unresolved tasks, permissions, Ask requests, native background work, and every additional live descendant block release. Incomplete samples and missing recovery proof also skip release, including unsupported ACP and plugin drivers.

Release ends only the original process; the next message resumes the original native conversation. Unverified exit continues to block replacement tasks and uses the existing stop recheck. These thresholds are product defaults, not measurements of production frequency or CPU savings.
