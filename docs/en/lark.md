# Lark Bridge Guide <a id="lark-guide"></a>

> [← Back to README](../../README.en.md) · [All docs](../../README.en.md#docs) · [简体中文](../zh/lark.md)

Lark task cards hide the Agent name by default. Enable the Agent name switch under the bot’s access and advanced settings to show a short name badge after the status (for example, `Completed` `CCFlash`), without parenthesized host details. You can also enable it with `dutydeck settings bot set <appId> showAgentName=true`, or set it to `false` to hide it.

## 1. Task lifecycle

1. **Dispatch**: DM the bot, or `@bot task` in a group.
2. **Receipt**: the bot reacts with `👌` on your message and removes it after the progress card arrives. When progress cards are hidden, `👌` stays until the task returns its result or completion reaction. A check mark is added when the turn finishes; a cross mark when it fails or is interrupted (not when you cancel). When the bot's 完成时只贴表情、不发结果卡 (completion reaction only) setting is on, a successful ordinary task only gets the completion reaction; `/plan` plans and tasks from the Lark task dispatch channel still get a result card, with the 批准执行 (approve) button on plan cards, and cards resent after a restart or a failed send follow the same rule.
3. **Approval**: the card starts with a one-line summary (e.g. "Run command: pnpm test"). Buttons: "Allow once", "Allow this command for the session" (initiator only, non-high-risk commands only), "本工作区允许此类命令" (allow this kind of command in this workspace), "Reject", and "Reject with a reason" (a text box on the card; same authorization as "Reject"). The reason is passed to terminal-mode CLI agents that support remote approval as the denial message (ACP agents do not receive it yet), recorded with the approval, and shown redacted and truncated on the collapsed card; the Web timeline approval card offers the same option and history shows "Rejected: reason". An unhandled card gets a reminder after 30 minutes (the task keeps waiting) and is auto-rejected after 24 hours.
   "本工作区允许此类命令" allows this request and saves the command as a rule for this bot in the execution directory shown on the card (such as `pnpm test` or `git status`; only whitelisted test, build and read-only git commands qualify). Later runs of that command by the same bot in the same execution directory, with only allowed arguments, are allowed automatically, also after a restart; see [Agent configuration: workspace approval rules](agents.md#workspace-approval-rules). Only bot-level admins can click it (on a bot connected to group management, admin roles not scoped to a group; group admins do not qualify; on a bot without group management, only people in a non-empty access whitelist), and the clicker must also be able to approve this request. An automatically allowed request gets no card; its permission line on the progress card reads "按工作区规则自动允许：<rule>" (allowed by workspace rule). The card states the risk: after allowing `pnpm test`, an Agent that edits the scripts in package.json can run arbitrary code through that command.
4. **Questions**: tap an option, or quote the card and reply with your answer. A question card with options also has an optional "Other" text box below the options. On a single-choice card, type your answer and tap "Submit other answer" to answer with your text; on a multi-select card the box is part of the same form, so selected options and text are submitted together, and the Agent receives the answer on two labeled lines (selected options and extra text); text alone is accepted too. The text is limited to 1000 characters. Tapping an option still submits immediately. If the card is too large to fit the box, only the option buttons are kept. With ADHD-friendly output, question cards keep only the question and buttons, with no text box. The full question and all options are shown when they fit; otherwise a full-text attachment is sent and the card is clearly marked as an excerpt. Dutydeck does not publish the answerable Lark card until attachment delivery succeeds; delivery resumes after recovery. Answered or expired cards retain the content originally displayed. Approval cards remain redacted; raw commands are not uploaded as full-text attachments.
5. **Result**: the result card shows the change summary, verification result and long attachments, plus a "View changes" link when the turn changed files. A `需要你：…` (action needed) line after the conclusion appears in a separate highlighted block with a bold label. Chinese punctuation touching `**` in Agent text (for example `**结论：**正文`) is moved outside the bold span before the card is sent (`**结论**：正文`), so Lark no longer shows the asterisks literally; code, inline code and link text are left alone, and text that already renders correctly (including bold spanning lines) is unchanged; text over 16KB or with more than 2000 `**` markers is not repaired. Turn completion, pending decisions and verification results are labeled separately; a completed turn does not imply passed verification.

**View details.** When the Web console requires login, "查看详情" (view details) on a task card sends the clicker a direct message with a one-time Web login link valid for 10 minutes; it grants full Web access. Only people in the bot's operator allowlist get it (managed groups check the high-risk execution permission). Without an operator allowlist, no login link is sent in Lark; open the task on the Web or use "导出执行记录" (export execution record).

Result cards and execution-record exports apply credential redaction to text. Escaped quotes inside JSON credential values do not end redaction early; subsequent non-sensitive fields and commands are preserved.

**Attachments and delivery.** Markdown and structured images in cards share a deduplicated limit of 4 images. Only real Markdown image syntax with a valid Lark `img_key` is read; code examples and ordinary image URLs do not trigger downloads.

Lark files fall back to Range downloads with the same bot identity only after an explicit platform size-limit response. Files stream to disk in chunks of at most 32 MB, with a **512 MiB local per-file limit** chosen by Dutydeck, not a Lark platform limit. Images do not use Range. Permission and restricted-message errors are not bypassed; failed, cancelled or timed-out downloads do not give the Agent partial files. The existing request deadline still applies (15 seconds by default); slow large files may need to be provided as smaller files.

Downloaded attachments live in an instance directory owned by the current database. Queued, running, pending-confirmation, recoverable or outcome-unknown work retains its files beyond 24 hours; active downloads are protected too. A later sweep reclaims a directory only when it has no remaining holder and is older than 24 hours. An incomplete reference read or a changed handoff snapshot skips that sweep. Legacy shared temporary directories with unknown ownership are retained without automatic migration or deletion.

Progress and result writes recheck task and turn ownership after rate-limit waits and before retries, so stopped or replaced turns stop writing. Requests already sent cannot be revoked. A final result explicitly rejected by content audit stops unchanged retries and attempts a fixed notice without the rejected body. A delivered notice does not mark the result delivered, and the body is not resent as an attachment to bypass audit.

The first result delivery time is saved before sending. Unknown deliveries are automatically retried only within one hour of that first attempt, including across restarts. After that, resending stops; check the original topic and the Web execution record. Confirmed receipts remain recoverable. This does not guarantee exactly-once remote effects.

**Early final delivery and custom cards.** An Agent in the active Lark turn can use `dutydeck agent --turn "$TURN" group send 'complete answer' --final`. Default `--delivery publish` sends to the original reply location. `--delivery reply-agent` only relays the summary to the bot that handed over the task; `--delivery both` publishes and relays. Relay requires a resolvable original bot still in the group, checked before publication. Content, card, mode and targets are fixed on first submission; retries must match. If publication succeeded but relay failed, only relay is retried; completion and restart recovery do not send another confirmed result.

A custom card is a static Card 2.0 **body**, without `schema`, `header` or `config`. For example, `/path/body.json`:

```json
{"elements":[{"tag":"markdown","content":"**Result**: complete"},{"tag":"hr"}]}
```

```bash
dutydeck agent --turn "$TURN" group send 'searchable summary' --final --card-file /path/body.json --delivery both
```

The summary is required but need not repeat all card data. Bodies are limited to 28,000 bytes and allowlisted static text, images, layouts and tables; interactive components, callbacks, `element_id` and script URLs are rejected. Lark still validates specific styles. Relay-only mode accepts a summary without a publication card. The host retains status, original routing, task/turn checks and completion handling; a rejected custom body is not replaced with another result. Legacy `dutydeck group send` supports the same options. These commands require session tool credentials and the host-provided `--turn` for this execution. Missing, stale or mismatched credentials are rejected. `$TURN` in examples denotes that credential.

**Sending files.** `group send-file` only sends files inside the session working directory, or inside this session's own `dutydeck-artifacts/<session id>/` directory under the system temp directory; other files under the temp directory are refused. Credential files (`.env`, private keys, Agent transcripts and the like), the instance data directory (database, secrets, attachments, plugins) and hard links are always refused. In `ask` / `approve-reads` the command always needs a human approval. Without `--idempotency-key`, deduplication only applies within one turn: a retry in the same turn is not sent twice, while a later turn sending the same file sends it again.

**Unknown outcomes.** After a restart or disconnect a turn may have an unknown result. The original Lark topic gets a card with "Run again / Mark done / Mark failed" and a details link. The initiator and admins can act; "Run again" needs a second click within 60 seconds. The Web session page has the same three actions. Who did what and when is shown on the card and recorded in the execution ledger. Tasks older than 24 hours get no Lark card and can only be handled on the Web. API: `GET /api/sessions/:id/unknown-tasks`, `POST /api/sessions/:id/unknown-tasks/:taskId` with `{target, action, allowDuplicateEffects?}`. A turn cut off by a service restart continues automatically in the original conversation (within 1 hour, at most twice) only when its execution record proves it did read-only work. Terminal-mode Agents without a transcript, or turns with no tool records at all, cannot be checked and always stop at this card for a person to decide. A message the restart caught before its acceptance was recorded is checked against the execution ledger: if the ledger accepted it, its result is reattached and it never runs twice; if it is over 1 hour old and the ledger never accepted it, it is not run and the original topic asks you to resend; if the ledger cannot be read, the notice says the outcome is unknown and nothing is resent.

A failure the driver proves happened before any prompt was written (for example Codex/Claude startup not ready, or stuck on the folder-trust page) is not an unknown outcome: it is recorded as failed and can be resent. An unknown outcome left unhandled for 24 hours gets one reminder in the original topic and the Web session explaining how to handle it; after 7 days, once the process that ran it is proven to have exited, it is closed as "unknown, abandoned": not rerun, not counted as done, with the decision and evidence in the execution ledger and one more notice in the original topic. It is not closed automatically while messages are queued behind it.

When Claude Code starts on a dialog that waits for a person (allowing CLAUDE.md imports from outside the working directory, enabling the project's MCP servers, or accepting bypass-permissions mode), Dutydeck does not answer it: the task fails at once as above and names the dialog; choose in the terminal and resend. Background Lark jobs (group memory, group participation decisions and replies) load only user settings, so the CLAUDE.md, project settings and .mcp.json of a code repository around their directory are not read and these dialogs do not appear. A memory job that fails before its run finishes closes its session and terminal; the next job starts a new session.

When a queued task is held back by an unresolved task or a leftover terminal in the same repository, the blocked session gets one notice (Web timeline; Lark sessions in the original topic, unless the task card already shows it is blocked) naming the blocking session and task and how to handle it; the task then continues on its own. One notice per queued task, plus one warning in the service log. If the original message a Lark session notice replies to has been recalled, the notice is posted as a new message in the same chat (group or private chat) instead; schedule notices are not redirected. Normal queueing behind a running task is only logged. A message that has waited in the queue for over 24 hours without starting is cancelled instead of run when its turn comes, and the session gets a notice to resend it if still needed; a message whose turn comes right after the same session's previous task finished in the Agent (within 15 minutes) still runs. For a schedule, that occurrence counts as not run and the next trigger proceeds normally. Lark group-memory jobs are exempt from this 24-hour queue cancellation rule and take no part in repository coordination; they only exclude sessions running in the same memory directory.

Admins can clear blockers with `dutydeck recovery` (local runtime only):
- `inspect <session-id>` shows blockers and the run ID.
- `retire-pty <session-id> --file <decision>` retires a leftover terminal. When neither the original tmux name nor its owner marker matches a session, and the old service process that recorded it has exited, it is recorded as gone; renaming a session does not make it gone. If the socket file is missing, retirement requires Linux to confirm that no service still binds that path; uncertain cases remain blocked. The service also retires such records at startup.
- `restore-configuration <session-id> --run-id <run-id>`: when a model or permission change has an unknown result (`DRIVER_CONFIGURATION_UNKNOWN`), re-applies and verifies the current configuration through the native session without sending any prompt. API: `POST /api/sessions/:id/recovery/restore-configuration` with `{runId}`. Native load or configuration receipt failures return `409 NATIVE_CONFIGURATION_RESTORE_FAILED`, retaining the blocker and prior state; a stale `starting` state becomes `failed` on failure. If the original native record is lost, inspect recovery evidence before explicit `replace-native`; a new native session is never created automatically.

Recovery reminders update in place when a block clears, execution starts or the turn ends, including with silent progress and after restart reconciliation. Old sessions confirmed idle with no background tasks are no longer falsely reported as blockers; tasks that have started no longer show workspace queue blockers.

**Notification tiers** (bot settings, effective only when the group-card @ switch is on):

| Tier | Includes | @ | Urgent push |
|---|---|---|---|
| Needs you | approvals, questions, unknown outcomes, recovery reminders | initiator / approvers (`notifyMentionAction`, default `true`) | yes, after the threshold |
| Done | result cards, pre-start failures | initiator (`notifyMentionDone`, default `true`) | no |
| Info | progress, receipts, queueing | none | no |

`notifyQuietHours` (e.g. `22:00-08:00`, daemon local time): during quiet hours the "Done" tier does not @; "Needs you" still @s and its urgent push is deferred to the end of the window. Scheduled-task results never @.

When urgent reminders are enabled, concurrent checks within one bot share the same per-card and per-chat slots: each card is urged at most once, and each chat has an hourly urgent-push cap (3 by default, `urgentMaxPerHourPerChat`), so duplicates cannot go out; a failed urgent push releases its slot, allowing a retry on the next check.

## 2. Commands

You don't have to remember these: tell the bot what you want ("redo this with codex", "show the status", "open this group to everyone") and the Agent runs the matching command for you. For read-only commands the Agent tells you the result in its answer instead of posting a card; commands that change something post a confirm card first and run after you click 确认. Stopping a task, approving a tool call and answering the Agent's question stay with you: use the card buttons or just say "停" / "可以".

Matches `/help` (6 per page by default; plugin commands are listed on the last page).

`/remember` and `/memory` manage Dutydeck's session memory, pooled by `groupMemoryScope`. Claude Code's own auto memory is stored per working directory, not per group; to keep it from carrying over between groups, set "Claude 自带记忆（群聊）" (Claude auto memory in group chats) to off in the memory section of bot settings (`dutydeck settings bot set <appId> claudeAutoMemory=off`). It applies only to Claude Code sessions in group chats; see [features.md](features.md) for the scope and precedence.

You can also ask the Agent in plain language. It uses `dutydeck agent --turn "$TURN" session resume [--id ID]` or `dutydeck agent --turn "$TURN" session fork [--task TASK]`, then posts a confirmation card before making changes. Failed restoration explains the reason and suggests `/new --handoff`. When restoring a task that has not yet started, launch options are re-checked against the requester's current permissions before creating the session.

Only the requester of the source conversation’s first task can fork it. The fork inherits the actual Agent, model and reasoning effort; permissions follow the bot’s current settings. Claude Code terminal mode copies durable context with `--resume ID --fork-session`; Codex terminal mode uses `fork ID`. ACP, other Agents, switching Agents, or a source without durable context use the existing handoff of recent results, git status and a note. Handoffs also include source indexes, known status and command receipts for earlier tasks, which can be checked by task/attempt in history; missing or truncated material is marked. When a native fork copies context, it adds source information and git status without repeating the full handoff summary. Codex uses handoff when explicitly sharing the same directory, so copied records cannot be mistaken for the source later. A worktree starts from committed code and excludes the original conversation’s uncommitted edits; the first message says so. The receipt links to the new topic. A private chat that shares one conversation cannot fork; first switch its bot setting to one topic per message.

When bare `/new` actually ends a worktree session and a valid Web address is configured, its receipt links to that old session's authenticated workbench with the workspace panel open. Preview and explicit cleanup confirmation are still required; busy or dirty worktrees are refused. Opening the link does not clean the directory or dissolve the group. `/stop` only stops the task and does not add this cleanup link.

**Plan first (`/plan <task>`).** The agent only investigates and produces a plan. On the card you can approve (runs in the same session with the bot's normal permission mode), request changes (on the card or by quoting it), or cancel. During planning, Dutydeck blocks tool calls that write files or run commands, plus common write commands in the shell. It is not a sandbox and cannot stop a deliberately crafted shell command, so don't have the agent read untrusted content while planning. Supported for Claude ACP and Claude terminal mode; other agents (e.g. codex) say they cannot plan first; terminal sessions that predate the feature need `/new`. Approve/revise/cancel need the same permission as interrupting a task (initiator or admin). Reminder after 30 minutes, closed after 24 hours; a newer task invalidates an old plan card. The Web composer's "plan first" switch applies to Web sessions only; while a plan awaits approval, an "execution plan awaiting approval" panel lets you approve, cancel or request changes. For Lark sessions, send `/plan <task>` in Lark and approve, request changes or cancel on the Lark plan card. Lark-initiated plans are read-only on the Web, where you can still send ordinary messages in that session. A restored Lark plan draft keeps its text and plan intent and cannot be sent directly: you must explicitly choose 改为普通消息 ("change to an ordinary message") to clear the plan marker first—it is never automatically downgraded to execution.

**Open a PR and follow up (`/pr [title]`).** Also available as "Open PR" in the Web task's "Results inspector".

- **Confirm, then push.** A confirmation card (Lark) or dialog (Web) lists the files and line counts to commit, the files that are excluded and why, local commits, source and target branches, and the title/body summary. Only after someone with permission confirms does it push; the proposal expires after 30 minutes. Lark uses the same permission as interrupt/retry (initiator or admin); the Web endpoints require the session's interrupt permission. Repeated or concurrent confirms push once and open one PR.
- **Where it pushes.** Only a new `dutydeck/<topic>-<8-char id>` branch, never with force, without switching branches or touching your checkout (HEAD, index and working files stay unchanged). It pushes with your local git credentials, so the machine must be able to `git push` to `origin`. If the remote already has that branch name it refuses.
- **PR description and commit traceability.** The PR description ends with the session's latest verification record (only the redacted command, result and time; "验证早于最后改动" (verification predates the last change) when code changed after it; no output and no directory; "未验证" (not verified) when there is none) and the DutyDeck session id, as plain text with no share link. Commits DutyDeck creates (the first push and every automatic fix round) end with the git trailer `Dutydeck-Session: <session id>` (on by default; it replaces the old "generated by DutyDeck session …" sentence), visible with `git log --format=%(trailers)`; git author and committer are unchanged.
- **Push address checks.**
  - Code goes to `origin`'s current push URL (`pushurl` when set). It must belong to the repository shown on the confirmation card; if it points to another repository (such as a personal fork), `origin` has several push URLs, or a `url.<base>.insteadOf` rule would rewrite it elsewhere, no proposal is created. Checking the push URL requires Git ≥ 2.31; older Git reports that an upgrade is needed.
  - After confirmation and before each automatic fix push, the push URL is checked again. If it differs from the one recorded with the proposal, nothing is pushed: the first push fails and needs a new `/pr`, and follow-up stops.
  - Unconfirmed proposals created before the upgrade are not pushed when confirmed; start again. PRs opened before the upgrade stop follow-up the next time an automatic fix needs to push.
  - Pushes go through a temporary remote named `dutydeck-<random id>`, and the push no longer updates a local `origin/dutydeck/...` tracking branch; run `git fetch` if you need one. Options set only for `origin`, such as a custom receiving command (`remote.origin.receivepack`), are not inherited either; repositories that depend on them are not currently supported by `/pr` push.
  - The workspace is writable by the Agent, so git that DutyDeck runs itself (`/pr`, per-turn diff snapshots, CI, the status line) runs no repository git hooks (pre-push included) and ignores program-valued settings in the repository's `.git/config` (`core.fsmonitor`, `core.sshCommand`, `credential.helper`, filters defined only in the repository, and so on). Remotes use the credentials and ssh settings from system and global git config, and git gets only the environment variables it needs, never service secrets.
- **Which files.** Only files that some turn of this session changed and that were not changed again afterwards (this relies on the per-turn diff records). The rest are listed as excluded ("not changed by this session", or "changed by this session, then changed again, cannot confirm"). If those files change between the proposal and the confirmation, nothing is pushed; start again.
- **Unpushed local commits** on HEAD that are not in `origin/<target>` go into the PR branch as ancestors (not rewritten) and are listed; without an `origin/<target>` tracking branch you get a warning that it cannot tell whether they are already on the target. With more than 50 unpushed local commits `/pr` refuses (the list would be incomplete): squash them first.
- **Oversized untracked files** (over 20 MiB each, 50 MiB total, or more than 2000 files): `/pr` and auto follow-up name the file or reason instead of skipping silently; add those files and build dirs to `.gitignore` and retry.
- **Follow-up** every 2 minutes (PR state, CI of the current head, new comments). CI failures: up to 3 rounds, stop when the same error appears twice or a round changes more than 10 files / 300 lines. Review comments: up to 5 rounds, 10 comments per round. **Only comments from personal accounts of the repo owner, members or collaborators** (GitHub `author_association` OWNER, MEMBER or COLLABORATOR, not a Bot) go to the agent automatically; anyone else, and bots such as coverage bots, only get a "needs your decision" card naming the author and role, and are handled only when you tap "Apply comment" (they do not use a round). The github plugin's token must be able to read organization membership (e.g. a fine-grained PAT needs organization Members read access); otherwise comments from members whose membership is private are treated as outside comments and only get a card. For automatic ones the agent marks each as handled (replied on the PR) or needs-a-human (a card with "Apply comment" / "Ignore"). Comments by Dutydeck itself (marker `<!-- dutydeck -->`) are skipped and no comment is handled twice. Fixes are fast-forward pushes to the same branch; if someone else pushed to it, follow-up stops. Follow-up stops when the PR is merged or closed, or when you click "Stop following" on the Web. The agent edits the working tree and is told not to commit, push or switch branches; Dutydeck commits that turn's changes onto the PR head. If you edit files the PR touches in the workspace, follow-up stops. If a fix round touches a file that already differed from the PR branch before the round (it holds uncommitted changes that don't belong to the PR, e.g. a local edit excluded at confirmation), nothing is pushed: follow-up stops and lists the files for a human. Fixes only push files already in the PR: if a round changes any other file (including new files, or files changed by another topic or your editor during the round), nothing is pushed and follow-up stops listing those files; if they belong in the PR, commit and push them to the PR branch yourself. `/ci cancel` or "Stop following" blocks automatic fixes that have not been submitted yet; tasks that have already started keep their existing semantics without forced interruption. Pipeline events arriving concurrently after a fix is pushed do not overwrite the new commit, and follow-up state such as comments and open questions is preserved.
- **Verification before pushing a fix**: when the session's bot has a verification command (bot setting `verificationCommand`), every automatic fix round (CI failure or review comments) that changed code runs that command in the workspace before pushing; the Web "Open PR" panel shows "verifying before push". What gets pushed is the snapshot taken when the round ended, so the files changed in that round are checked against the snapshot before verification and again before pushing; if they changed in the workspace, the verification counts as failed. The fix is pushed only if it passes, and the push notice says so and notes that other uncommitted changes in the workspace that are not part of this PR also took part in the verification but are not in the pushed commit. If it fails (failed, timed out, could not run, or the round's files changed around the verification), nothing is pushed or committed and the changes stay in the workspace; the PR shows "verification failed, needs a human" (distinct from "stopped following"), and the original thread gets a card with the failed command, exit code and up to the last 4 KB of redacted output, plus "Push anyway" (the other pre-push checks still apply) and "Stop following" buttons, with the same permission as the confirmation card; if the card could not be sent, it is resent about every 2 minutes. In the Web "Open PR" panel, a PR that needs a human also has "Push anyway" and "Stop following", with the same permission as confirming a push on the Web; the CLI has no such command. While it needs a human, the PR still counts as followed and other sessions cannot claim it; "Push anyway" first checks that this record is still the only one following the PR. A failed verification does not use a fix round and is not retried automatically. Temporary conditions are not failures and verification is retried on the next poll (about a minute): the session is busy or another verification is running, the session is stopping, the service is shutting down, or a run or write conflict occurred; other errors, such as a stopped session, count as failed. A verification interrupted by a restart runs again; it never pushes directly. If the service restarts after recording the failure but before stopping the PR, the PR is moved to needs-a-human and the card is sent after the restart. Bots without a verification command and non-Feishu sessions push as before, and the push notice says no verification command is configured.
- **No CI plugin installed**: `/pr` says "Open PR is not configured" with install steps; the Web shows no button, only that hint.

**Follow an existing PR (`/pr follow <PR link or number>`).** A PR opened on the platform by someone else (or by you) can be handed to the current session; it is then followed with the same rules as above for CI failures and review comments, and follow-up stops when the PR is merged or closed. On the Web, enter the link under "跟进已有的 PR" (follow an existing PR) below "Open PR"; on the CLI, `dutydeck pr follow <link or number> --session <session>` (`dutydeck pr list|stop` to view and stop); the API is `POST /api/sessions/:sessionId/pull-requests/follow` with body `{"pullRequest":"<link or number>"}`.

- **Permission**: same as opening a PR. In Lark the sender must be allowed to operate the session (initiator or admin); the Web/API require the session's interrupt permission.
- **Checks before claiming** (it refuses with the reason when one fails):
  - The PR belongs to the same repository as the session workspace's `origin`. The link is matched with the CI plugin's repository rules; unknown links and PRs of other repositories are refused. A bare number means a PR of the workspace repository.
  - The PR is still open; merged or closed PRs are refused.
  - The PR's source branch is in this repository (not a fork) and is neither the target nor the default branch; `origin` has that branch at the PR head reported by the platform. The CI plugin must report the PR's source branch (the bundled github plugin does).
  - Files the PR touches are identical in the session workspace and on the PR branch: check out the PR branch in the workspace first (`git fetch origin <branch> && git checkout <branch>`) and clear uncommitted edits to those files. Dutydeck never switches your checkout.
  - The push URL checks are the same as for opening a PR.
  - A PR is followed by one session at a time: claiming again in the same session returns the existing record; another session must stop the existing follow-up first.
- **After claiming**: comments already on the PR count as handled, only later comments are followed; trusted comments are decided as above (personal accounts of the owner, members or collaborators only). CI is checked from the PR's current head. Fixes go to the PR's own source branch, fast-forward only, never forced, and only for files already in the PR; if someone else pushes to the branch, follow-up stops instead of overwriting.

## 3. Group participation

Participation level (when the bot answers without an @; it never changes permissions): mention only / no @ inside topics it owns / `selective` / `eager`. Underlying fields: `mentionPolicy` and group participation `off|observe|selective|eager` (`observe` only listens and builds background; set it with `dutydeck settings group set <chatId> participation=observe`). New bots default `mentionPolicy` to `topic`. In a group with several bots (the group's subscribed alert sources don't count) and no responder, un-@ messages are not answered, except ones that call the bot by name, reply to it, or sit in a topic it owns (calling by name means the bot's full name or display name at the start of the message, such as "bdev-flash, take a look"; a fragment such as "flash" alone is judged like any other message, a message that @-mentions someone else is not taken even if it names the bot, and when the opening word matches a fragment of another bot's name this bot yields); @ the bot that should answer and say 「你负责接话」 ("you take the replies") and confirm, or pick the responder in the Web group settings; a late release announcement does not clear a newer responder claim. If the member list can't be read in full (read error, no permission to read group members, or truncated by a security policy), the group is treated as having several bots too; `/status` and "why didn't you reply" say so. A responder can be set in single-bot groups too; a `selective` responder without a scope also answers requests for help that don't name anyone and need a bot (e.g. 「有人知道今天的发布单在哪看吗」, "does anyone know where today's release ticket is?"); small talk, questions between members, @ to others and progress updates are still left alone. A role scope (Web "Bot management" → "负责范围" / scope, or `dutydeck settings bot set <appId> roleScope=...`; applies to every group the bot is in) lets a `selective` bot judge and answer un-@ messages within that scope regardless of the responder; bots with overlapping scopes may all answer. A `selective` bot without a scope that is not the responder, in a group with several humans, does not answer general questions and plain alerts that don't address it. In `eager` mode and in single-human groups, setting a scope also switches the bot to judging by scope, so it answers fewer messages. When the bot stays silent, @ it and ask 「刚才为什么没回」 ("why didn't you reply") for the reason and how to change it; `/status` shows the participation level, responder and scope. Level changes, "why didn't you reply" and responder phrases count only when the message is essentially just that phrase; a message with an extra request (e.g. 「按需求改一下」, "change it as required", or 「为啥不回退」, "why not roll back"), or one naming a responder that isn't a bot in the group, goes to the agent as a normal request. Mention-once flow: inside a topic you don't need to @ again; if you forgot to @, send a lone `@bot` within 10 minutes to claim the previous message. Leader mode (a front agent, a Leader and Workers) is described in [Leader mode](#leader-mode).
- **Bot-to-bot loop guard** (`botLoopGuard`) is off by default. Enable it in the bot settings or with `dutydeck settings bot set <appId> botLoopGuard=true`; once enabled, a topic stops receiving responses after 3 consecutive bot-triggered turns until a human speaks. When disabled, bot turns are neither counted nor blocked.

**Alert triage** (built-in scenario pack `alarm`, see [Built-in plugins](plugins.md#builtin-plugins)). @ the bot and say 「告警来了先帮我看看」 ("look at alerts first when they come") or 「告警来了先帮我初筛，只看 P0」 ("triage alerts first, P0 only"); it posts a confirmation card naming the source bot (by default the bot that posted most in the group recently), levels, dedupe window and hourly cap. Whoever confirms becomes the requester, and triage tasks run in their name. Say 「关闭告警初筛」 ("turn off alert triage") and confirm to turn it off; the settings are kept. Once on, alerts from the source bot skip the participation decision: the bot opens a topic under the alert and starts a triage task. The same alert is analysed once per dedupe window, alerts over the hourly cap are skipped, and asking 「刚才为什么没回」 under a skipped alert gives the reason. In multi-bot groups only the responder triages. `/status` shows the subscription and today's analysed and skipped counts. When you @ the bot quoting an alert card and it has handled the same alert rule in this group before, the earlier conclusion goes to the agent as reference material and the process card shows a 「📎 date 同一告警规则：…」 line. The Web group settings list each pack's parameters (sources, levels, dedupe window, hourly cap); a pack must be confirmed in the group once before it can be changed from the Web or with `dutydeck settings group set <chatId> scenarios=...`. The Web form submits only the fields you changed. If the group's duties were changed elsewhere (by someone else, another bot or a confirmation card in the group) after you started editing, saving reports that they were changed instead of overwriting them and keeps your input; choose 放弃修改 (discard changes) to load the latest settings and edit again. In multi-bot groups, a topic opened under an alert from the source bot does not count as another bot's topic, so un-@ follow-ups in it go through the participation decision as usual. Before deciding, the bot reads the topic's replies (50 per page, at most 4 pages) and stays out if another bot (other than the source bot and itself) has already posted there, if the topic runs past 4 pages, or if reading fails. Two bots deciding at almost the same moment may both answer; only one answering is not guaranteed.

**Team FAQ** (scenario pack `team-faq` in `plugins/team-faq`, installed separately). When a human in the group asks about a configured service or process, the bot uses the runbooks to decide whether to answer and, if it does, answers from them and cites the source; installation and parameters are in [the plugin README](../../plugins/team-faq/README.md). It works only at the `selective` and `eager` levels; messages that @ the bot or reply to it are handled as usual. A keyword match only hands the message to the participation decision model together with runbook excerpts; the model stays silent on discussion between colleagues, questions someone has already answered and questions the runbooks don't cover. If reading the runbooks times out or fails, or nothing was read while some files could not be read, the message is decided as if the pack were off, `/status` counts it as 「取材料失败」 (context failed), and "why no reply" gives the reason. `/status` shows the keywords, runbooks and today's answered, skipped and context-failed counts.

“Busy message triage” (`busyTriage`) is off by default in bot settings. Enable it there or with `dutydeck settings bot set <App ID> busyTriage=true`. When off, ordinary messages received during a turn keep queuing as before. When on, the host answers progress questions with the stage, latest step, elapsed time, queue size and pending approvals. Extra requirements are injected into the active turn when the ACP Agent supports steering; terminal Agents keep queuing them. Bot control requests use the same validation and permissions as `dutydeck agent`: reads reply immediately, changes require a confirmation card before execution. A short sentence identifies the interpretation. Card delivery failures, stop requests, uncertainty, errors and the 15-second timeout fall back to queuing without interrupting. Control phrases, slash commands, replies to pending cards, and bot or automation messages keep their existing routes.

Triage uses the group decision Agent/model (`decisionAgentId` / `decisionModel`), falling back to the memory Agent/model and then the default Agent/model. Choose a cheap, fast model in those decision settings. The classifier handles Agent view/control commands as well as requests such as “check CI every day at 9 am” and “use codex by default”. Schedule requests immediately receive an enable card while the draft stays disabled. A request to keep following something until it is done (“check this PR every 30 minutes until it is merged, stop by Friday 18:00”) becomes `schedule create --until '<condition>' --deadline <Beijing time>`; the card shows both, the Agent disables the plan with stop-self once the condition is met, and a plan still running at the deadline is disabled with a notice in the original topic (see scheduled Agent tasks in [web-console.md](web-console.md)). Bot settings immediately receive an admin confirmation card and are not saved before approval. Both cards reply to the current message using its sender’s identity, without waiting in the task queue. Progress elapsed time is shown in seconds, minutes and seconds, or hours and minutes.

### Leader mode <a id="leader-mode"></a>

Leader mode hands a task to three roles in turn:

| Role | Who | What it does |
|---|---|---|
| Front agent | The topic's default Agent, and the only Agent that talks to you | Decides whether to answer the message itself or hand it to the Leader |
| Leader | Another Agent that only makes judgements and never edits files | Following the "Leader guide", splits the task into steps and assigns Workers, or first asks you one question; judges the Workers' questions and tool approvals along the way; accepts the result at the end |
| Worker | The Agents that do the work (several can be configured) | Change code and run tests; its session stops automatically when it finishes |

It works in group chats (an @ to the bot, or a message the Tag on-demand participation decides to handle) and in private chats. In a group, the Leader's plan is dispatched only after you click 「开始执行」 ("Start"); in a private chat there is nothing to click, and the result is a reply under your message rather than a new topic.

**Setup.** In Web "Bot management", set "Execution mode" to "Leader mode: front agent + Leader + Workers", pick the Leader Agent, tick the Workers (up to 8) and optionally fill in "Leader guide". Command line:

```sh
dutydeck settings bot set <appId> executionMode=layered leaderAgentId=<agentId> workerAgentIds=<id1>,<id2>
dutydeck settings bot set <appId> leaderSkill=<guide>    # optional; leaderSkill= clears it and goes back to the built-in rules
```

Requirements: group tools are on (`groupToolsEnabled`); a terminal-mode Leader needs both the bot and that Agent to be `full-trust`, otherwise saving the settings fails. The stored value of `executionMode` is still `single` / `layered`, so existing settings need no migration.

**What the Leader handles.**

- **Workers' questions and tool approvals** go to the Leader first instead of straight onto a card. What it can settle it answers to the Worker directly; for a tool approval it may approve only when you personally are entitled to approve that kind of operation. Only what really is yours to decide reaches the goal card, which shows the Worker's original question and the Leader's 「问题 / 建议 / 不回复时」 ("Problem / Suggestion / If you don't reply"), and @ you as usual. If the Leader's judgement fails, times out, or the goal passes 30 judgements, it is escalated to you with the reason on the card. Requests from the Leader's own acceptance step are not judged by it; they go to you directly.
- **Acceptance**: the Leader checks the delivery against the guide and sends unacceptable work back to the Worker, with up to 2 automatic rework rounds before it hands the decision to you.
- **"Leader decided for you"** (「Leader 已替你定」): the decisions the Leader made on your behalf (problem → decision · basis) are listed on the goal card, the latest 5 with the total noted when there are more, and are attached to the delivery result too. If you disagree, just say so in the topic; the front agent passes the new requirement back to the Leader.

**What counts as your authorization.** Only your own words: the message that started the task, what you said in the topic afterwards, and your answers on the goal card, plus any standing authorization the Leader guide spells out. The Leader's own inferences and the front agent's paraphrased brief do not count.

**The Leader guide.** The guide is a skill (a `SKILL.md` plus reference files) that tells the Leader how to work: what to look at first, what it decides itself, what it escalates, which questions acceptance asks and how to word an escalation. The bot setting `leaderSkill` takes:

- a skill name, such as `leader`;
- `plugin-name/skill-name`, such as `leader-guide/leader`;
- the absolute path of a `SKILL.md` (or of the directory that contains it), which may start with `~/` and does not have to sit in a skill directory; only an administrator can set this value.

The skill can live in the project directory (`.claude/skills/` and so on), in your user directory, or be packaged as a plugin (see [Plugins](plugins.md#leader-guide)). Web lets you type it or pick from the skills discoverable from the bot's working directory. At the start of every Leader run (planning, judging, acceptance) the host looks the value up from the original topic's working directory, bot and group, reading a value that starts with `/` or `~/` as an absolute path, and matching any other value, in the workspace, the host user directory and the plugins active for this bot and workspace, first as a plugin reference (`plugin-name/skill-name`), then as a path relative to the topic's working directory, then as a skill name (duplicate names are an error), and gives the `SKILL.md` to the Leader. Reference files a plugin skill declares in `skillResources` come along; the rest, and the sibling reference files of a skill given by absolute path (whose `skillResources` are not inlined), the Leader reads itself by path when needed (the Leader Agent must be able to read them). Skill directories skip symlinks that point outside the directory, so a guide kept elsewhere should be given by absolute path. Left empty, the built-in rules apply. If the skill is not found, has duplicate names or is too large, that Leader run fails and says why in the topic; it never quietly falls back to the built-in rules.

**After a service restart.** A planning request that may already have reached the Leader but has no known result fails the delegation with a notice in the original topic instead of running again; an answer the Leader finished before the restart is reused; only requests that were never sent are planned again.

## 4. Bot setup

**Web (recommended)**: on the first screen click "Bind Lark Bot" (later "Manage Lark Bot"), choose "Add bot" in the dialog, then "One-click create Lark bot", enter a name and click "Create bot". It reuses the local Lark login (or asks for a QR scan), creates the app, configures scopes and events, publishes and stores the secret. Then pick the default Agent and workspace and enable listening.

If you close the dialog during creation, reopen 新增机器人 (Add bot) in the same browser tab and instance to keep following it; other instances never pick it up. 重新连接 (Reconnect) only checks progress and never starts another creation. If the current instance has no record of the creation, choose 重新提交本次创建 (resubmit with the same request ID, to avoid a duplicate on the same instance) or 放弃此记录 (clear this page's record without cancelling a creation already under way). A record left by an older page version that the current instance cannot find can only be discarded; check its progress on the instance that started it.

**CLI**:
```bash
dutydeck lark create "Dev Assistant" --agent ccflash --listen          # default: ask
dutydeck lark create "Dev Assistant" --agent <terminal agent id> --full-trust --listen   # required if the agent can't do Lark approvals
printf %s "$LARK_SECRET" | dutydeck setup --lark-app-id cli_xxx --lark-app-secret-fd 0 --agent claude --yes
```

Agents that support Lark per-action approval: ACP agents (based on a successful ACP protocol handshake, independent of optional model enumeration metadata), and Claude Code / Seed / Relay in terminal mode (via a PermissionRequest hook). Other terminal CLIs can only run `full-trust`.

**Route Agents by weight.** In bot settings, enter positive “Agent 分流权重” values for participating Agents; leave a field blank to exclude it, or clear all fields to disable routing. For example, Codex 30 and ccflash 70 select Agents for new primary Lark sessions with roughly 30% / 70% probability; short runs need not match the ratio exactly. Existing sessions keep their Agent when weights change or routing is disabled. A fixed group Agent, `/new --agent`, or explicit model/effort takes priority. The bot's default model and effort apply only to its default Agent; other Agents use their own defaults. Memory and group decisions are unaffected. Every candidate must support the chosen approval mode, and enforced risk control checks and installs hooks for all candidates. The CLI edits the same setting:

```bash
dutydeck settings bot set cli_xxx 'defaultAgentWeights=[{"agentId":"codex","weight":30},{"agentId":"ccflash","weight":70}]'
dutydeck settings bot set cli_xxx 'defaultAgentWeights=[]' # Disable routing
```

**Fallback Agent.** Select “兜底 Agent” in bot defaults or the setup wizard. For bots using `ask` / `approve-reads`, choose “Codex (ACP)” (`codex-acp`) as a Codex fallback; `codex` and `codex-cli` keep their terminal defaults. The CLI edits the same setting:

```bash
dutydeck settings bot set cli_xxx defaultAgentId=ccflash fallbackAgentId=codex-acp fallbackModel=gpt-6.1-sol
dutydeck settings bot set cli_xxx 'fallbackModel=' # Use the fallback Agent's default model
dutydeck settings bot set cli_xxx 'fallbackAgentId=' # Disable fallback and clear its model
```

A request switches at most once when the primary cannot start, is signed out, has invalid credentials, or reports a recognized rate limit, exhausted quota, or unavailable upstream. Switching requires no answer, reasoning, tool call, or approval request in the current turn. Ordinary task failures, cancellation, permission denial, and unknown outcomes are never replayed. Other queued or running work prevents switching. The optional fallback model applies only to this bot's new automatically switched sessions; blank uses the fallback Agent's default model. Effort always uses that Agent's default. Changing or disabling the fallback Agent clears its old model. Manual or weighted selection of the same Agent does not use the fallback model. The fallback follows the bot's approval and risk controls; enforced mode checks and installs its hook too. Cards explain the switch. A new session receives handoff material as background; full native history does not transfer between Agents. Existing fallback sessions remain sticky, while new conversations try the primary again. Explicit `/new --agent`, model, or effort settings disable automatic fallback.

When enforced risk control is on, use **配置拦截 Hook** in bot settings before saving a new workspace, primary, fallback or weighted Agent. Status checks and installation use the current draft workspace and every candidate. Preparation writes hook files only: it preserves the draft and the saved risk control mode. The CLI equivalent is `dutydeck settings bot install-hook <app-id> --prepare fallbackAgentId=codex-acp workspace=/path/to/workspace`, followed by `bot set` to save. Draft arguments also accept `defaultAgentId` and `defaultAgentWeights`. Without `--prepare` or draft arguments, installation retains its existing pattern/guidance save behavior, while already-enforced bots remain enforced. Save failures keep the draft; only revision conflicts display a concurrent-edit warning.

The save API strictly validates private-chat mode, group reply mode, group memory scope, Claude auto memory and app brand. Invalid values return `400 INVALID_LARK_CONFIG` and preserve saved values. `groupReplyMode=null` still clears the override; the CLI equivalent is `groupReplyMode=auto`.

**Claude Code gateway and API key.** In step 2 of bot registration, choose Claude Code, expand “模型服务配置” (model service settings), enter the gateway URL, auth mode and key, then save the model service settings before completing registration. Existing bots have the same panel beside their default Agent settings. Enter the gateway model ID in the bot's default model field. Built-in Claude Code and custom Agents with `adapterId: "claude"` or `"claude-code"` (such as ccflash) are supported. The gateway must implement the Anthropic Messages API.

```bash
printf %s "$MODEL_API_KEY" | dutydeck settings agent set claude --app cli_xxx baseUrl=https://gateway.example authMode=bearer --api-key-fd 0
dutydeck settings bot set cli_xxx defaultAgentId=claude defaultModel=your-model-id
dutydeck settings agent show claude --app cli_xxx
dutydeck settings agent set claude --app cli_xxx clearApiKey=true
```

`bearer` uses Authorization Bearer; `api-key` uses X-Api-Key. Settings are isolated per bot and Agent. Omitting `--app` changes shared Agent settings. A URL is activated only with a key in the same scope; clearing the bot key restores shared Agent / CLI connection settings. Keys live in private local secret files and are never returned by the API or CLI. The model uses the bot's `defaultModel`; an explicit session model takes priority, and other bots keep their own models. Gateway changes apply when the next Agent process starts; use `/new` to recreate a running session.

## Confirmation cards, message disposition, matters and prompt versions

When group participation infers that a message needs action, Dutydeck sends a confirmation card first. A person with task creation access can confirm; execution uses that person’s identity. Unconfirmed cards expire after 24 hours. Explicit mentions, topic follow-ups, proactive replies, and administrator-configured direct scenarios keep their existing behavior. The result inspector shows each turn’s authorization evidence, confirmer, and decision record.
Group participation records follow the group's retention days (`retentionDays`, default 30, `dutydeck settings group set <chatId> retentionDays=7`), pruned hourly: expired group messages, decision records with their feedback, finished participation actions and expired unclicked confirmation cards are deleted together. A decision referenced by an action that is still sending or has an unknown result is kept until that action settles; direct scenario records inside the dedupe window (up to 168 hours) are kept for dedupe and counting with their message excerpt removed.
Message disposition: the bot page lists ignored messages from the last 24 hours, 7 days, or 30 days. Use `dutydeck lark why <message_id> [--app <appId>]` or `dutydeck lark ignored --chat <chat_id> [--since 24h|7d|30d]`. Ignored receipts are retained for 30 days. Per bot, messages from other bots and messages from people are counted separately, each with a safety cap of 60,000 (about the peak 30-day volume of one bot), so a flood of alert cards cannot push out people's records. One hour after a message from another bot is ignored, only its disposition and a 160-character snippet are kept, not the card body; records that existed before the upgrade stay as they are until they expire. Older records may have no reason.
A matter connects sessions created through handoff, fork, resume, retry, and scheduled execution. Task lists group its sessions; the details show sessions and schedules. Plain `/new` starts a new matter; `/new --handoff` keeps the original one. To edit a schedule, find its id with `dutydeck agent schedules`, then use `dutydeck agent schedule update <id>` for its time or instructions and `schedule enable/disable <id>` for its state. Its id is preserved. Creating another recurring schedule when this matter already has an enabled one requires `--additional`. If the original session becomes unavailable, the next unaccepted scheduled run starts a new session.

A matter stays in Needs attention while a latest turn has an uncleared waiting or blocked report. A model-inferred action remains pending confirmation in message disposition until a person confirms and the task is accepted; the accepted record retains its decision as authorization evidence.

Bot pre-injected prompts now keep immutable versions when the text changes; existing nonempty prompts are backfilled at startup. Open “历史版本” in bot settings to view, compare lines, or confirm a rollback. A rollback creates a new version, and stale configuration edits are rejected. CLI commands under `dutydeck settings bot` are `prompt-history <appId>`, `prompt-show <appId> <version>`, `prompt-diff <appId> <a> <b>`, and `prompt-rollback <appId> <version>`. Each dispatched task records the prompt version and, when present, the group instruction revision outside the task request. Startup backfill, version lookup, or snapshot failures only warn and do not block startup or new tasks; unknown versions appear as “未记录版本”. Preparation snapshots are removed after successful usage recording.

Confirmation cards bind the original message content, attachment references and routing. Editing the message invalidates the old card with “原消息已修改，请重新确认”; send the request again for confirmation. The confirmer’s current permissions still apply, and a valid request is accepted once.

Task reports and message dispositions are side records: read or cleanup failures warn while task acceptance, scheduling and settlement continue. If a matter lookup fails, schedules use the original session availability and execution snapshot; authorization, admission idempotency and unknown-result safeguards still apply.
