## Why Dutydeck <a id="why-dutydeck"></a>

| Scenario | Traditional Terminal CLI | With Dutydeck |
|---|---|---|
| **Mobile & async dispatch** | Tied to a terminal; disconnects kill the run | Dispatch from Lark; runs in the background; results come back as cards |
| **High-risk actions** | Either YOLO mode or constant prompts | "Allow once" / "Reject" buttons on the Lark card |
| **Dirty working tree** | Edits your current checkout | Optional **Git Worktree** from HEAD. Web sessions default to a worktree; Lark tasks default to the selected directory (see below) |
| **Quality verification** | Agent claims "tests passed" | **The server runs the verification command** and records exit code, duration and a code fingerprint (Lark tasks, after you configure a command) |
| **Team memory** | Context resets every session | **Persistent memory**, selective group participation, scheduled tasks |
| **CI babysitting** | Watch CI by hand, re-open the agent on failure | With a CI plugin installed, failures can wake the agent to fix within limits (see [Plugins](plugins.md)) |

## Key Capabilities <a id="key-highlights"></a>

- **Lark bridge**: streaming progress cards; phone approvals ("Allow once / Allow this command for the session / 本工作区允许此类命令 (allow in this workspace) / Reject"); long output bundled as Markdown attachments; `adhdMode` for conclusion-first output; a "View changes" link on result cards for the diff of that turn, with line comments.
- **Git Worktree (optional)**: edits happen in a worktree derived from HEAD. Web defaults to a worktree, **Lark defaults to `shared`** (the selected directory). In Lark, use `/new --workspace worktree`.
- **Verification gate**: set a bot's `verificationCommand` (e.g. `pnpm test`); after a Lark task changes code, the server runs it on the host and records the result. On failure the output goes back to the agent for up to 2 repair rounds. Web sessions do not trigger it.
- **Memory**: **off by default** (`memoryEnabled` unset means on only when the default group participation is selective or eager). Private chats are independent. In groups all groups of one bot share a pool by default; set `groupMemoryScope=per-group` (Web "Group memory scope", or `dutydeck settings bot set <appId> groupMemoryScope=per-group`) to isolate the Dutydeck group memory of each group. Switching does not migrate or delete anything. The scope does not cover memory an Agent keeps by itself: Claude Code has auto memory on by default and stores it per working directory under `~/.claude/projects/<directory>/memory/`, shared by every group and by the bot owner's own Claude in the same working directory. To isolate it, set the bot's `claudeAutoMemory` to `off` (Web "Claude 自带记忆（群聊）", or `dutydeck settings bot set <appId> claudeAutoMemory=off`), or give the bot its own workspace. `off` applies only in group chats of a bot with session memory on, to Claude-family sessions (Claude Code / Seed / Relay / Genius terminals and the built-in ACP Claude), and only to Claude processes started afterwards; private chats, Web, scheduled tasks, work-item and delegated child sessions, and custom ACP Claude Agents are not affected. A `CLAUDE_CODE_DISABLE_AUTO_MEMORY` value the user sets explicitly in the Agent env or in the `env` of Claude settings wins; see [agents.md](agents.md). A background memory job that fails 5 times in a row with retryable errors, or whose memory Agent was deleted, is abandoned so the pool can take new jobs; jobs whose outcome is unknown stay held for recovery. Job records never store credential values; for each pool and job kind only the 2 most recent finished jobs are kept, reduced to task ids and result counts (no conversation text), and older ones are deleted.
- **Memory management**: use **管理记忆** in task details to search, revise and delete the actual Lark pool. Ordinary Web sessions can explicitly create and bind project memory; matching directories do not share it automatically. See [Configuration sources and memory management](web-console.md#configuration-and-memory).
- **Group participation**: four levels (mention only / no @ inside owned topics / selective / eager); natural-language schedules in groups and private chats (say "every 15 minutes, check whether this topic has a conclusion"; the Agent posts a card saying what, when and where, and it starts after you click 启用, no command needed); Leader-Worker collaboration.
  - Confirmation cards preserve the task text and its line breaks instead of clipping it to 200 characters. If the confirmation card cannot be delivered, the schedule stays saved and disabled. The Agent receives its ID and recovery instructions: retry with the same parameters in the current turn to resend the card, or have the user send `/schedule enable <ID>` in the current chat.
  - When the Agent changes a group collaboration mandate (`collaborate mandate-update`), pausing, stopping or pausing result delivery applies at once. Changing its instructions, time or condition, or resuming it, posts a change confirmation card in the original topic with the resulting settings and the full new instructions; it applies only after the requester or someone with operate permission clicks 确认, and the mandate keeps its current settings until then. If the mandate changes in the meantime, the card is rejected on confirmation. Changes made in the Web group settings do not need a card.
  - To change a schedule, the Agent finds its id with `schedules`, then uses `schedule update <id>` for its time or instructions. The id is preserved, and the plan pauses until you click 确认启用. Use `schedule enable/disable <id>` for its state. If the same matter already has an enabled recurring plan, creation is refused with its existing plans listed; another plan requires `--additional`. Retrying the same request still returns its original plan. Older conversations retain compatible updates to disabled plans with the same name; if the request's work template differs from the plan's, it is refused with a hint to use `schedule update` or a different name.
  - Recurring schedules created by the Agent or by Lark `/schedule every` default to a new conversation per run (`--mode fresh`), so each run does not carry the whole conversation; the chat is continued (`--mode session`) only when the user explicitly asks to continue from the previous conversation. One-time (`--at`) schedules still use this chat. Updates keep their current mode unless a mode is explicitly supplied. To try a schedule, the Agent runs it once in the current turn instead of creating a "test schedule".
  - Follow up until done: say "check this PR every 30 minutes until it is merged, stop if it is not merged by Friday 18:00" and the plan carries a completion condition and a deadline. Each run checks the condition first and the Agent disables the plan once it is met; a plan still running at the deadline is disabled with a "deadline reached, completion not confirmed" note in the original topic. A plan can also start a saved work-item template on every run. See scheduled Agent tasks in [web-console.md](web-console.md).
  - A schedule never fires again while its previous run is unfinished. When one run has not started or not finished after one period (at least 10 minutes, counted from when the run was created), a single reminder is posted in the schedule's original topic with where it is stuck (queue blocked, waiting for someone to resolve an "unknown result", or just "not started / not finished" when no reason is available); one stuck run gets one reminder. An interrupted send can be retried after 10 minutes without confirmation, within a total limit of 3 attempts. One-time schedules have no period, so they get none.
  - Fresh-session plans post results and notices back to the original topic. Each run carries only a summary of the previous result (about 500 characters); when you reply in that topic, the session that picks it up gets the latest result (about 1500 characters). Recurring Lark plans saved by older versions without a mode switch to a fresh session per run automatically, with no need to recreate them; plans that explicitly chose `--mode session` stay as they are.
  - When a run fails to start (the session cannot be opened or the dispatch fails): if the execution session is only temporarily unavailable (locked, stopping, or its terminal not yet cleaned up), the same scheduled time is retried once in a fresh session; the plan keeps its run mode, so the next run goes back to its usual session. Other errors, or a failed retry, get one line in the original topic saying what went wrong and when it runs next, plus a service-log warning with the plan, run ID and error code. A "new CI failure" condition that cannot be checked (for example the workspace moved to another commit while the plan still watches the one it was created on) is also recorded as not done. A run whose Agent reports "blocked" or "waiting for you" is recorded as not done; the task itself stays completed. A result card that fails to send is retried after 1 and then 2 minutes (right away after a service restart), at most 3 times, then left with the failure reason on the run record. When runs keep failing for the same reason (trigger errors by error code; Agent reports by "blocked" or "waiting"; execution failures as one kind), the second and later ones post nothing new and edit the previous message to "failed N times in a row: reason", replying with a short line only if the edit fails. After 3 in a row the plan is disabled and the usual disable notice is posted. Say "resume" in the topic and the Agent runs `schedule enable <id>` for you; counting restarts after re-enabling.
- **Open PRs and follow up**: `/pr [title]` in Lark, or "Open PR" in the Web task's "Results inspector"; confirm first, then Dutydeck pushes a new `dutydeck/` branch, opens the PR and follows up on CI failures and review comments. An existing PR can also be handed to a session with `/pr follow <PR link or number>`, the Web's "跟进已有的 PR" (follow an existing PR) or `dutydeck pr follow`, as long as it is in the workspace's repository, the workspace has the PR branch checked out, and the operator may operate the session. Needs a CI plugin that can create PRs (the bundled `plugins/github`).
- **CI follow-up**: provided by plugins only. This repo ships `plugins/github` and `plugins/codebase`.
