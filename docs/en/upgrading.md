# Upgrade Notes

> [← Back to README](../../README.en.md) · [All docs](../../README.en.md#docs) · [简体中文](../zh/upgrading.md)

- **Compatibility with invisible characters in pasted input on newer Claude builds**: before writing to a Claude-family terminal, Dutydeck now removes the same invisible codepoints that would make Claude hold the first Enter for review, and Dutydeck's own untrusted-boundary escaping uses a visible space. Valid emoji and combining sequences are preserved. This changes only the text written to the terminal and its native receipt matching, not the stored task prompt, ledger prompt or other Agents. If `Removed … invisible character · review and press Enter to send` still appears after input was written, Dutydeck never presses Enter again or resends automatically; an unknown outcome now tells you to confirm it in the terminal.

- **Empty-composer verification before Claude business input**: after the screen becomes quiet and before the first business byte, Dutydeck verifies the complete composer at the bottom. Ordinary prompts, the native placeholder, a permission footer, and up to two statusLine rows continue to work. A human draft, unsubmitted `/compact`, or slash menu left across a restart now fails as not written instead of receiving appended business text; handle it and retry. Once any chunk, soft newline, or Enter has been attempted, an external change remains an unknown outcome: Dutydeck does not clear it, press Enter again, or resend. No persistent field or migration is added. tmux reads and writes are not atomic, so concurrent writes from every other terminal are not claimed to be eliminated.

- **Mutual exclusion between automatic compaction and terminal raw writes**: compaction installs its maintenance fence before the first await, waits a bounded time for an already-started terminal write to settle, rejects new raw writes as not written, and checks again before the final Enter. A timeout before maintenance is written is not submitted; after `/compact` was written or Enter was attempted, a conflict keeps maintenance unknown and blocks later input until the old write settles. Stop, detach, and cancellation interrupt the wait, and business input is never automatically resent. Ordinary input gains no fixed delay.

- **Setup terminal preflight no longer migrates an old database**: after detecting a terminal Agent, setup now reads `dutydeck.terminal_backend` through a read-only SQLite query instead of opening the repository layer. It does not run migrations, write control tables or change the schema version, and a later invalid `--cwd` or cancellation leaves the old database unchanged. A missing database, `configs` table or setting key uses the tmux default; an invalid setting produces a read warning and skips the tmux probe. No command, setting or database migration is added.
- **Doctor isolates invalid bot entries individually**: `lark.exposure` now skips only the invalid entry, reports its count and continues evaluating every valid bot. Dangerous combinations such as non-loopback unauthenticated access, full trust, broad high-risk scope and disabled risk control retain their fail/warn instead of being downgraded to skip because another array entry is broken. A wholly unparseable configuration still degrades, with repair guidance in the separate Lark configuration finding.
- **Doctor checks socket state even when the service is stopped**: when the daemon record names a systemd unit, doctor follows `TriggeredBy` to each associated `.socket` even if the service is not running, then queries `ActiveState` and `SubState`. Only `active + listening` counts as listening. Failed queries, missing properties and contradictory states become unknown, and `lark.exposure` skips rather than guessing safety from a loopback address in `.env`. Check the socket's actual address in `ListenStream=` manually.

- **Option descriptions for Claude native questions (card layout change)**: for Claude native questions with `description`, the card moves each explanation from the end of the question body to below the corresponding option, and the body no longer repeats it. The description is optional plain text of up to 1000 characters; it counts toward the whole-card budget and stays in the text fallback and full-text attachments. Questions without descriptions and stored records keep their layout; request IDs, answer values and timeouts are unchanged. Older builds ignore the field and keep showing label/value.
- **Lark cancellation and interruption cards can name the actor**: when the ledger records an explicit interrupt actor, the result card resolves that open_id once and adds "由 <name> 取消" if a member name is available. Lookup failures, insufficient permission, and unresolvable bot or system actors retain the original wording without blocking terminal delivery; queued cancellations without actor evidence do not guess the requester. The name or fallback decision is frozen with the card input, so delivery retries, restart reconciliation and old-card repaints do not repeat the lookup. Card callbacks and ledger fields are unchanged, and no new setting is required.
- **Retrying an unknown queue / interrupt send outcome**: when the server accepted a submission but the browser missed the response, retrying the same unchanged draft snapshot reuses its idempotency key and returns the original task instead of executing it twice. An acknowledged submission, an edited snapshot, or “requeue at the back” uses a new key. `steer` is never retried automatically; inspect existing tasks after an unknown outcome. Clients that omit `idempotencyKey` behave as before, while explicitly sending it with `steer` returns 400 before dispatch.
- **Web login cookies on different ports of one host**: a Host with a valid explicit port now uses `dutydeck_access_<port>`, so logging in or out on one port no longer overwrites another port's cookie. A Host without an explicit port keeps `dutydeck_access`. Legacy cookies are still accepted only after validation against the current instance. With an explicit port, an additional shared legacy cookie is cleared only after such validation; the same-named cookie without an explicit port keeps the existing logout behavior. After rolling back, a browser that has only the new port-scoped cookie must log in again.
- **Long text in user bubbles**: long URLs and unbroken characters wrap inside user bubbles and their Markdown subtrees instead of causing page-level horizontal overflow on narrow screens. Agent output, code-block scrolling, and copied text are unchanged.

- **Duplicate progress from the same tool after final text (IN6-01)**: a small number of turns that previously failed now retain final text produced after a tool started. Only a repeated non-terminal `tool_call` with the same non-empty id after that text is ignored. Opening text before the tool, `tool_result`, `thinking`, calls with no id or a different id, and terminal calls keep their previous failure semantics. Stored events and the output digest are unchanged; no setting or database migration is needed.

- **Verification and schedule pre-check commands settle on main-process exit (BM6-01, behavior change)**: when the main shell succeeds but a background descendant still holds stdout or stderr, verification and schedule pre-check commands no longer report the main process as timed out. A pre-check previously blocked by this false timeout may now pass and fire a schedule once. One occurrence advances once; recovery after a pass continues with the original idempotency key and does not rerun that passed pre-check. Real main-process timeouts, non-zero exits, the result structure and exit-code meanings are unchanged. Dutydeck still sends SIGKILL to same-group resources after main-process exit and waits a bounded time for group exit and pipe drainage. A surviving same-group resource or observable undrained pipe still produces a cleanup error and blocks the run. Descendants that both escape the process group and redirect their pipes are not promised to be cleaned up.

- **Claude background Agent generations after follow-up (BM6-06)**: for Claude sessions that support `resumedAgentId` / `revivedAgentId`, follow-ups now create run generations using the notification's own timestamp and transcript position, so background counts and completion notices can differ from older versions. Late completion from an old generation cannot clear the new one; equal or missing timestamps never cause a guessed revival. Replay is idempotent, follow-up instructions are not resent automatically, and ordinary Bash / Monitor behavior is unchanged.

- **Schedules with a temporarily unavailable Agent environment (EV6-01)**: `AGENT_UNAVAILABLE` no longer causes a fresh-session retry or disables a schedule on a consecutive-failure streak. The occurrence and same-cause notices are still recorded, a later normal scheduled run can make progress, and the streak clears after recovery. Accepted or unknown execution is reconciled first; model-content failures, permission denials, user-requested stops and other error policies are unchanged.

- **Scheduler logs for slow work items (EV6-02)**: one-second callbacks are skipped while the previous tick is still running instead of adding wrappers. Log counts and durations can therefore be lower and now describe only real progress; this is not a throughput claim. Direct tick calls still share a Promise, and work-item timing, persistent state and recovery semantics are unchanged.

- **Abnormal-exit history and rollback**: `last-abnormal-exit.json` now has optional 10-entry `history`, deduplicated by runId+database, plus `lifecycleRuns`/`cleanExits`, each also deduplicated by runId+database and bounded to the latest 10 generations. Single-value `lifecycle`/`clean-exit` remain the current-generation compatibility view, and the top level remains the latest legacy `fatal|startup` record, which older builds can still read. However, an older build that writes another abnormal record drops the new history and lifecycle/clean-exit metadata, so rolling back does not preserve that history. Linux/systemd can add SIGKILL after an exactly matched exit record; launchd enrichment is unverified and not declared supported.
- **More actionable newer-schema errors**: `DATABASE_SCHEMA_TOO_NEW` and backup schema mismatches now include the database version, the version supported by this build and the read-only `dutydeck database execution-status --database <database-path>` command with the actual path. Opening is still refused; no automatic migration or downgrade occurs. Switching to older code is not a database rollback, and restoring a backup loses writes made after that backup.
- **Doctor exposure combinations (CT6-10)**: the new `lark.exposure` finding evaluates listener address, explicit local-only, local/token/open authentication, socket activation, full trust, high-risk user scope and risk-control mode together. It adds warn/fail only when non-loopback unauthenticated access coincides with runnable full trust, broad high-risk scope and weak risk control; normal configurations gain no new failure. Reports contain only non-secret scope categories and counts and never edit `.env`, units or bot configuration. Unknown socket addresses and unreadable bot configuration degrade to skip rather than guesses. Existing checks such as `access.posture` and rollback behavior are unchanged.

- **Claude guards now use launch records and skip Node when no policy exists**: each actual Claude launch or relaunch, including a resumed conversation, records the guard wiring in that launch's settings and the capability probe result from that moment. Later protected turns and terminal adoption after a service restart use only this record; they neither probe the on-disk CLI on every turn nor scan historical settings that the process never loaded. A later CLI upgrade cannot reject an older running process, and a downgrade cannot make a process launched without `onFailure: "block"` incorrectly trusted. A failed startup probe stays with that launch and is not retried on every turn. After upgrading from an older build, a still-running terminal without a launch record cannot prove its actual configuration, so protected sends remain rejected; reopen the session (`/new` in Lark). The credential guard also exits directly from the shell without starting Node when the session ID is empty or the turn's policy file is missing. An existing file is still read, and read errors, malformed JSON and script failures still block. No setting, command or database migration is added.

- **Blocking Claude guard failures requires official Claude Code 2.1.295+**: Dutydeck-generated credential and plan guards add `onFailure: "block"` on official Claude Code 2.1.295 and later. Timeouts and failures not already covered by the existing `|| exit 2` no longer return to the ordinary permission flow; policy read/JSON parse errors and a missing script for an active plan are rejected too. Older versions, failed probes and unverified forks do not receive the field. Protected turns still run, guard timeouts keep their previous behavior, and explicit denials and script crashes remain blocked by `|| exit 2`. Resumed or adopted terminals on supported versions are checked for the marker, exact matcher, command type and actual `onFailure` shape; older versions are not treated as unwired merely because that field is absent. Ask relay, PermissionRequest and user hooks are unchanged; there is no new setting, command or database migration.

- **New read-only logs command**: `dutydeck logs [-n N] [--unit <unit>]` shows the last 50 lines by default and accepts 1–10000 lines. Without `--unit`, it reads the end of the current daemon log file; with `--unit`, it reads that systemd user instance through a streaming `journalctl --user` child process without a shell. Both sources retain at most the last 256KiB, and follow mode is not included in this first version. With `--unit`, the command asks `journalctl` for the most recent N unfiltered lines, then filters suspected secrets, so fewer than N lines may be printed. Ordinary lines, errors and multiline stacks retain their order, while lines that appear to contain secrets are omitted. A unit that does not exist or has no matching log entries produces a clear error. The command writes no configuration and changes neither the original logs nor the database. Rolling back only removes the new command; existing logs are unaffected.
- **Plugin updates show executable command changes**: `plugin update` now lists slash commands, Agent launch configurations, and hook execution specifications with before/after SHA-256 digests, and JSON output gains `changes`. Interactive terminals ask the user to trust these changes again; declining leaves state unchanged. Non-interactive updates without `--yes` only print the changes and gain no new failure, while `--yes` behaves as before. Description-only edits produce no digest change, and an unchanged candidate is not prompted for again. The active artifact still requires the existing `plugin activate` flow; update never runs candidate commands.
- **`dutydeck update` accepts an exact version**: run `dutydeck update 1.2.3`; the version argument is mutually exclusive with `--dist-tag`, and omitting it still uses `latest`. Installation, verification, or restart failures append the manual rollback steps `npm install --global @byted/dutydeck@<actual previous version> && dutydeck restart`, which reinstall the old package directly without relying on the old CLI understanding `update [version]`; if no safe command can be generated, the error says so. No rollback runs automatically.
- **tmux preflight**: doctor adds `terminal.backend`, which checks the tmux command, version and session create/verify/cleanup on an isolated temporary socket without touching the default server. Every call uses `-f /dev/null` and a private `XDG_CONFIG_HOME`, and the session runs only a controlled command, so system and user configuration is not loaded. Setup adds one equivalent warning for terminal Agents that need tmux; a missing or broken tmux does not prevent configuration writes. ACP-only and Herdr configurations do not treat it as fatal.
- **First-start guidance without a bot**: an interactive foreground start with no readable bot configuration now prints setup, doctor and the actual Web address below the listening line every time the condition holds. No shown-state setting is added. `--json`, non-TTY output and daemon children omit it, and a CLI missing from `PATH` gets generic repair guidance.
- **Setup delivery checks are now user-initiated**: the dedicated confirmation defaults to No. After acceptance and temporary-listener startup, the terminal shows a one-time UUID for the user to send to the bot in a Lark direct message. Only a user DM containing this UUID within the bounded wait is accepted; the bot replies to that message with the same UUID. Lark accepting the reply means inbound passed and outbound was sent, and the user still confirms actual receipt in Lark. A timeout means inbound is unverified and nothing was sent. `--yes`, non-interactive mode and `--json` skip the check. The flow does not change bot scopes or persist a user's open_id.

- **Idle compaction in Claude-family terminals now uses native maintenance input**: the existing `idleCompactEnabled` / `idleCompactHours` settings are unchanged, and there is no new setting or database migration. The next message after the threshold first runs `/compact`; success requires its input receipt, a same-session manual boundary and a generation-bound summary. Maintenance creates no business turn. Explicit failure and unsupported CLIs continue the original message, while cancellation does not write it. If terminal recovery cannot be proven, the message fails as not submitted instead of becoming an unknown result that is automatically resent. Every later input rechecks the terminal and proceeds after recovery; if it remains unproven, that input is not written and you can retry later or use `/new` for a fresh session. Claude Code 2.1.220 is verified. Rolling back does not undo native compaction that already completed; the older program treats this terminal maintenance capability as unsupported and continues later business messages.

- **tmux session lifecycle**: on Linux, if cleanup removes a tmux socket while its old server is still running, startup now refuses to create another server with the same name and explains how to rebuild the socket with `SIGUSR1` or end the old server. Two CLIs will no longer attach to one conversation. With `remain-on-exit`, the next start reaps a Dutydeck-owned session only when every pane has exited; a session with any live pane is retained. Non-Linux behavior is unchanged.

- **Lark session notices are posted anew when the original message was recalled**: when a session notice (queue blocked, queued too long and cancelled, outcome unknown) replies to an original message that has been recalled, it is now posted as a new message in the same chat (group or private chat) instead of being lost, and the service log records one warning. Schedule notices stay on their frozen report target like the schedule's other deliveries and are not redirected; failures with an unknown outcome such as timeouts are not redirected either. No configuration is needed.
- **Claude sessions in long working directories**: when the encoded working-directory path exceeds 200 characters, Claude Code (2.1.224 and later) writes its transcript to a truncated, hash-suffixed project directory that Dutydeck previously could not find. Both the new and the old directory are now read, and the specific session file and its content proof decide: such sessions resume after a service restart, and results and usage are read from the transcript. Their usage now counts, which may trigger the monthly cap; completion is judged from the transcript instead of the screen; and when the session file is found but its Dutydeck marker cannot be read, or the same session has a copy in both directories that cannot be told apart, resuming is refused explicitly instead of silently starting a new session. Paths of 200 characters or fewer behave as before; after rolling back, the older program only reads the untruncated old directory and leaves nothing behind.
- **Turns started by a scheduled task inside a Claude session**: when a task created with `CronCreate` in a Claude terminal session fires, Claude starts a turn on its own. Its answer used to be taken as output of the previous message or of the message waiting to start; it now appears separately in the session as a background result, counts toward no message's result, and does not end the turn in progress early. Only the scheduled-fire records written by Claude Code 2.1.318 are recognised; other automatic wake-ups behave as before.
- **New bot setting `claudeAutoMemory`**: defaults to `inherit`, so nothing changes. With `off`, Claude processes started afterwards in group chats of a bot with session memory on run with Claude's own auto memory disabled; existing sessions pick it up the next time they start and resume the same conversation (see cross-session memory in [features.md](features.md)). The `features.md` promise that groups cannot see each other's memory now refers to Dutydeck group memory only. After rolling back to an older build the setting has no effect; saving that bot's configuration with the older build drops the key, and it reads as `inherit` after upgrading again.
- **Lark sessions continue across differently written workspace paths**: when a bot's configured workspace and the workspace a session recorded are written differently (a symlink, a trailing `/`, or `..`) but point to the same directory, a restart now continues the original session instead of opening a new one; identical paths behave as before. On the first restart after upgrading, a still-active session that was skipped because of the path spelling may be picked up again (the most recently created one in the same scope), resuming context that may be days old; send `/new` in Lark if you do not want to continue it. Older sessions that were replaced this way were never stopped and are not cleaned up automatically; archive them in the Web console (archiving also stops a session that is still running). `/status` for an isolated worktree session no longer shows "configured workspace" and instead names the workspace it is based on.
- **Migration records include names**: the database now records each migration's name. The first start after upgrading fills in names for existing records and builds any missing v47–v49 indexes. If a recorded name later differs from this build's migration at the same version (the database was upgraded by a build from another branch), start-up stops with `DATABASE_SCHEMA_LINEAGE_MISMATCH` instead of skipping that migration or failing halfway; restore a snapshot taken before that build, or keep using the build that wrote it. Older program versions can still open a database whose records carry names.
- **History summary index (v47)**: upgrades add a read index on the events table so session history summaries load faster; history data is unchanged. Building it on first start takes time proportional to the number of events: a database with about 240,000 events needs roughly 3.5 extra seconds on a cold cache, and later starts are unaffected. The index takes about 1 MB of disk per 10,000 events. Older program versions reject the newer database schema after migration.
- **Schedule pre-check commands (upgrade and rollback)**: the new pre-check command is stored as a separate record. The plan itself gains no field and its condition stays "always", so no database migration is needed and plans without a pre-check behave as before. After switching back to an older version, it still reads the plan but does not know the pre-check: the command no longer runs and the plan wakes the Agent every time; after upgrading again, the saved command applies again. Writing it as a new condition kind inside the plan would make the older version's strict parser treat the whole plan as an invalid record (no longer listed, an error when read by id, never fired again), which is why it is stored separately. Usage: [Scheduled tasks](web-console.md).
- **Stability**: terminals and live streams reconnect through the existing flow after connection failures or handshake timeouts; instance proxy configuration accepts only `http:` URLs. Scheduled mandates, memory, plugins and history use verified automatic capacity retry results while manual retries remain separate. PR background follow-up errors are logged, and later polling can recover. No new setting is required. After a lease handoff, the current executor can continue preparing scheduled mandate tasks that have not started execution and deliver results confirmed as not yet sent; scheduled tasks and CI continuations blocked in older versions by verified automatic capacity retries can resume one delivery attempt, while other unknown states remain unresolved.
- **Long conversations and live updates**: connection and record catch-up have separate statuses. Completed turns load summaries first and full records on expansion; raw logs can be explicitly viewed, copied and exported in full. No new setting is required.
- **Lark message handling**: receipt reactions start promptly while task preparation continues; late reactions are cleaned up after the task ends. A context timeout stops subsequent reads for that turn, preserving failure feedback and the material available to a retry. Concurrent authentication for the same bot is shared, while each request keeps its own deadline and retry budget. Closed historical interaction cards and result acceptance feedback require fewer repeated reads; history, failed-operation retries and deadline reminders remain available.
- **Native log reads**: when Codex switches logs within the same native session, usage reads periodically locate the current log again. Codex / TraeX session-source verification now yields between native log chunks, retaining the existing complete-log scan and ownership checks while other requests proceed.
- **Secret storage locks**: the system releases a secret modification lock when its connection closes or its process crashes. Upgrade all secret writers together; mixed old and new versions do not guarantee mutual exclusion. Legacy `.lock` files no longer block new versions, and new `.lock.sqlite` files must be retained. The secret storage package now depends on the project's existing `better-sqlite3`, whose native module must be available at installation.
- **Long-session history index (v49)**: in addition to the v47 history summary index, upgrades index user messages so splitting turns and building jump labels no longer parses every event. Building the index reads existing events once, so databases with many events take somewhat longer to upgrade; history is not rewritten. The session history API adds `GET /api/sessions/:id/history?tail=<1–1000>` (summaries of only the latest turns, plus every turn's position) and `GET /api/sessions/:id/history/turns?from=&through=` (summaries of completed turns within a sequence range); `/history` without parameters returns the same content as before. Older program versions reject the newer database schema after migration.
- **Lark inbox index (v48)**: upgrades add indexes for reading Lark inbound message records and pruning them by retention; existing records are not rewritten. Older program versions reject the newer database schema after migration.
- **Read indexes (v42)**: upgrades add indexes for sessions, usage events, automation and question state while retaining history. Persisted questions are read by ID; questions awaiting an answer remain immediately available. Older program versions reject the newer database schema after migration.
- **Terminal size**: resize requests accept positive integer rows and columns. Invalid requests return an error and leave the connection usable.
- **Work item concurrency**: Work item steps are limited to 6 executing globally and 3 per work item; their preparation and accepted queues are limited to 12 globally and 3 per work item. Pure queueing uses neither an execution slot nor the one-hour execution deadline. Workspace exclusion and conservative occupancy for unknown execution remain in effect.
- **Work item recovery**: steps blocked by an unknown execution resume remaining work on the next scheduler pass after the recovery API verifies the original execution and confirms success. A confirmed failure allows an explicit step retry. Permissions and configuration are rechecked; completed steps are not rerun. Unknown results, cancelled work and review stop decisions remain blocked.
- **Work item plan revisions**: upgrades refresh the work-item index so that steps removed by a revision keep their child-session ownership; existing records are not rewritten. Older program versions reject the newer database schema after migration. See [Goal plan revisions](web-console.md#work-plan-revision).
- **Work item history**: upgrades automatically build a scheduling index. Completed items with settled delivery no longer enter the per-second scan; history remains available and pending deliveries keep retrying. A failed delivery is retried after 1 and then 2 minutes (right away after a service restart), at most 3 attempts; after that it stays failed with the reason shown on the work item and is not resent automatically.
- **Idle overhead**: Lark process cards still refresh as soon as new events arrive; without new events they refresh the elapsed time every 10 seconds (previously every second). The hourly group sync no longer writes a version when a group name is unchanged, and leave detection covers all groups instead of the first 500. Inbound Lark message logs include the event type and event ID; member-joined events no longer trigger the SDK's unhandled-event warning.
- **Disconnect and stop recovery**: cross-instance live streams can reconnect after an upstream disconnect. Shutdown closes proxy connections and pending Lark listener connections. A failed terminal stop can be retried to release the process.
- **Background tasks**: blank answers no longer block later memory extraction; group notification limits use the complete hourly window; cron handles leap days across years and repeated daylight-saving times. Enabled recurring schedules with a missing next execution time are repaired automatically; completed one-time schedules are not rerun.
- **Web task state**: consecutive gaps in live events continue to be filled, with task state refreshed as well. A late task-list response no longer overwrites newer state received for the same run.
- **Terminal backend settings**: selecting Herdr checks its version asynchronously, so the service can handle other requests while validation waits.
- **GitHub read limits**: PR issue and inline comments support pagination, with a shared limit of 100 pages and 8 MiB. Exceeding it fails the whole read instead of returning partial comments. Each JSON response is limited to 2 MiB and each log download to 8 MiB of actual bytes; oversized reads are cancelled. Oversized logs are omitted while failed job and step summaries remain available. Logs for up to 10 failed jobs are read concurrently; results keep job order and an individual log failure does not affect other logs.
- **CLI startup**: reduced startup overhead for local management commands such as `secret`.
- **CI env vars moved to plugins**: see the upgrade paragraph under Plugins.
- **Alert triage is now the built-in scenario pack `alarm`.** The group phrases, confirmation card, sources, levels, dedupe and hourly cap are unchanged; existing subscriptions are converted to `alarm` bindings during the upgrade, and confirmation cards sent before the upgrade still work. Three things change: the alert text in the triage prompt now follows the instruction as untrusted material; the earlier conclusion that correlation passes to the agent is untrusted material too; duplicate checks read only this pack's triage records, so a busy group no longer makes the same alert get triaged twice. The CLI uses `scenarios=`; `alarm=` is kept for one release.
- **The alert triage pack is now 1.1.0 and topics under alerts can take follow-ups.** In multi-bot groups a topic opened under an alert from the source bot used to count as another bot's topic, so un-@ follow-ups were never answered. It no longer does: the bot stays out only when another bot has already posted in the topic, or the topic runs past 4 pages or cannot be read. Two bots deciding at the same moment may both answer. Existing bindings keep working with the new version without being confirmed again.
- **`model` scenario packs now load.** They used to be rejected at load; see `plugins/team-faq` for an example.
- **After the database reaches v38, older versions cannot open it.** v38 stores group duties as per-pack bindings. Going back to an older version fails at start with `DATABASE_SCHEMA_TOO_NEW`. If something goes wrong, fix forward or restore the database snapshot taken before the deploy; every write after that snapshot is lost.
- **The enforced-mode workspace hook now checks credential access (v3).** Bots that already use enforced mode need the hook reinstalled ("Configure hook" in the Web settings, or `dutydeck settings bot install-hook <app-id>`) before the check covers Codex over ACP; until then, saving that bot's settings reports that the hook is not ready. Bots whose default agent is a Claude Code terminal agent (including custom ones such as ccflash) or ACP Claude launched by Dutydeck are not affected and can now turn on enforced mode directly.
- **Agent commands use `dutydeck agent`.** Each turn supplies a command prefix bound to that execution. Status, task and queue reads return to the Agent for its answer instead of posting a result card. See [Agent CLI](cli.md#agent-cli-dutydeck-agent) for the required turn binding and upgrading existing sessions.
- **Per-turn changes could be missed** when a file was edited within the same second as the last index write and kept the same size (affecting "View changes" and the `/pr` file list). Fixed.
