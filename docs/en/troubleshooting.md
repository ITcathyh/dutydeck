## Known Limits <a id="known-limits"></a>

- **Allow rules in your local `~/.claude/settings.json` bypass Lark per-action approval.** Claude terminal sessions from Lark start in `default` mode, but `permissions.allow` rules still apply, and matching actions never produce an approval card. Clear those rules if you need strict per-action approval.
- **With `/plan`, pre-approved writes on the ACP side cannot be blocked.** Planning blocks writes by rejecting every permission request the agent sends. If Claude ACP has its own allow rules (e.g. in settings) or runs in bypass mode, those actions never ask Dutydeck. Don't pre-approve writes on the ACP side when you use `/plan`.
- **Credential protection matches rules; it is not isolation.** Rewriting a command (encoding, building the path, writing a script and running it) may get past it, and in full-trust mode senders outside the allowlist can still make the agent run any command as the local user. For bots open to others, use enforced mode or don't give them full trust.
- **The high-risk command pattern matches raw text; it is not a sandbox.** Quoting, backslashes, path prefixes or subshells (e.g. `"rm" -rf`, `\rm`, `/bin/rm`, `$(rm …)`, `git 'push'`) may get past it, and so does an option in between such as `git -C . push`. It narrows exposure, like credential protection.
- Cursor terminal sessions with raw-screen output only may show an answer in playback but still be recorded as failed because normalized final text is unavailable.
- The verification gate only applies to Lark tasks and needs a command configured.
- Traex terminal mode reports no usage; Codex terminal mode records per-turn tokens and estimated cost but is not yet counted against caps. Caps don't apply to either; cost figures are estimates.
- Plain token trigger auth has no timestamp or nonce and relies on HTTPS or an internal network; HMAC-signed requests carry a timestamp and a one-time nonce (see Plugins → Security).
- Draft pages are hidden unless "experimental features" is turned on.

## FAQ <a id="faq"></a>

**Why does inserting a queued message report `Workspace is held by another session`?** Another session holds the same workspace. The message stays queued. Its execution details list the blocking sessions and reasons. If the message says `This session's workspace needs recovery`, check whether this session’s working directory was moved or replaced.

**Startup reports `DATABASE_SCHEMA_TOO_NEW`, or a backup reports a schema mismatch?** The two versions in the error are the database's actual schema and the maximum supported by this build. Copy the complete read-only command with the actual path from the error; do not point `--database` at another instance:

```bash
dutydeck database execution-status --database /path/to/runtime/dutydeck.db
```

It does not repair, migrate or downgrade the database. Prefer a Dutydeck build that supports the schema. Only after stopping every writer and checking the backup timestamp should you consider restoring it into a separate new directory for inspection. Restoring loses writes made after the backup; switching to older code does not roll back the database.

**The Web UI works, but status / doctor says the service is stopped or another process owns the port?** A foreground root command and some externally supervised entry points may have no daemon state record. Current `status` and `doctor` request `/health` and `/health/ready` on the configured host and port with short timeouts and do not follow redirects. Both responses must succeed and carry `x-dutydeck-product: dutydeck`, while retaining the existing JSON shapes: `ok===true`, plus boolean `ready` and string-array `pending` on the ready endpoint. Only the product header and both shapes together identify an unregistered foreground service and clear the port conflict. `ready=false` changes only the new foreground field, not the legacy daemon `ready` field.

This recognition requires the Dutydeck product header rather than guessing from generic JSON; it is not authenticated identity verification. HTML, `{ "ok": true }` without the header, malformed shapes, connection refusal and timeout all preserve the original diagnosis. Registered, stale and malformed daemon records are not probed, and requests are sent only over plain HTTP to loopback or a local interface. For a temporary port, copy `dutydeck --port 14310 status` or `dutydeck --local-only --port 14310 doctor`: root `--host` / `--port` / `--local-only` flags now reach status/doctor instead of falling back to 4310. An unregistered process has no daemon listener record against which to verify Lark connectivity; inspect its startup terminal rather than starting a second instance.
After identifying an unregistered foreground service, `dutydeck update` refuses before any npm call and a default-instance `dutydeck restart` does not start another daemon; `update --force` does not bypass this refusal. Press Ctrl-C in the original startup terminal and rerun the original command with its original arguments. `dutydeck restart --unit <unit>` explicitly targets systemd and does not perform this default/current-directory foreground preflight.

**Why does doctor say the cause is pending enrichment after SIGKILL?** A killed process cannot run an exit handler, so the next generation first records an abnormal exit because the previous generation has no `clean-exit` marker. On Linux/systemd it queries a bounded journal asynchronously and adds `SIGKILL` only when unit, boot, PID and start time align exactly. A missing, inaccessible, timed-out or ambiguous journal leaves the basic record intact and never blocks readiness. Clean stops and planned restarts create no abnormal record when the clean marker is written successfully. If that write fails, the process prints an explicit warning to stderr and preserves its original exit code, but the next generation may still conservatively record an abnormal exit because the marker is missing; check the type, permissions and writability of the database directory and `last-abnormal-exit.json`. A previous PID that is still alive is not reported as crashed. Only the latest 10 records are retained; launchd enrichment is not supported in this release.

**The bot doesn't react in Lark?** Run `dutydeck doctor` (it checks the Lark listener and each default Agent's `--version`); make sure the app has the Bot capability and a long-connection event subscription (`im.message.receive_v1`); in groups, `@` the bot unless the topic is already owned (levels above "mention only").

**The long connection dropped and never came back?** The Lark SDK reconnects on its own first. If a reconnect stays stuck (e.g. a proxy accepts the connection but never answers) for more than 10 minutes, Dutydeck rebuilds just that long connection without touching running sessions, and rebuilds it again after the same interval if it is still stuck. Set the interval with the daemon environment variable `DUTYDECK_LARK_RECONNECT_STALL_MS` (milliseconds, minimum 60 seconds, `0` turns it off). When `doctor` says "Dutydeck 已在 … 重建长连接，仍未恢复" (the long connection was rebuilt at … and has not recovered yet), check the network and proxy path to the Lark Open Platform.

**`Persisted key policy violation`?** ACPX persists session options and requires `snake_case` keys. Don't write uppercase env names into session options.

**A custom Agent is missing or its command is not found?** The daemon does not read your shell aliases, and an Agent whose `command` cannot be found is not registered. `dutydeck doctor` names it; use an absolute path in `DUTYDECK_AGENTS_JSON` and `dutydeck restart`.

**Session fails because of per-action approval?** The Agent can't do Lark approval (only ACP and Claude Code / Seed / Relay terminal modes can). Either `dutydeck settings bot set <appId> permissionMode=full-trust fullTrustConfirmed=true`, or switch to an ACP / Claude terminal Agent.

**Several bots on one machine?** Yes; each has its own workspace, Agent and Lark credentials.

**A peer address change did not take effect, or a same-host peer is temporarily unavailable?** The primary reads `DUTYDECK_INSTANCES_JSON` once while assembling the service. After adding or removing a peer or changing its `url`, restart the **primary**; restarting only the peer does not reload that JSON. `/api/instances` only confirms loaded `id` / `name` entries and does not return URLs. Check the primary configuration and verify a known proxied request; do not treat this list as proof that a new address is active. A peer database path is not part of this JSON and does not require an instance-list edit. Each peer needs its own database and port, must start with `--local-only`, and uses an `http:` address such as `http://127.0.0.1:4311`. The primary strips its own login and origin headers before forwarding, so a remote address or one requiring a different authentication flow is not a valid peer setup. This is a static list with no dynamic discovery or health-based removal: proxy requests fail while the peer is unavailable, but its entry remains. Restore the peer, or correct the address and restart the primary; health checks do not rewrite the configuration.

**Claude Code / CCFlash finished, but the Lark card reports missing tool results?** Older versions could interpret historical API request snapshots in CLI logs as current tool calls. After upgrading, these snapshots neither enter the execution timeline nor acknowledge the current prompt. Actual tool calls without results still cause a failure status.

**A Claude terminal session reports "Claude 启动尚未就绪（最后屏幕：X）" (startup not ready, last screen: X)?** Within 30 seconds Claude showed neither an empty composer nor a recognized confirmation page. The task was not written, so it is recorded as failed and can be resent after you deal with the cause. X is the category of the last screen:
- **目录信任页未能核对** (trust page could not be verified): the screen is on the folder-trust page, but its folder does not match the session folder, the page is incomplete, or under `full-trust` the page was recognized but the automatic confirmation keys never took effect. Open the terminal and confirm the folder; if the folder is not what you expect, check the working directory in the session or bot settings.
- **空白** (blank): the terminal shows nothing. Check that the Claude command starts, then read the daemon log (`journalctl --user -u <unit>`).
- **未识别** (unrecognized): the screen shows a prompt Dutydeck does not recognize. Open the terminal and handle the current prompt.

A long folder that breaks mid-word onto several lines of the trust page is still recognized as the current folder: under `ask` / `approve-reads` you get "Claude 正在确认此目录是否可信" (Claude is asking whether this folder is trusted) and confirm it in the terminal; under `full-trust` the folder is trusted automatically. A folder with spaces that wraps at a space may not be recognized; startup then times out with 目录信任页未能核对, and confirming trust once in the terminal is enough.

**The tmux socket was deleted but the old terminal is still running?** On Linux, `/tmp` cleanup can remove the tmux socket file while its server and panes survive. Dutydeck refuses to start a second server for that name, so two CLIs cannot operate on one conversation. Follow the tmux manual to send `SIGUSR1` to the original server and rebuild the socket, or end that server before sending the message again. Point `TMUX_TMPDIR` at a directory that is not cleaned, or exclude the tmux directory from `systemd-tmpfiles`. Non-Linux systems keep the previous behavior because this kernel check is unavailable. With `remain-on-exit`, the next start reaps a Dutydeck-owned session only when every pane is dead; sessions with any live pane stay available for inspection.

**Logging in or out on different ports of one host affects the other port?** Upgrade to the version with port-scoped cookies. A Host with a valid explicit port uses `dutydeck_access_<port>`, while a Host without one keeps `dutydeck_access`. Legacy cookies are accepted only after validation against the current instance. With an explicit port, an additional shared legacy cookie is cleared only after such validation; the same-named cookie without an explicit port keeps the existing logout behavior. After a rollback, a browser with only the new port-scoped cookie must log in again; never copy another instance's token into this one.

**How do I retry a lost send response without executing twice?** For queue or interrupt, if the server accepted the submission but the client missed the response, retry the same unchanged draft snapshot: the idempotency key returns the original task. Editing the submission, intentionally sending again after acknowledgment, or choosing “requeue at the back” creates a new task. `steer` is never retried automatically. After an unknown steer outcome, inspect the existing tasks and execution record before deciding what to do next; do not immediately resend.

**An answer is visible, so why did the turn still fail?** Distinguish final text from opening text before a tool call. Only a repeated non-terminal `tool_call` with the same non-empty id is ignored, and only when that tool started before the final text. Opening text such as "I'll take a look" is not a final answer. A later `tool_result`, `thinking`, a call with no id or a different id, or a terminal call remains a boundary: without newer final text, the turn still fails. This interpretation does not change the stored events or output digest.

**Why did a successful verification or schedule pre-check used to time out, and what does a cleanup error mean now?** The old executor kept the main timer running until every pipe closed, so a background descendant holding stdout or stderr could produce both exit code 0 and a false timeout. The main shell's `exit` now settles the main process, and that false timeout no longer occurs. A pre-check previously blocked by it may now pass and fire one schedule occurrence. Dutydeck still waits for same-group processes to exit and for pipes to drain within a bounded cleanup period. A surviving group or undrained observable pipe produces a cleanup error and blocks the run; check for background descendants and inherited pipes. A descendant that both leaves the process group with `setsid` and redirects its pipes cannot be proven cleaned up by this executor. Once a pre-check passes, one occurrence advances once and recovery continues with the original idempotency key without rerunning that passed command.

**How are completion notices and run counts matched after resuming a Claude background Agent?** A `resumedAgentId` or `revivedAgentId` starts a new generation only when its notification timestamp is strictly later than the latest completion. A late notice from an older generation stays with that generation and cannot complete the new one; duplicate notices and transcript replays do not count twice. Equal or missing timestamps and ambiguous source order never cause a guessed revival. If the Claude version does not write these fields, an old notice alone does not create a new generation and Dutydeck does not resend the follow-up instruction.

**Will a schedule retry in a fresh session or become disabled when the Agent environment is temporarily unavailable?** `AGENT_UNAVAILABLE` has its own classification: the occurrence and coalesced same-cause notices are recorded, while the schedule stays enabled for the next normal scheduled time. There is no fresh-session retry and no streak-based disable for this classification; the streak clears after a successful run. Accepted or unknown work is reconciled rather than replayed. Model-content failures, permission denials, user-requested stops and other environment errors retain their existing policies. If the problem persists, run `dutydeck doctor` to check the Agent command and availability.

**How should scheduler counts and duration logs for a slow work item be read?** While an earlier tick is still making progress, later one-second callbacks are skipped rather than wrapped again. Logs therefore record real progress and its duration, not a stack of wrappers; this is not a throughput claim. After a rejected tick, a later normal tick can continue. Direct calls to the same tick still share the original Promise, and persistent state and recovery semantics are unchanged.

**No UTF-8 locale on the host?** Dutydeck forces every tmux client it launches to use UTF-8 (`-u`), so terminal sessions are still detected correctly and Chinese or other non-ASCII text is not replaced with underscores because of the host locale.

**`doctor` reports `lark.exposure`, or its listener address is unknown?** The finding becomes warn/fail only when non-loopback unauthenticated access, runnable full trust, broad high-risk scope and weak risk control coincide. Follow the report: use `dutydeck setup --local-only`, set an access password and re-enable authentication, or run the suggested `dutydeck settings bot set <appId> permissionMode=ask fullTrustConfirmed=false`. To retain full trust, run `dutydeck settings bot install-hook <appId>` before enabling `riskControlMode=enforced` and narrowing the high-risk list. A list does not restrict execution under `off`, and `guidance` is not enforcement. An invalid bot entry is skipped individually and counted while valid bots are still evaluated, so it cannot turn another bot's dangerous fail/warn into skip; repair that entry using the separate Lark configuration finding. For an unknown address, `LISTEN_*` or unit `TriggeredBy` proves only the activation relationship, not the inherited descriptor's address. Even when the service is stopped, doctor follows `TriggeredBy` to the associated `.socket` and checks `ActiveState=active` with `SubState=listening`; failed queries and incomplete states also remain unknown. The finding then skips rather than treating the `.env` host as fact. Check the socket unit's `ListenStream=` against the service `--host` / `--port`, then rerun `dutydeck doctor`. Reverse proxies, firewalls and port forwarding are outside this observation.

**A Claude guard times out or fails to read its policy, or restored settings are reported as incomplete?**
- **Guard timeout**: only official Claude Code 2.1.295 and later uses `onFailure: "block"` to block tool calls when a guard times out. Credential-protected and `deny-all` turns still run on older versions, failed probes and unverified forks, and timeouts keep their previous behavior; explicit denials and script crashes remain blocked by `|| exit 2`. Upgrade official Claude Code and reopen the session if timeout blocking is required.
- **Incomplete restored settings**: each actual Claude launch records the guard marker, exact matcher, command type, `onFailure: "block"` in that launch's settings and the capability probe result from that moment. Adoption after a service restart accepts only the valid launch record written by that real launch: it starts with `lstat` and accepts only a regular file. Missing, malformed, invalid, unreadable, symlink and dangling-symlink records are rejected without historical JSON settings snapshot fallback or `/proc` argv adoption. Valid records continue to recover; valid older-version or failed-probe records are checked against actual guard wiring rather than rejected solely for lacking a newer field. If a protected send is rejected because its record is missing or invalid, reopen the session (`/new` in Lark) to generate complete settings and a record.
- **Policy or script failure**: an empty session ID exits directly from the shell without starting Node. For a valid single-component ID and normalized policy path, only a provably missing (`ENOENT`) policy uses the shell fast path. Abnormal IDs, overlong paths, permissions, symlinks and other uncertain states go through Node fail closed; not every failed `test` or missing-policy shape is a fast miss. A disabled risk policy or no unauthorized match also allows the call. Read errors for an existing file, malformed JSON and a missing script for an active plan block the operation. Check the file types and JSON under `.dutydeck/security/sessions/`, the session-private settings directory and machine load. Error text does not echo sensitive policy values.

**How do I read recent service logs, and why are some lines missing?** Use `dutydeck logs` for a regular daemon or `dutydeck logs --unit <unit>` for a systemd user instance. Both request 50 recent lines by default; use `-n 200` for more. With `--unit`, the command asks `journalctl` for the most recent N unfiltered lines, then filters suspected secrets, so fewer than N lines may be printed. The command prints one snapshot rather than waiting for new entries. Ordinary lines, errors and multiline stacks are retained, but any line that appears to contain a token, password, credential or Authorization value is omitted to keep it out of terminal records. If the regular daemon log file does not exist (ENOENT), the error includes its full path: a foreground root command has no daemon log, so inspect its startup terminal; for a systemd-managed service, use `journalctl --user -u <unit>` or `dutydeck logs --unit <unit>` to read that unit's journal. The path and other read errors are unchanged. If the command reports that `journalctl` is unavailable, check that systemd is installed and `journalctl` is on PATH. If it reports that the unit does not exist or has no matching log entries, check the unit name; a correct name means that unit currently has no matching logs. A regular daemon does not need `journalctl`: omit `--unit` to read its current daemon log file.

If dispatch, send, or steering returns `OPERATION_REVOKED` or `DRIVER_STOP_UNVERIFIED`, find the warning by `sessionId` and read its `code` and `reason`. A revocation reason names the triggering event in `code` and the component or method in `by`. Each process logs a given session, error code, and reason once. Diagnostics from drivers, terminal backends, and stop rechecks also include `component`, `location`, and `error`.

**Doctor's `terminal.backend` check failed?** Use the reported stage. If the command is missing, install tmux or fix `PATH`; if `tmux -V` fails, check that the binary is executable and matches the machine; if private-session creation or verification fails, check temporary-directory permissions and the tmux server log. The check uses only an isolated temporary socket with `-f /dev/null` and a private `XDG_CONFIG_HOME`, and its session runs only a controlled command. It does not read system or user tmux configuration, connect to or stop your default tmux server, or install software. Setup's equivalent preflight reads `dutydeck.terminal_backend` read-only and never creates or migrates a database or writes control tables just to obtain this setting; a missing database, `configs` table or key uses the tmux default. A later invalid working directory or cancellation therefore leaves the old schema unchanged. Missing tmux is not fatal for ACP-only or Herdr configurations; only `pty-cli` terminal Agents that use tmux depend on it.

**The interactive-setup delivery check timed out or failed?** The dedicated confirmation defaults to No. After choosing Yes, wait for the one-time UUID in the terminal, then send that code to the bot in a Lark direct message. Group messages, wrong codes and bot messages do not count. A valid user DM within the bounded wait makes the bot reply to that message with the same UUID. “Inbound passed; outbound sent” means Lark accepted the reply, so confirm actual receipt in Lark. If the reply fails or its outcome is unknown, inbound still passed but outbound is unverified. A timeout means no valid DM arrived and nothing was sent. `--yes`, non-interactive mode and `--json` skip the check. The flow does not change bot scopes or persist a user's open_id.

**Why did the original message fail or remain unsent after idle compaction?**
- **Explicit failure such as insufficient context**: once the terminal is ready, the original business message continues automatically. Unsupported, untested non-Claude CLIs also continue without receiving `/compact`.
- **You interrupted the task**: only the compaction wait is cancelled; the business prompt is not written. Later messages proceed after the terminal recovers.
- **Compaction exceeded five minutes**: Dutydeck interrupts it first. Once the empty composer is proven ready, compaction is treated as failed and the original business message continues.
- **A terminal raw write was already in flight**: automatic compaction installs its maintenance fence and waits a bounded time; new raw writes are not written, and the final Enter is checked again. A timeout before maintenance is written and without a conflict is not submitted. A conflict with an in-flight raw write can nevertheless retain an unknown maintenance fence even before `/compact` was written, blocking later input until the old write settles and recovery is proven. A raw backend return means only transmission ended; recovery requires a new output revision after that write and 500ms of continuous quiet, so old idle evidence cannot clear unknown. Stop, detach and cancellation interrupt the wait; business input is not resent automatically.
- **The compaction outcome or terminal recovery is unknown**: maintenance may have been sent, but Dutydeck cannot prove that the terminal can safely accept another input. The business task fails as not submitted, not as an unknown result, and is not resent automatically. Every later input rechecks the terminal and proceeds once recovery is proven, without first rebuilding the session. If recovery still cannot be proven, that input is not written; retry later, or use `/new` for a fresh session if the problem persists. You can inspect the session terminal to see whether compaction finished or a permission or human prompt is waiting. Do not attach another Claude process to the same native session concurrently.

**Why is the task outcome unknown when Claude shows `Removed … invisible character · review and press Enter to send`?**
- Newer Claude builds remove invisible characters from a paste and hold its first Enter for human review. Dutydeck now removes the same codepoints before writing while preserving valid emoji and combining sequences; the original task prompt stored by Dutydeck is unchanged.
- Claude native keyed input may normalize NFD to NFC first, changing codepoint and UTF-8 byte counts in terminal text and receipts. Dutydeck's stored original task text is unchanged, and this Claude-specific sanitizer/NFC path does not run for other Agents; NFD filenames, hashes and exact-codepoint matches are not guaranteed byte-for-byte stability. Separately, the shared `wrapUntrusted` forged-boundary visible-space change affects every saved/dispatched caller, including other Agents that call it. It handles only forged boundaries that were not markers originally and were reconstructed by Claude cleaning. Dutydeck's own existing markers and ordinary body text outside those forged boundaries are not rewritten by this rule; Agents and content that do not call `wrapUntrusted` receive no additional processing.
- If the terminal is still showing this notice, input was written but submission was not confirmed. Dutydeck never presses Enter again or resends automatically. Inspect that session's terminal and decide whether to press Enter yourself; do not send the same message again.

**Why does a Claude task say the current composer is not empty, or become unknown after writing?**
- Ordinary long multiline Claude-family input uses one keyed submission: each logical line is chunked to at most 96 UTF-8 bytes, a hard newline becomes backslash + Enter as a soft newline, and only the final `submitInput()` is the final Enter. A soft newline is not submission, and whole-bracket paste does not trigger paste-burst folding.
- After waiting for a quiet Claude screen and before the first business byte, Dutydeck rechecks the complete composer at the bottom. An ordinary `❯`, the native `Try "…"` placeholder, a permission footer, and up to two statusLine rows are accepted. A human draft, an unsubmitted `/compact`, a slash menu, or a historical prompt without a current empty composer is not. In this case nothing was written; handle the draft in the terminal and then retry.
- Once any chunk, soft newline, or Enter has been attempted, an unreadable or externally changed composer makes the outcome unknown. Dutydeck does not press Enter again, clear the draft, or resend. Inspect the actual terminal content. tmux management-client reads and writes are not atomic, so this check cannot eliminate every concurrent write from another terminal.

**Why does an ACP Agent report `ACP_LAUNCHER_CLEANUP_UNKNOWN` or a cleanup timeout after exiting?**
- Ordinary downstream slow reading is not an error and has no five-second truncation deadline. After the main Agent exits, Dutydeck waits for the destination to resume, delivers the complete stdout/stderr tail, and then retains the original exit-code or signal semantics. Do not resend the original task merely because a reader paused for more than five seconds.
- A bounded failure is reserved for an inherited source descriptor or an owned process group whose exit cannot be proven. In the diagnostic, `sourcesClosed=false` means a descendant still holds an inherited stdout/stderr descriptor, `destinationFlushed=false` means the destination still has unwritten data during the abnormal teardown, and `groupExited=false` means process-group exit is unproven. They are not collapsed into a single `drained=false`.
- Do not delete the report under `.dutydeck/launchers/` in the session workspace. The internal protocol appends one `dutydeck_cleanup_unknown {"sourcesClosed":...,"destinationFlushed":...,"groupExited":...}` line and internal exit code 120; the adapter requires both the exact marker and that exit code before tracking the process tree as unconfirmed. Ordinary exit 1, or an ordinary bare exit 120 without the exact report marker, is not cleanup-unknown. The ACP adapter uses the retained report to adopt and stop the remaining process tree and deletes it only after exit is proven. Check for background descendants, inherited pipes, or a process group that cannot be inspected. Even when stderr backpressure hides the launcher's own diagnostic, the adapter identifies this path as `ACP_LAUNCHER_CLEANUP_UNKNOWN`. These internal markers add no task-result enum, setting, CLI, database field or external launcher protocol.

**Codex shows an input box but Dutydeck reports that startup is not ready?** Codex 0.169.0 moves `← for agents · ? for shortcuts` and its warning count to a separate footer row, which older Dutydeck builds reject. Upgrade to a build with this footer compatibility fix, confirm the original task failed with the startup-readiness error, then send it again; this failure occurs before the prompt is written. The updated check still requires an empty composer and initialized model status; permission menus, unsent drafts and busy screens continue to block input.
