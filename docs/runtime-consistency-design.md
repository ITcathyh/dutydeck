# Runtime 一致性修复设计

适用起点为 Dutydeck `5e2743e`，属于 [完整产品方案](full-product-parity-plan.md) 的 P0。本文固定实现约束；完成状态以 [实施记录](full-product-execution.md) 为准。设计基于当前 Runtime、SQLite 仓储、群身份授权和 AcpxAdapter 的实际调用链，并已吸收一次独立并发审查。

## 1. 用户可观察到的结果

同一会话的并发消息都能记录并按序显示；用户提升任务优先级后，重启仍遵守该顺序；停止旧任务后，新任务能正常执行，旧任务迟到返回不会改写新任务或操作者身份。

停止不依赖旧 `send` Promise 必须自行结束。它仍须等待已进入的持久写入完成，并证明旧执行资源不会继续与新资源争用。磁盘写入永久悬挂或资源创建尚未核实的情况下，明确拒绝开放替代运行，不能同时承诺两秒成功重启和无旧写污染。

## 2. 事件写入

每 Session 一条事件写链，覆盖读取最后序号、构造记录、append 与广播。持久化成功后更新序号缓存；写失败只拒绝该调用者，后续写链继续。不同会话可并行。清理按链的对象身份执行，不删除尚未完成的链；停止后产生的事件继续排在已有写入之后。

Runtime 的短状态写入序列可等待事件写链；事件链不得反向等待状态写入序列，避免锁循环。该修复保证一个 Runtime 内的排序，跨进程唯一写入者由后续持久租约保证。

shutdown 先关闭带外事件接收，异步读取 Session 后、实际入链前再次检查。已接纳的 driver 事件允许继续落库；关闭仓储前等待 driver 消费链和事件尾链真正排空，不能只等待某一刻的快照后清掉新尾链。

## 3. 持久队列

任务增加内部 `queuePosition`，SQLite 列名为 `queue_position`。公众响应隐藏该字段。创建时间用于历史展示，不能用修改创建时间实现插队。

存储提供三个方法：

| 方法 | 提交行为 |
|---|---|
| enqueue(task, front/back) | 在同一即时事务中判断 ID 是否已存在、分配位置并保存完整任务；返回实际记录与 created 标记 |
| promoteQueued(sessionId, taskId) | 仅提升该会话内仍为 queued 的记录，原子修改位置；其他情况返回无结果，不复活旧任务 |
| listQueued(sessionId) | 按位置、创建时间和原接收顺序返回 queued 记录；历史列表保持原排序 |

位置按当前排队记录的最小值减一或最大值加一计算，边界包含零。旧库迁移只为尚在排队的任务补位置，按 `created_at,rowid` 保留原先同时间戳的顺序；不修改任务内容、创建时间、状态或执行上下文。

Runtime 的接受、提升、取消和取出必须在同一会话的短写入序列协调。持久化成功后才更新内存并确认；幂等重投返回已有任务，不重复插入、不改变顺序。若持久接受已完成而通知失败，当前进程的恢复/幂等重投必须从真实 queued 记录重建缺失的内存投影并触发调度，不能只返回“已有任务”后继续搁置，也不能再次执行已经 running/终态的记录。停止取消旧队列时同样核对数据库中的已接受任务，不能遗漏尚未进入内存数组的记录。停止与接受的竞争按生命周期身份裁决，旧准备流程不能在重启后给新运行加任务。

## 4. 执行尝试与生命周期

保留 Session.runId 表示原生会话运行身份；每次指令另有唯一的进程内尝试对象。尝试对象持有任务快照、生命周期代际、驱动身份、撤销状态、停止原因、错误、事件链及等待者。活动尝试以对象身份比较，不能仅比较 taskId；恢复同一 taskId 也会产生新的本地尝试对象。

队列 drain 有自己的 owner，一个 drain 可执行多个尝试。生命周期改变时撤销旧 drain；旧 drain 从 await 返回后不得操作当前队列，旧 finally 只能清理自己占用的执行槽。没有 task 尝试的 start/resume、终端重连、闲置清理及模型/推理配置使用独立的 lifecycle/driver owner；每个创建、保存与 finally 清理均按身份匹配，不能删除其他操作刚接上的 driver。

所有可能恢复的异步边界均检查归属：材料/Skill 准备、授权、工作目录/策略准备、重连、prompt 生成、send/recover、事件消费、flush、结果计算和状态提交。事件在回调入队时固定 driver 与尝试身份，不能等到消费时借用下一轮身份。

同一个 driver 在自然完成后才发出没有轮次标记的旧事件，Runtime 无法可靠区分；driver 契约仍要求完成前交付该轮全部事件。发现供应商实现违反契约时，在对应 adapter 标记来源并修复，不把所有无标记事件都声称已隔离。

## 5. 短写入序列与停止屏障

每 Session 的短序列覆盖任务/会话事实、权限与工具事实、策略文件提交、身份提交和关联事件。写操作在真正执行前检查 owner；已经进入仓储的操作允许先完成，再执行停止屏障。新运行必须等屏障完成。

更新 Session 时读取当前持久值并合并本次变更字段，避免捕获的旧整行对象覆盖新 runId、模型或归档状态。内部保存 helper 不得递归进入同一序列。网络授权、driver.start/send/recover/stop、整轮等待不得占用短写入序列。

stop/archive/restart/硬介入使用同一内部撤销步骤，并由独立生命周期门禁协调：关闭本次运行的新接收；撤销旧尝试、回调与 drain；提交旧任务中断和权限失效；回收旧资源；在屏障后写入停止、归档或新运行身份。复合 restart 调内部停止原语，避免重复加同一生命周期锁。

显式 stop/archive/restart 取消旧队列；硬介入保留其余排队任务。正在准备但尚未调用 driver.send 的新任务记为 cancelled，已经提交的轮次记为 interrupted；已完整提交的自然完成不改回中断。撤销后的对外任务 Promise 可在对应状态持久化后结束，无法取消的底层 Promise 保留 rejection handler，不占新执行槽。

## 6. 两个必须一起接通的真实边界

群身份授权包含写操作：`groupManager.beginTurn` 在远端授权完成后设置 `activeOpenId`，安装者首次进入还可能创建 RunContext。只检查 Runtime 返回后的 generation，不能撤回这些迟到写入。拆出 `prepareTurn(sessionId, actorId)`，返回可选的本地提交函数；准备期间不写 RunContext，提交由 Runtime 在检查归属的短序列中执行。现有授权可能刷新群事实和 principal 展示缓存，这些全局事实更新保留；“准备不写”专指任务运行身份，不能声称授权链全部只读。提交不含远端请求，以当前 RunContext 合并 activeOpenId；目标 app/chat/binding 变化或原记录被删除时拒绝，不能恢复旧整行。原 beginTurn 保留 prepare 后立即 commit 的兼容包装。

AcpxAdapter.start 在 ensureSession 返回后才持有 handle。start 尚未结束时调用 stop，原实现可能看不到正在创建的资源。实现须记录启动所有权，停止后迟到创建的 handle 不得变成当前句柄；只有确认精确资源清理完成后才开放相同持久 key 的替代。保护范围同时覆盖 send 内 missing-session 处理：重置持久状态、再次 ensureSession、再次发送都必须属于同一个仍有效的操作；停止后不能由自动修复分支复活旧资源或重发原指令。若底层不能取消或确认创建结果，保留明确的资源未核实状态，给出核对后继续的入口。不得根据“内存里没有 handle”推断“没有资源”。优先接通现有 `AgentDriver.isStopped` 资源核验契约；不能把 stop Promise 已返回或 detach 当作同等证明，缺少可靠核验的组合保留未核实状态。

这一边界必须用真实 AcpxAdapter 类及其持久 session key 回归。若涉及 session 配置或环境注入，持久键仍为小写 snake_case；mock ACP 客户端本身不足以覆盖该契约。

ACP 超时向调用者返回后，SDK 事件流可能仍在完成持久化和资源回收。下一次顺序 send 应在资源操作序列外等待这段尾声，停止可撤销该等待；不能把它当成新的并发调用而使后续排队任务连续失败。stop 将对外失败通知与后台收尾分开：一旦 cancel/close 已明确失败，立即报告；其余悬挂操作与晚到资源继续受观察，保留环境文件，不宣称回收成功。

物理资源核验使用固定版本 SDK 的进程内观察接口，覆盖 agent、启动探测与 host terminal。实际创建流程发出开始、spawn 和结束事件，登记原始 ChildProcess；只接受真实 exit 或明确的无 PID 创建失败，killed、管道断开和持久 closed 不算退出。外层启动超时后，底层仍可能在异步命令解析后 spawn，因此创建中状态必须跟踪 SDK 原流程，不能仅看 Adapter 的 Promise 是否结束。关闭还要撤销迟到启动，不能以无限等待代替可回收的正常路径。

Adapter 的 isStopped 只有在撤销、后台收尾结束、创建/资源操作和 SDK 流均收口、全部受管进程确认退出后才返回 true；已确认退出的对象可移出集合。该证明覆盖 SDK 直接创建的进程，不能扩大到任意脱离进程组的工具后代，后者由 P3 的平台隔离处理。JSONL/Pipe 在 POSIX 上核实其独立进程组消失；未知的查询结果保持阻塞。

停止未核实的状态必须落库并关联原 Session/runId。重开 daemon 后没有旧 driver 对象时，不能靠空 Map 解除门禁，也不能为核验先构造同 key 的新 Adapter。同进程由原 driver 的精确资源证明解除；跨 daemon 的核对与解除须由后续持久资源身份恢复流程提供。这个临时拦截记录不能替代执行租约，也不覆盖尚未报告停止错误就崩溃的情形。

## 7. daemon 停机与跨进程恢复

显式停止与 daemon shutdown 分开处理。shutdown 先让 PTY transcript 刷入持久记录，再 detach；可恢复的已提交任务保留 running 与 checkpoint，未提交任务保持 queued。重启使用原 task、原生 turn/cursor 执行 recover，不重发 prompt。关闭仓储之前封住剩余旧 continuation。

恢复尝试从登记时便属于历史已提交轮次，包括尚在重新授权或读取恢复边界的阶段；再次 shutdown 不能把它误降为 queued。新任务提前创建 checkpoint 仅记录准备边界，并不证明 prompt 已提交。

任务执行事实与事件/通知交付还须分别收口：执行或接收已持久提交后，事件追加失败不能被通用 catch 改成任务执行失败，更不能自动重发指令。P0 后续接通持久待交付记录与独立重试；本轮事件排序修复不冒充这项交付保证。

本地 owner 和短序列只解决单 Runtime 内的异步竞争。跨进程还要持久运行代际、租约/资源身份以及提交处 CAS；旧进程仍可能活着时，不能用“本地 map 没有旧对象”证明已获得资源。该后续单元与接收/执行/交付恢复共同属于 P0，三个已复现缺陷修复后 P0 仍不自动完成。

## 8. 验收

真实 SQLite 配合 deferred 控制故障时序，至少覆盖：并发事件与写失败恢复；提升后关闭/重开数据库；停止后迟到成功和失败；准备/授权/策略读取暂停；已进入 session/task/permission/event 写入的暂停；旧消费链、flush 和 drain 遇到新任务；硬介入保留队列；并发生命周期操作；旧 actor 回调；真实 AcpxAdapter 迟到启动；PTY detach 与原任务恢复。

不以固定 sleep 作为竞争成立的唯一证据，不弱化已有断言。整合后运行对应 Runtime、存储、群权限、ACPX、PTY 恢复测试及 workspace 类型检查，再做完整 diff 的独立审查。真实供应商和跨进程故障验收另行记录，不能由本地模拟测试代替。
