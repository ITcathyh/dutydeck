### 浏览器内存验收的口径变化

旧测法只比较两个未经回收的堆快照。本轮原始快照增长先后为 119,636,120B 和 54,456,824B，**均没有通过原 32MiB 门槛**。分配诊断发现大量临时对象；已删除无消费者的索引，复用未变化的历史组件数据，并减少投影输出的临时分配。对应失败日志保留在 `/tmp/dutydeck-p1-browser-final.json` 和 `/tmp/dutydeck-p1-browser-verified.json`。

Chrome 官方建议在内存记录的开始和结束执行回收，以观察仍被引用的对象增长。[Chrome 内存排查说明](https://developer.chrome.com/docs/devtools/memory-problems)

据此，经独立复核，基准现在固定分为三段：

1. 原有 50 次实时更新保持自然回收，延迟 p95 仍须低于 80ms；报告最大延迟、原始堆起止、增长及每次更新后的采样峰值，保留“是否超过旧原始快照预算”的字段。
2. 再做等量 50 次更新，只在这段开始和结束执行回收，**回收后仍占用的内存增长须低于 32MiB**。
3. 在独立页面保留一个大于 32MiB 的实心 JS 数组，确认同一检查会拒绝；释放后再确认回落，防止把真正的持续占用漏掉。

这属于验收语义变更：取消了“某一时刻未回收对象增量不得超过 32MiB”的硬限制，不是原门槛等价通过。新结果只证明本次五万历史和固定更新样本的留存增长，不保证瞬时峰值低于 32MiB，也不保证无限历史的总内存有界。

浏览器基准保留原有首屏 800ms、补页 250ms、增量绘制 80ms 门槛。首屏现在先读尾页，补页指标改为显示上一页；另有完整五万条历史的逐页上翻、锚点和继续收消息验证。绘制计时从服务端发布前开始，到唯一目标消息出现后再等两帧；100ms 人为 DOM 延迟控制样本确认没有漏掉等待。旧的 Playwright 定位器轮询会额外计入重试等待，新旧测法不能直接算提速倍数。入口包变小是拆分结果，不代表整个页面下载量同幅下降。

## 使用与边界

分类和回复的新设置留空时，依次回落到原记忆设置、执行默认设置。当前完成的是独立选型能力和路由回归；真实模型的误介入率、回答质量、成本及低置信升档策略尚未做在线对照，不承诺换便宜模型后质量不变。

费用和次数限额的配置见 [用量计价与自动任务次数上限](usage-pricing-and-automatic-budget.md)。内置费率仍是带版本标识的旧费率，未核对当前采购账单。月度美元预算仍是按已知结算费用拒绝新任务的软上限，不限制在途支出。自动任务次数上限默认关闭，启用后也不限制一个根任务内部的调用量。

跨群显式查询仍需逐群检查当前内容版本，不是所有跨群查询都变成一次读取。日志分批读取也不能抢占单次 JSON 解析或一小块磁盘读取。没有改动 P2 的全局执行槽、硬预算预留、冷归档等机制。
