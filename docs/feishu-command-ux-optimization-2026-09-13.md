## 1. 裁决总结论

调研没有推翻 Dutydeck 的架构方向，结论是**现有地基（双卡终态、一次性审批、能力门、持久 inbox、串行队列、先答先赢）全部成立，优化集中在"把已经存在的能力接到飞书交互面上"**：大部分高 ROI 项是接线而非修路。

四条交付主线：

1. **决策不出飞书**：审批/问答/任务操作全部按钮化、就地化；新增两项现状实锤缺陷修复（群审批/结果卡不 @ 发起人、/work 等待中误推卡）。
2. **消灭手敲编号与参数**：/tasks 行操作、问答表单、/work 步骤按钮、/help 翻页、命令纠错、菜单。
3. **安静但确定的触达**：坚持"PATCH 不打扰、需要人行动才新消息并 @ 具体人"；补审批宽限、超时升级、停滞诚实终态；不加急、不用 reaction 承担通知。
4. **上手一分钟与安全不放松**：欢迎语、/repair 一键补权；同时补上两个被红队核实的真实缺口（agent 主动群发无脱敏、👍 误接会硬杀当前轮）。

两个被高调推荐的候选被主控改判或挡住：**"始终允许"只做会话级内存态 v1，持久授权规则 1.0 剔除**；**👍 升级必须先改 runtime 语义（只重排不杀轮），现状原语禁止接线**。

### 3.2 操作就地化（M 批，互相配套）

**P0-1　E15 /tasks 行内操作 + Web 深链（M）**
- 每行按任务状态只给**一个主操作**（queued→取消、running→中断、failed/interrupted→重试、带 pending permission→审批）；次要操作收进 overflow，避免手机按钮墙 [MO-A1]。
- 必须复用 `handleAction` 现有 task_id+turn 分发、白名单鉴权与 stale 检查；行内审批必须走 `workflow-interactions.respond` 的一次性决议 CAS，禁止旁路直 resolvePermission [EN E15, RT-C5]。
- 对**他人任务**执行中断/取消/重试时弹二次确认（本人不拦）[MO-C1]。
- 行 Web 链接走 safeLarkWebUrl 同款校验。
- 验收：行内审批有测试证明走 respond CAS（不可旁路直 resolvePermission）；终态/过期任务点按回 toast 兜底；10 行满页组件数 ≤180。

**P0-2　E10 问答卡结构化（M，V1 版本核查通过后上线）**
- ask 事件带选项时渲染单选/多选（按钮或 select），自由文本用 input（max 1000）；长答仍可引用回复。回调复用现有 respond CAS/鉴权。
- 表单是 JSON 2.0 原生组件，不依赖 CardKit（已核官方组件清单）；tlive 式多问游标（Back/整批提交）不做。
- 前置确认 relay ask 事件透传 choices 的 schema；PTY 无结构化问题源，不承诺。
- 验收：单/多选与短答回调落同一一次性决议；低版本客户端有"引用卡片回复"文字兜底。

**P0-3　E14 /work 卡 PATCH 化（M），三项配套强制**
- 回调先回 toast，再用被点消息 messageId 走普通 PATCH 覆盖原卡；revision CAS 失败回退发新卡。
- 配套 1：**E20 操作者归属完整版同批或更早**。work 步骤侧 actorId 已落服务端可直接渲染（work-items 层）；**普通任务的中断操作者目前没有现成承接**——`runtime.interrupt(id, expectedTaskId?)` 无 actorId 参数（已核 `packages/agent-runtime/src/index.ts:941`），`TaskRecord.executionContext.actorId` 只是任务发起人，`handleAction` 的 operatorOpenId 仅用于鉴权不落库。需要新增中断操作者落库（runtime.interrupt 增加 actorId 透传，或在 Lark card mapping 持久操作者字段），状态行才能在心跳重绘与重启后保留"由 X 操作"。不得按"已承接"估工。
- 配套 2：**N2 缺陷修复**——现状 waiting 一旦出现，fingerprint 含全部步骤状态（`workbench.ts:156`），其他分支每次正常流转都推新卡。改为只有 waiting/blocked/failed/completed 焦点态变化才允许新消息，running↔completed 正常流转只 PATCH [MO-B4]。
- 配套 3：两条回归测试——waiting 必推新卡（审批等待不得被静默 PATCH）、指纹不变不推卡。
- /work 步骤级操作按钮化（消灭带 2-4 个 ID 的 `/work answer/cancel/retry` 手敲，卡上仍印命令兜底）随本项一起做。

**P0-4　N1 群内审批卡/结果卡/失败卡 @ 发起人（S-M，V1 触达实测通过后上线）——现状实锤缺陷**
- 已核代码：审批卡（`workflow-interactions.ts:150-153`）、结果卡（`result-delivery.ts:25-37`）群聊均无 at 标签；项目群被免打扰时，"收到审批拍板"的主打场景锁屏不亮 [MO-B1/B3]。
- 发起人 open_id 在 inbox event 与 card mapping 双处持久化（inbox 存完整 event 取 `senderOpenId`，mapping 字段 `sender_open_id`），经任务 mapping 可反查。
- 规则：需要人行动的卡（审批/问答）和终态卡（完成/失败/被他人中断）@ 发起人；白名单其他人可见可点但不被 @；排队/心跳永不 @。与 §6 通知策略表一致。
- 私聊不 at（无必要）。
- 验收：重启 5s 对账补发的终态/待决卡仍正确 @ 发起人且不重复 @；群内白名单其他人收不到 at 提醒。

**P0-5　E24a 欢迎语（S-M）**
- 订阅 `im.chat.member.bot.added_v1`，bot 入群发一次欢迎卡（我能做什么、群里要 @、怎么看 /help）；私聊首次欢迎用持久化"已欢迎 chat"标记，避免每消息判一次。
- 存量 bot 靠 P0-6 的 /repair 补事件订阅后才生效。
- 验收：同一 chat 重启/重复事件不重发欢迎；bot 被拉入大群只触发一次。

**P0-6　E12 /repair 一键增量补权并重新发布（S-M，前置项）**
- 把 configurator 现有"读目录→更新→回读校验→发版→审核态校验"包成一个入口；E24a（bot added 事件）、阶段 2 的 👍（reaction 事件）都依赖它先做。
- **发布飞书应用版本是不可撤销外部动作，命令实现后，实际执行发布必须显式向用户确认；审核态如实回显，未过审核不得声称已生效。**

**P0-7　PTY 模式明示（S，红队翻案项的立即部分）**
- PTY ask 会话的任务卡卡面标注"终端模式，工具确认需在电脑前响应"；配置远程 agent 使用 ask 模式时给配置警告 [RT-D4]。
- 现状实锤：PTY driver 无 resolvePermission，`getPendingPermissions` 返回空（`agent-runtime/src/index.ts:1142-1145`），任务在终端提示处挂起时飞书侧无卡无通知——不得在文案上承诺手机能批 PTY。

## 4. 阶段 2（P1）：近期两个迭代

### 4.1 审批主线（一个主题交付）

**P1-1　审批按钮 v1：两个拒绝按钮 + 会话级"始终允许"（M，主控改判产品/红队分歧）**

四方分歧：[PR] 要求四按钮 P0 且持久化规则；[RT-B1] 要求剔除持久"始终允许"（单源 wiki、Bash+目录≈任意命令放行、无存储/撤销/审计设计、现行卡片明文承诺"只处理这一条请求"、tlive 只敢内存态）。主控核实：协议层 `PermissionRequestData.operation` 已携带脱敏有界的 `{cwd, resource, command}`（`packages/shared/src/index.ts:231`），runtime 已有 ToolRiskPolicy per-session 下发链路——规则判定可在 observe 层命中后走同一个 resolvePermission 入口，不旁路、不改驱动。裁决**折中且偏安全**：

- **本次允许**：现状，不动。
- **拒绝（换方案）**：现状 reject 语义本就是拒绝本次、agent 换路，仅改文案让用户看懂（S）。
- **拒绝并中断**：reject + interrupt 一次完成（S-M），缩短错误方向燃烧时间。
- **"本会话始终允许此类操作"（M 偏大，严格边界）**：
  1. 规则仅 daemon 内存态、绑定 lark session id，**重启 daemon 或 /new 即失效**；session 退役（/new 的 retireScopeSession）时同步清表，不残留——不做跨会话持久授权（持久化规则+Web 撤销口+跨 agent 规则语义统一为 v2，需另行立项评审）；
  2. 匹配键用 operation **全字段精确匹配**（工具 + command 前缀模式/resource + cwd），**禁止"某工具在某目录一律放行"这种粗粒度**，Bash 必须带命令模式；
  3. 高危请求永不出现该按钮。注意现状 high_risk 是**人维度的授权门**（`high_risk.execute` + enforced ToolRiskPolicy，决定"谁能批"），**不是对请求内容的分类门**；本项需新写 highRiskPattern 对 `operation.command` 的匹配判定（决定"这类请求根本不允许被规则化"）；deny 永远优先于 allow；
  4. 仅任务发起人本人可见可点（群内其他白名单成员只见三按钮）；
  5. **规则仅对创建者本人发起的任务自动放行**。规则按（session id, 创建者 open_id）存储；群话题 scope（`thread:${threadId}`）不按发送人隔离，话题内所有白名单用户复用同一持久 lark session。observe 命中规则时必须比对当前任务发起人 open_id 与规则创建者，他人任务即使 operation 完全相同也照常发卡——堵掉"A 的规则静默替 B 的任务授权"这个跨用户漏洞（独立复核发现）。规则寿命仍跟随会话：任一人 /new 都是话题级显式上下文重置（现有语义，线程内有受理回执），整个 scope 会话退役、所有人的规则随之清空，这与"上下文被重置"一致，不属于跨用户问题；
  6. 每次自动放行落审计（复用 `savePermission`，审计记录含规则创建者与实际任务发起人），进度卡可见"已自动放行 N 项（仅本会话）"，并提供撤销入口（规则列表卡，一键清空本会话规则）；
  7. ACP only；卡面替换现行"只处理这一条请求"契约文案，如实说明新按钮的边界（仅本会话、仅本人任务、重启失效）。
- 验收：误授权测试（高危 pattern 不可规则化、Bash 无命令模式不可规则化、重名/歧义命令不命中）；**跨用户测试（同一话题会话存活期间，A 建规则后 B 的同 operation 任务仍发卡；任一人 /new 后规则随会话退役清空，新会话从无规则开始）**；重启/退役清表；自动放行有审计；群成员看不到该按钮。

**P1-2　E2 审批发卡前 10s 宽限（M，ACP only，可配置可关）**
- pending 事件到达先起 10s 定时器不发卡，窗口内任一端（IM/Web）已答或 agent 撤回则取消；超时再走现有发卡。
- 10s 是 tlive README 单源经验值，默认值标注未经用户数据验证，上线后按本地应答率调参 [RT-A4]。
- 强制回归（真实持久化路径，不只 mock）：grace 窗口内 daemon 重启必须对"从未发卡"的 live pending 补发卡（否则审批永久不可见，比今天更差 [RT-C3]）；agent 撤回竞态；世代围栏；发卡后抑制同事项空闲提醒，一事不亮两次。

**P1-3　审批/问答超时升级（M）**
- 永不自动拒绝（现状，保持）；但 pending 超过阈值（建议默认 30 分钟，可配置）时**每事项最多发 1 条升级消息，只 @ 发起人**，再无响应保持静默 [MO-B2/B3]。
- 同一任务 60s 内新增的审批 PATCH 进同一张待决卡（多组按钮），不每审一条新消息。

**P1-4　K1 停滞诚实终态（S-M）**
- runtime 已有 `lastActivity`（每事件 touch，`agent-runtime/src/index.ts:87,121`）。判定条件必须是"无任何事件**且**无在途工具调用/构建"持续 N 分钟（宽松默认、可关），长命令不算卡死。
- 通用 agent：发一张停滞卡，给「中断任务/重试/知道了」；终止走正常终态通道（冻结卡+说明卡），禁止静默杀。
- **PTY 场景（合并移动端方案）**：停滞卡只给「中断任务」（Ctrl-C，pty-driver 已支持）和「知道了」，**不给自由输入、不给回车**——向未知终端提示发回车可能等于授权；仅当 runtime 能确定提示类别（如纯 informational Press Enter）时才出「继续」，识别失败 fail-closed 到只给中断 [MO-A4]。
- V6 hooks sidecar spike 通过后，PTY 结构化审批按 M-L 重估，不提前承诺。

## 6. 通知策略（写入产品契约，所有新功能遵守）

**一句话原则：新消息只花在"需要人知道或需要人行动"的时刻；需要人行动就 @ 具体那个人；其余一切原位刷新。**

| 事件 | 触达 | 群内定向 |
|---|---|---|
| 接收/入队 | 首卡新消息 + OK reaction | 不 @ |
| 排队/心跳/阶段/工具流/恢复注记 | 仅 PATCH | — |
| 审批/问答 | 新消息卡（ACP 先走 10s grace） | **@ 发起人**（N1 新增） |
| 完成成功 | 结果新消息（现状） | **@ 发起人**（N1 新增） |
| 失败/中断/被他人中断 | 新消息 | @ 发起人，卡面注明操作者 |
| 审批/问答超时 | 每事项最多 1 条升级 | 只 @ 发起人，不加急 |
| 停滞/疑似卡死 | 每任务最多 1 条 | @ 发起人 |
| /work 目标 | 一块看板只 PATCH；亮屏仅限：进入 waiting（@ 发起人）、失败 30-60s 合并播报、全部完成汇总一条 | 单分支成功不发；每目标亮屏 ≤2+待决次数+1 升级 |
| reaction/pin | 永不承担通知 | — |
| 加急 | v1 全禁 | — |

总量规则：同任务 60s 同类触达合并；对账补发、重启恢复遵守同一表（恢复事实只 PATCH）；典型长任务锁屏亮屏从现状 3 次（首卡/审批/完成）降到人在终端前 2 次。

## 7. 工程与发布约束（实施时强制）

1. ACPX 持久化键必须 snake_case；不得把 UPPER_SNAKE 环境变量名写入 `acpx.session_options.env`；群工具运行时变量只用小写 `dutydeck_group_tools_url`/`dutydeck_group_tools_token`。

4. 事件订阅扩容（bot added、reaction 等）走 configurator 增量 add + /repair；**应用版本发布是不可撤销外部动作，逐次显式确认，审核未过不得声称生效**。
5. 鉴权单一事实源：行操作复用 handleAction、审批决议复用 workflow-interactions.respond、自动放行复用 resolvePermission，任何新交互不得旁路。

7. 平台 unverified 项（见各评估附注表）在真机/官方文档证实前，代码可以写但默认关闭或不承诺。
