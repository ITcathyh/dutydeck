# Dutydeck 团队 Tag 底座评估

实施方向与范围已收敛到[最终方案](team-tag-foundation-plan.md)；本文保留现状、调研证据和推导过程。

范围：本项目只交付通用能力和扩展接口。本文保留的报警、服务树、外部任务等内容用于说明使用方如何应用底座；具体业务实现、适配器及领域评价不属于本项目任何一期的交付。

调研日期：2026-09-18。代码基线：`a220928`。范围：当前代码、定向测试、产品官方公开资料；本次仅新增调研文档。产品资料用于比较机制，没有实测第三方产品，也没有核验本机正在运行的 Bot 配置。

参考讨论：开发机 `10.37.23.29` 的 Claude Code session `ad414047-5731-4fe5-8e01-abb3a89d348b`，以及本地 session `406fd991-a5dd-466c-a4be-23d4af559cac` 和其产出的[基座能力设计](team-tag-foundation-design.md)，均为 2026-09-18。已读取会话讨论、调研回执与最终复核；其中的数字、API 名称和完成声明不直接作为当前事实，相关能力按本轮代码核查修正。

**结论：Dutydeck 适合继续演进为通用群协作 Agent 底座。最优先补齐的是持续观察、选择性介入、可持续跟踪的事项和条件提醒。** 已有 Agent 适配、话题上下文、记忆、执行账本、工作流和定时任务可以复用。报警分级、服务树、Argos 规则与 RCA 评价标准由使用方在项目外实现。

建议按“通用群协作与持续执行 → 完善扩展运行能力 → 评价与策略迭代”推进。从第一阶段就保存来源和人工修订，避免以后无法回放；具体外部待办及业务规则调优不列入本项目交付。

补充实证：[Milo 群内发言模式观察](milo-speaking-patterns-20260918.md)。读取两个指定群中 9 月 4 日至 18 日的 Milo 消息及重点讨论后，首期进一步明确：持续委托要保存，提醒状态与事项状态要分开，人工纠正要落实到后续计划。发言少不等于已经验证了正确沉默。

**远程参考会话的分层保留，四项通用接口仍需补充行为约束**

参考会话最终提出通用事件入口、卡片交互、超时调度、快照评测，并把团队 Tag 放进独立业务包。这一分层可采用，但不足以证明只写 YAML、Prompt 和 Skill 就能完成全部需求。

| 参考方案中的判断 | 本报告的取舍 |
|---|---|
| 保持单机与 SQLite，业务逻辑独立打包 | 保留单实例与 SQLite；业务包由使用方在本项目外维护，可以包含适配代码和版本化状态，不能只靠提示词保存业务事实 |
| Webhook 映射为 Task | 接入先生成可追踪事件，再决定是否更新事项、继续已有执行或创建新任务；群内普通消息也要走观察路径 |
| 同一 `dedup_key` 聚合、追加或丢弃 | 拆开投递去重与业务关联。同一事件重投可去重；同类新事件必须保留时间和计数，再关联到原事项 |
| 总结写入 Memory 即完成记录 | 记忆保存精炼经验；原始证据、事项状态和确认结论单独保留。群里安静一段时间也不能直接认定事情已解决 |
| 新建通用卡片门禁与超时引擎 | 先复用问题/审批卡、WorkItem wait、会话定时执行和独立调度的持久化基础，再补事项版本、责任人、期限与取消条件；独立调度尚不能执行 |
| 所有待办必须点击确认；固定时间梯度、固定倍数折叠 | 这些是业务策略候选，不作为底座限制。支持逐项确认，也支持管理员预先授权范围内的自动动作；模糊或超出范围的提议再交人处理 |
| 全部工具轨迹可直接回放，达到零漏报 | 轨迹完整性和可拦截能力需要按驱动验证；历史样本通过不代表线上零漏报。回放缺材料时应明确不可评，而非算通过 |

LangGraph 的 `interrupt` 确实支持持久等待与恢复，但恢复时会从节点开头重新执行，节点内此前发生的副作用仍要处理幂等。这个细节也说明“支持恢复”不能替代外部动作保证。[Interrupts](https://docs.langchain.com/oss/javascript/langgraph/interrupts)

**你举的例子：进群后怎样决定是否回复**

推荐把消息处理分成以下顺序：

1. **确定能看什么。** 从当前群授权和平台实际可见范围读取群信息、有限历史、话题与引用；记录来源和缺失。初始化摘要先供 Agent 使用，需要发布到群时再走投递策略。入群前历史是否可读必须用真实群验证，不能由 SDK 方法存在来推断。
2. **更新观察记录。** 同一消息只接收一次，区分人类、可信系统和其他 Agent；保存时间与关联。系统通知可成为事实输入，但不能直接取得执行权限。
3. **拼出相关上下文。** 当前话题、相关群消息、已有事项和群记忆优先；需要时按来源下钻。延续现有预算与增量读取，避免每条消息重新加载全部历史。
4. **选择动作。** 明确 @ 或控制命令进入既有交互；被动观察结合上下文判断是否有新增价值、是否已有成员处理、是否补充已有工作。允许“只更新事项、无需发言”。
5. **由宿主执行与投递。** 判定阶段不持有写外部系统的工具。结构化结果经校验后，才启动任务或投递；静默由宿主保证。正式动作执行前复核授权、事项版本与最新消息；若生成期间已有成员解决问题，取消或重算待发的主动回复。

确定性规则可以先拦重复投递、自身消息和未授权来源；其他消息即使不回复，也可能补足上下文，不能为了减少模型调用就提前丢弃。静默决策同样保存输入引用、命中规则、策略版本、动作和简短理由，并受数据保留期约束；不要求保存模型思维链。上线前先在脱敏回放和授权试点中只记录候选决策，比较误介入与遗漏，再逐群启用主动行为。

判断不能只使用单条消息分类器。例如前一句是“我怀疑昨天的变更”，下一句是“这里是错误日志，但今天没人能看”，两句合起来才构成可介入的任务。Claude Tag 的官方更新也明确介绍了这类跨消息判断。[官方案例](https://claude.com/blog/claude-tag-now-reads-even-more-of-the-room)

| 群内发生的事 | 建议默认行为 |
|---|---|
| 两个人继续交换进展，已经有人处理 | 更新上下文或事项，不发言 |
| 有人明确说“我来处理” | 更新认领信息，取消未认领提醒；身份或指代不清时保留待确认状态 |
| 问题长时间无人回应，Agent 有可核对的材料 | 在原话题简短回答，或按配置提醒相关人 |
| 新消息属于正在执行的工作 | 关联到已有事项和执行，避免再开一个任务 |
| 内容不足以判断，且无人明确要求执行 | 保持沉默；保留缺失原因供管理端排查 |
| 显式 @ 但权限不足或资料不可读 | 向请求者说明具体缺失，不能假装读到了上下文 |

允许群管理员设置“仅 @”“观察并记录”“主动协作”等行为。连续消息可合并判断；空闲群降低判断频率，显式 @ 及时响应。先采样测每群调用次数、上下文量与误介入率，再决定是否引入专用便宜模型。宿主必须控制静默，不能只在 prompt 中要求输出某个特殊词。

当前存在两个需要先明确的边界：自动上下文直接读取 service，而群工具读取走 `group_tools.read`；记忆工具验证会话与开关，但没有相同的群策略复核。[coordinator.ts:2167](../apps/server/src/lark/coordinator.ts#L2167)、[agent-tools.ts:330](../apps/server/src/lark/agent-tools.ts#L330)、[agent-tools.ts:371](../apps/server/src/lark/agent-tools.ts#L371)。这是已确认的路径差异；是否违背产品授权语义仍待定义，不据此宣称存在已验证的越权漏洞。

本地参考会话补充的来源问题也成立，但应保留已有保证：群工具结果已经携带发送者、消息 ID 和时间，缺的是与自动上下文一致的“外部材料不授予权限”声明；自动记忆提取已有 taskId 证据和不执行材料内记忆指令的提示，但提取输入只有 prompt/answer，统一标为“用户”，没有逐条发送者类型。[agent-tools.ts:505](../apps/server/src/lark/agent-tools.ts#L505)、[agent-tools.ts:703](../apps/server/src/lark/agent-tools.ts#L703)、[memory-pipeline.ts:562](../apps/server/src/lark/memory-pipeline.ts#L562)、[memory-pipeline.ts:802](../apps/server/src/lark/memory-pipeline.ts#L802)。应贯通来源与可提取范围，避免把机器人推送或引用当作团队新约定。统一声明只能辅助模型识别材料，实际动作仍需服务端授权。

当前仅 `riskControlMode=enforced` 创建这条执行的 `riskPolicy`；不能把提示指导或关闭模式描述成同等强制保证。已有群工具权限和任务授权仍是独立控制，本轮没有验证完整利用链。[coordinator.ts:2105](../apps/server/src/lark/coordinator.ts#L2105)

**记录与提醒：先建立可核对的状态**

通用跟进记录包含稳定 ID、所属群/话题、目标、状态、时间线、证据引用和版本；责任人、期限、结果和外部关联按需保存。Agent 执行继续使用已有 WorkItem/Task/Attempt；记录通过引用关联这些执行，不默认给每条消息建档。业务字段和状态解释由使用方扩展提供。

事件至少区分来源事件 ID 与事项关联键。例如同一回调重投两次，只处理一次；同一事项五分钟后有新进展，保留为新事实并关联原事项。对外部来源分别记录发生时间和接收时间，避免补偿读取改变时间线。

“记录”至少区分三种内容：原始来源、系统推断、人工确认。模型推断某人已认领或某次发布相关时，保留来源，不覆盖人的修订。需要确认的事项结论卡可编辑、确认和重新打开，并保存确认人和版本；普通 Agent 回复无需逐轮验收。耗时由可信事件时间及约定的起止状态计算，不能从模型总结里的数字直接入账。

卡片应显示事项的当前状态：一般进展原地更新，材料放进话题，仅在需要新的人工动作或提醒时增加通知。沿用现有卡片交互能力，新增动作携带事项版本，防止旧卡上的确认影响后来已经修改的结论。[workflow-interactions.ts:161](../apps/server/src/lark/workflow-interactions.ts#L161)

“提醒”需要把条件写成持久状态，例如：

```text
事项仍 open 且 owner 为空，持续到 deadline
→ 执行前读取最新版本与权限
→ 提醒当前应负责的人
→ 保存动作 ID、发送结果和下一次检查

认领 / 关闭 / 取消 / 失去授权
→ 使旧提醒失效
```

“有人发过消息”不一定等于“有效回复”；“机器人回了收到”也不应解除无人处理状态。底座维护等待条件和时间，业务扩展定义哪些事件构成认领、响应或关闭。发送前的复核减少过时提醒；检查与发送之间仍有竞态时，要可更新原卡片并阻止下一次升级。

持续委托还需保留委托人、来源、范围、检查时间与停止条件。降低频率、暂停通知、取消委托和事项完成分别改变状态，并按当前授权处理；不能把“别催这么频繁”解释成放弃跟踪。部分完成后只跟进剩余项，调整计划时使旧提醒失效。上述要求来自 Milo 的实际纠正与后续执行案例，详见补充观察。

确定内容的提醒可直接走投递动作，无需每次启动 Agent。首期应补全所选调度路径的执行、取消、恢复和投递结果记录；不是移除独立调度的禁用标志就算接通。两套现有调度是否收敛可在实施时决定，不把永久并存或全面重写设为前提。

本项目提供来源引用、关联记录和通知去重。已知问题登记、同类判断及有效期折叠由使用方实现，不作为首期的通用功能。

**适度开放业务定制的边界**

| 扩展面 | 底座负责 | 使用方在项目外实现的示例 |
|---|---|---|
| 事件来源 | 来源身份、外部 ID、幂等接收、游标、补偿读取、权限 | 报警事件、发布完成、配置变更；也可用于客服请求或项目讨论 |
| 上下文与实体解析 | 统一返回证据、时间、可见范围；缺失可辨认 | 按服务树解析负责人，查询变更记录或已有案例 |
| 事项模板与策略 | 字段校验、状态版本、条件等待、结论确认 | 报警字段、认领规则、提醒时限、已知期；内核不定义 SEV 等级 |
| 外部动作 | 动作身份、权限、执行状态、幂等键、结果查询 | 创建飞书任务、登记已知问题、生成 Argos 规则建议 |
| 评价规则 | 样本版本、输入快照、回放、差异和回滚记录 | 比较人工分级与系统分级，比较人工根因与 RCA |

使用方可用 Bot 指令、群覆盖、Agent/Skill、外部适配器和版本化配置组成业务包。本项目仅提供通用配置、注册入口和运行保证；仅安装 Skill 不会自动获得持久触发、幂等和状态同步。交互动作复用现有表单与回调，再补必要的版本校验，不必先做通用卡片 DSL。

共享案例应经显式授权进入团队可读范围，原群权限不能因为“提炼成知识”就失效。原始材料与共享摘要分别保留可见范围；读取时按当前授权过滤，撤权、删除和到期能影响后续使用。匹配已知案例只意味着可以关联和减少通知，出现新影响或差异仍可新建、重新打开事项。

外部动作必须处理“请求已经成功但响应丢了”：先记录意图，使用下游幂等键，或通过请求前已保存、下游支持查询的关联键对账；已有外部 ID 时按 ID 查询状态。无法确认结果时进入待核对状态，避免盲目重试。现有本地任务幂等与飞书投递能力可以复用，但不能直接推导出第三方建任务也只会执行一次。

行动项导出后，明确标题、负责人、截止时间和完成状态各自由哪一侧负责。优先以外部任务系统为任务状态的权威源，Dutydeck 保留关联和同步时间；同步失败展示最后确认状态。incident.io 的导出模型提供了可参考的边界。[Follow-ups](https://docs.incident.io/post-incident/follow-ups)

**使用方四项规划如何使用底座（非本项目交付清单）**

| 团队规划 | 可复用的通用能力 | 使用方另行实现 |

| 自优化 | 反馈样本、版本化规则、回放比较、启停和回滚 | 分级/RCA 的评价指标；Argos 只生成建议和跟踪任务；向 Oncall Agent 导出授权范围内的 case |

人已确认的结论优先作为参考答案。自优化需要区分“模型答错”“上下文缺失”“负责人解析错误”“外部系统失败”，否则可能用改规则掩盖数据问题。回放按当时可见的信息执行，后续人工结论只用于打分，防止答案进入输入；保留未参与调优的样本，避免只对旧案例有效。

快照保存可观察的输入、输出、证据与动作结果，不依赖模型私有思维链。会过期的外部材料按数据权限和保留期保存必要副本及摘要，不承诺永久留存。首期回放限定为可拦截的受控工具接口；任意 CLI 的工具输出完整性与离线隔离未验证时，不宣称支持完整回放。

**实施顺序与完成标准**

| 阶段 | 完成后能做什么 | 验证方式 |
|---|---|---|
| 首期：通用群协作与持续执行 | 授权群内观察、选择性参与、轻量跟进记录、持续委托、条件提醒及暂停/恢复/取消，重启后继续跟踪 | 用入群初始化、每日总结、材料提交跟进等通用场景检查误介入、误记录、漏记录和误提醒；闲聊不发可见回执；重复事件不重复处理；少催不丢事项；取消使旧提醒失效；取消/停止回归全部通过 |
| 第二期：完善扩展运行能力 | 外部事件、上下文查询、动作和状态回传的通用契约 | 用测试扩展验证重复回调、响应丢失、改期、取消和撤权，无需实现某个业务系统的接入 |
| 第三期：评价与策略迭代 | 通用参与和执行策略经回放后可逐步启用 | 比较误介入、遗漏、误提醒、重复动作、人工修订率及成本；退化可回滚，领域评价与调优由使用方提供 |

主动判断的结构化输出和静默投递从首期就需要，但首期可先限制为确定范围内的记录与提醒。更主动的调查、自动归并和规则调优在验证之后扩大。

首期即可使用稳定主机上的单实例部署。对团队的日常依赖，需要可发现的监听中断、积压和补偿失败，以及数据库备份恢复演练；暂不以高可用集群为先决条件。本次没有测量实际吞吐、费用或在线可靠性，不给出工期或容量承诺。
