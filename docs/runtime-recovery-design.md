# 持久执行控制与恢复设计

属于完整产品 P0。数据库访问登记与单 Runtime 控制权已实现并通过独立复核；后续 Task/Attempt 事务单元正在实施，持久资源与交付恢复尚未完成。打开接口、实例绑定和关闭顺序按有效意见补实。它接续本地 owner、短写入序列、持久队列和 driver 退出核验，不能用现有进程内保证代替跨进程恢复。

## 现状与必须阻止的行为

本轮隔离双 Node 进程探针已证实：A 在真实 SQLite 上执行任务且 send 尚未结束，B 打开同一数据库并 initialize，能把 A 的 running 任务改成 interrupted。两个进程也能交替写同一配置。探针使用假 driver，没有启动 HTTP、真实 Agent 或飞书，临时数据库和两个子进程均已回收。

现有 daemon 的 cwd/最近目录指针与 PID 检查有防误启动作用，但不按数据库实体原子占位。前台默认命令和导出的 startLocalServer 可绕过它。service 在监听 HTTP 端口前已经初始化 Runtime，因此同端口失败也不能阻止恢复写入。Runtime.initialize 首先回收 verification 进程，再修改任务、准备工作区和恢复 PTY；门禁必须覆盖整个流程。

仓储打开还会启用 WAL、备份和迁移。数据库执行者排他、升级时的迁移排他与管理 CLI 访问应明确区分；只给 daemon start 增加 PID 文件不能覆盖它们。

## 控制权与旧资源是两个判断

同一数据库只允许一个活跃 Runtime 控制者。控制记录包含随机实例 ID、单调代际、数据库身份、宿主身份和 OS 进程启动身份。PID 单值、应用写入的 startedAt、心跳超时或 lease 过期均不能证明原进程退出。当前本地主机先证明原控制者已经结束，才允许事务内比较原版本并接管；并发接管只有一个成功，证据不可读时保持阻塞。

首选复用 SQLite 事务实现持久控制记录，避免另起通用分布式租约服务。控制记录的引导和 schema 升级必须在业务迁移与任何恢复动作之前完成，具体打开 API 与旧版本兼容路径需在实现前复核。实际数据库路径按已存在文件或父目录 realpath 统一；软链接、相对路径和不同 cwd 指向同一文件不能得到两份控制权。SQLite 不安全的硬链接别名不能默许为独立数据库。

只有原控制者已经结束，才获得控制数据库的资格；这不等于旧 Agent、tmux、验证命令和工具进程已退出。接管后先核对各类资源，再决定附着原轮次、继续未提交任务，或进入待核对状态。不能因为新进程的 driver Map 为空便创建同 key 的替代 Adapter。

正常释放先等待全部服务尾声和 Runtime.shutdown，关闭业务连接并完成文件权限处理，再由最后一个控制连接按版本释放登记，最后关闭控制连接。此后没有应用层尾声。启动失败也按同一顺序清理；关闭失败不能先写“已安全释放”。异常强退由后续启动核对真实进程身份。过期实例的最终提交、释放和迟到清理均带预期代际，不能覆盖新控制者。

## 仓储打开、升级与 Runtime 实例绑定

保留现有同步 `createRepositories` 入口，增加 `mode: 'runtime' | 'management'` 和 `upgrade: 'never' | 'if-idle'` 选项，避免为了门禁把所有调用改成异步。默认 management / if-idle 保留离线 CLI 首次建库行为；service 必须显式用 runtime 模式，在任何签名密钥或 token 写入之前预留控制权。所有持久库打开均参与登记，没有绕过门禁的旧导出。

每个 RepositoryBundle 有独立随机 accessId，即使同进程、同数据库也不能合并。当前 schema 下，管理 CLI 的访问可以与 Runtime 并行。需要业务升级时，if-idle 只允许没有其他活跃访问者的打开者进入维护阶段；never 明确报需要升级。维护阶段阻止新访问，完成 WAL、备份、迁移并重新验证 schema 后才暴露业务仓储。崩溃留下维护状态时，下一维护者先核对原进程并完成恢复检查，不能直接开放管理访问。

控制协议有独立版本，在业务 schema 之前以短 SQLite 事务引导。进程身份读取不占用写事务；事务内比较已检查记录的完整版本，清理或接管时重新核对。没有 TTL、心跳抢占或长期数据库事务。路径先统一实体；硬链接别名拒绝，不能让 SQLite 为同一实体维护两套旁路 WAL。

仓储暴露 `control.attachRuntime(runtimeInstanceId)`，返回带代际的 claim，提供 `assertCurrent()` 和释放当前实例绑定的方法。Runtime.initialize 的第一项操作取得该绑定，在 verification 回收、任务修改、工作区准备和任何驱动恢复之前检查。management 打开者如显式构造 Runtime，也必须在此原子晋升并排除现存控制者。随机 runtimeInstanceId 由 Runtime 构造时生成，同一 bundle 的第二个活跃 Runtime 不能复用第一个 claim。

有副作用的 Runtime 公开入口必须持有当前实例的有效绑定，否则返回 RUNTIME_NOT_INITIALIZED；包括可能进行工作区恢复写的 getter，不能绕过 initialize 直接 send 或触发恢复。纯读取可使用仓储管理入口。初始化内部在已取得 claim 的范围内恢复，不能借用另一实例的绑定。现有恢复测试中直接构造第二个 Runtime 并 send 的写法需要改为先关闭原实例、再显式初始化新实例，保留原会话、任务、系统提示词和仅提交一次等断言。

同一实例的并发 initialize 共享一次 Promise；初始化成功后重复调用不再恢复或覆盖配置。初始化失败不能继续执行任务，也不由下一次 initialize 悄悄重复部分恢复；完成清理后使用新实例。shutdown 撤销正在初始化的实例，仍须等待其真实写入尾声。初始化后编辑配置使用已有管理入口。

Runtime 完成 shutdown 后可释放自身绑定，允许调用者在同一 bundle 上重新构造 Runtime；该 bundle 的数据库控制预留仍保留到仓储关闭，其他 bundle/进程不能趁服务收尾间隙接管。只有当前实例可以释放自己的绑定，下一次绑定获得新的代际；旧 claim 之后不能提交或释放新绑定。仓储关闭须先确认活跃 Runtime 已停止接收并完成其写入尾声，不能由 close 偷偷替代 Runtime.shutdown。

`:memory:` 保持独立数据库语义，同时检验同一 bundle 的实例绑定；没有持久跨进程身份可以恢复。Linux 的真实进程启动身份与退出证据先单独验收；其他平台必须有实际可核验的实现和对应实测才能声明支持；弱身份匹配不得当成原进程归属或停止授权。macOS 的数据库回收采用单独设计的保守死亡证明，匹配不充分时保持 unknown，见 [平台设计](macos-database-control-design.md)。

旧版本不登记的 daemon、CLI 和任意 SQL 客户端不会被新控制表拦住。首次启用及不兼容升级必须走明确的离线切换流程；没有访问记录不能证明旧进程不存在。备份恢复、数据库文件替换和克隆还需核对物理实体与旧资源定位，不能默默把副本当作原实例已经安全退出。

## 任务有可持久核对的执行尝试

保留 Session、Task 和 Attempt 的区别：Session 是原生上下文，Task 是用户已接受的指令，Attempt 是一次实际执行或恢复尝试。每个 Attempt 保存任务/会话、控制者与代际、执行器、原生恢复定位、提交阶段、资源登记和终态依据。重开 Runtime 不能仅凭 task.status 推断指令是否发出。

| 已保存事实 | 崩溃后的行为 |
|---|---|
| queued，未进入提交 | 原任务按持久顺序执行，不另建任务 |
| preparing，确定尚未提交 | 重新授权和准备，同一任务继续 |
| 提交意图已落库，对端是否接受不明 | 核对原生句柄/回执，不能自动再发 prompt |
| PTY 原轮次与 transcript cursor 可核实 | 附着原轮次，保留原 task/turn，回放去重 |
| ACP 原上下文存在，活动轮次不可附着 | 保留上下文和不确定结果，先核对；不声称继续了原活动轮次 |
| 执行终态已持久化，通知失败 | 仅重试交付，不重跑指令 |
| 停止未核实 | 保留资源阻塞和任务核对入口，不自动重建执行器 |

提交意图先落库，再调用驱动。即使进程恰在两者之间崩溃，也只能得到保守的不确定状态，不能以可能未发送为由自动重发。新的 checkpoint 尚未实际提交与历史已提交轮次的恢复等待必须分开；第二次 daemon shutdown 不能把恢复中的 running 任务降回 queued。

资源登记先记创建意图，再记录实际进程或原生会话身份。SDK 的外层 Promise 已结束不代表底层创建结束；沿用 P0 的真实创建观察范围。突然崩溃留下没有结果的创建意图时必须阻塞并核对，不能假造 PID 或用新 Adapter 的资源集合替代旧证据。进程身份不明、权限不足及任意脱离受管范围的后代仍需明确显示，平台隔离由 P3 补齐。

## 接收、执行与交付各自恢复

接受消息的幂等键、完整任务和队列位置在同一事务落库；相同键重投返回同一任务及状态，变化的载荷报告冲突。队列领取记录唯一 Attempt 和控制代际，不能由两个 drain 各自执行同一 queued 记录。

任务终态与待发布事件记录在同一事务提交。事件编号由数据库事务分配，本地链继续负责有序消费；不能先保存终态，再依赖一个易失的 Promise 保证通知不丢。网络交付引用持久待交付记录，失败可独立重试，执行成功不因卡片或 SSE 交付失败改成失败。

平台发送的超时可能表示“已发送但回执丢失”。有幂等或查询能力时按原交付 ID 核对；没有时记录不确定交付，不能无限盲重试并声称 exactly once。P6 接入真实平台前需用对应 API 的实际样本验证这一点。

## 用户恢复入口

Web 和 CLI 均能查询原任务、尝试阶段、原控制者、资源核验结果与待交付状态。用户可以重试仅失败的交付、附着已核实的原轮次、停止已识别的旧资源，或对不确定结果作出明确决定。重试执行另建 Attempt 并保留前次证据；不得把历史未知状态改写成“从未执行”。

解除 stop-block 要保存操作者、依据和原 runId，并与当前资源记录匹配。自动证明与操作者对不确定结果的决定分别记录；人工选择不能伪装成内核已经证明退出。仍活着的原控制者不能被普通恢复按钮抢占。真实生产资源的停止与源 Botmux 切换属于后续具体操作授权，本次开发只使用隔离样本。

## 实施与验收顺序

1. 固定数据库控制记录、打开/迁移顺序和持有期；覆盖前台、daemon、直接 service 调用、同库不同端口和路径别名。管理 CLI 的在线读取、写入与离线迁移各有明确入口，不能因引入控制权而无声失效。
2. 持久 Attempt、领取和提交阶段接入 Runtime；覆盖所有恢复动作和提交位置。先封住双进程反例，再补运行中控制者死亡和并发接管。
3. 接通各驱动的资源/原生轮次核对与 stop-block 解除，保留 PTY 原有 detach/recover 保证。
4. 完成持久待交付记录和用户恢复入口，进行真实 SQLite、真实本地子进程的分阶段崩溃注入。

验收至少包含：活控制者拒绝第二实例；第二实例不能杀第一实例的 verification；迁移并发启动；进程正常关闭与 SIGKILL 后重开；PID 复用/身份不可读；同一提交点多次崩溃；恢复途中再次重启；外部接受结果未知；执行完成后交付失败；旧控制者迟到提交与释放。macOS/平台供应商实测单列，未经验证不计完整产品验收通过。
