# 飞书交互审查：先让状态和操作可信

> **说明**：修复前历史审查，文中当前/下一轮指基线 61b6e5a；最终结果见 feishu-ux-delivery-20260916.md。原历史内容保留。

审查基线：`61b6e5a6462eb66e08c87f83cca82e7e9822920e`，2026-09-16。当前服务已部署该版本。本轮只做审查，未改业务代码、线上配置或发送消息。

**当前飞书端能完成正常的发起、执行和结果回传，但用户遇到等待、取消、重启恢复时，卡片显示与实际执行存在明显断点。下一轮应先修复操作和状态的一致性，再改善引导与信息层级。**

从用户视角，每张任务卡应让人回答四个问题：有没有收到我的要求；现在在做什么、等什么；是否需要我操作；完成了什么、还剩什么。当前第一项已有接收表情和过程卡，后面三项在异常路径上不够可靠。

| 用户操作 | 当前体验判断 | 下一步重点 |
| --- | --- | --- |
| 首次 @ 机器人 | 正常接收有回执；托管群权限拒绝可能完全静默 | 明确请求必须收到“已接收”或“未执行＋原因” |
| 在话题中继续沟通 | 隔离与续聊已有能力；上下文边界不够可见 | 告诉用户在哪里续聊，顶层查询提供任务导航 |
| 等待执行 | 能看到阶段、工具和终端记录；排队、思考、恢复混在一起 | 展示实际阻塞原因和下一步，减少日志承担解释的情况 |
| 回答问题或批准操作 | 已支持工作流提问；选项入口及失效状态仍不完整 | 可回答时有入口，过期后立即关闭并给恢复方法 |
| 取消、重试、重开 | 存在已复现的操作未落实问题 | 优先修复，不能只改卡片文案 |
| 查看和验收结果 | 独立结果卡方向正确；长文附件和历史失败削弱结果判断 | 首屏保留结论、交付物、未完成项和验收入口 |

**优先级说明**：P1 为操作失效、误报状态或阻断用户继续；P2 为容易误解、重复操作或增加阅读成本。不据此推断线上发生频率。

**P1：取消和中断必须对应真实执行结果。**

已复现两条不同问题：

- 取消排队按钮及部分 `/cancel` 路径没有把操作人传给执行记录层。按钮先返回成功类型的“正在取消排队任务”提示，后台却拒绝操作，任务保持 `queued`。`/new` 的停止旧会话路径也缺操作人；有队列时可能先停止进程，再失败并留下待核对任务和队列。
- 真正的终端驱动收到中断后没有输出任务结算事件。运行层将任务设为 `reconcile_required`（无法确认执行结果，需要核对），飞书卡片却提前标为“已中断”，后续任务继续排队。

这会直接破坏用户对“停止”按钮的信任。建议贯通操作人身份；按钮收到请求时显示“正在停止”，确认执行结束后才显示“已停止”。无法确认时明确显示“停止结果待核对”，提供后续处理入口。

验收：使用真实 Runtime、SQLite 和 PtyCliDriver 验证取消、中断、重开；取消只影响选中任务，中断确认后才释放队列。不得只用会主动发完成事件的假驱动验收。

证据：[取消调用](../apps/server/src/lark/coordinator.ts#L1579)、[重开调用](../apps/server/src/lark/coordinator.ts#L1136)、[中断卡片更新](../apps/server/src/lark/coordinator.ts#L1616)、[终端中断](../packages/pty-driver/src/driver.ts#L355)、[缺结算事件处理](../packages/agent-runtime/src/index.ts#L1395)、[操作人校验](../packages/storage/src/task-execution.ts#L726)。本地隔离功能检查已复现，[实测输出](/tmp/dutydeck-ux-review-20260916/observed-results.json)；未操作线上任务。

**P1：排队和恢复不能让用户无期限等待。**

需要核对的任务，在恢复过程卡中可能显示“运行中”，在 `/tasks` 中却显示“已结束”，现有取消和重试选择器又不处理它。同一任务在不同入口表达不同含义，用户无法判断该等还是该处理。

真实话题还提供了一个值得跟进的样本：9 月 16 日 10:35 的只读快照中，两条任务已排队 13.39 小时；对应会话为 idle，任务没有 attempt。飞书卡片最近一次更新在 10:28，仍写“排队中 · 用时 796m”和“正在思考中…”，没有取消入口。两条记录来自同一条用户消息，对应两个机器人。

进一步只读检查确认，两条任务都有 `DRIVER_RESOURCE_UNSAFE` 和 `DRIVER_STOP_BLOCKED`：执行记录尚未确认旧驱动资源已安全结束，且保留着停止阻塞标记。队列认领会检查这些条件；飞书卡片没有把已知阻塞原因呈现给用户。两条任务的冻结输入版本均为 2，校验完整，收件记录和发送人字段齐全，排除了“旧版输入缺失”的假设。**最初停止失败和双机器人接收的原因仍为 unverified**，本轮未尝试解除阻塞。它们也不是上一轮已修复的“回答被误当作新任务”的同一话题。

建议统一“排队中、执行中、等待你、需要核对、已结束”的含义。排队卡展示等待对象和已等待时间；没有可继续执行的条件时，转为明确的阻塞提示。不要给没有依据的预计完成时间。恢复入口须校验当前权限和原执行状态，不能直接重新执行可能已经产生副作用的工作。

验收：重启、历史输入缺失、未知执行结果三类场景中，过程卡、`/status`、`/tasks` 表达一致；用户能找到查看原因、取消或重新提交的适用入口。

证据：[恢复映射](../apps/server/src/lark/reconciler.ts#L99)、[任务导航状态](../apps/server/src/lark/task-dashboard.ts#L89)、[队列认领检查](../packages/storage/src/task-execution.ts#L624)、[只读阻塞检查摘要](/tmp/dutydeck-ux-review-20260916/live-blockers-summary.json)、[真实话题](https://applink.feishu.cn/client/thread/open?open_chat_id=oc_f136323ebbade983a5c5c97af6c2effa&open_thread_id=omt_19cd4ce2b24f9b84)。现场卡片 ID：`om_x100b65a00ca530a4b347f387156889e`、`om_x100b65a00cb60cacb4a7e0caceded54`。

**P1：提问必须有完整的等待、回答和过期状态。**

真实 broker 与工作流检查发现：问题超时后，broker 已 expired，但交互记录仍 pending，卡片保留“等待回答”和选项。点击后才报失效，且没有更新旧卡；交互记录改为 expired 后，任务结束清理又会跳过它。

建议在问题卡显示期限及回答方式；超时主动关闭选项，并说明如何重新发起。对过期卡的点击也补做卡片更新，避免错误入口长期保留。

验收：超时后一个心跳周期内显示“已过期”、移除可操作选项；点击旧卡不会新增任务，也不会继续显示“等待回答”。

关于上一轮的终端选项需求，需要区分已交付和剩余范围：`session ask --choices` 及普通话题回答路由已在当前版本中；当前两个机器人配置均未开启结构化提问卡，因此仍以文字方式呈现选项。任意终端原生菜单的自动识别、转为飞书卡片并把选择写回终端，仍是能力缺口。产品上应优先让常见的单选、多选和文字回答在飞书完成，并明确无法处理的原生菜单如何继续；本轮没有改变配置。

证据：[失效回答处理](../apps/server/src/lark/workflow-interactions.ts#L371)、[心跳处理](../apps/server/src/lark/coordinator.ts#L276)、[复现输出](/tmp/dutydeck-card-ux-review-20260916.json)。

**P1：明确 @ 的请求被拒绝时，应告诉用户发生了什么。**

托管群授权拒绝发生在接收表情和命令解析之前，直接返回。用户即便发 `@机器人 /help`，也可能没有任何反馈。群配置未生效的异常还有只记日志的路径。当前线上为 `legacy_unmanaged`，这条结论来自托管模式的代码和本地复现，不能宣称两个线上机器人都触发了该问题。

建议显式 @ 的人类请求得到简短的“未执行＋原因＋下一步”；只读帮助按自身权限判断。未唤醒机器人的普通群聊继续保持安静。

验收：无权限、群停用和配置未生效均有可理解回执，不创建任务；普通闲聊不增加机器人消息。

证据：[授权后静默返回](../apps/server/src/lark/coordinator.ts#L674)、[群配置检查](../apps/server/src/lark/group-management.ts#L289)。本地显式 @ 拒绝场景中，发送与 reaction 调用数均为 0。

**P2：首次使用和上下文边界要说清楚。**

欢迎卡提示“发送 `/help`”，但默认必须 @ 才唤醒，照抄会没有回应。当前两个机器人的 `mentionPolicy` 都是 `always`。另外，逐话题模式下，用户换到顶层查 `/status`，可能得到“会话尚未创建”，即使另一个话题中任务仍在执行。

建议欢迎卡只给当前配置下可用的例子，例如“`@当前机器人 /help`”，并说明在哪继续回复。顶层找不到当前会话时，提示“这条消息不在已有任务话题中”，给 `/tasks` 或原话题入口，不暗示所有任务都不存在，也不要自动绑定最近任务。

验收：每种唤醒策略的欢迎示例都可实际触发；已有其他话题任务时，状态查询能引导找到任务，且不串用户或机器人的上下文。

证据：[欢迎文案](../apps/server/src/lark/welcome.ts#L74)、[唤醒判断](../apps/server/src/lark/coordinator.ts#L668)、[空会话提示](../apps/server/src/lark/coordinator.ts#L1152)、[私聊话题隔离](../apps/server/src/lark/session-resolver.ts#L199)。逐话题 `/status` 已本地复现；不代表当前所有私聊都使用该配置。

**P2：控制命令不能制造新的困惑。**

`/cancle` 会提示是否想用 `/cancel`，同时仍作为普通请求交给 Agent，可能新增排队任务。另一个断点是帮助承诺已取消任务可重试，但真实取消队列产生的 `cancelled` 不在 `/retry` 选择范围中。

建议明确接近控制命令的拼写错误只给纠正提示，不新增任务，也不自动执行猜测的命令。统一取消状态与重试能力；如果不支持重试，说明需重新发送。路径和无关原生命令保持已有透传行为。

验收：`/cancle` 不调用 Agent、不自动停止；用户随后明确 `/cancel` 才执行。已取消任务的帮助、列表入口和实际行为一致。

证据：[未知命令透传](../apps/server/src/lark/coordinator.ts#L805)、[重试选择器](../apps/server/src/lark/coordinator.ts#L1055)、[重试帮助](../apps/server/src/lark/commands.ts#L218)。

**P2：结果首屏应让用户判断是否达成目标。**

长文超出预算后只发送固定名称的 `执行结果.md`；任务标题、群 @ 和可见验收入口随之消失，验收说明藏在文件末尾。另一个已复现场景是第一次执行失败、重试成功，结果正文写“已完成”，下方仍突出“1 个步骤执行失败”，没有解释这是历史失败。

真实消息中，用户收到包含代码路径、调用链和请求表的长报告后回复“看不懂”。原话题还有 Agent 一轮结束、业务操作仍等待扫码的情况。这些样本提示：用户要判断的是请求完成了多少，轮次结束和工具调用记录不足以表达这一点。这里不对 Agent 业务分析的正确性作判断。

建议结果首屏固定保留任务名、简短结论、交付物、未完成事项及下一步。长文件配简短结果卡，群通知只在卡片上触发；历史失败留在记录内并明确标为“执行中曾失败”，不能靠命令名猜测哪些失败已经恢复。Agent 等待外部扫码时，结果应明确“尚待扫码”，避免把轮次结束作为目标达成的唯一表达。

验收：无需打开文件就能识别任务、知道是否需要继续操作并验收；全文可下载；重试交付不重复通知。失败后恢复的卡面不会暗示仍有未解决错误，历史证据仍可追溯。

证据：[长结果交付](../apps/server/src/lark/result-delivery.ts#L21)、[历史失败汇总](../apps/server/src/lark/card-renderer.ts#L758)、[“看不懂”话题](https://applink.feishu.cn/client/thread/open?open_chat_id=oc_f136323ebbade983a5c5c97af6c2effa&open_thread_id=omt_19cd4ce2b24f9b84)。文件分支的手机推送效果为 unverified，已确认的是发送载荷不包含上述卡片元素。

**P2：详细记录必须有可达入口。**

过程卡超过阶段上限时会写“完整记录见 Dutydeck Web”，但链接只在配置了合法 Web 地址时出现。本地已复现有指引无链接；当前 bdev-flash 的配置也没有 `webBaseUrl`。实际用户设备能否访问 mux 配置的内网地址，本轮未验证。

建议有可用入口才显示该指引；否则提供聊天内导出记录。当前状态和需要用户做的事留在主卡，终端输出继续作为展开后的排障材料。不要要求用户从“省略了多少字符”和历史报错行中推断任务状态。

验收：每条“查看完整记录”都有可执行入口；没有 Web 配置也能获取完整记录。飞书桌面端和手机端实际折叠、点击与可读性仍需客户端验收，本轮预览不能替代。

证据：[裁剪提示](../apps/server/src/lark/card-renderer.ts#L776)、[Web 入口条件](../apps/server/src/lark/service.ts#L422)。

**建议按三步实施。**

| 顺序 | 交付内容 | 用户能观察到的完成标准 |
| --- | --- | --- |
| 1. 修复操作和状态 | 取消/中断/重开、恢复状态、提问过期、拒绝回执 | 每次显式操作有真实结果；卡片和任务列表一致；阻塞时知道原因和处理方式 |
| 2. 完成常用对话路径 | 欢迎示例、上下文提示、结构化问答、命令纠错与重试 | 常见任务在飞书完成发起、回答、停止和续办；用户不必理解终端机制 |
| 3. 收敛结果与细节 | 结果摘要、长文配卡、历史错误表达、记录导出 | 用户能先判断结果，再按需看证据；完整内容仍可获得 |

**应保留的已有设计。** 过程卡与结果分开发送、过程同卡更新、长文完整保存、消息交付幂等、审批范围提示、任务上下文隔离都已有价值。此次隔离端到端检查通过了多机器人多群配置、话题续聊、重启后持久会话、权限排队及结果交付，说明正常路径有可用基础。下一轮应围绕上述断点修补，不需要整体重写。
