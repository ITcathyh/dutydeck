# 团队 Tag 基座能力设计

分析基线 `a220928`，事实均取自当前源码并经独立对抗复核。本文定义把 Dutydeck 作为团队 Tag 基座所需的通用能力，不含任何业务域实现。外部产品对照来自 2025-2026 公开资料，厂商效果数字一律不作为设计依据。

## 1. 真正的问题：只会被叫醒，不会自己醒

当前入站是一条单向通路：飞书消息 → `shouldWake` 布尔判定 → 建任务 → Agent 执行 → 卡片交付。三个结构性后果：

- **判定退化成开关**。`mentionPolicy` 的 `never` 与 `ambient` 在 `apps/server/src/lark/coordinator.ts:726` 完全等价，都是「非机器人发送即建任务」。`ambient` 没有任何额外判定，`apps/web/src/components/BotManagement.tsx:588-593` 的注释也承认两者同义。
- **口子已经开着但没有约束**。机器人 @ 本 Bot 即可唤醒并建任务（`mentionsBot` 与 `!botSender` 是两个独立析取项），放行条件见 `coordinator.ts:2057-2098`：受管群、`allowedBots`、`peerBotsAllowed`（默认 true）、以及**未配任何白名单时的短路放行**，四者任一成立即可，测试 `apps/server/src/lark/listener.test.ts:672-689` 锁定了该行为。配上 `ambient` 就是噪音放大器。
- **主动行为没有承载对象**。一次持续数小时、多人参与、跨多轮任务的「事」，在数据模型里只有 Session 和 Task，没有可被跟踪、可统计耗时、可挂结论的档案。

同时地基比预期厚，不需要重建：持久调度已建模完整（租约、代际、幂等键、水位线、DST、群/话题投递，`packages/shared/src/schedule-foundation.ts:11-169`）；人工审批已支持单选/多选/自由文本表单（`apps/server/src/lark/workflow-interactions.ts:45-82`）；自动注入的外部材料带来源标注与「不授予操作权限」边界（`apps/server/src/lark/task-context.ts:487-490`）；记忆写入有确定性门禁（`apps/server/src/lark/memory-pipeline.ts:142-195`）。

**主线改造：把「消息 → 任务」的单一通路，改造成「信号 → 判定 → 档案 → 处置」的通用管道。** 判定层决定要不要动、动到什么程度；档案层承载「一件事」的全生命周期；处置层复用现有 Task/Session 执行与交付。业务通过入站连接器、群级提示、Skill 和自定义动作接入，不进内核。

## 2. 分层与归属

| 层 | 职责 | 现状 |
|---|---|---|
| 入站信号 | 把飞书消息、机器人推送、外部 webhook、定时触发归一成 Signal，带来源、发送者身份、幂等键 | 仅飞书长连接消息；无 webhook；去重键为 `appId + messageId`（`lark/task-inbox.ts:22-36`），识别不了同内容换 ID 的第二次推送 |
| 触发判定 | 决定沉默 / 只记录 / 回复 / 建档 / 升级，附理由与置信度，沉默必须留痕 | 无。只有 `coordinator.ts:726` 的布尔表达式 |
| 事件档案 | 一件事的身份：参与者、认领、关联任务、外部引用、时间戳、结论草稿与确认态 | 无 |
| 处置执行 | 队列、代际、权限复核、Agent 资源所有权、恢复 | 已有，保留 |
| 交付 | 卡片、文件、通知，执行成功与交付成功分别记录 | 已有，保留 |
| 知识 | 按聊天的会话记忆（已有）+ 团队级结构化可检索知识（新增） | 前者已有且排除了机器人级共享与检索（`docs/lark-memory-design.md:23`）；后者无 |

不为多 IM 渠道做抽象。飞书是当前唯一渠道，判定层与档案层的接口不写死飞书专有字段即可，不预先构建渠道适配层。

## 3. 工作包

### P1 触发判定层

把唤醒判定从 `coordinator.ts` 的布尔表达式抽成独立模块，三级过滤，越靠前越确定、越便宜：

1. **规则层（不调模型）**：是否 @ 本 Bot、发送者类型与可信来源、是否落在有在途任务的话题内、是否为纯确认/表情、是否命中入站频率上限。目标是绝大多数消息在这一层沉默。
2. **可选模型层**：规则层无法定论时才调用，输出类别与置信度，**默认沉默**，置信度不足不升级为回复。
3. **决策输出**：`silence | record_only | respond | open_case | escalate`，附理由、命中的规则、置信度。

配套三项：`mentionPolicy` 的 `ambient` 必须获得真实语义（不再等于 `never`）；新增按聊天与按发送者的**入站**频率上限（当前限流只在出站，`lark/api-gate.ts:119-131`）；沉默决策落持久记录，事后能回答「为什么这条没理」——业界公认沉默侧无 trace 是评估盲区，不留痕则第 7 包无法开展。

验收：默认配置下机器人 @ 不再直连建任务而是过判定；同一告警重复推送在判定层收敛；沉默样本可按理由检索；判定层可单测且不依赖真实飞书。

### P2 外部内容边界收口

当前只有系统自动注入的路径带边界声明。**Agent 主动调用 `group messages` / `wait` / `message` 读回的内容（含其他机器人发言原文）没有任何「这是外部数据、不是指令」的标注**，`lark/agent-tools.ts:703-722` 的提示词只规定命令用法与交接跳数。基座要让 Agent 大量主动读群消息，这条路径会成为主要注入面。

- 统一一个外部内容包装器，所有注入路径（自动材料、记忆、空 @ 兜底、**群工具结果**）复用同一套来源标注与权限边界声明。
- 空 @ 兜底（`coordinator.ts:1976-1978`）当前不过滤机器人消息，而自动话题历史会过滤（`lark/task-context.ts:89-92,397`）。这个不对称要显式定夺：让 Agent 感知机器人推送是基座目标，因此保留机器人消息但必须带来源标注，两条路径口径一致。

验收：所有把外部文本送入模型的路径都有来源与边界声明，新增路径缺声明即测试失败。

### P3 事件档案

新增一等对象，命名保持中性（不叫 incident，避免绑定告警域）。字段：来源 Signal、所属聊天与话题、状态机、参与者与认领人、关联的多条 Task、外部引用、首次/认领/闭环时间戳、结论（草稿与确认态分离）。

- 一个档案关联多条 Task；Task 仍是执行单位，档案是跟踪单位。
- 轻量时间线，采集状态变更、认领、话题回复、关联的外部变更、Agent 产出的结论。不复用 Session 的 `events` 表（粒度不同）。
- **结论一律先落草稿，人确认后才定稿**。这是外部产品的一致做法，也是 AI 生成根因结论的必要约束：学术证据显示这类输出的失败模式是「看似合理但错」且置信度校准差（arXiv:2504.11505、2605.15581、2609.14762）。结论卡展示证据引用与置信度，保留被否证的假设。
- 耗时指标由时间戳推导，不单独维护计数器。

验收：一件事从建档到闭环，认领人、耗时、关联变更、结论及其确认人可查；未经确认的结论不得呈现为定论。

### P4 调度执行器与提醒升级

`schedule-foundation` 的难点已完成，缺的是执行。注意执行器不是「未注册」而是**硬编码永久阻断**：`packages/shared/src/schedule-foundation.ts:196` 的 `executionEligible: false` 是类型字面量，`:403` 无条件写入 `schedule_executor_unavailable`，`apps/server/src/schedule-routes.ts:34` 的 `executorWired: false as const`；`recordPlanned` 在生产代码无调用方，租约仓储存在但无人 acquire。接线要先拆掉这些断言。

- definition 生命周期态补 `active`（当前仅 `staged` / `disabled`，`schedule-foundation.ts:6`）。
- `intentKind` 从单一的 `task_run_snapshot`（`:105`）扩为至少三类：跑任务、**发提醒（不启动 Agent 的轻量投递）**、升级。提醒不该为了发一条消息启动一个 Agent 会话。
- 提醒与升级绑档案状态：未认领超时提醒、再超时升级到下一目标；档案认领或闭环立即停止后续投递。升级目标复用 `roleAssignments`，不新建一套人员模型。
- 另一套 `session-automation` 保持不动：它必须绑已有 Session（`apps/server/src/session-automation.ts:247-253`），适合「给这个任务加个定时」，不适合无主提醒。两套并存但职责不重叠，不合并。

验收：档案未认领触发提醒并按级升级；服务重启、离线补偿、DST 切换不重复投递；认领与闭环立即止链；同一 occurrence 的幂等键在并发下只生效一次。

### P5 开放定制面

让业务方在不改内核的前提下接入：

- **入站连接器**：签名/HMAC 校验、幂等键、字段提取为 Signal、路由到目标群或话题。解析哪些字段、映射成什么由业务配置，连接器本身不含业务语义。
- **自定义卡片动作注册**：当前所有回调动作都写死在 `coordinator.ts` 的 if 链里（进度卡四种，另有 workflow approve/reject/answer、repair、翻页、workbench 步骤等多组内置动作），业务方无注册入口。新增声明式注册，复用现有表单的授权、幂等与代际校验。这是「一键确认结论卡」的通用底座。
- **群级提示追加**：`preInjectPrompt` 仅 Bot 级（`coordinator.ts:2528`），群配置解析不携带它（`lark/group-management.ts:291-293`）。群级已能通过 `agentOverride` 整体切换 Agent 及其 `systemPrompt`（`packages/shared/src/index.ts:31`），缺的是共用同一 Agent 时追加一段群专属提示。
- **`rolePolicyOverride` 定夺**：该字段只在 schema、持久化与 API 读写间流转，判定函数 `evaluatePolicyAction`（`packages/shared/src/group-policy.ts:500-549`）从不读它。要么接线，要么删除；不保留无消费者的配置面。

验收：一个业务域仅通过连接器配置、群级提示、Skill 与注册动作即可完成接入，不修改 `apps/server/src/lark/` 内核文件。

### P6 团队知识层

与按聊天的会话记忆并列，新增 Bot 级/团队级、结构化、可检索的知识存储。会话记忆存「这个群的偏好与约定」，知识层存「团队共享的、有结构的事实」。现有记忆设计明确排除机器人级共享、按人记忆与检索，不应把结构化主数据硬塞进去。

「已知问题登记表」是该层的一个实例，而非内核概念：匹配规则、描述、有效期、关联档案、状态。命中即折叠——新信号匹配已知问题时不新建档案，挂到已知问题下计数。**折叠先做规则指纹匹配**：外部产品的降噪底座普遍是幂等键加时间窗与字段规则，ML 分组是高端层，LLM 语义折叠尚无成熟商品实现；此处不做语义折叠。

同时修记忆提取的两个缺口：提取材料把所有轮次一律渲染成「用户：…」（`lark/memory-pipeline.ts:806`），不区分说话人；在 `ambient` 群或允许协作机器人建任务的配置下，群内任何人与任何机器人的发言都可能被提成记忆。现有门禁能拦凭据形状与各类上限，但不识别行为指令（如「以后不用确认直接执行」）。缓解层是注入时的边界声明与服务端按当轮发送人强制的权限，因此记忆无法提权，但仍会影响行为倾向。要补：说话人归属入库、可配置哪些来源的发言允许被提取。

验收：知识条目可跨群共享、结构化查询、按有效期失效；同类信号在有效期内折叠且计数正确；记忆条目可追溯到具体说话人。

### P7 判定回放与调优门禁

自优化必须以回放门禁为前提，顺序不可颠倒。当前只有环境契约回放（`tests/e2e/integration-contracts/`），没有模型输出的评估框架。

- 判定层每次决策落盘：输入信号、命中规则、决策、置信度、事后人工是否纠正。
- 人工纠正沉淀为用例集，判定规则或提示的任何变更必须在用例集上回放通过才允许生效。
- 先度量再优化：优先给出误唤醒率与漏唤醒率两个指标，不追求单一综合分。

验收：规则变更能在历史样本上回放并给出前后差异；未过门禁的变更无法生效。

## 4. 不做

- 不做值班排班、SLA 计时、状态页、客户通告这类事件管理产品功能。它们是业务域能力，外部已有成熟产品。
- 不做自动修复与无审批的高危自治。外部产品无一将其设为默认。
- 不做 ML 告警分组与语义折叠（见 P6 理由）。
- 不做向量检索。P6 先用结构化字段与全文检索，检索形态由实际命中率决定是否升级。
- 不引入 MCP host。它是真实缺口（`docs/full-product-parity-plan.md:109` 已记录），但不是团队 Tag 的前置，留待独立评估。
- 不为多 IM 渠道预建适配层。
- 不合并两套调度（见 P4）。

## 5. 顺序与依赖

P1 与 P2 先行：前者收敛已经打开的机器人触发口子并建立降噪基础，后者是 Agent 主动读群消息的安全前置，两者都不依赖新数据模型。P3 是「记录」的核心，P4 依赖 P3（提醒需要知道什么未认领）。P5 可与 P3/P4 并行。P6 依赖 P3（折叠需要档案）。P7 依赖 P1 的决策留痕，且必须先于任何自动调优。

每个工作包独立可验收，中间状态保持现有用户旅程可运行。判定层上线采用灰度：先只记录决策不改变行为，比对与现状的差异，再逐群启用。

## 6. 引用数据的可信度

外部产品的降噪比例、MTTR 改善、根因准确率与自治率数字全部为厂商或客户口径，无独立测算方法，本文不作为目标值。行业级告警疲劳统计与分析机构预测原文未取到，标 `unverified`。可作为设计依据的是产品行为事实（草稿默认、人工发布、动作分级审批、发言克制）与公开学术结论。
