# Dutydeck 跨端交互设计蓝图

> 日期：2026-08-30  
> 状态：本轮交互重构的执行规范  
> 范围：飞书消息、飞书卡片、Dutydeck Web，以及三者之间的状态契约

## 1. 产品范式：用户义务优先的 Agent 操作台

Dutydeck 不是“聊天机器人加一个管理后台”，也不是展示 Agent 忙碌程度的监控大屏。它是一个以“用户此刻应该做什么”为首要秩序的 Agent 操作台。

核心排序不按数据类型、机器人或工作区划分，而按用户义务划分：

1. **待你处理**：系统无法自行前进，需要授权、补充指令、修正失败或恢复任务。
2. **进行中**：系统已承诺推进，用户通常无需操作，但可查看进度。已排队的任务也属于此层。
3. **已完成**：已交付、可回顾的任务，用户没有当下义务。

**已归档与这三层正交，不属于第三层**：归档任务是只读历史，被整体排除在三层之外，只在“已归档”筛选下出现，其计数也独立于三层，不与任何一层相加。

代码中这三层的内部标识依次是 `attention` / `active` / `recent`；`recent` 是历史命名，用户可见的分区标题与筛选芯片一律写“已完成”。本文其余章节出现这三个英文名时，指的都是内部标识。

这一范式有五条不可妥协的原则：

- **先给结论，再给过程**：用户先看状态、结果与下一步，执行轨迹是证据，不是主角。
- **显示义务，不只显示机器状态**：“等待授权”必须同时告诉用户要授权什么；“失败”必须指向查看原因与恢复。
- **一个状态，一个主要下一步**：同一任务在同一界面上只突出一个主操作，其他能力下沉到详情。
- **不用颜色单独表意**：状态必须有文本，可辅以图标和色彩；颜色不是状态的唯一载体。
- **诚实表达系统能力**：有排队的任务数与待执行的指令数是两个不同的计量单位，不混用；没有历史数据不伪造趋势；没有最终输出要直说“结果不完整”。

## 2. 跨端分工：聊天下达，卡片承诺，Web 深挖

### 2.1 聊天消息：下达与追加

飞书聊天是最低成本的意图入口，承担新任务、补充要求、追问结果与恢复上下文。它不承担完整的调试和运维界面。

- 单聊中，每条有明确意图的消息可直接进入任务。
- 群聊中，以 `@机器人` 和原消息/话题为上下文边界，回执应留在原问题附近。
- 仅 `@机器人` 但没有明确请求时，允许用最近上下文识别指代，但必须先复述理解并请用户确认；确认前不产生副作用。
- 聊天中不堆叠工具日志、内部分析和多个等权操作。

### 2.2 飞书卡片：任务承诺

进度卡不是 transcript 的另一份拷贝，而是系统对用户的可见承诺：“这个请求已经接收，会被执行，并会收敛到明确终态。”

卡片仅保留以下信息层：

1. 任务名与 Agent/工作区身份。
2. 当前状态与已用时。
3. 有用的当前进度，而非无界增长的日志墙。
4. 异常、风险或需人工介入的明确原因。
5. 与当前状态匹配的唯一主操作，例如“取消”或“重试”。

卡片一旦进入终态，就从“承诺”转为“收据”，不再被后续轮次覆写。

### 2.3 Dutydeck Web：证据、诊断与精细控制

Web 是任务的深度工作面，承担聊天和卡片不适合展开的信息：

- 跨工作区的任务优先级和全量过滤。
- 完整执行记录、工具调用、错误细节与上下文。
- 需要时的终端、任务中断/重启、排队指令管理和归档。
- 复杂输入，包括文件引用、模型与思考强度选择。

跨端导航文案必须诚实。当飞书运行为 `full-trust` 时，Web 入口只说“下达任务、跟进执行与接收结果”，不暗示用户可在飞书内回复授权。

## 3. 跨端状态与“单一下一步”

Runtime 任务是状态事实源；飞书 reaction、卡片和 Web 只是不同密度的投影。各端可以使用适合当场的文案，但不得改变状态含义，也不得让终态回退为运行态。

| Runtime / 信号 | 用户含义 | Web 层级 | 飞书表达 | 唯一主要下一步 |
| --- | --- | --- | --- | --- |
| 消息刚接入、尚未建立任务 | 系统已看到请求 | 尚不展示为稳定任务 | 原消息上固定 `OK` reaction | 等待进度卡 |
| `queued` / `created` 且已有排队指令 | 任务已接收，将被执行 | 进行中 | “已接收/排队中”进度卡 | 查看排队进度 |
| `starting` / `thinking` / `running_tool` / `running` | Agent 正在推进 | 进行中 | “执行中”进度卡 | 查看进度 |
| `waiting_for_permission` | 任务被保护操作阻塞 | 待你处理 | 说明需前往 Web；飞书 `full-trust` 链路不伪造授权入口 | 前往 Web 查看并处理 |
| `idle` / 无排队指令的 `created` | Agent 在等待明确目标 | 待你处理 | 请用户补充要求 | 补充下一条指令 |
| `interrupted` / `stopped` | 本轮已停止 | 待你处理 | 冻结取消收据 + fresh final | `interrupted` 输入新指令继续；`stopped` 重新启动（从空白上下文开始） |
| `failed` | 任务未成功收敛 | 待你处理 | 冻结失败收据 + fresh final | 查看原因后重试 |
| `completed` | 结果可以验收 | 已完成 | 冻结完成收据 + fresh final | 查看结果 |
| `archived` | 只读历史 | 不进入任何分区，仅“已归档”筛选可见 | 无新交互 | 查看历史 |

主操作文案采用“动作 + 对象/原因 + 预期结果”，例如“查看失败详情，修正后重新运行”。禁止用“处理”“继续”这类缺少对象的抽象动词作为唯一指引。

## 4. 飞书时序：reaction → 进度卡 → 冻结收据 + fresh final

```text
用户消息
   │
   ├─ 立即添加固定 OK reaction（短暂的接收确认）
   │
   ├─ 解析/路由失败 ──→ 移除 reaction + 只读失败回执
   │
   └─ 创建可变进度卡 ──→ 移除 reaction
          │
          ├─ 排队/执行：原卡片更新状态与精简进度
          │
          └─ 终态：原卡片冻结为只读收据
                 └─ 以新消息发送 fresh final（结果/失败原因/取消结论）
```

### 4.1 Reaction 是回执，不是状态

- reaction 固定使用 `OK`，不随机使用微笑、鼓掌等可能带情绪的表情。
- 它只表示“请求已被接入”，不表示已开始、已成功或已认可内容。
- reaction 在进度卡成功建立或失败回执送达后移除，避免两个竞争状态并存。
- reaction 失败不影响任务执行，但必须纳入日志与延迟监测。

### 4.2 进度卡可变，但不做日志墙

- 从“已接收”到“执行中”使用同一张卡片，保持群聊位置稳定。
- 心跳更新受频率限制；限流时保留上一份成功内容，不闪回空白。
- 运行时最多展开最近且完整的阶段；内部分析只告知“已完成”，不暴露推理原文。
- 工具调用、异常和风险提示必须按完整阶段呈现，不用滑动窗口切断语义。
- 操作按钮随状态收敛：排队可取消，运行可中断，失败/取消可重试，只读卡不提供假操作。

### 4.3 终态使用两件套：冻结收据 + fresh final

任务完成、失败或取消时，不将长结果继续塞进早已滚出视区的进度卡。

- **冻结收据**：原进度卡变为只读，记录任务终态、已用时，并明确说明最终结果已作为新消息发送。
- **fresh final**：在当前对话的最新位置发送独立终态消息，先显示执行结论，再给精简证据摘要和下一步。
- 完成时，fresh final 展示真实 final assistant text；如果工具还有未收敛调用，不得将阶段性文字提升为完成结论。
- 默认在完成结果中折叠详细 trace，只保留证据摘要和 Web 深挖入口。
- 群聊中的下一步明确写为“回复当前消息并 `@机器人`”，避免用户在群里盲目续话。
- 重试必须创建新进度卡，不覆写旧收据。每轮 fresh final 使用任务 ID、轮次和终态生成幂等键。
- 进程重启后由对账器恢复终态。“收据已冻结且 fresh final 已送达”才算交付完整。

## 5. Web 信息架构：Bot 接入 → 待你处理 → 进行中 → 已完成

### 5.1 首屏先答“Bot 能不能收到我的话”，再答“有什么在等我”

飞书 Bot 是 agent 交互核心，Web dashboard 为它服务：承担 Bot 接入状态、配置、任务记录与排障。首屏因此分两段。

- 上段是飞书 Bot 概览：主操作是绑定或管理 Bot。无 Bot 时说明绑定后在飞书私聊发目标、群聊 `@机器人`，并用 `/help` 查看可用操作；有 Bot 时逐个展示名称、Agent、工作区与准确状态。
- 下段是任务列表，用于查看进展、失败与历史。页首那句话仍回答“有几个阻塞项、有几个正在进行”。
- Web 创建任务保留为次操作（`variant="secondary"`），不与“绑定/管理 Bot”争夺主操作层级。已有筛选、导航、搜索、键盘与移动端能力全部继续可用。
- 删除营销式大 Hero、英文 slogan、背景网格、渐变与不承载信息的装饰。已有任务以整行作为进入详情的主操作。
- 同屏不得出现两颗可及名相同的绑定按钮：绑定/管理入口在 Bot 概览卡片里只有一颗，侧栏“飞书接入”是另一处常驻直达（打开任务后概览卡片已卸载）。

### 5.1.1 Bot 状态只能来自真实字段

状态投影集中在 `apps/web/src/lark-status.ts`，首页、侧栏与设置面板共用，缺字段一律不当在线：

| 判据（按顺序） | 用户可见状态 |
| --- | --- |
| 查询未就绪 | 状态加载中 |
| 查询失败（含已有缓存但本轮 refetch 失败） | 状态未确认 |
| 无记录 或 `setupComplete === false` | 配置未完成（尚未选择默认 Agent 或确认执行权限） |
| `LarkConfig.listeningDisabled` | 本次启动禁用监听 |
| `listening === false` | 用户暂停监听 |
| `activeListening === false` | 监听尚未启动 |
| 以上都不命中 | 监听已启动 |

聚合口径（侧栏 hint 那句“N 个机器人 · …”）必须先逐个投影再看聚合，不得在聚合层前置判断 `listeningDisabled`：那会与本表的顺序打架——“未配置完成 + 全局禁用监听”这一组合下，卡片说“配置未完成”而 hint 说“本次启动禁用监听”。“本次启动禁用监听”只在每个 Bot 都落到该档时才作为整体结论显示；这不表示它不算阻塞，它在本表里仍排在 `listening` / `activeListening` 之前。

“状态未确认”与“配置未完成”不可互换：查询失败时 `isLoading` 为 false、`data` 为 undefined，把它读成“没有 Bot”就是把“读不到”说成“没有”。有缓存时列表照常列出 Bot，但每张卡片都降级为“状态未确认”，不沿用旧值宣称在线。

`setupComplete` 在服务端等于 `Boolean(defaultAgentId && fullTrustConfirmed)`，所以它只能表达“Agent 与执行权限是否齐备”，不得据此声称机器人能力、事件订阅或版本发布未配置。

`activeListening` 只是 listener 启动标记，不证明 WebSocket 已连通、更不证明消息已送达。文案上限是“监听已启动，可到飞书发送消息”，禁止写“长连接已建立”“全部可用”“已验证消息送达”，也不把字段名暴露给用户。

当前没有可用 Agent 时，Bot 概览内给出“准备 Agent”入口并说明后果（机器人收到消息后无法执行），但不阻塞用户先配置 Bot。

“在飞书中打开”使用官方 AppLink `lark://applink.feishu.cn/client/bot/open?appId=<encoded>`（来源：飞书官网示例 <https://www.feishu.cn/content/7270877743058698268>）。App ID 必须 URL 编码，协议与域名写死，不猜 ID、不自造协议；文案需标明需要客户端。无法构造链接时退化为“在客户端搜索 <Bot 名>”的指引。

### 5.2 状态筛选是紧凑导航，不是指标墙

- 筛选顺序为：总览、待你处理、进行中、已完成、已归档，共 5 项；数字快捷键 1–5 必须严格对应这个视觉顺序，不得让按 2 跳到屏幕上的第 3 项。
- “失败”不单列为筛选项。失败与已停止属于“待你处理”——§1 对该层的定义本就包含“修正失败”，单列会让同一个任务在两个筛选项下重复出现，也会让“待你处理”的数字看起来比真实待办少。具体失败原因在任务行内标注，不靠一个筛选项承载。
- “有排队的任务”不单列为筛选项：真实数据下该视图恒为 0，而任务行已显示“待执行指令 N 条”。
- 数字默认按“任务数”计算。“有排队的任务数”与“待执行的指令数”仍是两个不同口径，不得混用或相加；待执行指令总数以筛选条旁的说明性标签展示，它是一个计数说明，不是可点击的视图。
- 筛选芯片的计数与分区标题的条数必须来自同一个判据函数：除“总览”和“已归档”之外的每个筛选项都必须委托给分区判据，不得在旁边裸判 Runtime 状态。任何一处新增状态归属，都必须改那一个函数，不得在调用点旁另写一套条件。
- “已归档”是与三个分区正交的独立筛选：归档任务被排除在三个分区之外，其计数也单独统计，不与任何分区计数相加。
- 移动端使用水平滚动的 40px 筛选芯片，不将筛选项强行排成多行卡片阻塞首屏。
- 任何过滤视图必须展示全部匹配项，不以“最近 6 条”等无出口截断数据。

### 5.3 决策行必须支持快速决策

本节约束的是**主区的任务行**——用户在它上面判断“这条任务怎么了、要不要现在处理”。每行至少包含：

- 任务目标，截断显示时保留完整 `title`。
- 文本状态徽标，不只是一个彩色圆点。
- 工作区与 Agent 身份。
- 待处理任务的具体可行动原因。
- 如有排队，单独显示待执行指令条数，统一写“待执行指令 N 条”，所有入口不得再造第二种写法。
- “更新于 N 分钟/小时/天前”，并以 `title` 保留精确时间。

#### 5.3.1 侧栏一行是导航项，不适用本节

侧栏回答的是“有哪些任务、我在哪一条”，不是“这条任务怎么了”。它只保留**状态圆点 + 任务标题**，上面六项中的其余五项一律不出现在视觉层。

这不是宽度妥协，而是分工：桌面端 ≥768px 侧栏恒常可见，与主区任务列表同屏并列。让 248px 的侧栏逐项复述主区已给出且更完整的字段（主区还多给工作区名与失败原因），得到的是同一批信息在一屏内横向出现两次——实测 18 条任务时侧栏塞进 822 个字符，讲的全是右边讲过的事。

约束仍在，只是换了承载方式：

- **状态词必须留在可访问树**，用 `sr-only` 承载。读屏用户仍然听到“已归档”“失败”，圆点对他们本就是 `aria-hidden` 的装饰。§7.3“状态徽标的文字必须留在可访问树中”不因此松动，被禁止的是“只有一个彩色圆点、文字根本不存在”。
- **不得用颜色单独表意**（§1）同样靠这个 `sr-only` 文本满足。
- **任务身份（Agent、飞书来源、只读）也必须留在可访问树**，同样用 `sr-only`。它可以另在 `title` 属性里给鼠标用户备一份，但 `title` 不能是唯一载体——§7.3 禁止把信息只放在 hover tooltip 中，键盘与读屏用户拿不到 hover。
- 状态词、文字色、圆点色、是否呼吸必须出自同一个判据函数。此前它们各判各的，归档的失败任务显示成“已归档”+ 失败红。

#### 5.3.2 侧栏工作区分组默认折叠，但折叠必须真的省行

分组标题是折叠开关（`aria-expanded`），折叠时任务行**不进 DOM**——若改成 CSS 隐藏，读屏与 Tab 顺序里仍然躺着全部任务，降噪只对眼睛生效。

默认展开规则两条，都以“折叠是否真的省行”为准：

- **当前打开任务所在的组**默认展开：选中态藏在折叠区里等于没有选中态。
- **只有一条任务的组**默认展开：折叠它把“1 行任务”换成“1 行组头”，一行也没省，却让用户点两次才够得到那条任务。降噪的收益全部来自多任务的组，这条规则不削弱它。

用户手动折叠或展开过的分组，其选择压过上面两条默认规则。折叠状态只记录用户改过的分组，不预填完整表：预填会在每次 `sessions` 刷新（15 秒一次 refetch）时重算，把用户展开的组重新收起。

因此“侧栏一行因宽度限制省去‘指令’二字”这条旧妥协已作废：侧栏根本不再显示排队条数，写法分裂的来源随之消失。

## 6. 从 botmux 借鉴什么，明确拒绝什么

### 6.1 借鉴

- **Calm Console 语义 token**：使用 surface / text / border / action / status / focus 分层，避免页面内散落的品牌色和“差不多的灰”。
- **needs-you / active / recent 工作台分组**：直接映射用户义务，并保留待处理原因与等待时间。
- **稳定的列表操作对象**：任务行是主交互，分组和选中不应因活动刷新不断跳动。
- **辅助文字而非神秘图标**：状态和行为用短文案说清楚，图标只用于辅助扫描。

### 6.2 明确拒绝

- **拒绝伪趋势**：botmux 的本地定时采样 sparkline 不是可追溯历史，在 Dutydeck 中不作为决策信号。
- **拒绝无出口的列表上限**：不照搬 attention 6 条、working 7 条等截断；如需限制首屏，必须提供明确的“查看全部”。
- **拒绝人员/机器人头像墙成为首要导航**：人和 Agent 是任务的属性，不得覆盖“什么事在等我”。
- **拒绝盲目复制视觉表层**：不照搬 botmux 的品牌紫、图标、阴影和主题切换；只借鉴经验证的信息秩序。
- **拒绝用虚假精致遮蔽不确定性**：未知时间、结果缺失、恢复中和限流都要直说，不用动画或“一切正常”的空状态掩盖。

## 7. 桌面、移动与可访问性约束

### 7.1 桌面端

- 左侧导航只负责工作区维度（按目录聚合任务）、创建任务和设置入口；状态筛选唯一存在于总览页，侧栏不得再渲染第二份。桌面端 ≥768px 侧栏恒常可见，两份状态筛选必然同屏并列、逐字重复且各自漂移。侧栏回答“按目录找”，总览回答“按状态找”，这是两条正交的检索路径，各留一处。
- 工作区默认排序也必须让待处理工作区在前。
- 首页上段是飞书 Bot 概览，下段是任务列表；两者纵向分区，不横向并列争抢注意力。Bot 概览的主操作是绑定或管理 Bot，Web 创建任务是次操作。
- 主内容使用有上限的阅读宽度，任务标题、状态、更新时间在一次横向扫描中可得。
- 阴影只用于移动抽屉/浮层的层级分离，普通内容靠表面和边框建立层级。

### 7.2 移动端

- 以 **390 × 844** 为基线视口，不滚动时必须看到真实内容（Bot 接入状态或任务），不得只看到品牌、口号与指标。
- 页首、Bot 概览与任务区之间不插入营销内容；Bot 概览只保留状态、主操作与使用指引，卡片内条目在窄屏单列排布。
- 轻量筛选水平滚动；任务列表纵向滚动；不让同一手势同时竞争两个轴向。
- 移动侧栏关闭时必须同时设置 `inert` 和 `aria-hidden`，不只移到屏幕外；打开时移入焦点，`Escape` 关闭后恢复到触发器。
- 打开侧栏的浮动汉堡按钮固定在滚动内容之上，必须自带不透明底色与边框，不能是透明图标：否则任务内容滚到它下面会与图标叠字，图标缝隙里的点击还会穿透到任务行。

### 7.3 可访问性

- 按钮、筛选和行操作的触控高度至少 40px；高频移动操作目标建议 44px。
- 正文默认 14px，辅助文字不回退到无法轻松阅读的 8–10px 装饰字；11px 仅用于低频 ID 等次要元数据。
- 所有键盘可操作元素使用语义 `button` / `a` / `tab`，提供明确 `focus-visible` 轮廓。
- 状态筛选使用 `aria-pressed` 或 `aria-current`；区块使用有意义的标题与 `aria-label`。
- 状态徽标的文字必须留在可访问树中；只有重复表意的彩色圆点/箭头使用 `aria-hidden`。
- 相对时间保留可读精确时间；不将信息只放在 hover tooltip 中。
- 遵守 `prefers-reduced-motion`，禁用不可关闭的状态脉冲作为唯一运行指示。

## 9. 已落地（当前变更集）

### 飞书

- 消息接入后立即添加固定 `OK` reaction，进度卡成功后撤销；reaction 失败不阻断任务。
- 消息解析或会话路由失败会返回只读失败卡，不再静默失败。
- 初始卡片区分“已接收/排队”和“执行中”，并按状态提供取消、中断或重试。
- 终态会将原进度卡冻结为只读收据，再发送 fresh final；重试新建进度卡。
- fresh final 幂等键、终态交付标记、轮次防过期回调和进程重启对账已接入持久化。
- 完成结果默认折叠详细 trace，保留证据摘要与 Web 入口；群聊提示使用“回复 + `@机器人`”续话。
- 空 `@` 只用上下文识别指代，确认前禁止副作用。

### Web

- 已删除大 Hero 和 7 张等权巨型指标卡；首屏改为“飞书 Bot 概览 + 任务中心”两段。
- 总览页的分区顺序为待你处理 → 进行中 → 已完成。侧栏已改为纯工作区导航、不再自带状态视图，但它跟随总览页当前筛选：处于“总览”筛选时，工作区之间与工作区内部的任务仍按同一优先级排序，让待处理的工作区和任务排在前面。
- 状态筛选改为紧凑可滚动导航，不再是等权指标墙。
- 过滤视图展示全部匹配任务，不再硬截最近 6 条。
- 任务行已增加文本状态、具体下一步、待执行条数和相对更新时间。
- 已建立 surface / text / border / action / status / focus 语义 token，并提升触控目标和辅助字号。
- 移动侧栏的 `inert`、焦点进入/恢复、`Escape` 和背景阻断契约已有 DOM 测试。
- “待你处理”收敛为唯一判据函数，筛选计数与分区归属共用它；失败和已停止归入待你处理，页首、筛选芯片与分区标题不再各报一个数。
- 状态筛选从 7 项收敛为 5 项：总览、待你处理、进行中、已完成、已归档。“失败”并入待你处理并在任务行内标注具体原因；“有排队的任务”不再是可点击视图，待执行指令总数改为筛选条旁的说明性标签。
- 首页上段改为飞书 Bot 概览：主操作是绑定或管理 Bot，无 Bot 时说明在飞书私聊发目标、群聊 `@机器人`、用 `/help` 查看操作；有 Bot 时逐个展示名称、Agent、工作区与真实状态。任务列表移到 Bot 概览之下，继续承担进展、失败与历史查看。Web 创建任务降为次操作。
- Bot 状态改由 `lark-status.ts` 统一投影，首页、侧栏与设置面板共用同一份判据，逐档区分状态加载中、状态未确认（查询失败）、配置未完成、本次启动禁用监听、用户暂停监听、监听尚未启动与监听已启动；缺字段不当在线，`activeListening` 只表达“监听已启动”而不声称消息已送达（见 §5.1.1）。
- 已配置 Bot 提供“在飞书中打开”官方 AppLink（`lark://applink.feishu.cn/client/bot/open?appId=`，App ID 经 URL 编码），文案标明需要客户端；无法构造时退化为客户端搜索 Bot 名的指引。
- 设置与接入的“建议下一步”不再按 Bot 条数宣称“N 个飞书 Bot 已可用”：判据改用同一份状态投影（因此覆盖用户暂停监听与本次启动禁用监听两种同样收不到消息的情况），措辞上限是“监听已启动”。全部就绪时主建议仍是飞书优先，标题写“管理飞书 Bot”——它必须与这颗按钮真正的动作（打开绑定/管理向导）一致；“下一步去飞书发消息”放在说明里讲，不让标题承诺一个按钮做不到的跳转，也不替用户挑一个 Bot 跳转。同一面板的 Bot 卡片与“消息监听”一格同源改口，不再把 `activeListening` 说成“已连接”；Agent 卡片上的 Bot 计数改称“已绑定”——它只数了 defaultAgentId 指向该 Agent 的 Bot，从未读取监听状态。
- 绑定向导的监听开关说明与 Bot 标签上的成功圆点同样收口：`activeListening` 只表示监听已启动（服务端那一步不等待 WebSocket 握手，断连后也不会置回），文案上限为“监听已启动，可到飞书发送消息”，且在用户暂停监听或本次启动禁用监听时不显示成功态。
- 侧栏顶部的“创建任务”由整块实底降为描边次操作（仍走 sidebar-* 语义色、保持 40px 与键盘行为）：它此前与首屏 Bot 主入口在桌面端同屏争夺主操作层级。
- Bot 状态查询失败单列为一档“状态未确认”，不再映射成“尚未配置机器人”：`larkConfig` 请求失败时 `isLoading` 为 false、`data` 为 undefined，此前首页、侧栏与设置面板都会把它读成“没有 Bot”。首页与设置面板各给出重试动作（同一个 refetch），侧栏 hint 同步改口；已有缓存但 refetch 失败时三处都标注状态未确认，不沿用旧数据宣称在线。Bot API 失败只影响这三处，不进入 `mainQueryFailures`——任务详情不因为飞书接口挂了而被挡住。
- 侧栏不再渲染状态筛选和“绑定 Bot”按钮，只保留工作区导航、创建任务、功能导航和设置入口；状态筛选唯一存在于总览页。飞书接入有两个入口，各有分工：侧栏“飞书接入”是常驻直达（打开任意任务后仍在场，首页 Bot 概览此时已卸载），首页 Bot 概览是首屏上段并展示每个 Bot 的真实状态。两处的状态措辞与“正在读取”态共用 `formatLarkNavSummary`，不再各写一份——它们在桌面端同屏，此前侧栏缺 loading 分支，读不到时会谎报“尚未接入”，且两处都把“有配置记录”当成“已接入”。
- 总览页页首只保留“创建任务”一枚控件（次操作层级）。搜索、外观切换、快捷键帮助归全局顶栏常驻；页首曾各有一份副本，但自顶栏落地起调用点就不再传入，属永不渲染的死代码，且一旦接回就会与顶栏同屏重名。
- 同一个计数不在同屏出现第三遍：页首那句话回答“有几个阻塞项、有几个在进行”，筛选芯片带各自计数，分区标题不再重复条数。
- 数字快捷键 1–5 已与筛选芯片的视觉顺序对齐。
- 总览页第三个分区的标题已从“最近”改为“已完成”，与同名筛选芯片对齐；分区内部标识仍是 `recent`，只是历史命名，不再出现在任何用户可见文案里。
- “已完成”芯片不再裸判 `state === 'completed'`，改为委托同一个分区判据：此前“completed 且排了一条指令”会被“已完成”和“进行中”两个芯片同时数到，分区里却只出现一次。现在除“总览”和“已归档”外的每个视图都委托分区判据，芯片计数与分区条数在结构上不可能分裂。
- 归档态的展示收敛为唯一判据，侧栏、任务详情页、总览与命令面板四处一致显示“已归档”，不再露出归档前那一刻的运行状态与呼吸动画；归档任务不再出现可点击的“重新启动”按钮——归档是只读，此前那是功能缺陷而非显示错误。
- 展示层术语统一为两级：一条 Session 对用户叫“任务”，一条排队记录叫“指令”；“任务运行”“运行”“会话”不再作为任务的用户可见叫法。
- “待执行指令 N 条”是全站唯一写法。旧的“仅侧栏省去‘指令’二字”例外已作废——侧栏精简为单行后不再显示排队条数，写法分裂的来源消失（见 §5.3.1）。
- 侧栏一行收敛为“状态圆点 + 任务标题”，原先的状态词、Agent 名、飞书来源、待执行条数、更新时间共 5 个槽位撤出视觉层：这些字段主区任务行逐项都有且更完整，而桌面端两者同屏。状态词与任务身份改由两个 `sr-only` span 承载，读屏仍可听到，`aria-hidden` 的圆点不成为颜色单独表意；`title` 属性里的那份是鼠标用户的补充，不是唯一载体。
- 侧栏工作区分组可折叠：18 条任务平铺时侧栏是主区列表的一份低配副本，折叠后默认只剩“目录名 + 条数”。默认展开当前打开任务所在的组与只有一条任务的组（折叠单任务组一行也不省，只多一次点击），用户的手动选择压过默认规则；折叠状态只记录用户改过的分组，避免 15 秒一次的 refetch 把用户展开的组重新收起。详见 §5.3.2。
- 重启文案已更正为“任务已停止，可重新启动；重启会从空白上下文开始”，不再承诺保留上下文。
- 移动端浮动汉堡按钮已补上不透明底色、边框与阴影，任务内容滚过时不再与图标叠字，图标缝隙也不再穿透点击到任务行。
- Web 全量测试和 production build 已通过。

## 10. 后续项（不得与已落地混写）

### P0：跨端契约与真实环境验证

- 建立单一的 presentation model，集中定义 Runtime 状态、用户义务、主下一步和各端文案，取代 Web/飞书中的重复映射。
- 用真实飞书测试应用完成 E2E：验证 reaction 可见时延、卡片原地更新、群/话题回复位置、冻结收据、fresh final 和重试新卡。
- 补齐“发送 final 成功但持久化前崩溃”、长时限流、原消息被删除、卡片内容审核拒绝的混沌 E2E。
- 把任务身份、轮次、进度卡 ID 和 final 消息 ID 纳入跨端可观测链路，并对重复 final、终态回退、长时无卡片承诺告警。

### P1：完整的 attention 信息

- 由服务端输出结构化 `attention_reason`、`waiting_since`、`next_action`，Web 不再只根据原始 state 推断。

- 在真机上验证水平筛选、任务行换行、安全区与输入法键盘，不以 jsdom 代替布局验收。

### P2：用数据证明设计有效

- 监测从飞书消息到 reaction、进度卡和 fresh final 的 P50/P95 延迟。
- 监测待处理任务的首次打开时间、恢复成功率、重复指令率与“任务是否已接收”类追问率。
- 只在真实任务数据证明用户需要时，再增加趋势、主题、个性化看板或更强视觉表达。

## 11. 发布门槛

本蓝图后续任何改动，在发布前必须同时满足：
